01 — i18n

ส่ง { th, en } เข้ามาแล้วหายเงียบ

อาการ · POST

ตาย NOT NULL ที่ name_th → PG 23502 → 400 ที่ชี้ผิดจุด

อาการ · PUT (ร้ายกว่า)

ตอบ 200 แต่ไม่ได้บันทึกอะไรเลย ไม่มี error ให้ใครเห็น

ต้นเหตุ

forbidNonWhitelisted เป็น false ทั้งแพลตฟอร์ม (IBootstrapOptions default) — คีย์ name ที่ DTO ไม่รู้จักจึงถูก whitelist ตัดทิ้งเงียบ ๆ ก่อนถึง service ไม่ใช่ถูกปฏิเสธ

ทำไมไม่มีใครเห็น

ไม่มีใครเคยส่ง nested เข้ามา เพราะเอกสารบอกว่า “ห้ามส่ง” — บั๊กจะโผล่ก็ต่อเมื่อมีคนทำตามสัญชาตญาณ (GET มาแล้ว PUT กลับ) ซึ่งเป็นสิ่งที่ AI frontend ทำเป็นอย่างแรก

แก้อย่างไร · 71c519e

LocalizedBodyPipe ลงทะเบียนก่อน ValidationPipe แปลง nested เป็นคู่ flat ตั้งแต่ raw body — DTO ทั้ง 62 ไฟล์ไม่ต้องแก้สักบรรทัด · แปลงตาม schema ของคลาส ไม่ใช่เดาจากรูปทรง จึงไม่แตะ jsonb อิสระ · ส่งมาทั้งสองแบบ = flat ชนะ + meta.warnings · รายละเอียดเต็ม: i18n Guide §03.1

เทสต์ที่คุมไว้

02 — Envelope

status.code เป็นเลข 3 หลักมาตลอด

// เอกสารเขียนไว้ตั้งแต่ต้น: status.code = HTTP × 1000 + serial
// ของจริงก่อนแก้ —
409 → { "status": { "code": 409 } }      // 3 หลัก
404 → { "status": { "code": 404 } }      // 3 หลัก
400 (validation) → { "code": 400001 }  // 6 หลัก — มีแค่สองตัวนี้ที่ทำตามกฎ
ต้นเหตุ

AllExceptionsFilter ใส่ exception.getStatus() ลง status.code ตรง ๆ ในสามกิ่ง (HttpException / QueryFailedError / catch-all) · มีแค่ 400001/400002 ที่ hardcode เลข 6 หลักไว้ · client จึงต้องเช็กสองความกว้างแล้วแต่ว่าเจอ error ตัวไหน

แก้อย่างไร · a0890be

toEnvelopeStatusCode(status, serial) + normalizeEnvelopeStatusCode() ใน status-code.util.ts · ทุกกิ่งของทั้ง HTTP และ RPC filter ประกอบผ่านตัวนี้ · serial 000 = รูปธรรมดา, ผู้โยนกำหนด 409001 เองได้ · ฝั่งรับข้าม BC ไม่ต้องแก้ เพราะ resolveRpcHttpStatus() รับได้ทั้งสองความกว้างอยู่ก่อนแล้ว

⚠ breaking สำหรับ client

ใครที่เทียบ status.code === 404 ต้องเปลี่ยนเป็น 404000 หรือ Math.floor(code / 1000) · HTTP status เองไม่เปลี่ยน — คนที่ดู response.status ไม่กระทบ

เทสต์ที่คุมไว้

status-code.util.spec.ts (6) · all-exceptions-filter.spec.ts (13 · ทุกกิ่ง) · rpc-exceptions-filter.spec.ts (9) · customers.e2e-spec.ts ล็อก 404000/409000 ผ่าน pipeline จริง

03 — Rate limit

429 ไม่เคยถึง client เลยสักครั้ง — มันตอบ 500

// ตั้ง RATE_LIMIT_MAX=5 บนเครื่อง dev แล้วยิงรัว 14 ครั้ง (ก่อนแก้)
 1–5  http=200 code=200000
 6+   http=500 code=500000 INTERNAL_SERVER_ERROR   // ที่ควรเป็น 429

// ใน log ของ service:
ERROR [AllExceptionsFilter] Unhandled Exception: [object Object]
{ "status": { "code": 429000, ... }   // envelope ที่ประกอบไว้ ไปโผล่แค่ใน log
ต้นเหตุ

@fastify/rate-limit โยนสิ่งที่ errorResponseBuilder คืนออกมา (index.js:341 — default ของมันเองสร้าง Error พร้อม statusCode) · เราคืน envelope เป็น object เปล่า มันจึงกลายเป็น exception ที่ AllExceptionsFilter ไม่รู้จัก แล้วตกกิ่ง catch-all

ทำไมไม่มีใครเห็น

ค่า default คือ 10,000 request ต่อ 15 นาที — ไม่มีใครยิงทะลุโดยบังเอิญ และไม่มีเทสต์ไหนจำลองการทะลุ เพราะ plugin ทำงานที่ชั้น Fastify ซึ่ง unit/e2e ที่ mock ไว้ไม่แตะเลย

แก้อย่างไร · 1c11305 + ebadd51

คืน HttpException (เป็น Error plugin จึงพอใจ) แล้วปล่อยให้กิ่ง HttpException ของ filter ประกอบ envelope ให้ · แยกเป็น buildRateLimitException() เพื่อให้เทสต์ยิงตรงที่ข้อ “ต้องเป็น Error” ซึ่งคือตัวบั๊กจริง

ยืนยันบนเครื่องจริงหลังแก้

5 ครั้งแรก 200/200000 · ครั้งที่ 6+ 429/429000 TOO_MANY_REQUESTS พร้อม header retry-after: 58 · x-ratelimit-limit: 5 · x-ratelimit-remaining: 0 — แล้วคืนค่า .env กลับเป็น 10000 ตรวจซ้ำด้วย header

04 — Envelope

ลิงก์แบ่งหน้ามี ? สองตัว

// GET /customers?limit=1  (ก่อนแก้)
"links": {
  "next": ".../customers?limit=1?page=2&limit=1"   // page กลายเป็นส่วนหนึ่งของค่า limit
}
// หลังแก้
  "next": ".../customers?page=2&limit=1"
ต้นเหตุ

TransformInterceptor สร้าง baseUrl จาก request.url ซึ่งมี query string ติดมาด้วย แล้ว createPaginatedResponse ต่อ ?page=…&limit=… ของตัวเองเข้าไปอีก

ทำไมไม่มีใครเห็น

ลิงก์จะถูกเฉพาะตอนที่คำขอไม่มี query string เลย ซึ่งเป็นกรณีที่เทสต์เขียนกันบ่อยที่สุด · และไม่มี client ตัวไหนในระบบเดินตาม links จริง ๆ จึงไม่มีใครสะดุด

แก้อย่างไร · 1c11305 · เทสต์ transform-interceptor.links.spec.ts (2)

กิ่ง paginated สร้างลิงก์จาก path ล้วน (path.split('?')[0]) · self ของ response ที่ไม่ได้แบ่งหน้ายังสะท้อน query เดิมตามเจตนา · เทสต์ assert ว่าทุกลิงก์มี ? ได้แค่ตัวเดียว

05 — i18n × sparse fieldset

?fields= ทำให้ response โกหก

// GET /customers?fields=id,code   บนลูกค้าที่ชื่อจริงไม่ได้เป็น null (ก่อนแก้)
"attributes": {
  "code": "CUST-TEST-02",
  "name": { "th": null, "en": null }   // ← โกหก: ไม่ได้ขอมา ไม่ใช่ null จริง
}
ต้นเหตุ · พฤติกรรมของ TypeScript ตอน runtime

field ของคลาสใน TS เกิดเป็น own property ค่า undefined (target ES2023 → useDefineForClassFields) · entity ที่ select แค่บางคอลัมน์จึงยังมีคีย์ name_th/name_en อยู่ · LocalizationInterceptor เช็กด้วย in จึงเห็นครบคู่แล้วยุบเป็น { th: null, en: null } ตามสัญญา “ส่ง { th, en } เสมอ”

ทำไมไม่มีใครเห็น

LocalizationInterceptor ไม่เคยมี spec เลยสักบรรทัด ทั้งที่เป็นครึ่งหนึ่งของสัญญา i18n — และ ?fields= แทบไม่มีใครใช้ในระบบจริง

แก้อย่างไร · ebadd51 · เทสต์ localization-interceptor.util.spec.ts (8)

undefined ทั้งสองด้าน = ไม่ได้ถูก select → ไม่ส่งคีย์นั้นออกไป · null = โหลดมาแล้วว่าง → ยุบเป็น { th: null, en: null } ตามสัญญาเดิมทุกประการ · สัญญา “ส่งเสมอ” ใช้กับคอลัมน์ที่ถูกขอมาเท่านั้น

07 — คำถามที่ตามมา

แล้ว name.th ใน query param ล่ะ?

อัปเดต · ใช้ได้แล้วตั้งแต่ 2026-09-20 (รอบเดียวกัน)

ตอนสำรวจครั้งแรก 400002 ทุกช่องทาง ตามตารางข้างล่าง · ตอนนี้ TypeOrmQueryBuilder แปลง name.th → name_th ให้แล้วทั้ง filter · or · s · sort · fields — เก็บตารางเดิมไว้เพราะมันคือเหตุผลว่าทำไมต้องแปลงที่ชั้นนั้น ไม่ใช่ชั้นอื่น

ในเมื่อขาเข้าของ body รับ nested แล้ว คำถามที่ตามมาทันทีคือ ?filter=name.th||$eq||xxxx จะถูกแปลงเป็น name_th ให้ TypeOrmQueryBuilder กรองจริงไหม — ตอนสำรวจคือไม่ และได้ 400 ทุกช่องทาง ผลการยิงข้างล่างคือสถานะ ณ ตอนนั้น ซึ่งเป็นข้อมูลที่ใช้ตัดสินว่าจะไปแปลงที่ชั้นไหน

ยิงจริงบนเครื่อง deploy · 2026-09-20
คำขอผลข้อความจริง
filter=name.th||$eq||test400002Invalid relation: 'name' in path 'name.th'. Allowed relations are: [customer_group]

ทำไมถึงเป็น 400 ไม่ใช่การแปลงให้

1. LocalizedBodyPipe ทำงานเฉพาะ metadata.type === 'body' — query param ไม่เคยผ่านมันเลย
2. ใน TypeOrmQueryBuilder จุดที่มีเครื่องหมาย . ถูกตีความว่าเป็น relation path (validateFieldNamesRecursive → findRelationWithPropertyPath('name')) · ไม่มี relation ชื่อ name จึงโยน InvalidParameterException
3. มันไม่ไปเข้าทาง JSONB เพราะ isJsonbPath() ต้องการให้ segment แรกเป็นคอลัมน์ jsonb/json จริง ซึ่ง name ไม่ใช่ (ฟิลด์ i18n เป็นคอลัมน์ flat สองตัว)

⚠ ข้อยกเว้นเดียวที่ต้องระวัง

ถ้า entity ไหนมีคอลัมน์ jsonb ชื่อ name จริง ๆ — name.th จะไม่ 400 แต่จะกลายเป็น JSONB path ("name" #>> ARRAY['th']) แล้วกรองจาก JSON ข้างในแทน ซึ่งคนละอย่างกับที่ตั้งใจ · เครื่องหมายจุดในระบบนี้จึงมีความหมายสองแบบอยู่แล้ว (relation path กับ JSONB path) และ i18n ไม่ใช่ทั้งสองอย่าง

ทางแก้ · ทำไมต้องเป็น TypeOrmQueryBuilder ไม่ใช่ @ValidatedQuery
❌ @ValidatedQuery

เป็นชั้น binding — ไม่รู้ว่า endpoint นี้ query entity ไหน จึงตอบไม่ได้ว่ามีคอลัมน์ name_th/name_en จริงไหม หรือ name เป็น jsonb อยู่แล้วหรือเปล่า
ถ้าดักที่นี่ต้องเดาด้วย string ล้วน ๆ ซึ่งจะพัง mock_data.th ทันที · แถมต้องแกะไวยากรณ์ย่อยทั้ง 4 แบบ (field||op||value, field:dir, CSV, JSON) ซ้ำกับที่ query builder แกะอยู่แล้ว

✅ TypeOrmQueryBuilder

ถือ repository.metadata อยู่แล้ว จึงแยกความหมายทั้งสามของจุดได้จริง · และแกะ path ของทั้ง 5 ช่องทางอยู่ที่เดียวอยู่แล้ว
เป็นด่านสุดท้ายก่อนลง SQL ด้วย — อะไรที่ผ่านตรงนี้ไปคือสิ่งที่ Postgres จะเห็นจริง

ลำดับความสำคัญ · ออกแบบให้พฤติกรรมเดิมไม่เปลี่ยนเลยสักข้อ

resolveLocalizedFieldPath() ทำงานตามลำดับนี้ แล้วคืน path เดิมถ้าไม่เข้าเงื่อนไข (ปล่อยให้ validation เดิมรายงาน error ของมันเอง):
1. มีคอลัมน์ชื่อ <base> อยู่แล้ว → ไม่แตะ · mock_data.th ยังเป็น JSONB path เหมือนเดิม
2. มี relation ชื่อ <base> → ไม่แตะ · relation path ยังชนะ
3. มีคอลัมน์ <base>_th และ <base>_en ครบคู่ → แปลงเป็น <base>_<leaf>
4. นอกนั้นคืนเดิม → ยังได้ 400002 เหมือนก่อน
relation hop ข้างหน้าถูกเดินก่อน ดังนั้น customer_group.name.th ถูก resolve เทียบ metadata ของกลุ่มลูกค้าแล้วกลายเป็น customer_group.name_th · คอลัมน์ที่บังเอิญลงท้าย _th แต่ไม่มีคู่ (note_th เดี่ยว ๆ) ไม่ถูกนับเป็นคู่ i18n

สรุปสำหรับ client (ปัจจุบัน)

body → name_th หรือ name: { th, en } ก็ได้ · query param → name_th หรือ name.th ก็ได้ ทั้ง filter/or/s/sort/fields · response → name: { th, en } เสมอ
ยังไม่รองรับ: name เปล่า ๆ (ไม่มี .th/.en) เพราะกำกวมว่าจะหมายถึงด้านไหน · และ entity ที่มีคอลัมน์ jsonb ชื่อชนกับ base จะยังเป็น JSONB path ตามข้อ 1
เทสต์: typeorm-query-builder.i18n-path.spec.ts (8 เคส · ครบทั้ง 5 ช่องทาง + jsonb + relation + half-pair) และ smoke localized-input.smoke.mjs ยิงของจริงว่า filter=name.th คืนแถวชุดเดียวกับ filter=name_th
