On-Premise Deployment
(Docker Compose · Kong · Cloudflare Tunnel)

แนวทางติดตั้งระบบ ERP บนเครื่องที่ลูกค้าซื้อมาเองและดูแลเอง (on-premise) — ตั้งแต่เตรียมเครื่อง/VM, ตั้ง datastore + Kong API Gateway ด้วย Docker Compose, ไปจนถึงเปิด domain สาธารณะผ่าน Cloudflare Tunnel โดยไม่ต้อง เปิด port forward บน router หรือมี public IP คงที่เลย

01 — ภาพรวม

รูปแบบ Deployment สำหรับลูกค้าที่ซื้อเครื่องเอง

ลูกค้าหลายรายซื้อเครื่อง/VM มาเองและติดตั้ง ERP ในเครือข่ายภายใน (LAN ส่วนตัว, IP วง private) ไม่มี public IP คงที่ ไม่อยาก/ไม่สามารถเปิด port forward บน router ขององค์กรได้ — สถาปัตยกรรมนี้แก้ปัญหาด้วย Cloudflare Tunnel: เครื่อง on-prem เป็นฝ่าย "เชื่อมออก" หา Cloudflare เอง (outbound connection) แทนที่จะรอรับ inbound connection จากอินเทอร์เน็ต — ไม่ต้องเปิด firewall/port ใด ๆ เข้าเครือข่ายภายในเลย

RULE

Cloudflare terminates TLS ที่ edge เสมอ — จาก cloudflared เข้าไปที่ Kong เป็น HTTP ธรรมดาตลอด ไม่ใช่ HTTPS แม้ domain ปลายทางที่ผู้ใช้เห็นจะเป็น https:// ก็ตาม — สำคัญมากตอนตั้งค่า Tunnel route และค่า COOKIE_SECURE/TRUST_PROXY ใน §08

ข้อดี

ไม่ต้องมี Public IP / Port Forward

เครื่อง on-prem อยู่หลัง NAT/Firewall ขององค์กรได้ตามปกติ — Cloudflare Tunnel เป็น outbound connection ล้วน ๆ ลูกค้าไม่ต้องขอสิทธิ์แก้ router/firewall จาก IT องค์กรเลย

เงื่อนไข

ต้องมี Domain ผูกกับ Cloudflare

ลูกค้าต้องมี domain (ซื้อเองหรือมีอยู่แล้ว) และ nameserver ชี้ไปที่ Cloudflare — ถ้าไม่มี domain ระบบยังใช้งานได้ในวง LAN ภายในผ่าน IP ตรง แต่จะไม่มี HTTPS/public access

03 — เตรียม VM (Proxmox)

สร้างและตั้งค่า VM

1

สร้าง VM ด้วย disk size ที่เผื่อไว้ตั้งแต่แรก

อ้างอิงตาราง §02 — ตั้ง virtual disk อย่างน้อย 80 GB ตั้งแต่สร้าง VM ครั้งแรก (thin-provision ได้ ไม่กินพื้นที่จริงจนกว่าจะใช้) ดีกว่าต้องมาขยายทีหลังตอนเจอปัญหา

ถ้าจำเป็นต้องขยาย disk ทีหลัง ต้องทำ 2 ระดับ

1) ขยาย virtual disk ใน Proxmox ก่อน (qm resize <vmid> scsi0 +40G หรือผ่าน UI) 2) เข้าไปขยาย partition/filesystem ข้างใน guest OS เองอีกที — สอง VM ที่ config ต่างกัน (LVM ธรรมดา vs. loop-mounted rootfs แบบ cloud-image) ใช้คำสั่งขยายต่างกัน เช็ค lsblk/df -h / ก่อนเสมอว่า disk ใหม่ที่ Proxmox เห็นจริง ๆ ถูกขยายเข้าไปถึง filesystem จริงหรือยัง (ไม่ใช่แค่ระดับ virtual disk)

ตั้งค่า network interface ให้ได้ IP คงที่ในวง LAN (เช่นผ่าน Proxmox network config หรือ DHCP reservation ที่ router) — ค่านี้จะถูกใช้ซ้ำหลายจุด: Kong's BC_UPSTREAM_HOST, Konga's KONGA_BIND_HOST, และ Cloudflare Tunnel's origin URL (§07) — ถ้า IP เปลี่ยนทีหลังต้องไปแก้ทุกจุดพร้อมกัน

05 — Deploy Apps & CI/CD

Build + รันด้วย pm2

เครื่องเดียวรัน 2 repo — erp-api (8 BC) และ erp-frontend (Next.js) — และทั้งคู่อยู่บน pm2 daemon ตัวเดียวกัน ข้อนี้สำคัญกว่าที่คิด เพราะทำให้คำสั่ง pm2 แบบเหมารวม (pm2 delete all) ของ repo หนึ่งไปดับอีก repo หนึ่งได้ — ดู RULE ท้ายหัวข้อนี้

1

Deploy key — ทั้ง 2 repo เป็น private

git clone/fetch ผ่าน HTTPS แบบไม่ล็อกอินใช้ไม่ได้แล้ว — ต้องมี credential แบบ อ่านอย่างเดียว บนเครื่อง ใช้ SSH deploy key แยกคนละอันต่อ repo (GitHub ไม่ยอมให้ใช้ deploy key ซ้ำข้าม repo — จะขึ้น key is already in use) 

# 1) สร้าง key คนละอันต่อ repo (ไม่ตั้ง passphrase — deploy รันแบบ non-interactive)
ssh-keygen -t ed25519 -N '' -C "ovh-dev deploy key (erp-api)" -f ~/.ssh/id_ed25519_erp_api
ssh-keygen -t ed25519 -N '' -C "ovh-dev deploy key (erp-frontend)" -f ~/.ssh/id_ed25519_erp_frontend

# 2) ตั้ง host alias ให้ ssh เลือก key ถูกตัว
cat >> ~/.ssh/config <<'EOF'
Host github-erp-api
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_erp_api
  IdentitiesOnly yes

Host github-erp-frontend
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_erp_frontend
  IdentitiesOnly yes
EOF
chmod 700 ~/.ssh && chmod 600 ~/.ssh/config ~/.ssh/id_ed25519_erp_*

# 3) เอา public key ไปใส่ที่ repo → Settings › Deploy keys › Add deploy key
#    อย่าติ๊ก "Allow write access" — deploy ต้องการแค่อ่าน
cat ~/.ssh/id_ed25519_erp_api.pub
cat ~/.ssh/id_ed25519_erp_frontend.pub

# 4) ยืนยันว่าใช้ได้จริงก่อนไปต่อ
GIT_TERMINAL_PROMPT=0 git -C /root/erp-api ls-remote origin HEAD
IdentitiesOnly yes ไม่ใช่ของประดับ

ถ้าไม่ใส่ ssh จะเสนอ key ทุกอันที่มีให้ GitHub ตามลำดับ — GitHub รับ key แรกที่ผ่าน แล้วผูก session นั้นกับ repo ที่ key นั้นเป็น deploy key อยู่ ผลคือ clone อีก repo หนึ่งจะขึ้น ERROR: Repository not found ทั้งที่ key ถูกต้องและสิทธิ์ครบ — เป็น error ที่หลอกมาก เพราะข้อความบอกเหมือน repo ไม่มีอยู่จริง

① CI/CD — GitHub Actions + self-hosted runner

workflow คือ .github/workflows/deploy.yml แยกเป็น 2 job — resolve หาว่า push นี้แตะอะไรบ้าง แล้ว deploy build + ส่งของ ทั้งคู่รันบน runner เครื่องเดียวกัน 

push main / develop  (หรือ workflow_dispatch)
  │
  ├─ job resolve   node scripts/resolve-deploy-scope.mjs <before> <sha>
  │                  → apps=... migrate=... full=true|false
  │
  └─ job deploy    (environment: main→production, อื่น→development)
       ├ pnpm install --frozen-lockfile
       ├ pnpm nx run-many -t build --all   # app ที่ไม่เปลี่ยน replay จาก .nx/cache
       ├ npm run build:assets:iam            # esbuild — nest build ไม่ทำให้
       ├ เขียน ~/.ssh/config  ProxyCommand cloudflared access ssh --hostname %h
       ├ ssh -T ovh-dev 'echo ssh-ok'        # gate: ต่อไม่ได้ก็จบตรงนี้ ยังไม่แตะ server
       └ ./scripts/deploy-ovh-dev.sh --prebuilt <branch> [--only=… --migrate=…]
            ├ rsync dist/apps/<app>/ → server:<repo>/.deploy-staging/dist/apps/<app>/
            └ ssh → pipeline ฝั่ง server (ดูแผนผังท้ายหัวข้อ)

runner ไม่ได้เปิด port เข้า server — มันต่อผ่าน Cloudflare Tunnel ตัวเดียวกับที่ §07 ตั้งไว้ โดยใช้ cloudflared access ssh เป็น ProxyCommand ดังนั้น server ยังไม่มี inbound port ใด ๆ เปิดออกเน็ต

environment secret ไม่ข้าม repo — ต้องตั้งซ้ำทุก repo

OVH_SSH_HOSTNAME ที่ตั้งไว้ใน environment production ของ erp-api ไม่ถูกมองเห็นจาก erp-frontend เลย ต่อให้ชื่อ environment และเครื่องปลายทางเดียวกันเป๊ะ — อาการคือ deploy ตายที่ step ตรวจ secret ว่า secret ... is not set ทั้งที่ "ตั้งไปแล้ว" (คนละ repo) และอย่าลืมว่า push ขึ้น develop จะไป resolve เป็น environment development ซึ่งต้องตั้ง secret ชุดเดียวกันอีกรอบ ถ้าอยากตั้งที่เดียวจบให้ใช้ organization secret แทน (แต่ environment secret จะ override เสมอ)

build ทุก app แต่ ส่งเฉพาะ app ที่อยู่ใน scope

CI build --all เพราะนั่นคือสิ่งที่ทำให้ nx cache อุ่นสำหรับรอบถัดไป (app ที่ไม่เปลี่ยน replay จาก cache ในไม่กี่วินาที) แต่ตอน rsync จะส่งเฉพาะ app ที่ deploy รอบนี้ จะ reload จริง — ถ้าส่งทั้งหมดทั้งที่ reload แค่บางตัว ไฟล์บนดิสก์กับโค้ดที่ pm2 โหลดไว้จะ ไม่ตรงกันแบบเงียบ ๆ แล้วไปโผล่ตอน restart ครั้งถัดไปด้วยโค้ดที่ไม่เคยผ่าน health check

--prebuilt มีไว้ให้ CI ใช้ ไม่ใช่สำหรับรันมือ

รันมือเปล่า ๆ จะได้พฤติกรรมเดิมทุกอย่าง — lint/test/build บนเครื่อง dev แล้ว server build ซ้ำของมันเอง ส่วน --prebuilt เป็น flag แบบ opt-in ที่บอกว่า "dist/ ใน working tree นี้ build เสร็จแล้วและถือเป็นของจริง" แล้วข้าม build ฝั่ง server ไปเลย ถ้าจะใช้เองต้อง build ให้ครบก่อน มิฉะนั้น script จะหยุดให้ ตั้งแต่ยังไม่ ssh (มันเช็ค dist/apps/<app>/main.js ทุกตัวก่อนส่ง)

RULE · ต่อให้ส่ง artifact แล้ว server ก็ยัง git reset --hard อยู่ดี

คำถามที่ต้องมีคนถามคือ "ถ้า rsync dist ขึ้นไปแล้ว ยังต้อง clone source ไว้บนเครื่องทำไม" — เพราะยังมีของอีก 4 อย่างที่อ่านจาก source ตรง ๆ ไม่ใช่จาก bundle: migration:run รันผ่าน ts-node บนไฟล์ .ts จริง · permissions:sync สแกน apps/*/src/**/*.ts หา @RequirePermission() และสแกน views/** หา data-permission · iam เสิร์ฟ EJS template จาก apps/iam/views ตอน runtime · และ webpack ตั้ง webpack-node-externals ไว้ แปลว่า bundle ไม่ self-contained — node_modules ยังจำเป็นอยู่

สรุปคือ --prebuilt ตัดแค่ "การ build บน server" ไม่ได้ตัด "source บน server" ซึ่งเป็นส่วนที่แพงจริง — เครื่องนี้รัน Postgres, Redis, RabbitMQ และ erp-web อยู่ด้วย การให้มัน webpack แปด Nest app คือขั้นที่ช้าและกวนที่สุดของ deploy ถ้าจะตัด git ออกจากเครื่องให้หมดจริง ๆ ต้องแปลง migration/permissions:sync ให้รันจาก compiled output ก่อน

snapshot ต้องอยู่ก่อน build ไม่ใช่ก่อน pm2

สัญชาตญาณบอกให้ copy dist ตอน "ก่อนสลับเวอร์ชัน" คือก่อน pm2 start — แต่ตรงจุดนั้น dist เป็นของใหม่ที่เพิ่ง build เสร็จไปแล้ว สิ่งที่ได้จึงเป็นสำเนาของสิ่งที่กำลังจะ deploy ไม่ใช่สิ่งที่กำลังจะถูกแทนที่ — ใช้ rollback ไม่ได้ ต้องวางไว้ก่อน build ตรงที่ dist ยังเป็น bundle ที่ pm2 รันอยู่จริง และเก็บ apps/iam/dist (esbuild asset) กับไฟล์ COMMIT ไปด้วย เพราะ dist เปล่า ๆ บอกไม่ได้ว่า build มาจาก source ไหน

health check ต้อง gate ไม่ใช่แค่ print

curl -w '%{http_code}' เฉย ๆ ไม่ return non-zero เมื่อเจอ HTTP 500 (ต้องมี -f หรือเช็คค่าที่ได้เอง) — script ที่แค่พิมพ์ ตัวเลขออกมาแล้วจบด้วย "done" จึงรายงานว่าสำเร็จทั้งที่ service พังอยู่ และต้องเช็ค ทุก app ไม่ใช่แค่ตัวเดียว เพราะ BC ที่ crash เพราะ env ขาดจะเงียบจนมี user เจอ

ใช้ /health/ready ไม่ใช่ /health

liveness (/health) ตอบ 200 แม้ระหว่างที่ process กำลัง drain ปิดตัว จึงแยกไม่ออกระหว่าง "เพิ่งขึ้นมาพร้อมใช้" กับ "กำลังจะตาย" — readiness (/health/ready) ตอบ 503 ตอน shutting down ทั้งสอง route ลงทะเบียนตรงกับ Fastify adapter จึงไม่ผ่าน AuthGuard ไม่ต้องใช้ token (ดู libs/common/src/utils/bootstrap.util.ts)

Kong ทำ path-based routing — แต่ละ BC ยังคง prefix เดิมของตัวเอง (/auth/v1, /iam/v1, ...) ไม่ต้องแก้โค้ดแอปฝั่งไหนเลย รายละเอียดเต็มอยู่ที่ infrastructure/kong/ ใน repo หลัก

Cloudflare terminate TLS ให้ผู้ใช้ที่ edge อยู่แล้ว (ดู diagram §01) — เลือก HTTPS ไปที่ Kong's port 443 จะไปเจอ TLS listener ที่ไม่มี certificate ที่ใช้งานได้จริง (ดู §09 บั๊ก #5 เรื่อง ACME) ทำให้ tunnel handshake ล้มเหลว ใช้ HTTP เข้า port 80 ธรรมดา ปลอดภัยเพียงพอเพราะ traffic ระหว่าง cloudflared ↔ Kong วิ่งอยู่ในเครื่อง/LAN เดียวกัน ไม่ใช่อินเทอร์เน็ตเปิด

หนึ่ง route ต่อ host ที่ Kong รู้จัก — ไม่ใช่แค่ erp-api.<domain> เท่านั้น ทุก host ที่ตั้งไว้ใน infrastructure/kong/.env (§06 — DOMAIN, MINIO_DOMAIN, FRONTEND_DOMAIN) ต้องมี Public Hostname entry ของตัวเองใน tunnel เดียวกันนี้ — Service Type/URL เหมือนกันทุกอัน (HTTP → <LAN IP>:80) เพราะ Kong เป็นคนแยกปลายทางจริงด้วย Host header เอง ไม่ใช่ Cloudflare — เพิ่ม Subdomain ใหม่แล้วชี้ไปที่ URL เดิมซ้ำได้เลย ไม่ต้องสร้าง tunnel ใหม่

  • AUTH_PUBLIC_URL / REPORT_PUBLIC_URL — ค่านี้ถูกฝังลงหน้า admin ของ iam เป็น URL ที่ browser ของผู้ใช้เองยิง fetch ตรง ๆ ไม่ใช่ server-to-server เหลือเป็น private IP/localhost แล้ว browser จริงจะโดนบล็อกด้วย Private Network Access policy ของ Chrome ทันที
  • CORS_ORIGIN — ต้องเป็น origin จริงเป๊ะ ๆ (ไม่ใช่ *) เพราะแอปใช้ credentials: true สำหรับ cookie auth flow
  • COOKIE_SECURE — เปิดเป็น true ได้ปลอดภัยเพราะผู้ใช้คุยกับ Cloudflare ด้วย HTTPS จริงเสมอ แม้ hop ภายใน (cloudflared → Kong → app) จะเป็น HTTP ก็ตาม
  • TRUST_PROXY — หา subnet ของ Kong's docker network ด้วย docker network inspect kong_default แล้วใส่รวมกับ host's LAN IP (Docker NAT อาจ rewrite source IP เป็น host IP ตอน container เรียกกลับเข้า host) — ไม่งั้น req.ip/req.protocol จะอ่านผิดจาก Kong's X-Forwarded-* headers
RULE — แก้จากของเดิมที่เขียนผิด

เอกสารฉบับก่อนเขียนไว้ว่า “pm2's env_file อ่านค่าแค่ตอน pm2 start — ต้อง pm2 delete all && pm2 start” ผิดทั้งข้อเท็จจริงและวิธีแก้ และยังขัดกับ RULE ใน §05 ที่ห้าม pm2 delete all บนเครื่องที่แชร์ daemon กัน (ดู §09 บั๊ก #9)

ของจริง: env_file ไม่ inject อะไรเลย — ค่าถึงแอปผ่าน NestJS ConfigModule ที่อ่าน .env เองด้วย dotenv ตอน bootstrap (envFilePath: ['.env'], resolve จาก process.cwd() = /root/erp-api ซึ่ง 8 BC ใช้ไฟล์เดียวกัน และมี Joi schema ตรวจ — ค่าขาด/ผิดชนิด = ตายตอน boot ไม่ใช่พังตอน runtime)

ดังนั้น process เกิดใหม่แบบไหนก็ได้ค่าใหม่ — pm2 reload ก็พอ และได้ zero-downtime แถมมาด้วย deploy script จึงใช้ pm2 startOrReload ไม่ต้อง delete ทิ้งอีกต่อไป

erp-frontend — config อยู่คนละที่กับ backend

erp-web ไม่มี .env เลยในสถานะปัจจุบัน — ค่าทั้งหมดมาจาก env: {} ใน ecosystem.config.js (ต่างจาก env_file ตรงที่อันนี้ทำงานจริง) พอเริ่มต่อ API จะมีสองที่ให้เลือก และเลือกผิดจะเงียบ:

ค่าอยู่ที่เปลี่ยนแล้วต้อง
PORT, NODE_ENV (runtime) ecosystem.config.js → env: {} pm2 reload
NEXT_PUBLIC_* (build-time) apps/web/.env build ใหม่ — reload ไม่พอ
server-only (ไม่มี prefix) apps/web/.env pm2 reload
ทำไมไฟล์ต้องอยู่ที่ apps/web/ ไม่ใช่ root

Next อ่าน .env จาก working directory ของตัวเอง และ pm2 ตั้ง cwd: 'apps/web' ไว้ — วางไว้ที่ root ของ repo จะไม่ถูกอ่านและไม่มี error ให้เห็น ส่วน NEXT_PUBLIC_* ถูก inline เข้า client bundle ตอน next build จึงเป็นค่าที่ “ติดไปกับ build” ไม่ใช่ค่าที่อ่านตอนรัน — แต่ไม่มีกับดัก bundle ค้าง เพราะ turbo.json ประกาศ .env* เป็น build input — ยืนยันด้วย deploy จริงสองรอบ (สร้าง .env แล้ว deploy → ลบทิ้งแล้ว deploy): 

รอบ A (มี .env)   web:build: cache miss, executing 156a2900214a8ed6
รอบ B (ลบ .env)   web:build: cache miss, executing 5b4fa78adcd8ca6a
                  web:lint : cache hit   ← lint ไม่ผูกกับ .env จึงไม่ถูก invalidate

build ถูกสร้างใหม่ทั้งสองรอบ ส่วน lint ยัง cache hit — แปลว่า invalidation ผูกอยู่กับ build เท่านั้นตามที่ควร ไม่ได้เหวี่ยงล้าง cache ทั้งหมด template อยู่ที่ apps/web/.env.example

10 บั๊กจริงที่เจอตอนตั้งระบบครั้งแรก

บันทึกไว้ละเอียดกันคนถัดไปเจอปัญหาเดิม — 5 ข้อแรกเจอตอนตั้ง Kong+Cloudflare Tunnel ครั้งแรกบน on-prem VM, ข้อ 6 เจอตอนเพิ่ม MinIO S3 API เข้าหลัง domain จริงทีหลัง, ข้อ 7-8 เจอตอนทำ deploy script ให้มี gate ครบ (lint/test/migration/health check) แล้วรันจริง — ทั้งคู่เป็นบั๊กที่อ่าน script เฉย ๆ ไม่มีทางเห็น ต้องรันถึงจะโผล่, ข้อ 9-10 เจอตอนตั้งคำถามว่าทำไม deploy ต้องมี downtime ทั้งที่ pm2 รองรับ zero-downtime อยู่แล้ว — คำตอบคือคอมเมนต์ที่อธิบายเหตุผลไว้ผิด

1

Disk เต็มกลางทางตอนตั้ง Kong stack

อาการ: kong-database container crash ตอน initdb ด้วย FATAL: could not extend file ... No space left on device

สาเหตุ: VM root disk ตั้งไว้พอสำหรับ datastore stack เดิมเท่านั้น (20 GB) — Kong+Konga+Mongo images เพิ่มมาอีก ~4-5 GB ดันให้ disk เต็มพอดีตอน initdb ต้องเขียนไฟล์

แก้: ขยาย virtual disk จาก Proxmox (ดู §03 ขั้นตอน 1 — ต้องขยายทั้งระดับ virtual disk และ filesystem ข้างใน guest) ก่อนจะตั้ง stack ใหม่ใด ๆ เพิ่ม — ป้องกันได้ตั้งแต่ต้นด้วยการเผื่อ disk ตามตาราง §02 ตั้งแต่สร้าง VM ครั้งแรก

2

Kong Admin API bind 127.0.0.1 แต่เข้าจากนอก container ไม่ได้

อาการ: curl 127.0.0.1:8001/status จาก host ได้ Connection reset by peer ทั้งที่ตั้ง port mapping 127.0.0.1:8001:8001 ไว้แล้ว

สาเหตุ: Docker's published-port NAT ส่ง connection เข้า container ผ่าน bridge interface ไม่ใช่ loopback — service ที่ bind 127.0.0.1 ข้างใน container จะปฏิเสธ connection ที่มาทาง bridge เสมอ ไม่ว่า host-side port mapping จะจำกัดแค่ loopback แค่ไหนก็ตาม

แก้: bind เป็น 0.0.0.0 ข้างใน container เสมอ (KONG_ADMIN_LISTEN: "0.0.0.0:8001") แล้วปล่อยให้ host-side port mapping (127.0.0.1:8001:8001) เป็นตัวจำกัดการเข้าถึงจริงแทน

3

Konga ใช้งานกับ MongoDB รุ่นใหม่ไม่ได้เลย

อาการ: ทุก query จาก Konga ล้มเหลวด้วย Unsupported OP_QUERY command

สาเหตุ: Konga (pantsel/konga, ไม่มีการดูแลต่อมาหลายปี) ใช้ driver เก่า (sails-mongo) ที่พูด legacy OP_QUERY wire protocol — MongoDB เอา protocol นี้ออกตั้งแต่ 5.0

แก้: pin image เป็น mongo:4.4 (เวอร์ชันสุดท้ายที่ยังรองรับ OP_QUERY) แทน mongo:7/latest

4

Browser บล็อก request เพราะ Private Network Access policy

อาการ: หน้า admin เปิดผ่าน https://erp-api.<domain> ได้ปกติ แต่ login ไม่ได้ — console error blocked by CORS policy: Permission was denied for this request to access the 'local' address space

สาเหตุ: AUTH_PUBLIC_URL ยังเหลือเป็น private IP (http://172.x.x.x:3001) — browser ของผู้ใช้ (อยู่บนหน้า public HTTPS) พยายามยิง fetch ตรงไปที่ IP วง private โดน Chrome's Private Network Access ปฏิเสธทันที ไม่ว่า CORS header จะถูกต้องแค่ไหนก็ตาม

แก้: ตั้ง AUTH_PUBLIC_URL/REPORT_PUBLIC_URL เป็น public domain เสมอ ตาม §08 — ปัญหาหมดทันทีเพราะ browser ยิงไปที่ domain สาธารณะผ่าน Kong ปกติ

5

Let's Encrypt (ACME) ออก certificate ไม่ได้เมื่อผ่าน Tunnel

อาการ: ตั้ง Kong's acme plugin ไว้แล้วแต่ certificate ไม่เคยออกสำเร็จ ค้าง retry ตลอด

สาเหตุ: Let's Encrypt's HTTP-01 challenge ต้องการเข้าถึง port 80 จากอินเทอร์เน็ตเปิดตรง ๆ เพื่อยืนยันว่าเราคุม domain จริง — เมื่อ Cloudflare Tunnel เป็นทางเข้าเดียว ไม่มี path แบบนั้นให้ Let's Encrypt ไปถึงได้อีกแล้ว (มีแต่ผ่าน tunnel ซึ่ง Let's Encrypt เข้าไม่ถึง)

แก้: ไม่ต้องพึ่ง ACME เลยในสถาปัตยกรรมนี้ — Cloudflare terminate TLS ให้แทนที่ edge อยู่แล้ว (ดู §01/§07) ปล่อยปลั๊กอิน acme ไว้เฉย ๆ ก็ได้ (ไม่กระทบอะไร แค่ retry ค้างไปเรื่อย ๆ) หรือปิดไปเลยถ้าต้องการ ความสะอาด — ปัญหานี้จะกลับมาเกี่ยวข้องเฉพาะกรณีเปิด port 80/443 ตรงสู่อินเทอร์เน็ตแทน tunnel เท่านั้น

6

Presigned URL ใช้ virtual-hosted style แทน path-style หลังเปลี่ยนจาก IP เป็น domain

อาการ: พอเปลี่ยน STORAGE_S3_ENDPOINT จาก internal IP (http://172.x.x.x:9000) เป็น public domain ผ่าน Kong แล้ว presigned URL ที่คืนออกไปกลับมีรูปแบบ <bucket>.<domain>/... (virtual-hosted style) แทนที่จะเป็น <domain>/<bucket>/... (path-style) ทั้งที่ตั้ง STORAGE_S3_FORCE_PATH_STYLE=true ไว้แล้ว — รูปแบบ virtual-hosted ต้องมี wildcard DNS record ของตัวเอง (*.<domain>) ซึ่งไม่มีใครตั้งไว้ ทำให้อัปโหลดจากเบราว์เซอร์จริงล้มเหลวทันที (resolve ไม่ได้)

สาเหตุ: STORAGE_S3_FORCE_PATH_STYLE ไม่ได้อยู่ใน Joi validation schema ของ libs/config — ConfigService.get() จึงคืนค่าตามที่ dotenv parse มาตรง ๆ คือสตริง "true" ไม่ใช่ boolean แท้ ๆ และพบว่า AWS SDK v3's S3 client เลือก address style ผิดเมื่อ config หลายค่าพร้อมกันมาจาก env (สตริงที่ไม่ผ่านการ type-coerce) — ยืนยันซ้ำหลายรอบว่า literal boolean ตรง ๆ ไม่มีปัญหา แต่ค่าที่มาจาก process.env ทำให้ SDK behavior ไม่แน่นอน

แก้: coerce เป็น boolean แท้ ๆ อย่างชัดเจนในโค้ดแทนที่จะเชื่อว่า SDK จะปฏิบัติกับสตริง truthy เหมือน boolean เสมอ — forcePathStyle: configService.get('STORAGE_S3_FORCE_PATH_STYLE', 'true') !== 'false' (apps/storage/src/storage.service.ts) ยืนยันด้วยการทดสอบ presigned upload ผ่าน domain จริงซ้ำหลายรอบหลังแก้ — path-style ถูกต้องสม่ำเสมอ

7

ssh ไม่รักษาขอบเขต argument — argument ว่างหายไปทั้งตัว

อาการ: deploy script ตายทันทีด้วย bash: line 10: $8: unbound variable ทั้งที่ส่ง argument ไปครบ 8 ตัว เกิดเฉพาะตอนไม่ระบุ branch — ถ้าสั่ง deploy-ovh-dev.sh main กลับผ่านปกติ

สาเหตุ: ssh host bash -s -- a "" c ไม่ได้ส่ง argv เป็น array — ssh เอาทุกอย่างหลังชื่อ host มาต่อเป็นสตริงเดียว แล้ว shell ปลายทาง split ใหม่ด้วย whitespace argument ที่เป็นสตริงว่างจึงหายไปเลย ไม่ได้มาถึงเป็น "" — ตัวที่เหลือเลื่อนตำแหน่งลงมาหนึ่งช่อง แล้ว set -u ก็ฆ่า script ทิ้ง 

# ผิด — BRANCH ว่างเมื่อไม่ระบุ branch ⇒ remote เห็นแค่ 7 ตัว
ssh -T "$REMOTE_HOST" bash -s -- "$REMOTE_DIR" "$BRANCH" "$NODE_VERSION" ...

# ถูก — printf %q เขียนสตริงว่างเป็น '' ให้ shell ปลายทางเห็นเป็น argument จริง
REMOTE_ARGS=""
for arg in "$REMOTE_DIR" "$BRANCH" "$NODE_VERSION" ...; do
  REMOTE_ARGS="${REMOTE_ARGS} $(printf '%q' "$arg")"
done
ssh -T "$REMOTE_HOST" "bash -s --${REMOTE_ARGS}" <<'REMOTE_SCRIPT'

บทเรียน: เวอร์ชันเดิมของ script ส่งแค่ 2 argument และอ่านด้วย ${2:-} — บั๊กนี้มีอยู่แล้วแต่ถูกกลบ เพราะ default value ดูดซับความผิดพลาดพอดี พอเพิ่มเป็น 8 argument มันจึงโผล่ ทดสอบยืนยันด้วยการ echo $# กลับมาจาก server จริงว่าได้ครบ 8 และ $2 เป็นค่าว่างจริง

8

nx lint ไม่เคยเขียว เพราะ lint ไฟล์ที่ generate ขึ้นมาเอง

อาการ: ใส่ nx run-many -t lint --all เป็น gate ใน deploy แล้ว deploy ไม่ผ่านสักครั้ง — 12 project fail ด้วย Parsing error: ... was not found by the project service รวมถึงไฟล์ที่ไม่ควรถูก lint เลย เช่น apps/iam/dist/public/**/bundle.js (build output ของ esbuild) และไฟล์ใน git submodule

สาเหตุ: @nx/eslint/plugin รัน eslint . ต่อ project คือลาก ทุก .js/.mjs เข้ามาด้วย ขณะที่ npm run lint ของ repo glob แค่ {apps,libs}/**/*.ts จึงไม่เคยเห็นไฟล์เหล่านั้น พอเจอ projectService: true แล้วไฟล์ไม่ได้อยู่ใน tsconfig ก็ parse ไม่ได้

แก้: เพิ่ม ignores สำหรับ **/dist/**, coverage/, .nx/, docs/ (submodule) แล้ว lint ไฟล์ JS แบบไม่ใช้ type information ด้วย disableTypeChecked

ลำดับใน flat config เป็นเรื่องเป็นตาย

บล็อก disableTypeChecked ต้องอยู่หลังบล็อก rules ที่ไม่มี files — เพราะบล็อกนั้นมีผลกับทุกไฟล์ จึงเปิด type-checked rules กลับมาให้ .js อีก ผลลัพธ์ไม่ใช่ lint error ธรรมดา แต่เป็น eslint crash ทั้งตัว ด้วย Error while loading rule '@typescript-eslint/no-floating-promises'

9

pm2 env_file ไม่ทำงานเลย — และมันทำให้ยอมรับ downtime ฟรีมาตลอด

อาการ: deploy script ใช้ pm2 delete + start (ดับทุก BC พร้อมกัน) โดยมีคอมเมนต์กำกับว่า “env_file อ่านแค่ตอน pm2 start — reload จะเสิร์ฟ .env เก่า” ไม่มีใครตั้งคำถาม เพราะฟังดูสมเหตุสมผล

สาเหตุ: เหตุผลนั้นผิดทั้งสองท่อน — วัดบนเครื่องนี้ (pm2 7.0.3) 

# ตั้ง env_file แล้วดูว่าตัวแปรถึง process จริงไหม (ลองทั้ง relative และ absolute path)
tr '\0' '\n' < /proc/<pid>/environ | grep PROBE_VALUE   # → ไม่มี
pm2 env <id> | grep PROBE_VALUE                          # → ไม่มี

# แล้วแอปได้ค่าจากไหน? NestJS ConfigModule อ่าน .env เองด้วย dotenv ตอน bootstrap
# (envFilePath: ['.env'], libs/config) → process ใหม่ทุกตัวได้ค่าใหม่ รวมถึง reload
after start        -> v1-original
# แก้ .env เป็น v2-changed แล้ว reload
after pm2 reload   -> v2-changed        ← อ่านค่าใหม่ได้
non-200 ระหว่าง reload: 0/400

แก้: ใช้ pm2 startOrReload ecosystem.config.js (ไม่ใช่ reload เปล่า ๆ เพราะ startOrReload start ให้ด้วย ถ้ามี BC ใหม่ในไฟล์ที่ยังไม่ได้รัน) แล้วลบ env_file ออกจาก ecosystem.config.js — ปล่อยไว้คือปล่อยกับดักให้คนถัดไป วัดซ้ำบน iam ตัวจริง: 300/300 request ตอบ 200 ระหว่าง reload

10

interpreter: 'none' ใช้ร่วมกับ cluster mode ไม่ได้

อาการ: จะให้ erp-web ได้ zero-downtime แบบเดียวกับ backend ต้องเปลี่ยนเป็น exec_mode: 'cluster' แต่ config เดิมมี interpreter: 'none' อยู่ (จำเป็น เพราะ node_modules/.bin/next ที่ pnpm สร้างเป็น shell shim ไม่ใช่ JS — ดู §05)

สาเหตุ: cluster mode ต้องให้ Node fork() ตัวสคริปต์เอง และ fork shell script ไม่ได้ — สองอย่างนี้ใช้ร่วมกันไม่ได้โดยสิ้นเชิง

แก้: ชี้ script ไปที่ JS ตัวจริงแทน shim — node_modules/next/dist/bin/next เป็นไฟล์ #!/usr/bin/env node ธรรมดา ใช้ interpreter default ของ pm2 ได้ แล้วตัด interpreter: 'none' ทิ้ง วัดกับ Next ตัวจริง: 

fork/1    + pm2 restart  →  56 request พัง (~2.8 วิ ECONNREFUSED)
cluster/2 + pm2 reload   →  0 request พัง   (250/250 ตอบ 200)
reload เปลี่ยน instances ไม่ได้ — ต้องมี guard

วัดแล้ว startOrReload อัปเดต node_args ให้ แต่ไม่เปลี่ยน instances (2→3 ยังคงเป็น 2) แปลว่าการสลับ fork/1 → cluster/2 จะเงียบ — deploy รายงานสำเร็จทุกครั้งแต่ยังทิ้ง request เท่าเดิม deploy script ทั้งสอง repo จึงเทียบ exec_mode/instances ที่รันอยู่จริงกับที่ config ต้องการ แล้ว recycle เฉพาะ app ที่รูปทรงต่างกันจริง — ทดสอบแล้วว่า app ที่ตรงอยู่แล้ว (เช่น BC ที่เป็น cluster/2 อยู่) ไม่ถูกแตะ จึงไม่เกิด downtime ฟรีทุก deploy

10 — Day-2 Operations

สองอย่างที่ไม่ตั้งแล้วพังแน่นอน

ทั้งสองข้อนี้ไม่ทำให้ระบบพังตอน deploy — มันพังทีหลัง ตอนไฟดับ หรือตอน disk เต็มในอีกหลายเดือน ซึ่งเป็นเวลาที่ไม่มีใครนั่งเฝ้าอยู่ สำหรับเครื่อง on-premise ที่ลูกค้าดูแลเอง ทั้งคู่คือ ขั้นตอนบังคับตอนส่งมอบ ไม่ใช่ของเสริม

1

pm2 startup — ให้ process กลับมาเองหลังไฟดับ

pm2 โดย default ไม่ ผูกกับ systemd — ถ้าเครื่อง reboot (ไฟดับ, patch kernel, ลูกค้ากดปิด) ทุก process จะหายหมดและไม่มีอะไรพากลับมา ระบบจะดับค้างจนกว่าจะมีคน ssh เข้าไป pm2 start เองทีละตัว 

pm2 startup systemd -u root --hp /root   # สร้าง systemd unit ชื่อ pm2-root
pm2 save                                 # freeze process list ปัจจุบันลง ~/.pm2/dump.pm2

# ยืนยัน — ต้องได้ enabled
systemctl is-enabled pm2-root

ตอน boot systemd จะเรียก pm2 resurrect ซึ่งอ่านจาก dump.pm2 — ไม่ใช่ จาก ecosystem.config.js ของ repo ไหนเลย

RULE

ทุกครั้งที่เพิ่ม/ลบ process ต้อง pm2 save ซ้ำ — ไม่งั้น dump.pm2 ยังเป็นชุดเก่า และ reboot ครั้งถัดไปจะได้ process ชุดที่ ไม่ตรงกับความจริง (เช่น มี erp-web อยู่ตอนนี้ แต่ตอน boot ไม่มี เพราะ save ไว้ก่อนเพิ่ม) deploy script ควรเรียก pm2 save ปิดท้ายเสมอ

2

pm2-logrotate — กัน disk เต็มจาก log ตัวเอง

pm2 เขียน stdout/stderr ของทุก process ลง /root/.pm2/logs/ แบบไม่มีเพดาน — ไฟล์เดียวโตถึงหลักร้อย MB ได้สบายถ้ามี error loop (เคยพบ iam-error-1.log ~740 MB จากรวม ~1 GB) 

pm2 install pm2-logrotate

pm2 set pm2-logrotate:max_size 10M          # rotate เมื่อไฟล์เกิน 10 MB
pm2 set pm2-logrotate:retain 14             # เก็บย้อนหลัง 14 ไฟล์
pm2 set pm2-logrotate:compress true         # gzip ไฟล์เก่า
pm2 set pm2-logrotate:rotateInterval '0 0 * * *'   # rotate ทุกเที่ยงคืนด้วย

pm2 conf pm2-logrotate                      # ยืนยันค่าที่ตั้งไป
du -sh /root/.pm2/logs                      # เช็คขนาดรวม
rotation ไม่ย้อนหลัง

pm2-logrotate จัดการเฉพาะไฟล์ที่โตขึ้นหลังติดตั้ง — ก้อนที่ค้างอยู่ก่อนหน้า (รวมถึง log ของโปรเจกต์เก่าที่เลิกรันไปแล้วแต่ไฟล์ยังอยู่) ต้องลบเอง ตรวจด้วย ls -S /root/.pm2/logs | head ตอนส่งมอบ

log มี 2 ระบบ แยกกันคนละทาง — อย่าสับสน

เครื่องนี้มี log 2 สายที่ไม่เกี่ยวกันเลย คนละไฟล์ คนละกลไก rotate คนละปลายทาง — การตั้ง pm2-logrotate จึงไม่กระทบ pipeline ที่ส่งเข้า Loki (Alloy tail คนละ path กัน) และในทางกลับกัน log ที่เห็นใน Grafana ก็ไม่ใช่ทุกอย่างที่ process พ่นออกมา
