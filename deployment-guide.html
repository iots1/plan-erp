Technical Implementation Guide

On-Premise Deployment
(Docker Compose · Kong · Cloudflare Tunnel)

แนวทางติดตั้งระบบ ERP บนเครื่องที่ลูกค้าซื้อมาเองและดูแลเอง (on-premise) — ตั้งแต่เตรียมเครื่อง/VM, ตั้ง datastore + Kong API Gateway ด้วย Docker Compose, ไปจนถึงเปิด domain สาธารณะผ่าน Cloudflare Tunnel โดยไม่ต้อง เปิด port forward บน router หรือมี public IP คงที่เลย

01 — ภาพรวม

รูปแบบ Deployment สำหรับลูกค้าที่ซื้อเครื่องเอง

ลูกค้าหลายรายซื้อเครื่อง/VM มาเองและติดตั้ง ERP ในเครือข่ายภายใน (LAN ส่วนตัว, IP วง private) ไม่มี public IP คงที่ ไม่อยาก/ไม่สามารถเปิด port forward บน router ขององค์กรได้ — สถาปัตยกรรมนี้แก้ปัญหาด้วย Cloudflare Tunnel: เครื่อง on-prem เป็นฝ่าย "เชื่อมออก" หา Cloudflare เอง (outbound connection) แทนที่จะรอรับ inbound connection จากอินเทอร์เน็ต — ไม่ต้องเปิด firewall/port ใด ๆ เข้าเครือข่ายภายในเลย

RULE

Cloudflare terminates TLS ที่ edge เสมอ — จาก cloudflared เข้าไปที่ Kong เป็น HTTP ธรรมดาตลอด ไม่ใช่ HTTPS แม้ domain ปลายทางที่ผู้ใช้เห็นจะเป็น https:// ก็ตาม — สำคัญมากตอนตั้งค่า Tunnel route และค่า COOKIE_SECURE/TRUST_PROXY ใน §08

ข้อดี

ไม่ต้องมี Public IP / Port Forward

เครื่อง on-prem อยู่หลัง NAT/Firewall ขององค์กรได้ตามปกติ — Cloudflare Tunnel เป็น outbound connection ล้วน ๆ ลูกค้าไม่ต้องขอสิทธิ์แก้ router/firewall จาก IT องค์กรเลย

เงื่อนไข

ต้องมี Domain ผูกกับ Cloudflare

ลูกค้าต้องมี domain (ซื้อเองหรือมีอยู่แล้ว) และ nameserver ชี้ไปที่ Cloudflare — ถ้าไม่มี domain ระบบยังใช้งานได้ในวง LAN ภายในผ่าน IP ตรง แต่จะไม่มี HTTPS/public access

02 — Hardware / OS Requirement

ขนาดเครื่องที่ต้องเผื่อไว้จริง

03 — เตรียม VM (Proxmox)

สร้างและตั้งค่า VM

1

สร้าง VM ด้วย disk size ที่เผื่อไว้ตั้งแต่แรก

อ้างอิงตาราง §02 — ตั้ง virtual disk อย่างน้อย 80 GB ตั้งแต่สร้าง VM ครั้งแรก (thin-provision ได้ ไม่กินพื้นที่จริงจนกว่าจะใช้) ดีกว่าต้องมาขยายทีหลังตอนเจอปัญหา

ถ้าจำเป็นต้องขยาย disk ทีหลัง ต้องทำ 2 ระดับ

1) ขยาย virtual disk ใน Proxmox ก่อน (qm resize <vmid> scsi0 +40G หรือผ่าน UI) 2) เข้าไปขยาย partition/filesystem ข้างใน guest OS เองอีกที — สอง VM ที่ config ต่างกัน (LVM ธรรมดา vs. loop-mounted rootfs แบบ cloud-image) ใช้คำสั่งขยายต่างกัน เช็ค lsblk/df -h / ก่อนเสมอว่า disk ใหม่ที่ Proxmox เห็นจริง ๆ ถูกขยายเข้าไปถึง filesystem จริงหรือยัง (ไม่ใช่แค่ระดับ virtual disk)

2

ติดตั้ง Docker + dependencies

# Docker Engine + Compose plugin
curl -fsSL https://get.docker.com | sh

# nvm + Node.js (เวอร์ชันตาม package.json ของ erp-api)
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
nvm install --lts

# pnpm + pm2
npm install -g pnpm pm2
3

ตั้ง static IP / DHCP reservation

ตั้งค่า network interface ให้ได้ IP คงที่ในวง LAN (เช่นผ่าน Proxmox network config หรือ DHCP reservation ที่ router) — ค่านี้จะถูกใช้ซ้ำหลายจุด: Kong's BC_UPSTREAM_HOST, Konga's KONGA_BIND_HOST, และ Cloudflare Tunnel's origin URL (§07) — ถ้า IP เปลี่ยนทีหลังต้องไปแก้ทุกจุดพร้อมกัน

ตั้ง infra-erp stack

# แนะนำ: วางไว้นอก repo checkout เช่น /root/infra-erp (ไม่ใช่ /root/erp-api/infrastructure/infra-erp)

docker compose up -d

Build + รันด้วย pm2

06 — Kong API Gateway

รวม 8 BC ไว้หลัง domain เดียว

Kong ทำ path-based routing — แต่ละ BC ยังคง prefix เดิมของตัวเอง (/auth/v1, /iam/v1, ...) ไม่ต้องแก้โค้ดแอปฝั่งไหนเลย รายละเอียดเต็มอยู่ที่ infrastructure/kong/ ใน repo หลัก 

cp -r erp-api/infrastructure/kong /root/infra-erp/kong  # วางคู่กับ datastore stack เหมือน §04
cd /root/infra-erp/kong
cp .env.example .env
# KONG_PG_PASSWORD / KONGA_MONGO_PASSWORD / KONGA_TOKEN_SECRET / ACME_ACCOUNT_EMAIL
# DOMAIN=erp-api.<ลูกค้า>.com
# BC_UPSTREAM_HOST=<LAN IP ของเครื่องจาก §03>   — ไม่ใช้ host.docker.internal default
# KONGA_BIND_HOST=<LAN IP เดียวกัน> ถ้าต้องการเข้า Konga UI จากเครื่องอื่นในวง

docker compose up -d
./setup-routes.sh   # สร้าง service+route ให้ 8 BC พร้อม preserve_host=true
  • BC_UPSTREAM_HOST ต้องเป็น IP ที่ Kong container เข้าถึงได้จริง — ใช้ LAN IP ของเครื่องเป็นค่าง่ายสุด เพราะทุก BC bind 0.0.0.0 อยู่แล้ว
  • preserve_host=true (ตั้งให้อัตโนมัติโดย setup-routes.sh) ทำให้แต่ละ BC เห็น Host header เป็น domain จริง ไม่ใช่ upstream address — จำเป็นสำหรับ cookie/CORS ที่ §08
  • Kong Admin API (8001) และ Konga (1337) ควรเปิดแค่ในวง LAN/loopback เท่านั้น — ห้ามเปิดสู่อินเทอร์เน็ตผ่าน Tunnel
07 — Cloudflare Tunnel

เปิด Domain สาธารณะโดยไม่เปิด Port

1

เตรียม Cloudflare account + Domain

ลูกค้าต้องมี domain ที่ nameserver ชี้ไปที่ Cloudflare อยู่แล้ว (ย้าย DNS เข้า Cloudflare ฟรี ถ้ายังไม่ได้ทำ) แล้วเข้า Zero Trust dashboard → Networks → Tunnels → สร้าง tunnel ใหม่ (type: cloudflared)

2

ติดตั้ง cloudflared บนเครื่อง on-prem

Dashboard จะให้คำสั่งติดตั้งพร้อม token เฉพาะของ tunnel นั้น — รันบนเครื่อง on-prem โดยตรง (ติดตั้งเป็น systemd service อัตโนมัติ): 

# คำสั่งตัวอย่าง (ค่าจริงมาจาก dashboard ตอนสร้าง tunnel)
curl -L --output cloudflared.deb https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64.deb
sudo dpkg -i cloudflared.deb
sudo cloudflared service install <TUNNEL_TOKEN>

เช็คสถานะด้วย systemctl status cloudflared — ต้องเห็น Environment is healthy ใน log ก่อนไปขั้นถัดไป

3

เพิ่ม Public Hostname route → Kong

ในหน้า tunnel เดียวกัน → Add a route → เลือก "Published application" (ไม่ใช่ Private hostname/Private CIDR/Workers VPC — สามแบบนั้นสำหรับ Zero Trust/WARP client เข้าถึง private app ภายใน ไม่ใช่ publish เว็บสู่สาธารณะ)

Fieldค่า
Subdomainerp-api (หรือชื่อที่ต้องการ)
Domaindomain ของลูกค้า
Service TypeHTTP — ห้ามเลือก HTTPS
URL<LAN IP จาก §03>:80
ทำไมต้อง HTTP ไม่ใช่ HTTPS

Cloudflare terminate TLS ให้ผู้ใช้ที่ edge อยู่แล้ว (ดู diagram §01) — เลือก HTTPS ไปที่ Kong's port 443 จะไปเจอ TLS listener ที่ไม่มี certificate ที่ใช้งานได้จริง (ดู §09 บั๊ก #5 เรื่อง ACME) ทำให้ tunnel handshake ล้มเหลว ใช้ HTTP เข้า port 80 ธรรมดา ปลอดภัยเพียงพอเพราะ traffic ระหว่าง cloudflared ↔ Kong วิ่งอยู่ในเครื่อง/LAN เดียวกัน ไม่ใช่อินเทอร์เน็ตเปิด

08 — Production .env Checklist

ค่าที่ต้องเปลี่ยนก่อนขึ้นจริง — พลาดแล้วพังแบบเงียบ

ห้าค่านี้เป็น dev default ที่ใช้ได้ตอน localhost เท่านั้น — ถ้าลืมแก้หลังต่อ domain จริงผ่าน Kong+Tunnel จะพังแบบไม่มี error message ที่ตรงจุดให้เห็นง่าย ๆ (พบจริงระหว่างตั้งระบบ — ดู §09 บั๊ก #4)

ตัวแปรDev default (ผิดสำหรับ prod)ต้องเปลี่ยนเป็น
AUTH_PUBLIC_URLhttp://localhost:3001https://erp-api.<domain>
REPORT_PUBLIC_URLhttp://localhost:3007https://erp-api.<domain>
CORS_ORIGINhttp://localhost:3002https://erp-api.<domain>
COOKIE_SECUREfalsetrue
TRUST_PROXY(unset — default whitelist ไม่รวม Kong)รวม Kong's docker network subnet + host LAN IP

รายละเอียดทีละตัว

  • AUTH_PUBLIC_URL / REPORT_PUBLIC_URL — ค่านี้ถูกฝังลงหน้า admin ของ iam เป็น URL ที่ browser ของผู้ใช้เองยิง fetch ตรง ๆ ไม่ใช่ server-to-server เหลือเป็น private IP/localhost แล้ว browser จริงจะโดนบล็อกด้วย Private Network Access policy ของ Chrome ทันที
  • CORS_ORIGIN — ต้องเป็น origin จริงเป๊ะ ๆ (ไม่ใช่ *) เพราะแอปใช้ credentials: true สำหรับ cookie auth flow
  • COOKIE_SECURE — เปิดเป็น true ได้ปลอดภัยเพราะผู้ใช้คุยกับ Cloudflare ด้วย HTTPS จริงเสมอ แม้ hop ภายใน (cloudflared → Kong → app) จะเป็น HTTP ก็ตาม
  • TRUST_PROXY — หา subnet ของ Kong's docker network ด้วย docker network inspect kong_default แล้วใส่รวมกับ host's LAN IP (Docker NAT อาจ rewrite source IP เป็น host IP ตอน container เรียกกลับเข้า host) — ไม่งั้น req.ip/req.protocol จะอ่านผิดจาก Kong's X-Forwarded-* headers
RULE

pm2's env_file อ่านค่าแค่ตอน pm2 start เท่านั้น — แก้ .env แล้วต้อง pm2 delete all && pm2 start ecosystem.config.js (ไม่ใช่ restart/reload) ค่าใหม่ถึงจะมีผลจริง

09 — บั๊กที่เจอระหว่าง Implement และวิธีแก้

5 บั๊กจริงที่เจอตอนตั้งระบบครั้งแรก

บันทึกไว้ละเอียดกันคนถัดไปเจอปัญหาเดิม — ทุกข้อเจอจริงตอนตั้ง Kong+Cloudflare Tunnel ครั้งแรกบน on-prem VM

1

Disk เต็มกลางทางตอนตั้ง Kong stack

อาการ: kong-database container crash ตอน initdb ด้วย FATAL: could not extend file ... No space left on device

สาเหตุ: VM root disk ตั้งไว้พอสำหรับ datastore stack เดิมเท่านั้น (20 GB) — Kong+Konga+Mongo images เพิ่มมาอีก ~4-5 GB ดันให้ disk เต็มพอดีตอน initdb ต้องเขียนไฟล์

แก้: ขยาย virtual disk จาก Proxmox (ดู §03 ขั้นตอน 1 — ต้องขยายทั้งระดับ virtual disk และ filesystem ข้างใน guest) ก่อนจะตั้ง stack ใหม่ใด ๆ เพิ่ม — ป้องกันได้ตั้งแต่ต้นด้วยการเผื่อ disk ตามตาราง §02 ตั้งแต่สร้าง VM ครั้งแรก

2

Kong Admin API bind 127.0.0.1 แต่เข้าจากนอก container ไม่ได้

อาการ: curl 127.0.0.1:8001/status จาก host ได้ Connection reset by peer ทั้งที่ตั้ง port mapping 127.0.0.1:8001:8001 ไว้แล้ว

สาเหตุ: Docker's published-port NAT ส่ง connection เข้า container ผ่าน bridge interface ไม่ใช่ loopback — service ที่ bind 127.0.0.1 ข้างใน container จะปฏิเสธ connection ที่มาทาง bridge เสมอ ไม่ว่า host-side port mapping จะจำกัดแค่ loopback แค่ไหนก็ตาม

แก้: bind เป็น 0.0.0.0 ข้างใน container เสมอ (KONG_ADMIN_LISTEN: "0.0.0.0:8001") แล้วปล่อยให้ host-side port mapping (127.0.0.1:8001:8001) เป็นตัวจำกัดการเข้าถึงจริงแทน

3

Konga ใช้งานกับ MongoDB รุ่นใหม่ไม่ได้เลย

อาการ: ทุก query จาก Konga ล้มเหลวด้วย Unsupported OP_QUERY command

สาเหตุ: Konga (pantsel/konga, ไม่มีการดูแลต่อมาหลายปี) ใช้ driver เก่า (sails-mongo) ที่พูด legacy OP_QUERY wire protocol — MongoDB เอา protocol นี้ออกตั้งแต่ 5.0

แก้: pin image เป็น mongo:4.4 (เวอร์ชันสุดท้ายที่ยังรองรับ OP_QUERY) แทน mongo:7/latest

4

Browser บล็อก request เพราะ Private Network Access policy

อาการ: หน้า admin เปิดผ่าน https://erp-api.<domain> ได้ปกติ แต่ login ไม่ได้ — console error blocked by CORS policy: Permission was denied for this request to access the 'local' address space

สาเหตุ: AUTH_PUBLIC_URL ยังเหลือเป็น private IP (http://172.x.x.x:3001) — browser ของผู้ใช้ (อยู่บนหน้า public HTTPS) พยายามยิง fetch ตรงไปที่ IP วง private โดน Chrome's Private Network Access ปฏิเสธทันที ไม่ว่า CORS header จะถูกต้องแค่ไหนก็ตาม

แก้: ตั้ง AUTH_PUBLIC_URL/REPORT_PUBLIC_URL เป็น public domain เสมอ ตาม §08 — ปัญหาหมดทันทีเพราะ browser ยิงไปที่ domain สาธารณะผ่าน Kong ปกติ

5

Let's Encrypt (ACME) ออก certificate ไม่ได้เมื่อผ่าน Tunnel

อาการ: ตั้ง Kong's acme plugin ไว้แล้วแต่ certificate ไม่เคยออกสำเร็จ ค้าง retry ตลอด

สาเหตุ: Let's Encrypt's HTTP-01 challenge ต้องการเข้าถึง port 80 จากอินเทอร์เน็ตเปิดตรง ๆ เพื่อยืนยันว่าเราคุม domain จริง — เมื่อ Cloudflare Tunnel เป็นทางเข้าเดียว ไม่มี path แบบนั้นให้ Let's Encrypt ไปถึงได้อีกแล้ว (มีแต่ผ่าน tunnel ซึ่ง Let's Encrypt เข้าไม่ถึง)

แก้: ไม่ต้องพึ่ง ACME เลยในสถาปัตยกรรมนี้ — Cloudflare terminate TLS ให้แทนที่ edge อยู่แล้ว (ดู §01/§07) ปล่อยปลั๊กอิน acme ไว้เฉย ๆ ก็ได้ (ไม่กระทบอะไร แค่ retry ค้างไปเรื่อย ๆ) หรือปิดไปเลยถ้าต้องการ ความสะอาด — ปัญหานี้จะกลับมาเกี่ยวข้องเฉพาะกรณีเปิด port 80/443 ตรงสู่อินเทอร์เน็ตแทน tunnel เท่านั้น
