Implementation Guide · inventory-bc + storage-bc

อัปโหลดรูปสินค้า
(Product Images — Presigned & Multipart)

บันทึกการ implement จริงของฟีเจอร์อัปโหลดรูปสินค้า ครอบคลุมทั้งสินค้าปกติ (single), template (has_variants=true) และ variant ที่ generate ออกมา — ตาราง product_images ตัวเดียวรองรับทั้งสามกรณี พร้อม 2 flow การอัปโหลด (presigned URL ตรงไป MinIO และ multipart ผ่าน backend) — เขียนขึ้นแทนที่ร่างเดิมใน srs-p2.html §04 ซึ่งยังอิง schema file_objects ที่ไม่ตรงกับของจริงที่ build แล้ว

MinIO / S3-Compatible @fastify/multipart Presigned PUT/GET RMQ (TRANSPORT=rmq)
01 — ภาพรวม & การตัดสินใจออกแบบ

ทำไมตารางเดียวพอสำหรับทุกกรณี

product.entity.ts ออกแบบไว้แล้วว่า template (has_variants=true) และ variant ที่ generate ออกมา (template_product_id ชี้กลับ) เป็นแถวใน products เหมือนกันทั้งหมด — ดังนั้นตาราง product_images ที่ FK ไป product_id เพียงคอลัมน์เดียวจึงครอบคลุมทั้ง 3 กรณีโดยไม่ต้องมี polymorphic table หรือ schema แยก

DECISION 1

ไม่เก็บ Signed URL ลง DB

เก็บแค่ bucket + object_key — presigned URL หมดอายุ (1 ชม.) เก็บลง DB คือเก็บค่าที่เน่า ต้อง sign ใหม่ทุกครั้งตอนอ่าน

DECISION 2

size/extension/etag มาจาก S3 เท่านั้น

ไม่เชื่อค่าที่ client ส่งมา — HeadObject คือแหล่งความจริงเดียว ก่อน insert แถวเสมอ (ดู §04/05)

DECISION 3

Soft-delete แถว ไม่ลบ object บน S3

เหมือน print_templates — ย้อนดู/กู้คืนได้ทันที ไม่ต้อง compensating-delete ตอน insert fail ทีหลัง

TRANSPORT · ไม่เกี่ยวกับ RMQ/TCP

Flow B (presigned) ทำให้ไบต์ไฟล์ไม่วิ่งผ่าน message broker เลย ไม่ว่า TRANSPORT จะเป็น rmq หรือ tcp — inventory-bc คุยกับ storage-bc แค่ 2 คำสั่งเล็ก ๆ (ขอ presigned URL / verify object) ไม่ใช่ buffer ไฟล์ จึงไม่ต้อง override transport ของ platform เลย

03 — storage-bc · คำสั่งใหม่ (AppMicroservice.Storage.cmd)

2 RPC command ที่เพิ่มเข้ามา

storage-bc เป็น thin wrapper รอบ S3 SDK ล้วน ๆ (ไม่มี DB) — เพิ่ม 2 คำสั่งใหม่ต่อจาก Upload/UploadWithMeta/Remove/GetPath/GenerateSignedUrls เดิม

cmdInputOutput
GeneratePresignedUploadbucket, key, original_name, mime_type{ bucket, path, upload_url } — PUT URL อายุ 5 นาที
HeadObjectbucket, key{ size, content_type, etag } | null — null = ยังไม่มีการอัปโหลดจริง
headObject คืน null ไม่ throw

"ยังไม่ได้อัปโหลด" เป็น outcome ปกติที่ caller ต้องตัดสินใจเอง (เช่น client ขอ presigned URL แล้วไม่เคย PUT จริง) — ไม่ใช่ error ของ storage-bc

04 — Flow A · Presigned Upload (client อัปตรงเข้า MinIO)

เพิ่ม/เปลี่ยนรูปหลังสร้างสินค้าไปแล้ว

ตรงตาม flow ที่ SRS วาดไว้ตั้งแต่แรก — backend ไม่เคยเห็นไบต์ไฟล์เลย เบาที่สุด เหมาะกับหน้า "จัดการรูปสินค้า" ของสินค้าที่มีอยู่แล้ว

1

ขอ presigned URL

POST /products/:product_id/images/presigned-url
{ "original_name": "photo.jpg", "mime_type": "image/jpeg" }

→ 200
{ "bucket": "erp-storage",
  "object_key": "inventory/products/<id>/photo-915e46ef.jpg",
  "upload_url": "https://minio.../erp-storage/...?X-Amz-Signature=..." }
2

Client PUT ไฟล์ตรงเข้า MinIO

ไม่ผ่าน inventory-bc เลย — curl -X PUT "$upload_url" --data-binary @photo.jpg

3

Confirm — ยืนยันว่าอัปโหลดสำเร็จจริง

POST /products/:product_id/images
{ "bucket": "erp-storage", "object_key": "inventory/products/<id>/photo-915e46ef.jpg",
  "original_name": "photo.jpg", "mime_type": "image/jpeg" }

Service เรียก HeadObject ยืนยันว่ามีจริง แล้วดึง size/etag จากผลลัพธ์นั้นตรง ๆ — ไม่เชื่อ ค่าที่ client ส่งมา

OWNERSHIP GUARD

object_key ที่ส่งมา confirm ต้องขึ้นต้นด้วย inventory/products/<product_id>/ ของ product นั้นเท่านั้น — กัน client ชี้ไปที่ object เดิมของสินค้าอื่นที่ตัวเองไม่เคยอัปโหลดจริง (ตรวจก่อนยิง HeadObject ด้วยซ้ำ)

Sequence Diagram · ครบทุก scenario (happy path + error)
sequenceDiagram
    autonumber
    actor FE as Frontend
    participant BE as inventory-bc
    participant ST as storage-bc
    participant S3 as MinIO

    FE->>BE: POST /products/:product_id/images/presigned-url
    BE->>BE: assertProductExists(product_id)
    alt product ไม่มีอยู่จริง
        BE-->>FE: 404 Not Found
    else product มีอยู่จริง
        BE->>ST: GeneratePresignedUpload(bucket, key, name, mime)
        ST-->>BE: bucket, path, upload_url (5 นาที)
        BE-->>FE: 200 OK (bucket, object_key, upload_url)

        FE->>S3: PUT upload_url (ไฟล์จริง)
        S3-->>FE: 200 OK

        FE->>BE: POST /products/:product_id/images (confirm)
        BE->>BE: assertObjectKeyOwnedByProduct(object_key)
        alt object_key ไม่ตรง prefix ของ product นี้
            BE-->>FE: 400 Bad Request (ownership guard)
        else object_key ถูกต้อง
            BE->>ST: HeadObject(bucket, key)
            alt ยังไม่เคยอัปโหลดจริง (client ขอ URL แล้วไม่ PUT)
                ST-->>BE: null
                BE-->>FE: 400 Bad Request (no uploaded object found)
            else อัปโหลดสำเร็จแล้วจริง
                ST-->>BE: size, content_type, etag
                opt is_primary = true ในคำขอ
                    BE->>BE: demote รูปหลักเดิม (ในทรานแซกชันเดียวกัน)
                end
                BE->>BE: INSERT product_images (size/extension/etag จาก HeadObject)
                BE-->>FE: 201 Created
            end
        end
    end
05 — Flow B · Multipart Create (สร้างสินค้าพร้อมรูปในจังหวะเดียว)

POST /products รับ multipart/form-data ด้วย

Endpoint เดิมยังรับ application/json ตามปกติ — multipart เป็นทางเลือกเสริมสำหรับฟอร์มสร้างสินค้าที่อยากแนบรูปในคลิกเดียว ไฟล์ในกรณีนี้ผ่าน backend จริง (ต่าง Flow A) จึงใช้ UploadWithMeta ธรรมดา ไม่ใช้ presigned

Request shape
POST /products
Content-Type: multipart/form-data

data:   '{"sku":"...","name_th":"...","name_en":"...","type":"single","item_group_id":"...","stock_uom_id":"..."}'
images: <file>, <file>, ...   // สูงสุด 5 ไฟล์ · jpeg/png/webp · ≤5MB/ไฟล์
ทำไมใช้ @Req() แทน @Body()

Fastify ไม่เติม request.body ให้ multipart request (นอกจากตั้ง attachFieldsToBody) — ถ้ายังใช้ @Body() dto: CreateProductDTO global ValidationPipe จะ validate undefined→{} แล้ว throw ก่อนโค้ด handler จะได้รันด้วยซ้ำ handler จึงต้องรับ @Req() เองแล้ว validate มือทั้งสอง content-type ผ่าน validateDto()/parseMultipartJsonBody() (libs/common/utils/multipart-json-body.util.ts) ซึ่งโยน ValidationException แบบเดียวกับ pipe อัตโนมัติทุกประการ

Product id ถูก mint ล่วงหน้า

อัปโหลดทุกไฟล์ก่อน (นอกทรานแซกชัน — network call ไม่ควรค้างอยู่ในทรานแซกชัน DB) โดยใช้ randomUUID() เป็น product id ล่วงหน้า แล้ว insert product + product_images ทั้งหมดในทรานแซกชันเดียว — รูปแรกในลิสต์ = is_primary: true โดยอัตโนมัติ ที่เหลือ sort_order ตามลำดับ

Sequence Diagram · JSON vs multipart บน endpoint เดียวกัน
sequenceDiagram
    autonumber
    actor FE as Frontend
    participant BE as inventory-bc
    participant ST as storage-bc
    participant S3 as MinIO

    FE->>BE: POST /products
    BE->>BE: request.isMultipart() ?

    alt Content-Type: application/json
        BE->>BE: validateDto(CreateProductDTO, request.body)
        alt validate ไม่ผ่าน
            BE-->>FE: 400 Validation Failed
        else validate ผ่าน
            BE->>BE: INSERT product (ไม่มีรูป)
            BE-->>FE: 201 Created (product)
        end
    else Content-Type: multipart/form-data
        BE->>BE: parseMultipartJsonBody() → dto + files[]
        alt error ระหว่างอ่าน multipart (เกิน 5 ไฟล์ / ข้อมูลเสีย ฯลฯ)
            BE-->>FE: 400 Bad Request (ดู §08 · ไม่ใช่ 500)
        else อ่านสำเร็จ
            alt mime type ไม่ใช่ jpeg/png/webp
                BE-->>FE: 400 Unsupported image type
            else mime type ผ่านครบทุกไฟล์
                BE->>BE: productId = randomUUID()
                loop แต่ละไฟล์ในลิสต์
                    BE->>ST: UploadWithMeta(bucket, key=".../"+productId, file)
                    ST->>S3: PutObject
                    S3-->>ST: 200 OK
                    ST-->>BE: path, size, extension
                end
                BE->>BE: INSERT product (id=productId) + product_images[] (ทรานแซกชันเดียว)
                BE-->>FE: 201 Created (product + images[], รูปแรก is_primary=true)
            end
        end
    end

07 — การแสดงรูป (Signed URL)

Resolve ทีละรูป ไม่ฝังไว้ในทุก response

GET .../images และ GET .../:id คืนแค่ bucket/object_key ดิบ — ไม่แนบ signed URL ให้อัตโนมัติ เพราะ URL หมดอายุใน 1 ชม. การ embed ไว้ในทุกแถวของตารางแบบ paginated จะเสียเปล่าสำหรับแถวที่ผู้ใช้ไม่ได้กดดู และเสีย request ไป storage-bc เพิ่มทุกครั้งที่โหลดหน้า ตรงตาม pattern เดิมของ PrintTemplatesService.fetchTemplateAsset ที่ resolve URL เฉพาะตอนจะใช้จริง 

GET /products/:product_id/images/:image_id/url

→ 200
{ "url": "https://minio.../erp-storage/...?X-Amz-Signature=...&X-Amz-Expires=3600" }

08 — ปัญหาที่เจอระหว่างทดสอบจริง (curl + ไฟล์จริง)

4 บั๊กที่ยืนยัน/แก้ระหว่างทดสอบ end-to-end

3 ข้อแรกเจอตอนทดสอบด้วยไฟล์จริง (jpeg + png ชื่อไทย) ผ่าน superadmin เต็ม flow บนเครื่อง dev — ข้อ 4 เจอทีหลัง ตอนย้าย STORAGE_S3_ENDPOINT จาก internal IP ไปเป็น public domain จริงบน ovh-dev (รายละเอียด deploy เต็มอยู่ที่ Deployment Guide §09)

1

ชื่อไฟล์ไทยเพี้ยน (mojibake) ตอน multipart create

storage.service.ts เดิมมี decodeOriginalName() ที่ reinterpret ชื่อไฟล์เป็น latin1→utf8 เสมอ — comment เดิมอ้างว่าเป็นการแก้ mojibake ของ Busboy/Multer แต่ @fastify/multipart (ตัวจริงที่ repo นี้ใช้) decode UTF-8 ถูกต้องอยู่แล้ว การรัน fix ซ้ำจึงไป corrupt ชื่อไฟล์ที่ถูกต้องอยู่แล้วแทน

Fix

ลบ decodeOriginalName() ออกจากทั้ง upload() และ uploadWithMeta() — ยืนยันด้วย regression test ที่ assert original_name ไม่เปลี่ยนแปลง

2

เกิน files limit → 500 แทนที่จะเป็น 400

ส่ง 6 ไฟล์ (เกิน limit ของ @fastify/multipart ที่ตั้งไว้ 5) — คาดว่าจะได้ FST_FILES_LIMIT ตามเอกสาร แต่ log จริงขึ้น ERR_STREAM_PREMATURE_CLOSE จาก Node stream แทน (stream ของ part ถูก destroy กลางทางตอน toBuffer()) — error นี้ไม่ใช่ HttpException เลยหลุดไปเจอ catch-all ของ AllExceptionsFilter กลายเป็น 500 เปล่า ๆ

Fix

parseMultipartJsonBody() ครอบ try/catch รอบการวน request.parts() ทั้งหมด แล้วแปลง error อะไรก็ตาม ที่เกิดระหว่างอ่าน multipart body ให้เป็น BadRequestException (400) — ไม่จำกัดเฉพาะ error ที่มี code ขึ้นต้นด้วย FST_

3

ลืม resolve viewable URL ตามแผนเดิม

แผนแรกระบุ "read path: GenerateSignedUrls แบบ batch" แต่ implementation จริงข้ามขั้นตอนนี้ไป — ทดสอบ end-to-end แล้วโหลดรูปไม่ได้เลยเพราะ response มีแค่ object_key ดิบ

Fix

เพิ่ม GET .../images/:id/url (§07) — ตรวจ byte-for-byte ด้วย SHA-256 checksum เทียบไฟล์ต้นฉบับกับไฟล์ที่ดาวน์โหลดผ่าน signed URL ที่ resolve ได้ ทั้ง 2 flow (presigned + multipart) ตรงกันทุกไบต์

4

Presigned URL กลายเป็น virtual-hosted style หลังเปลี่ยนเป็น public domain

ย้าย STORAGE_S3_ENDPOINT จาก http://172.x.x.x:9000 เป็น https://erp-bucket-api.iotechsoft.com (ผ่าน Kong ตาม Deployment Guide §06) แล้ว upload_url ที่คืนออกไปกลับกลายเป็น erp-storage.erp-bucket-api.iotechsoft.com/... (virtual-hosted) แทนที่จะเป็น erp-bucket-api.iotechsoft.com/erp-storage/... (path-style) ทั้งที่ STORAGE_S3_FORCE_PATH_STYLE=true ตั้งไว้แล้ว — virtual-hosted ต้องมี wildcard DNS ของตัวเอง ซึ่งไม่มี ทำให้อัปโหลดจากเบราว์เซอร์จริง resolve host ไม่ได้เลย

Fix

STORAGE_S3_FORCE_PATH_STYLE ไม่ได้อยู่ใน Joi validation schema (libs/config) จึงมาเป็นสตริง "true" ไม่ใช่ boolean แท้ — coerce ให้ชัดเจนใน storage.service.ts: forcePathStyle: configService.get(..., 'true') !== 'false' รายละเอียดการ debug เต็ม + วิธียืนยันดูที่ Deployment Guide §09 บั๊ก #6
