01 — ทำไมต้องมีคู่มือนี้

ปัญหาที่ Caddy แก้ให้

erp-api เป็น 8 BC แยกกัน แต่ละตัว bind คนละพอร์ต (3001–3008) ด้วย prefix ของตัวเอง (app.setGlobalPrefix('<prefix>/<version>') — ดู libs/common/src/utils/bootstrap.util.ts) — งานฝั่ง FE ที่ต้องยิงหลาย BC พร้อมกัน (เช่นหน้า System Settings ที่คุยกับ 4 BC) จะต้องจำ/สลับพอร์ตไปมา และ CORS ระหว่าง origin ต่างกันก็ยุ่งยากกว่าที่ควร

ไม่มี Caddyมี Caddy
จำ 8 พอร์ต: localhost:3001..3008โดเมนเดียว: http://erp-api.internal
FE ต้อง config base URL แยกทีละ BCทุก BC อยู่ใต้ path เดียวกัน — เปลี่ยนแค่ prefix
CORS ข้าม origin ทุกครั้งที่ข้าม BCทุก request มาจาก origin เดียว (โดเมน Caddy)
ต้องคอยเช็คว่า BC ไหน "รันอยู่พอร์ตอะไร" หลัง merge ใหม่รัน pnpm caddy:generate ครั้งเดียว รู้ทันที (มี warning ถ้า map ไม่ได้)
02 — Local Dev: ติดตั้งครั้งเดียว

Setup สำหรับเครื่อง BE/FE ทุกคน

1

ติดตั้ง Caddy

# macOS
brew install caddy

# หรือดูวิธีติดตั้งแพลตฟอร์มอื่นที่ caddyserver.com/docs/install
2

ผูกโดเมนกับเครื่องตัวเอง

เพิ่มบรรทัดนี้ใน /etc/hosts (macOS/Linux) หรือ C:\Windows\System32\drivers\etc\hosts (Windows): 

127.0.0.1 erp-api.internal
ทำไมเป็น .internal ไม่ใช่ .local

.local ชนกับ mDNS/Bonjour (macOS/Linux ใช้ resolve ชื่อเครื่องในวง LAN อยู่แล้ว) — เลือก .internal แทนเพื่อไม่ให้ปนกับ service discovery ของ OS เอง เปลี่ยนชื่อได้เองผ่าน LOCAL_DOMAIN= ใน .env ถ้าอยากใช้ชื่ออื่น (จำได้ไหมว่าต้องแก้ /etc/hosts ให้ตรงด้วยเสมอ)

3

Generate Caddyfile ครั้งแรก

pnpm caddy:generate

อ่าน .env รากโปรเจกต์แล้วเขียน infrastructure/caddy/Caddyfile (gitignored — ต่างคนต่างมีของตัวเองตาม .env ของเครื่องนั้น) พร้อม log ว่า map ได้กี่ route + warning ถ้ามี *_MODULE_HTTP_PORT ตัวไหน map prefix ไม่ได้

04 — Generator แม็พ prefix ยังไง

กฎการจับคู่ (mirrors bootstrap.util.ts)

scripts/generate-caddyfile.mjs หาทุกตัวแปรที่ลงท้ายด้วย _MODULE_HTTP_PORT ใน .env แล้วพยายามหา <KEY>_PREFIX_NAME คู่กัน — ถ้าไม่เจอ จะลองตัด _BC ท้าย key ออกก่อนแล้วลองอีกครั้ง (เพราะสอง env family นี้ไม่ได้ตั้งชื่อ suffix ตรงกันเป๊ะทุกตัว):

*_MODULE_HTTP_PORTลองหาตรงๆ ก่อนFallback (ตัด _BC)ผลลัพธ์
AUTH_MODULE_HTTP_PORTAUTH_PREFIX_NAME—match ตรงๆ
INVENTORY_BC_MODULE_HTTP_PORTINVENTORY_BC_PREFIX_NAME (ไม่มี)INVENTORY_PREFIX_NAMEmatch ผ่าน fallback

จับคู่ได้แล้วจึงเขียน reverse_proxy /<prefix>/* localhost:<port> — ไม่ strip path ก่อน proxy เพราะแอปแต่ละตัวตั้ง app.setGlobalPrefix('<prefix>/<version>') เองอยู่แล้ว route จริงจึงขึ้นต้นด้วย /<prefix>/... เป๊ะ ๆ — ตัด path ออกจะได้ 404 ทันที (หลักการเดียวกับ strip_path=false ที่ Kong ใช้ตาม deployment-guide.html §06)

Map ไม่ได้ = skip พร้อม warning เสมอ ไม่เดาให้

ถ้า *_MODULE_HTTP_PORT ตัวไหนหา *_PREFIX_NAME คู่กันไม่เจอเลย (แอปยังไม่ scaffold จริง) script จะ console.warn แล้วข้ามไปเฉยๆ — เช็ค log ตอนรัน pnpm caddy:generate เสมอหลังเพิ่ม BC ใหม่ ว่า route ที่คาดว่าจะมีขึ้นจริงหรือไม่

05 — บั๊กที่เจอมาแล้ว

Caddy ค้างหลาย process — หน้า Scalar/Swagger ขึ้นขาว

pnpm caddy:run เป็นคำสั่งที่ค้างอยู่ foreground ตลอด — ถ้าสั่งซ้ำโดยไม่ปิดตัวเก่าก่อน (เปิด terminal ใหม่, รันซ้ำหลังแก้ .env) จะได้ Caddy process ใหม่ซ้อนขึ้นมาอีกตัวโดยไม่มี error เตือน — macOS/Linux ยอมให้หลาย process bind พอร์ต 80 พร้อมกันได้ (SO_REUSEPORT)

อาการ — เจอจริงตอนเปิด http://.../inventory-bc/v1/api-docs

หน้า Scalar โหลด HTML ได้ (ขึ้นหน้าเปล่า) แต่ขึ้นขาวไม่มีอะไรเกิดขึ้น — เพราะหน้านั้น fetch สเปก (/<prefix>/v1/json-docs) เพิ่มอีกทีด้วย JavaScript ฝั่ง browser

เจอ PID มากกว่า 1 ตัว เวลาเริ่มต่างกัน
สาเหตุสัญญาณที่ยืนยันได้
มี Caddy process เก่าหลายตัวค้างที่ config คนละเวอร์ชัน (คนละเวลาที่ generate)lsof -iTCP:80 -sTCP:LISTEN
เคอร์เนลสุ่มว่าจะส่ง request ไปให้ process ไหนตอบ — request หน้า HTML กับ request fetch spec อาจตกคนละ process กันrequest บาง endpoint ได้ 200 OK แต่ Content-Length: 0 และไม่มี security header ที่ backend จริงต้องใส่ (เช่น x-content-type-options) — แปลว่า response นั้นไม่เคยไปถึง backend จริงเลย
แก้
# หาว่ามีกี่ process ค้างอยู่
lsof -iTCP:80 -sTCP:LISTEN -n -P

# ปิดให้เหลือตัวเดียว (หรือ pkill ทั้งหมดแล้วเริ่มใหม่)
pkill caddy
pnpm caddy:run

ก่อนสั่ง pnpm caddy:run ทุกครั้ง เช็คก่อนว่ามีตัวเก่าค้างอยู่ไหมด้วยคำสั่งข้างบน — วินิจฉัยแบบนี้เหมือนกับ head-of-line block ของ RabbitMQ ใน rabbitmq-reliability-guide.html §03: อาการหน้าตาเหมือนบั๊กสุ่มๆ แต่จริงๆ คือ process เก่าที่ไม่มีใครฆ่าทิ้ง

06 — Caddy vs Kong

เลือกยังไงตอน deploy ให้ลูกค้าจริง

Kong (deployment-guide.html §06) คือของที่ deploy จริงอยู่ตอนนี้ — มี Admin API + plugin ecosystem (ACME, rate-limit, auth plugin ฯลฯ) แต่ต้องแบก Postgres + Konga + Mongo เป็น stack แยกอีกก้อน (~4-5 GB disk ตาม deployment-guide.html §02, ดันให้ RAM แนะนำขยับจาก 8 GB เป็น 16 GB) — Caddy ทำ path routing + TLS แบบเดียวกันได้ โดยเป็นbinary เดียวไม่มี database

KongCaddy
DependencyKong + Postgres (ของ Kong เอง) + Konga UI + Mongo (ของ Konga)ไม่มี — binary เดียว ไม่มี database
Disk เพิ่ม~4-5 GB (Docker images ทั้ง stack)~40-50 MB (binary เดียว)
RAM เพิ่มเป็นเหตุผลหลักที่ต้องขยับจาก 8→16 GB (deployment-guide.html §02)หลักสิบ MB ระหว่างรัน
TLS จริง (domain สาธารณะ)ต้องพ่วง Cloudflare Tunnel/ACME plugin แยก ตั้งค่าเยอะกว่า (§07-08 ของ deployment-guide.html)ในตัวเลย — ขอ Let's Encrypt cert อัตโนมัติแค่ domain resolve มาถึงเครื่องและเปิดพอร์ต 80/443
Admin UI / pluginKonga UI, ปรับ rate-limit/auth/logging ผ่าน plugin ได้หลากหลายไม่มี Admin UI แบบ Kong — แก้ config ผ่านไฟล์/JSON API เท่านั้น
Config เปลี่ยนแบบ zero-downtimeผ่าน Admin API ได้caddy reload — graceful, ไม่ drop connection ที่ค้างอยู่
เลือก Caddy เมื่อ

ลูกค้าเครื่องเล็ก/งบจำกัด, ต้องการแค่ path routing + HTTPS จริงให้ 8 BC ไม่ได้ใช้ Kong plugin เฉพาะทางไหนเลย (rate-limit ระดับ gateway, custom auth plugin ฯลฯ) — ประหยัด RAM/disk ได้จริงตามตาราง และตั้ง TLS ง่ายกว่าเดิมด้วยซ้ำ (ไม่ต้องพึ่ง Cloudflare Tunnel ถ้าลูกค้ามี public IP + domain ของตัวเอง)

ยังเลือก Kong เมื่อ

ต้องใช้ Kong plugin จริง (rate-limit ต่อ consumer, custom auth ที่ gateway, request/response transform), มี Admin API ให้ทีม ops ปรับ route ได้โดยไม่ต้องแตะไฟล์, หรือระบบเดิมผูกกับ infra Kong อยู่แล้ว — การย้ายฐานลูกค้าเดิมจาก Kong ไป Caddy ไม่ใช่เป้าหมายของคู่มือนี้ นี่คือทางเลือกสำหรับดีลใหม่ที่เครื่องจำกัดเท่านั้น

07 — ตั้ง Caddy เป็น Production Gateway

โครงร่างสำหรับดีลที่ตัดสินใจใช้ Caddy แทน Kong

ยังไม่ได้ทดสอบ/ใช้จริงหน้างาน

ส่วนนี้เป็นโครงร่างจากหลักการเดียวกับ §02-04 (ที่ใช้จริงกับ local dev แล้ว) ต่อยอดไปเป็น production — ต้องทดสอบเต็มรูปแบบก่อนใช้กับลูกค้าจริง โดยเฉพาะ ACME ผ่าน domain สาธารณะจริง และพฤติกรรมตอน reload ระหว่างมี traffic

1

โครงสร้าง Caddyfile สำหรับ domain สาธารณะ

ต่างจาก local dev (§02-04) 2 จุด: ใช้ domain จริงแทน erp-api.internal และไม่ต้องมี auto_https off — ปล่อยให้ Caddy ขอ Let's Encrypt cert เอง: 

# infrastructure/caddy/Caddyfile.prod — ตัวอย่าง ไม่ใช่ไฟล์ generate อัตโนมัติ
erp-api.example.com {
	encode gzip

	# reverse_proxy /<prefix>/* localhost:<port> — เหมือน dev ทุกอย่าง
	# ต่างแค่ upstream host อาจเป็น container network แทน localhost ถ้าใช้ Docker
	reverse_proxy /auth/*         localhost:3001
	reverse_proxy /iam/*          localhost:3002
	reverse_proxy /inventory-bc/* localhost:3003
	reverse_proxy /supplier-bc/*  localhost:3004
	reverse_proxy /sales-bc/*     localhost:3005
	reverse_proxy /finance-bc/*   localhost:3006
	reverse_proxy /report-bc/*    localhost:3007
	reverse_proxy /storage/*      localhost:3008
}
แนวทาง — ยังใช้ generator ตัวเดิมได้ ไม่ต้องเขียนสองชุด

scripts/generate-caddyfile.mjs อ่าน LOCAL_DOMAIN จาก .env อยู่แล้ว — ตั้งค่านั้นเป็น domain จริงบนเครื่อง production (เช่น LOCAL_DOMAIN=erp-api.example.com) แล้วลบ/ปรับ block {'{'} auto_https off {'}'} ที่ script เขียนให้เสมอ ก่อนตั้งเป็น production จริง — ยังไม่คุ้มที่จะแยก flag --prod ในตัว generator จนกว่าจะมีดีลจริงที่ใช้ path นี้

2

รันเป็น systemd service (ไม่ใช่ foreground)

brew services/caddy run ตรงๆ ใช้ได้แค่ dev — production ต้องมี process manager คุมให้ restart อัตโนมัติเมื่อ crash/reboot: 

# ติดตั้งผ่าน apt/dnf package จะได้ systemd unit ให้เลย (แนะนำ)
# ดู https://caddyserver.com/docs/install#debian-ubuntu-raspbian
sudo systemctl enable --now caddy

# วางไฟล์ config ที่ /etc/caddy/Caddyfile แล้ว reload (ไม่ downtime)
sudo systemctl reload caddy
กันบั๊ก §05 ซ้ำในระดับ production

systemd คุมให้มี Caddy instance เดียวเสมอ (unit เดียว, systemctl status caddy เช็คได้ตรงๆ) — ห้ามรัน caddy run มือเพิ่มบน production เด็ดขาด เพราะจะกลับไปเจอปัญหาเดียวกับ §05 (หลาย process แย่งพอร์ต 80/443) ซึ่งบน production คือ downtime บางส่วนที่วินิจฉัยยากกว่าเดิม

เพิ่ม BC ใหม่ — อย่าลืม Caddy

เช็คทำไม
