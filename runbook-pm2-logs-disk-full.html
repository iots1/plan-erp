Disk เต็ม
จาก pm2 Logs ที่ไม่เคย rotate

/root/.pm2/logs/ โตขึ้นเรื่อย ๆ จนกิน disk หลาย GB โดยไม่มีใครสังเกต — เพราะ pm2 ไม่มี log rotation ให้โดย default และไฟล์ที่โตเร็วที่สุดมักเป็น error log ของ BC ที่ retry วนอยู่เงียบ ๆ

Severity: High (นำไปสู่ outage ทั้งเครื่อง) Est. fix time: 5–10 นาที
1 — อาการ (Symptom)

เจอได้ 2 จังหวะ — ก่อนเต็ม กับ ตอนเต็มแล้ว

เคสนี้ต่างจาก incident อื่นตรงที่มันไม่มีสัญญาณเตือนระหว่างทางเลย ระบบทำงานปกติทุกอย่าง จนถึงวินาทีที่ disk เต็มแล้วทุกอย่างพังพร้อมกัน — ส่วนใหญ่จึงถูกเจอตอนบังเอิญไปรัน df -h ด้วยเรื่องอื่น

จังหวะที่ 1 — ยังไม่เต็ม (เจอตอนตรวจสุขภาพเครื่อง)

$ du -sh /root/.pm2/logs
994M    /root/.pm2/logs

$ ls -lS /root/.pm2/logs | head -4
-rw-r--r-- 1 root root 774866121 Aug  1 18:10 iam-error-1.log     # ~740 MB ไฟล์เดียว
-rw-r--r-- 1 root root  77506602 Aug  1 18:10 auth-error-0.log
-rw-r--r-- 1 root root  29188034 Aug 16 14:14 iam-out-1.log

จังหวะที่ 2 — เต็มแล้ว (ทุกอย่างพังพร้อมกัน)

ENOSPC: no space left on device
Error: EROFS: read-only file system   # Postgres อาจ remount RO เพื่อกันข้อมูลเสีย
docker: failed to create endpoint ... no space left on device
pnpm install → ERR_PNPM_ENOSPC
สัญญาณที่แยกเคสนี้ออกจาก "disk เต็มเพราะ Docker"

Docker images/volume โตแบบก้าวกระโดดตอน deploy แต่ pm2 logs โตแบบเชิงเส้นตลอดเวลา แม้ไม่มีใครแตะเครื่องเลย — ถ้า df ขยับขึ้นทุกวันทั้งที่ไม่ได้ deploy อะไร ให้สงสัยเคสนี้ก่อน

2 — ผลกระทบ (Impact)

เต็มเมื่อไหร่ = ทั้งเครื่องหยุด

SCOPE

ทุกอย่างบนเครื่องเดียวกัน

8 BC + erp-web + Postgres/Redis/RabbitMQ/MinIO + Kong — เพราะทุกตัวใช้ filesystem เดียวกัน ไม่มีตัวไหนรอด

SEVERITY

High — แต่ป้องกันได้ 100%

ต่างจาก incident อื่นตรงที่รู้ล่วงหน้าเสมอ และแก้ถาวรได้ด้วยคำสั่งเดียว — ถ้าเกิดขึ้นแปลว่าพลาดขั้นตอนส่งมอบ

DATA SAFETY

เสี่ยงถ้าปล่อยจนเต็มจริง

Postgres เขียน WAL ไม่ได้จะหยุดรับ write ทันที (กันข้อมูลเสีย) — ไม่ถึงกับ corrupt แต่ recovery ช้ากว่าการล้าง log มาก

3 — วินิจฉัย (Diagnosis)

ยืนยันว่าใช่ pm2 logs ก่อนลบอะไร

1

ดูว่า disk เหลือเท่าไหร่จริง

df -h /
2

หาว่าใครกิน — เทียบ 3 ผู้ต้องสงสัยหลัก

du -sh /root/.pm2/logs /var/log /var/lib/docker 2>/dev/null | sort -h

ถ้า /root/.pm2/logs ขึ้นมาเป็นอันดับต้น ๆ (หลักหลายร้อย MB ถึง GB) แปลว่าใช่เคสนี้ — ถ้าเป็น /var/lib/docker ให้ไปทาง docker system prune แทน ไม่ใช่ runbook นี้

3

ดูว่าไฟล์ไหนตัวการ และเป็นของ process ที่ยังรันอยู่ไหม

ls -lS /root/.pm2/logs | head -10   # เรียงตามขนาด
pm2 list                            # process ที่ยังรันอยู่จริง
ให้สังเกต

มักเจอ log ของโปรเจกต์เก่าที่เลิกรันไปแล้วปนอยู่ด้วย (ชื่อ process ที่ไม่มีใน pm2 list แล้ว) — พวกนี้ลบได้อิสระเพราะไม่มี process ไหนถือ file descriptor อยู่ ต่างจาก log ของ process ที่ยังรัน ซึ่งต้องใช้วิธีใน §5

4 — สาเหตุ (Root Cause)

pm2 ไม่มี log rotation ให้ และไม่เคยเตือน

pm2 เปิดไฟล์ <name>-out-<id>.log กับ <name>-error-<id>.log ค้างไว้แล้ว append ไปเรื่อย ๆ ไม่มีเพดาน ไม่มี rotation — ต้องติดตั้ง module pm2-logrotate เองเท่านั้น ซึ่งไม่ได้อยู่ในขั้นตอนติดตั้งมาตรฐานของใคร

ทำไมไฟล์เดียวถึงโตถึง 740 MB

ตัวเร่งเกือบทุกครั้งคือ retry loop — เช่น BC ต่อ DB/RabbitMQ ไม่ได้แล้ว NestJS retry ทุกไม่กี่วินาที แต่ละรอบพ่น stack trace เต็ม ๆ ลง error log ระบบยัง "ทำงานอยู่" ในสายตาคนดู (pm2 list ขึ้น online) แต่เขียน log หลัก MB ต่อนาที ยิ่งไม่มีใครดู log ยิ่งโตนาน

5 — การแก้ไข (Fix)

ล้างของเก่า แล้วปิดสาเหตุถาวร

อ่านก่อนพิมพ์ rm

rm ไฟล์ log ที่ pm2 ยังเปิดอยู่ จะไม่คืนพื้นที่ — Linux ปลด directory entry ให้ก็จริง แต่ inode ยังถูกถือไว้ด้วย file descriptor ของ process พื้นที่จะคืนก็ต่อเมื่อ process ปิด fd (คือตอน restart) ผลคือ df ไม่ขยับเลยทั้งที่ไฟล์หายจาก ls แล้ว — สับสนหนักตอนกำลังกู้ระบบ ให้ใช้ pm2 flush หรือ truncate แทน

1

ล้าง log ของ process ที่ยังรันอยู่ — ใช้ pm2 flush

pm2 flush              # ล้างทุก process (ตัดไฟล์เป็น 0 ไม่ใช่ลบ — คืนพื้นที่ทันที)
pm2 flush erp-web      # หรือระบุตัวเดียว

ปลอดภัยกับ process ที่รันอยู่ ไม่ต้อง restart อะไรเลย — แต่ลบ log ทิ้งจริง ถ้ายังต้องสืบสาเหตุ retry loop ให้ copy ส่วนที่ต้องการออกไปก่อน

2

ลบ log ของโปรเจกต์เก่าที่ไม่มี process แล้ว

# ดูก่อนว่าจะลบอะไรบ้าง — อย่าเพิ่งลบ
ls -lS /root/.pm2/logs | head -20
pm2 list

# ลบเฉพาะไฟล์ของ process ที่ไม่มีอยู่ใน pm2 list แล้ว (ตัวอย่าง)
rm /root/.pm2/logs/<ชื่อโปรเจกต์เก่า>-*.log

เคสนี้ rm ใช้ได้ปลอดภัย เพราะไม่มี process ถือ fd อยู่แล้ว

3

ติดตั้ง rotation เพื่อไม่ให้กลับมาอีก

pm2 install pm2-logrotate

pm2 set pm2-logrotate:max_size 10M
pm2 set pm2-logrotate:retain 14
pm2 set pm2-logrotate:compress true
pm2 set pm2-logrotate:rotateInterval '0 0 * * *'
ผลลัพธ์ที่ต้องได้

pm2 list จะมีบรรทัด pm2-logrotate อยู่ในตาราง Module แยกจาก process ปกติ และ pm2 conf pm2-logrotate แสดงค่าตามที่ตั้งไป

4

ถ้า retry loop ยังอยู่ ให้ตามแก้ต้นเหตุด้วย

rotation กันไม่ให้ disk เต็ม แต่ไม่ได้แก้ว่าทำไมถึงพ่น error ตลอดเวลา — ดูว่า BC ไหนเป็นตัวเขียน แล้วไล่ต่อจากตรงนั้น 

pm2 logs <name> --err --lines 50
6 — ยืนยัน + ป้องกัน (Verify / Prevent)

เช็คว่าคืนพื้นที่จริง แล้วปิดจบ

1

พื้นที่คืนมาจริงหรือแค่ไฟล์หายจาก ls

df -h /
du -sh /root/.pm2/logs
ผลลัพธ์ที่ต้องได้

ตัวเลข Avail ใน df ต้องเพิ่มขึ้นจริง — ถ้า du ลดแต่ df ไม่ขยับ แปลว่าโดนกับดัก rm-ไฟล์ที่ยังเปิดอยู่ ให้เช็คด้วย lsof +L1 | head แล้ว restart process ตัวนั้นเพื่อปล่อย fd

2

ยืนยันว่า rotation ทำงานและทุก process ยังปกติ

pm2 conf pm2-logrotate    # ค่าตรงกับที่ตั้งไว้
pm2 list                  # ทุก process ยัง online + มี pm2-logrotate ใน Module

ป้องกันไม่ให้เกิดซ้ำ

มาตรการทำเมื่อไหร่อ้างอิง
ติดตั้ง pm2-logrotate ตั้งแต่วันแรก ตอนติดตั้งเครื่องใหม่ ก่อนส่งมอบ Deployment §10
ใส่ "log rotation ทำงาน" ในเช็คลิสต์ส่งมอบ ทุกครั้งที่ส่งมอบเครื่องลูกค้า Deployment §11
ตั้ง disk usage alert ที่ ~80% ตอนตั้ง observability stack Observability Guide
ไล่ error log ที่โตผิดปกติเป็นงานประจำ ตรวจสุขภาพเครื่องรายเดือน ls -lS /root/.pm2/logs | head
log อีกกองที่ไม่ได้อยู่ในนี้

HTTP access log ของ erp-api เขียนผ่าน pino-roll ไปที่ /var/log/erp-api/*/http/ ซึ่งคนละกองกับ pm2 logs และ rotate ด้วยกลไกของตัวเอง — pm2 flush ไม่แตะกองนั้น และ pm2-logrotate ก็ไม่ได้ดูแลให้ ดูตารางเทียบใน Deployment §10
