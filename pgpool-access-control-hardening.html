Security Hardening Guide

Pgpool Access Control
pool_hba.conf

pool_hba.conf คือประตูบานแรกและบานเดียวที่เห็น IP จริงของ client — การรัด pg_hba.conf ให้แน่นแค่ไหนก็ไม่ช่วย เพราะ PostgreSQL เห็นแค่ IP ของ pgpool เอกสารนี้คือแนวทางตั้งค่าให้ถูกตั้งแต่แรก

First-match-wins · No fall-through Least Privilege Role Defense in Depth
เอกสารนี้ไม่มี IP จริงเลย — ตั้งใจ

ทุกที่อยู่ในหน้านี้เป็น placeholder แบบ <ชื่อ> หรือช่วง 192.0.2.0/24 / 198.51.100.0/24 ซึ่งเป็นช่วงสำหรับเอกสารตาม RFC 5737 (ไม่มีอยู่จริงบนอินเทอร์เน็ต) — คัดลอกไปใช้ต้องแทนค่าจริงเองเสมอ ห้าม commit ค่าจริงกลับเข้าเอกสารนี้ เพราะ repo นี้เป็น public repo

01 — สามชั้นที่มักสับสน

PostgreSQL ไม่เคยเห็น IP ของ client เลย

นี่คือความเข้าใจผิดที่ทำให้คนคิดว่าระบบปลอดภัยทั้งที่ไม่ — เมื่อมี pgpool คั่นกลาง connection ที่ไปถึง PostgreSQL มี source IP เป็นของ pgpool node เสมอ ไม่ใช่ของ client ตัวจริง เพราะฉะนั้น pg_hba.conf จะรัดยังไงก็กรอง client ภายนอกไม่ได้

psql -h <pgpool-host> -p <port> -U <admin-user> -tAc "show pool_status;" \
  | grep enable_pool_hba
02 — กฎการอ่านไฟล์

สี่กฎที่ต้องรู้ก่อนแตะไฟล์นี้

1

First match wins · ไม่มี fall-through · ไม่แมตช์ = ปฏิเสธ

แถวแรกที่ตรงทั้ง type + address + database + user จะถูกใช้ทันที และถ้า auth ด้วยแถวนั้นแล้วไม่ผ่าน จะไม่ไปลองแถวถัดไป ส่วนถ้าไม่มีแถวไหนตรงเลย pgpool ปฏิเสธเอง

ผลที่ตามมาที่สำคัญที่สุดของทั้งเอกสารนี้

วิธีปิดช่องโหว่คือ ลบแถวที่กว้างเกินไปทิ้ง ไม่ใช่ไปเพิ่มแถว deny ต่อท้าย — เพราะ default คือ deny อยู่แล้ว การเติม deny ท้ายไฟล์ไม่มีผลอะไรเลยถ้าแถวกว้างๆ ยังอยู่ข้างบน

2

ลำดับสำคัญกว่าเนื้อหา — reject ต้องอยู่ก่อน

reject เป็น method ที่ pgpool รองรับ (พร้อมกับ trust, md5, scram-sha-256, pam) ใช้ปิดเฉพาะ user บางตัวจากบางที่ แต่ต้องวางให้ถูกลำดับ 

# ✅ ถูก — reject โดนตรวจก่อน
host  all  <superuser>  0.0.0.0/0        reject
host  all  all          0.0.0.0/0        scram-sha-256

# ❌ ผิด — แถวบนแมตช์ก่อน reject ไม่มีวันถูกอ่าน
host  all  all          0.0.0.0/0        scram-sha-256
host  all  <superuser>  0.0.0.0/0        reject
3

ไม่มี group — ต่างจาก pg_hba.conf ตรงนี้

pgpool ไม่รู้จัก role membership ใน PostgreSQL จึงไม่รองรับ +groupname ในช่อง user และไม่รองรับ samegroup ในช่อง database ต้องระบุชื่อเป็นรายตัวหรือคั่นด้วย comma ถ้ามีหลาย role ให้ใช้ไฟล์แยกด้วย @ 

# ระบุตรงๆ หรือคั่น comma
host  <db-name>  <app-role-a>,<app-role-b>  <cidr>  scram-sha-256

# หรือดึงรายชื่อจากไฟล์แยก (ดูแลง่ายกว่าเมื่อมีหลาย service)
host  <db-name>  @app-roles.txt             <cidr>  scram-sha-256
4

อย่าเชื่อว่า reload พอ — ทดสอบด้วย connection จริงเสมอ

ไฟล์ pool_hba.conf.sample ที่มากับ package ระบุว่า "This file is read on pgpool startup. If you edit the file on a running system, you have to restart the pgpool for the changes to take effect." — ต่างจาก pgpool.conf หลายพารามิเตอร์ที่ reload พอ

ทำไมข้อนี้อันตราย

ถ้าคุณแก้ไฟล์ให้แน่นขึ้นแล้ว reload แล้วเชื่อว่าจบ — อาจกำลังเปิดช่องอยู่โดยไม่รู้ตัว พิสูจน์ด้วยการต่อจริงเสมอ (ดู §07) และถ้าจำเป็นต้อง restart ให้รู้ไว้ว่า connection ที่ค้างอยู่จะหลุดทั้งหมด ต้องวางแผนจังหวะ — restart node ที่ถือ VIP เป็นตัวสุดท้ายเสมอ

03 — Anti-Pattern

เจ็ดแบบที่เจอบ่อย เรียงตามความอันตราย

#รูปแบบทำไมอันตรายแทนด้วย
1 host all all 0.0.0.0/0 scram-sha-256 เปิดให้ทุก IP บนโลกลองรหัสได้ไม่จำกัดครั้ง — scram กันการดักฟังได้ แต่ไม่ได้กันการเดา ยิ่งถ้า user ที่โดนเดาเป็น superuser ก็คือเดิมพันทั้งคลัสเตอร์ ลบทิ้ง แล้วระบุ CIDR ที่เจาะจง — หรือถ้าจำเป็นต้องเปิดกว้างจริงๆ ต้องมี reject ปิด superuser ไว้ก่อน (§04)
2 host all all 127.0.0.1/32 trust
local all all trust		 ใครก็ตามที่มี shell บน pgpool node เป็น superuser ของทุก DB ได้ทันทีโดยไม่ต้องรู้รหัส — รวมถึง service account ที่ถูกยึด, deploy user, หรือ process ที่หลุดมา ไม่ต้องผ่านอะไรเลยสักชั้น scram-sha-256 — cost แทบไม่มี แต่ปิดช่องยกระดับสิทธิ์ที่ใหญ่ที่สุดในเครื่อง
3 application ต่อด้วย role superuser credential ตัวเดียวรั่ว = อ่าน/เขียน/ลบได้ทุก DB, ปิด audit, สร้าง extension, อ่านไฟล์บน host ได้ — และ pool_hba แยกไม่ออกว่า connection ไหนคือ "แอป" ไหนคือ "แอดมิน" เพราะเป็น user เดียวกัน role แยกต่อ service ตาม least privilege (§05) — ทำให้ reject superuser จากภายนอกเป็นไปได้
4 whitelist IP บ้าน / dynamic แบบ /32 พังเงียบวันที่ ISP เปลี่ยน IP ให้ — และคนแก้มักจะ "ขยายให้กว้างขึ้น" เป็น prefix ของ ISP ซึ่งเท่ากับเปิดให้ลูกค้าหลายหมื่นรายของ ISB นั้น ไม่ต่างจากข้อ 1 ให้ตัวตนมาจาก credential/tunnel ไม่ใช่จาก IP — VPN/tunnel ทำให้ client โผล่มาจาก CIDR ภายในที่นิ่ง (§06)
5 คิดว่า pg_hba.conf กรอง client ให้แล้ว PostgreSQL เห็น source IP เป็นของ pgpool ทุก connection — กฎ CIDR ใน pg_hba จึงไม่มีผลกับ client ภายนอกเลยสักข้อ (§01) ย้ายกฎ CIDR ของ client ทั้งหมดมาไว้ที่ pool_hba.conf ส่วน pg_hba ให้แคบลงเหลือแค่ pgpool node + replication
6 แก้ไฟล์ด้วยมือ ทั้งที่มี installer generate ให้ script ที่ generate config มักเขียนทับทั้งไฟล์ — การรัดความปลอดภัยที่ทำด้วยมือจะหายเงียบในรอบ deploy ถัดไป และไม่มีใครรู้จนกว่าจะโดน แก้ที่ template/flag ของ generator เสมอ แล้ว re-run — ถ้าแก้มือเป็นการชั่วคราว ต้องมี ticket ตามปิด
7 ใช้ md5 ทั้งที่ backend รองรับ scram-sha-256 md5 ของ PostgreSQL อ่อนต่อการ crack offline ถ้า hash รั่ว และไม่มี mutual proof แบบ SCRAM scram-sha-256 ทุกแถว — ให้ตรงกับ password_encryption ของ backend
ข้อ 1 กับ 3 คูณกันแล้วอันตรายกว่าที่คิด

แต่ละข้อเดี่ยวๆ ยังพอรับได้ — เปิดกว้างแต่ user มีสิทธิ์น้อย หรือ user แรงแต่เข้าถึงได้จากวงในเท่านั้น แต่พอมีทั้งคู่พร้อมกันคือ บัญชี superuser ของ production เปิดให้ทั้งอินเทอร์เน็ตลองรหัสได้ไม่จำกัดครั้ง และเนื่องจาก pgpool ไม่มี rate limit หรือ lockout ในตัว การเดาจึงทำได้เร็วเท่าที่เครือข่ายจะไหว โดยไม่มีอะไรหยุดและไม่มี alert ใดๆ นอกจากบรรทัด log ที่ดูเหมือน noise

04 — Config เป้าหมาย

สองแบบ ขึ้นกับว่า client อยู่ในวงหรือนอกวง

แบบ ก — client ทุกตัวเข้าผ่าน VPN/tunnel (แนะนำ)

เมื่อ client ภายนอกเข้ามาทาง tunnel มันจะโผล่ที่ pgpool ด้วย IP ภายใน ทำให้ ไม่ต้องมีแถวสำหรับอินเทอร์เน็ตเลยแม้แต่แถวเดียว — นี่คือรูปที่ปลอดภัยที่สุดและดูแลง่ายที่สุด 

# TYPE  DATABASE  USER  ADDRESS              METHOD
local   all       all                        scram-sha-256
host    all       all   127.0.0.1/32         scram-sha-256
host    all       all   <internal-cidr>      scram-sha-256

# ไม่มีแถว 0.0.0.0/0 — ไม่ต้องเขียน deny เพราะ "ไม่แมตช์ = ปฏิเสธ" อยู่แล้ว
แบบ ข — จำเป็นต้องเปิดให้ต่อจากภายนอกจริงๆ

ถ้าเลี่ยงไม่ได้ ให้ยอมรับว่ากันด้วย IP ไม่ได้ (โดยเฉพาะเมื่อฝั่ง client เป็น dynamic IP) แล้วย้ายการป้องกันไปที่ "ใครล็อกอินได้" แทน — กุญแจคือแถว reject ที่ต้องอยู่ก่อน 

# TYPE  DATABASE      USER            ADDRESS            METHOD
local   all           all                                scram-sha-256
host    all           all             127.0.0.1/32       scram-sha-256
host    all           all             <internal-cidr>    scram-sha-256

# --- ปิด superuser จากนอกวงเด็ดขาด ต้องอยู่ "ก่อน" แถวล่าง ---
host    all           <superuser>     0.0.0.0/0          reject
host    all           <repl-admin>    0.0.0.0/0          reject

# --- แอปจากภายนอก: จำกัดทั้ง role และ database ---
host    <app-db>      <app-role>      0.0.0.0/0          scram-sha-256
สังเกตว่าแถวสุดท้ายแคบลงสองมิติพร้อมกัน

ไม่ใช่แค่ all ในช่อง user แต่ช่อง database ก็ระบุเจาะจงด้วย — ถ้าแอปแตะแค่ DB เดียว ก็ไม่มีเหตุผลที่ connection จากอินเทอร์เน็ตจะเปิด DB อื่นได้ ยิ่งแคบทั้งสองช่อง ความเสียหายตอน credential รั่วยิ่งจำกัด

ถ้าจะระบุ CIDR ภายนอกได้จริง

ใช้ได้เฉพาะเมื่อฝั่งนั้นมี static IP จริงเท่านั้น (เช่นสำนักงานที่ซื้อ fixed IP ไว้) — แทนแถวสุดท้ายด้วยแบบนี้ และคอมเมนต์กำกับไว้เสมอว่าเป็นของใคร จะได้รู้ตอนเลิกใช้ว่าลบได้ 

# สำนักงาน <ชื่อไซต์> — static IP, ทบทวนทุกไตรมาส
host    <app-db>   <app-role>   192.0.2.10/32       scram-sha-256
# วง VPN ของ <ผู้ให้บริการ>
host    <app-db>   <app-role>   198.51.100.0/24     scram-sha-256
05 — แยก Role · pool_passwd

งานที่ pool_hba ทำแทนไม่ได้

ทุกอย่างใน §04 จะทำไม่ได้เลยถ้าแอปยังต่อด้วย superuser — เพราะแถว reject จะตัดแอปตัวเองไปด้วย ลำดับจึงต้องเป็น สร้าง role ก่อน แล้วค่อยรัด pool_hba ไม่ใช่กลับกัน

1

สร้าง role ต่อ service ตาม least privilege

CREATE ROLE <app-role> LOGIN PASSWORD '<password>';
GRANT CONNECT ON DATABASE <app-db> TO <app-role>;
GRANT USAGE ON SCHEMA <schema> TO <app-role>;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA <schema> TO <app-role>;

-- ตารางที่สร้างในอนาคตจะได้สิทธิ์เองโดยไม่ต้อง grant ซ้ำ
ALTER DEFAULT PRIVILEGES IN SCHEMA <schema>
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO <app-role>;

แยก role สำหรับงานที่อ่านอย่างเดียว (report, BI, exporter) ให้เหลือแค่ SELECT — เป็นการแบ่งที่ให้ผลมากที่สุดต่อแรงที่ลงไป

2

เพิ่ม role เข้า pool_passwd — ขั้นที่ลืมกันมากที่สุด

pgpool ต้องมี entry ของ role นั้นใน pool_passwd เพื่อ auth ต่อ backend แทน client — สร้าง role ใน PostgreSQL อย่างเดียวไม่พอ และต้องทำทุก pgpool node 

sudo -u <pgpool-user> PGPOOLKEYFILE=<keyfile> \
  pg_enc -m -f <pgpool.conf> -u <app-role> -p
อาการเวลาลืม — หลอกให้ไล่ผิดทางได้ทั้งวัน

ERROR: authentication failed ตามด้วย DETAIL: username "<role>" or password does not exist in backend — ข้อความนี้อ่านเหมือนรหัสผิด ทั้งที่รหัสถูกทุกตัวอักษร มันแค่แปลว่า pgpool หา entry ใน pool_passwd ไม่เจอ วิธีแยกให้ขาด: ลองต่อตรงเข้า PostgreSQL ข้าม pgpool ด้วยรหัสเดียวกัน ถ้าตรงนั้นผ่าน = รหัสถูก ปัญหาอยู่ที่ pool_passwd ไม่ใช่ credential

3

เปลี่ยนฝั่งแอป แล้วค่อยปิด superuser

เปลี่ยน connection string ของทุก service ให้ใช้ role ใหม่ → ยืนยันว่าทุกตัวทำงานได้จริง → แล้วค่อยเพิ่มแถว reject ของ superuser ถ้าสลับลำดับกันคือระบบดับทันที

ตรวจว่าไม่มีใครหลงเหลือใช้ superuser อยู่
SELECT usename, client_addr, count(*)
FROM pg_stat_activity
WHERE usename IN (SELECT rolname FROM pg_roles WHERE rolsuper)
GROUP BY 1,2 ORDER BY 3 DESC;

ควรเหลือแค่ connection จากงานดูแลระบบ (replication, repmgr, admin session) — ถ้ายังเห็นจาก IP ของ pgpool node จำนวนมาก แปลว่ายังมีแอปที่ยังไม่ได้เปลี่ยน

06 — ชั้นนอก pool_hba

pool_hba ปิดได้แค่ประตู ไม่ได้ปิดถนน

ชั้นนอกสุด

อย่าเผยแพร่พอร์ต DB ออกอินเทอร์เน็ต

ถ้าไม่มี NAT/port-forward ชี้เข้า pooler ตั้งแต่แรก anti-pattern ข้อ 1 ก็ไม่มีความหมาย — การเอา rule นั้นออกคือการแก้ที่ให้ผลมากที่สุดต่อแรงที่ใช้ มากกว่าการไปไล่รัด pool_hba

FIREWALL

พอร์ตบริหารต้องไม่เปิดทั้ง LAN

พอร์ต PCP และ watchdog ควรจำกัดเฉพาะ pgpool node ด้วยกันเอง — เครื่องใดในวงโดนยึด ไม่ควรเดินเข้าช่องทางบริหารคลัสเตอร์ได้ตรงๆ host firewall ที่ปิดอยู่ = ไม่มีชั้นนี้เลย

TUNNEL

ให้ตัวตนมาจาก key ไม่ใช่จาก IP

VPN (WireGuard/mesh VPN) หรือ tunnel ที่ auth ด้วย key/service token ทำให้ client โผล่มาจาก CIDR ภายในที่นิ่ง — แก้ปัญหา dynamic IP ได้จริง และได้ audit log ว่าใครต่อเมื่อไหร่แถมมาด้วย

DETECTION

ตั้ง alert ที่นับ auth failure

pgpool ไม่มี lockout หรือ rate limit ในตัว การเดารหัสจึงไม่มีอะไรหยุด — ต้องชดเชยด้วย alert เมื่อ auth failure เกิน threshold ต่อนาที ไม่งั้นการเดานับแสนครั้งจะดูเหมือน log noise ธรรมดา

rate limit ระดับ network ถ้าจำเป็นต้องเปิดพอร์ตออกนอกจริงๆ

ไม่ใช่การป้องกันที่แข็งแรง แต่ทำให้การเดาแบบหมื่นครั้งต่อชั่วโมงเป็นไปไม่ได้ และทำให้ alert มีเวลาทำงาน — ปรับตัวเลขตามจำนวน connection จริงของแอป (แอปที่มี pool ปกติเปิด connection ใหม่ไม่บ่อย) 

# จำกัดจำนวน connection ใหม่ต่อ source IP (ตัวอย่าง — ปรับค่าตามงานจริง)
iptables -A INPUT -p tcp --dport <pooler-port> -m conntrack --ctstate NEW \
  -m recent --set --name PGPOOL
iptables -A INPUT -p tcp --dport <pooler-port> -m conntrack --ctstate NEW \
  -m recent --update --seconds 60 --hitcount 20 --name PGPOOL -j DROP
07 — Checklist ตรวจสอบ

พิสูจน์ทุกข้อด้วยการต่อจริง อย่าอ่านแค่ไฟล์

ทุกข้อในตารางนี้ตรวจได้จากภายนอกโดยไม่ต้องแก้อะไร — ควรรันหลังเปลี่ยน config ทุกครั้ง และตั้งเป็นงานประจำทุกไตรมาส เพราะ config มีโอกาสถูก generator เขียนทับกลับ (anti-pattern ข้อ 6)

✓ตรวจอะไรผ่าน = เห็นอะไร
☐enable_pool_hba เปิดอยู่จริงในค่าที่โหลด (ไม่ใช่แค่ในไฟล์)on จาก show pool_status
☐ต่อจากนอกวงด้วย superuserถูกปฏิเสธ — ถ้าต่อติดคือยังไม่ปลอดภัย
☐ต่อจากนอกวงด้วย app role เข้า DB ที่ไม่ใช่ของแอปถูกปฏิเสธ (พิสูจน์ว่าช่อง database แคบจริง)
☐ต่อจากนอกวงด้วย app role เข้า DB ของตัวเองสำเร็จ (พิสูจน์ว่าไม่ได้รัดจนแอปพัง)
☐ไม่มีแถว trust เหลืออยู่ในไฟล์grep -c trust = 0
☐ไม่มี login role ที่เป็น superuser ถูกใช้โดยแอปquery ใน §05 ข้อ 3 เหลือแต่งานดูแลระบบ
☐พอร์ตที่เปิดออกอินเทอร์เน็ตจริง (ทดสอบจากเครื่องนอกวง)มีเฉพาะพอร์ตที่ตั้งใจ — พอร์ตบริหารต้องปิด
☐จำนวน auth failure ต่อชั่วโมงในช่วงปกติใกล้ 0 — ถ้าไม่ใช่ แปลว่ามีคนหรือแอปกำลังเดารหัสอยู่
คำสั่งทดสอบ — รันจากเครื่องที่อยู่นอกวงจริงเท่านั้น
# 1) superuser จากนอกวง — ต้องถูกปฏิเสธ
PGPASSWORD=<pw> psql -h <public-endpoint> -p <port> \
  -U <superuser> -d <app-db> -tAc 'select 1'
# คาดหวัง: authentication failed / ต่อไม่ได้

# 2) app role เข้า DB ที่ไม่ใช่ของตัวเอง — ต้องถูกปฏิเสธ
PGPASSWORD=<pw> psql -h <public-endpoint> -p <port> \
  -U <app-role> -d <other-db> -tAc 'select 1'

# 3) app role เข้า DB ของตัวเอง — ต้องสำเร็จ และบอกได้ว่าไปโผล่ backend ตัวไหน
PGPASSWORD=<pw> psql -h <public-endpoint> -p <port> \
  -U <app-role> -d <app-db> -tAc 'select current_user, inet_server_addr()'
# 4) พอร์ตอะไรเปิดออกนอกบ้าง — รันจากเครื่องนอกวง
for p in <port-list>; do
  printf '%s: ' "$p"
  timeout 4 bash -c "</dev/tcp/<public-endpoint>/$p" 2>/dev/null \
    && echo OPEN || echo closed
done

# 5) นับ auth failure ย้อนหลัง 1 ชั่วโมง — รันบน pgpool node
journalctl -u <pgpool-unit> --since '-1h' --no-pager \
  | grep -c 'authentication failed'
ข้อ 8 คือข้อที่คุ้มที่สุดและคนมองข้ามบ่อยที่สุด

ตัวเลข auth failure ต่อชั่วโมงควรใกล้ศูนย์ในระบบที่สุขภาพดี เพราะแอปที่ config ถูก จะ auth ผ่านทุกครั้ง ตัวเลขที่สูงและคงที่มักไม่ใช่การโจมตี แต่คือ service ของเราเองที่ถือ credential เก่า แล้ว retry วนอยู่ — ซึ่งแปลว่ามี config drift ที่ยังไม่มีใครเห็น ส่วนตัวเลขที่สูงและแกว่งค่อยน่าสงสัยว่ามาจากภายนอก ไม่ว่ากรณีไหน ถ้าไม่เคยวัดก็จะไม่มีวันรู้ เพราะ log พวกนี้ดูเหมือน noise ทั้งหมด
