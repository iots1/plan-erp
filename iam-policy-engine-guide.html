01 — ที่มา

คำถามเดียวที่เปิดแผลทั้งหมด

จุดเริ่มไม่ใช่ error หรือ alert แต่เป็นคำถามเชิงออกแบบว่า policies → policy_statements → statement_actions → permissions แบบนี้ permission หนึ่งตัวควรซ้ำได้กี่แถวในหนึ่ง policy — คำตอบที่ถูกคือ แถวเดียวต่อหนึ่ง effect แต่ของจริงมีถึง 7 แถว

อาการที่มองเห็น

ไม่มีเลย

ไม่มี error, ไม่มี log, สิทธิ์ยังทำงานถูก — เพราะ evaluator รวม allow ทั้งหมดเป็น union ข้อมูลซ้ำจึงไม่เปลี่ยนผลลัพธ์

อาการที่วัดได้

598 / 268

statement_actions มี 598 แถว แต่คู่ (policy, permission, effect) ที่ไม่ซ้ำมีเพียง 268

ความเสี่ยงจริง

รอวันระเบิด

statement_targets ยังไม่ถูก enforce — วันที่เปิดใช้ per-service scoping ข้อมูลเพี้ยนชุดนี้จะกลายเป็นช่องสิทธิ์ทันที

บทเรียนหลัก

บั๊กที่อันตรายที่สุดในเอกสารนี้ไม่มีอาการให้สังเกตเลย — มันถูกพบเพราะมีคนตั้งคำถามว่าโมเดลข้อมูลควรเป็นอย่างไร แล้วเอาคำตอบนั้นไป query เทียบกับของจริง ไม่ใช่เพราะระบบร้อง การรู้ว่า "อะไรคือ invariant" จึงมีค่ามากกว่า monitoring ในกรณีนี้

หัวใจอยู่ที่ statement เป็นหน่วยของ "ขอบเขต + เงื่อนไข" ไม่ใช่หน่วยของ permission — หนึ่ง statement ถือได้หลาย permission และหลาย target พร้อมกัน ดังนั้นคำถามว่า permission ซ้ำได้ไหม จึงต้องตอบจากความหมายของ statement ไม่ใช่จากจำนวนแถว

AND · ภายใน statement

conditionsHold() ใช้ .every() — condition ทุกแถวใน statement เดียวต้องเป็นจริงพร้อมกัน

OR · ระหว่าง statement

evaluate() ใช้ .some() — statement ใดใดหนึ่งผ่านก็พอ (deny ตรวจก่อนและชนะเสมอ)

ผลที่ตามมา

เพราะ AND อยู่ในสถานะ "ภายใน" และ OR อยู่ "ระหว่าง" — การเขียนเงื่อนไขแบบ dept = A หรือ dept = B ทำได้ทางเดียวคือ สร้าง allow สองstatement ที่ถือ permission เดียวกัน นี่คือกรณีเดียวที่การซ้ำมีความหมาย และเป็นเหตุผลที่กฎในหัวข้อถัดไปต้องพูดถึง "ชุด condition" ไม่ใช่แค่ effect

03 — กฎแกนกลาง

Invariant ที่ schema ไม่เคยบังคับใช้

CORE INVARIANT

1 policy + 1 permission + 1 effect + 1 ชุด condition = 1 แถวเท่านั้น

เมื่อไม่มี condition (สถานะของระบบตอนตรวจ: statement_conditions = 0 แถวทั้งระบบ) กฎนี้ยุบลงเป็น: allow ได้ 1 แถว · deny ได้ 1 แถว เท่านั้น

สิ่งที่ทำให้กฎนี้ถูกเข้าใจผิดง่ายคือมันดูเหมือนควรมีข้อยกเว้นสามข้อ — แต่จริง ๆ มีแค่ข้อเดียว

ไม่ใช่ข้อยกเว้น · TARGETS

(service, resource) เป็นคุณสมบัติของแถว permissions เอง — permission หนึ่งตัวจึงสังกัด target เดียวโดยธรรมชาติ การที่ warehouse:view ไปโผล่ใน statement ที่ scope auth/* คือความผิดพลาด ไม่ใช่การ scope

ไม่ใช่ข้อยกเว้น · PLANE

permissions.plane ก็เป็นคุณสมบัติของ permission เอง — permission หนึ่งตัวอยู่ได้ plane เดียว การเอา ui-permission ไปใส่ statement plane: 'api' ไม่ได้ให้สิทธิ์เพิ่ม แต่สร้าง scope ที่ guard ไม่เคย enforce

ข้อยกเว้นเดียวที่แท้จริง · CONDITIONS

statement สองอันที่ต่างกันเฉพาะชุด condition ต้องแยกกันอยู่ เพราะเป็นวิธีเดียวที่เขียน OR ได้ (ดูหัวข้อ 02) — ถ้าบังคับให้ allow เหลือแถวเดียวตายตัว จะเขียน ABAC แบบ "อนุญาตเมื่อ A หรือ B" ไม่ได้เลยตลอดกาล

allow + deny คู่กัน มีความหมายเมื่อไร

เฉพาะเมื่อฝ่ายใดฝ่ายหนึ่งมี condition — ถ้าทั้งคู่ไม่มี condition computeAllowDenyConditional() ให้ deny ชนะเสมอ แถว allow จึงเป็นขยะที่ไม่มีผลใด ๆ (ไม่อันตราย แต่ไร้ความหมายและทำให้อ่านนโยบายผิด)

บังคับใช้ได้ถึงระดับไหน

กฎบังคับที่ทำได้จริงไหม
ซ้ำใน statement เดียวกัน Partial unique index บน (statement_id, permission_id) WHERE is_deleted = false ได้ที่ระดับ DB — ไม่มีข้อเสีย ต้องทำ
ซ้ำข้าม statement PoliciesService.setStatements() — merge statement ที่ (effect, plane, targets, conditions) ตรงกัน แล้ว dedupe permission_ids ต้องทำที่ application layer — condition อยู่ตารางลูก DB จึงทำ unique constraint ไม่ได้
Entity · partial unique index (ต้องอยู่บน entity ไม่ใช่แค่ใน migration)
// migration-only constraint จะถูก migration:generate รอบหน้า drop ทิ้งเงียบ ๆ
@Index(
  'uq_statement_actions_statement_id_permission_id',
  ['statement_id', 'permission_id'],
  { unique: true, where: 'is_deleted = false' },

04 — สัญญา API

Contract ที่เปลี่ยน (Breaking)

targets เป็น "คู่" ไม่ใช่สองอาร์เรย์

รูปแบบเดิมส่ง service[] และ resource[] แยกกัน ทำให้ service ฝั่ง backend ต้องประกอบกลับเป็น ผลคูณคาร์ทีเซียน — เลือก 2 คู่ ได้ 4 แถว โดย 2 แถวไม่มีใครเลือก

✗ เดิม
{
  "service":  ["iam", "inventory-bc"],
  "resource": ["role", "warehouse"]
}

// backend สร้าง 4 targets:
//   iam/role           ← เลือก
//   iam/warehouse      ← ไม่ได้เลือก!
//   inventory-bc/role  ← ไม่ได้เลือก!
//   inventory-bc/warehouse ← เลือก
✓ ใหม่
{
  "targets": [
    { "service": "iam",
      "resource": "role" },
    { "service": "inventory-bc",
      "resource": "warehouse" }
  ]
}

// เก็บตามที่ส่งมาเป๊ะ 2 targets
จุดที่เปลี่ยนเดิมใหม่
PUT :id/statementsservice[] + resource[]targets: [{ service, resource }]
GET :id/statementsคืนเฉพาะ permissions[] (string)คืน permission_ids[] ด้วย — client ไม่ต้องเดา id ย้อนกลับ
statementsส่ง [] ได้ → ล้างสิทธิ์เงียบ@ArrayNotEmpty()
conditions[].operator@IsString()@IsIn(CONDITION_OPERATORS)
permission_idsไม่ตรวจอะไรต้องมีจริงใน catalog และ plane ตรงกับ statement
Permission ที่ใช้policy:create คุม update/delete ด้วยแยก policy:update · policy:delete
valid_from / valid_untilคอลัมน์ datetimestamptz + ต้องส่ง ISO 8601 เต็มรูป
ทำไม permission_ids ในขา GET จึงสำคัญ

permission string ไม่ unique เดี่ยว ๆ — unique แค่ระดับ (service, permission) ตาม uq_permissions_service_permission ดังนั้นการเดา id ย้อนจาก string ใน statement ที่ scope service = '*' จะ map ทุก candidate ไปที่แถวเดียวกันแบบสุ่ม → สิทธิ์ของอีก service หายเงียบตอนกด Save การคืน id มาตรง ๆ ทำให้ไม่มีอะไรต้องเดา

06 — Anti-pattern

Grant migration ที่เลือก statement แบบไม่ดู scope

นี่คือต้นเหตุที่แท้จริงของข้อมูลซ้ำ ไม่ใช่ seed และไม่ใช่ UI — และเป็น pattern ที่ถูก copy ต่อกันมาในทุก migration ที่ชื่อ Grant*PermissionsToMockPolicies ดังนั้นถ้าไม่หยุดที่ pattern ทุก migration ใหม่จะเติมขยะเพิ่มทุกครั้ง

✗ Anti-pattern — match ทุก allow/api statement ของ policy
INSERT INTO statement_actions (statement_id, permission_id)
SELECT ps.id, perm.id
FROM policy_statements ps
JOIN policies pol ON pol.id = ps.policy_id
JOIN permissions perm ON perm.permission = ANY($2)
WHERE pol.code = ANY($1)
  AND ps.effect = 'allow'
  AND ps.plane  = 'api'   -- ← ไม่ดู targets เลย

-- policy หนึ่งมี allow/api ได้หลาย statement (คนละ scope)
-- → พ่น permission เข้าไปทุกอัน รวมอันที่ scope ผิดความหมาย
-- → warehouse:* ไปโผล่ใน statement ที่ scope auth/* และ */tax_config
✓ ที่ถูก — เจาะ statement ที่ถือ sibling permission อยู่แล้ว
INSERT INTO statement_actions (statement_id, permission_id)
SELECT anchor.statement_id, perm.id
FROM (
  -- statement ที่ถือ policy:create อยู่แล้ว = ที่ที่ญาติของมันอยู่
  SELECT DISTINCT sa.statement_id
  FROM statement_actions sa
  JOIN permissions anchor_perm
    ON anchor_perm.id = sa.permission_id
   AND anchor_perm.service = 'iam'
   AND anchor_perm.permission = 'policy:create'
  WHERE sa.is_deleted = false
) anchor
CROSS JOIN permissions perm
WHERE perm.service = 'iam'
  AND perm.permission = ANY($1)
  AND perm.is_deleted = false
  AND NOT EXISTS (  -- idempotent
    SELECT 1 FROM statement_actions existing
    WHERE existing.statement_id = anchor.statement_id
      AND existing.permission_id = perm.id
      AND existing.is_deleted = false
  )
กฎ

migration ที่ grant permission ต้องระบุปลายทางแบบเจาะจงหนึ่ง statement เสมอ — ไม่ว่าจะโดยการอ้าง sibling permission, โดย targets, หรือโดย statement id ตรง ๆ การกรองด้วย effect + plane เพียงสองอย่างไม่เคยเพียงพอ และต้องมี NOT EXISTS เพื่อให้รันซ้ำได้

07 — การล้างข้อมูล

ล้างเท่าที่พิสูจน์ได้ว่าไม่เสียความหมาย

1

ซ้ำใน statement เดียวกัน — lossless

แถวที่สองไม่ได้ให้สิทธิ์อะไรที่แถวแรกไม่ได้ให้ · เก็บแถวที่เก่าที่สุด ลบที่เหลือ (12 คู่)

2

statement ที่เหมือนกันเป๊ะ — lossless

เหมือนกันทั้ง (policy_id, effect, plane, ชุด targets, ชุด conditions) → ย้าย permission ที่ผู้รอดยังไม่มีเข้าไป แล้วลบตัวซ้ำ (FK cascade เก็บลูกให้เอง) (3 statements)

3

สร้าง partial unique index

การที่ CREATE UNIQUE INDEX สำเร็จ คือหลักฐานว่าขั้น 1 ล้างครบจริง

—

ที่ไม่ล้าง: permission เดียวอยู่หลาย statement ที่ targets ต่างกัน

การตัดสินว่า statement ไหนควรเป็นเจ้าของเป็นเรื่องเชิงความหมาย ไม่ใช่เชิงกลไก และวันนี้ไม่มีผลใด ๆ เพราะ evaluator ไม่ enforce targets — ควรทำเป็นรอบเดียว พร้อมกับตอนเปิด per-service scoping

08 — Checklist

สำหรับโค้ดที่แตะ policy engine ต่อจากนี้

01 · INVARIANT

การเขียน statement_actions ทุกครั้งต้องผ่าน merge/dedupe — และ statement ซ้ำได้เฉพาะเมื่อชุด condition ต่างกันจริง

02 · TARGETS

ส่ง/เก็บเป็นคู่ (service, resource) เสมอ · ห้ามแตกเป็นสองอาร์เรย์แล้วประกอบกลับ

03 · OPERATOR

เพิ่ม operator ใหม่ต้องแก้ 3 ที่พร้อมกัน: CONDITION_OPERATORS · switch ใน evaluator · picker ใน UI — ขาดที่ใดที่หนึ่งคือ deny fail-open

04 · PLANE

ตรวจ permission.plane === statement.plane ทุกครั้ง — ไม่มี FK ไหนกันให้

05 · CATALOG

อ่าน permission ผ่าน PermissionsService เท่านั้น (ไม่ inject Repository<Permission>) และให้ขา read กับ write กรอง is_deleted เหมือนกัน

06 · CONSTRAINT

unique/check ต้องประกาศบน entity ด้วย ไม่ใช่แค่ใน migration — ไม่งั้น migration:generate รอบหน้า drop ทิ้งเงียบ ๆ

07 · GRANT MIGRATION

เจาะ statement ปลายทางแบบเจาะจง + NOT EXISTS · ห้าม copy pattern ที่กรองด้วย effect+plane เท่านั้น

08 · ลำดับ DEPLOY

permissions:sync ก่อน แล้วจึง migration:run — สลับลำดับแล้ว grant migration จะถูกบันทึกว่า applied แต่ match 0 rows

ข้อควรระวังตอนเพิ่ม validation ย้อนหลัง

การเพิ่ม @Matches ให้ code เกือบทำให้ policy เดิมที่ code เป็นตัวพิมพ์เล็กแก้ไขไม่ได้ (ฟอร์มส่ง code เดิมกลับไปด้วยทุกครั้ง) — validation ใหม่ต้องเทียบกับข้อมูลที่มีอยู่จริงก่อน ไม่ใช่กับรูปแบบที่ตั้งใจให้เป็นเท่านั้น
