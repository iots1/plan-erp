Runbook · Database / Infra

Pgpool Cascade จาก
max_connections เต็ม

ปลายทางเหมือน Runbook 01 เป๊ะ — pgpool is not accepting any new connections — แต่ต้นเหตุคนละเรื่องสิ้นเชิง: PostgreSQL ไม่เคยตายเลยแม้วินาทีเดียว connection แค่ล้นเพดาน จน health check ของ pgpool จองสล็อตไม่ได้ แล้วมันตีความว่า node ตาย → ทยอย degenerate ทีละตัวจนหมดใน 1 ชม. 46 นาที

Severity: Critical (Total DB Outage) Slow burn: ~1 ชม. 46 นาที ก่อนล่มสนิท Est. fix time: 2–5 นาที
1 — อาการ (Symptom)

Log ที่จะเห็น

IP ในเอกสารนี้ถูก mask ไว้

เอกสารชุดนี้เป็น repo สาธารณะ จึงปิด octet กลางของที่อยู่ภายในไว้เป็น 172.xx.x.NNN — octet สุดท้ายเป็นของจริง เพื่อให้ยังแยกโน้ดออกจากกันได้ (เช่น .221 กับ .222 คือคนละเครื่อง) · เวลารันจริงให้แทนด้วย subnet ของตัวเอง ส่วน 127.0.0.1 และ 0.0.0.0 เป็นค่าจริงตามความหมายเดิม ไม่ได้ mask · เวลาใน log ทุกบรรทัดเป็น UTC (เครื่องตั้งเป็น UTC) ต้อง +7 ถ้าเทียบกับเวลาที่ user แจ้ง

ฝั่ง client จะเห็นแค่ 500 ธรรมดา แต่ถ้า error handler ส่ง message จาก driver ออกมาตรงๆ จะอ่านต้นเหตุได้ทันทีจาก response: 

{
  "status": { "code": 500, "message": "pgpool is not accepting any new connections" },
  "errors": [{ "code": 500, "title": "Server Error",
               "detail": "pgpool is not accepting any new connections" }],
  "meta": { "timestamp": "…T06:41:48.117Z", "traceId": "…" }
}

บน pgpool node จะเห็นสามบรรทัดนี้ซ้ำนับหมื่นครั้ง — เหมือน Runbook 01 ทุกตัวอักษร ตรงนี้ยังแยกสองเคสออกจากกันไม่ได้: 

child pid xxxxx: FATAL:  pgpool is not accepting any new connections
child pid xxxxx: DETAIL:  all backend nodes are down, pgpool requires at least one valid node
child pid xxxxx: HINT:  repair the backend nodes and restart pgpool
ลายเซ็นที่แยกเคสนี้ออกจาก Runbook 01 — health check "สำเร็จ" หลัง degenerate ไป 1 วินาที

ถ้า node ตายจริง health check จะ fail ต่อเนื่องหลายนาที แต่เคสนี้มันกลับมาเองทันที ช้าไปแค่ 1 วินาที — นั่นคือหลักฐานว่า node ไม่เคยตาย แค่ตอบไม่ทันเพราะไม่มีสล็อตว่าง 

04:48:52  health_check0: LOG:  health check retrying on DB node: 0 (round:1)
04:48:53  health_check0: LOG:  health check retrying on DB node: 0 (round:2)
04:48:54  health_check0: LOG:  health check retrying on DB node: 0 (round:3)
04:48:55  main:          LOG:  starting degeneration. shutdown host 172.xx.x.221(5432)
04:48:56  health_check0: LOG:  health check retrying on DB node: 0 succeeded   <-- ช้าไป 1 วินาที

และอีกสองอาการที่ต้องเจอคู่กันเสมอในเคสนี้ — ต้นเหตุจริงอยู่ใน log ของ PostgreSQL ไม่ใช่ของ pgpool: 

# /var/log/postgresql/postgresql-NN-main.log บน primary — เกิดก่อน degeneration ไม่กี่วินาที

                                        roles with the SUPERUSER attribute
04:48:50  postgres@<db>         FATAL:  sorry, too many clients already
04:48:51  repmgr@repmgr         FATAL:  sorry, too many clients already
04:48:52  postgres@<db>         FATAL:  sorry, too many clients already      <-- ตรงนี้ health check ก็โดนด้วย
# journalctl -u pgpool2 — fork storm หลัง node ตกครบ: ทุก connection ที่เข้ามา child รับแล้ว exit(1) ทันที
main: LOG:  child process with pid: 1740864 exits with status 256

2 — ผลกระทบ (Impact)

Total DB Outage — แต่มาแบบค่อยๆ ทรุด ไม่ใช่ดับทันที

SCOPE

ทุก BC ที่ผ่าน VIP นี้

auth, iam, inventory-bc, supplier-bc, sales-bc, finance-bc, report-bc — ทุก request ที่แตะ DB ล้มเหลว 100% รวมทุก database บนคลัสเตอร์เดียวกัน ไม่ใช่แค่ของ ERP

SEVERITY

Critical — escalate ทันที

แต่มีหน้าต่างให้เบรกได้ ~1 ชม. 46 นาที ระหว่าง node แรกตกกับ node สุดท้ายตก — ถ้ามี alert ที่ถูกจุดจะไม่ล่มเลย (ดู §6)

DATA SAFETY

ข้อมูลไม่เสี่ยง

PostgreSQL ปกติตลอดเหตุการณ์ · replication lag 0 · ไม่มี failover จริง ไม่ต้อง restore อะไรเลย

อาการหลอกในช่วงกลาง — write ล้มแต่ read ยังได้ ทำให้ทีมไล่ผิดทาง

หลัง node 0 (primary) ถูก degenerate แล้ว pgpool หา primary ตัวใหม่ไม่เจอ (เหลือแต่ standby) จึงตั้ง primary node: -1 — ผลคือ read ยังทำงานได้ปกติ แต่ write ทุกตัวเด้ง ด้วย error ที่ดูเหมือนบั๊กแอป ไม่เหมือนปัญหา infra: 

ERROR: cannot execute UPDATE in a read-only transaction
ERROR: cannot execute INSERT in a read-only transaction
ERROR: cannot execute CREATE EXTENSION in a read-only transaction

เจอ error สามบรรทัดนี้เมื่อไหร่ = pgpool ไม่มี primary แล้ว ให้เข้า runbook นี้ทันที อย่ารอให้ล่มสนิท เพราะจากจุดนี้ไปมันจะทรุดต่อเองเสมอ (ดู §4)

3 — วินิจฉัย (Diagnosis)

แยกให้ออกว่าเป็นเคสนี้ ไม่ใช่ Runbook 01

การแก้เหมือนกันทั้งสองเคส (pcp_attach_node) แต่ถ้าไม่แยกให้ออกว่าเป็นเคสนี้ จะ attach เสร็จแล้วตกซ้ำอีกใน 5 นาที เพราะต้นเหตุจริงยังอยู่ — §3 นี้จึงมีไว้เพื่อหาว่าใครกิน connection ไม่ใช่แค่ยืนยันอาการ

1

เช็คว่า PostgreSQL/repmgr จริงยังปกติไหม

เหมือน Runbook 01 ข้อ 1 — ในเคสนี้จะปกติทุกโหนด ไม่มี failover จริง

ssh ovh-ppm "sudo -u postgres repmgr cluster show"
2

เทียบ timestamp: degeneration กับ "health check succeeded" ห่างกันกี่วินาที

นี่คือคำสั่งที่แยกสองเคสออกจากกันได้ตรงที่สุด — ถ้า succeeded โผล่ตามหลัง starting degeneration ภายใน 1–2 วินาที ทุกครั้ง = เคสนี้ 

ssh ovh-pgpool1 "sudo journalctl -u pgpool2 --since '6 hours ago' --no-pager \
  | grep -E 'starting degeneration|health check retrying|find_primary_node_repeatedly|no valid backend'"
รูปแบบที่ต้องเห็น — ตกทีละ node ห่างกันเป็นสิบนาทีถึงชั่วโมง ไม่ใช่พร้อมกัน

Runbook 01 คือ 3 node ตกพร้อมกันในไม่กี่วินาที (primary หาย/watchdog เสีย quorum) · เคสนี้คือทยอยตก โดยแต่ละครั้ง health check กลับมาเองทันที

3

ยืนยันต้นเหตุใน log ของ PostgreSQL — ไม่ใช่ของ pgpool

ถ้าไม่เจอ too many clients ในช่วงก่อน degeneration แปลว่าไม่ใช่เคสนี้ ให้กลับไป Runbook 01

ssh ovh-ppm "grep -aE 'too many clients|remaining connection slots' \
  /var/log/postgresql/postgresql-*-main.log | tail -40"
4

หาว่าใครกิน connection — ต้องรู้ก่อนแก้ ไม่งั้นตกซ้ำ

ตอนที่ pgpool ปฏิเสธทุก connection แล้ว ตัวเลขนี้จะต่ำหลอกตา (ไม่มี traffic ไปถึง PG เลย — ในเหตุการณ์จริงเหลือแค่ 4 connection) ให้ดู restart count ของ pm2 ควบคู่ไปด้วย เพราะ service ที่ restart loop คือผู้ต้องสงสัยอันดับหนึ่ง — ทุกครั้งที่บูตใหม่มันเปิด pool ใหม่ทั้งชุด 

# ใช้ได้แม้ pgpool ตายอยู่ — ไม่ต้องผ่าน pgpool
ssh ovh-ppm "curl -s localhost:9187/metrics \
  | grep -E '^pg_settings_max_connections|^pg_settings_superuser_reserved|^pg_stat_activity_count' \
  | grep -v '} 0$'"

# ใครรีสตาร์ทวน = ใครเปิด pool ใหม่ซ้ำๆ (คอลัมน์ restart สูงผิดปกติ)
ssh app-server "pm2 list"
5

เช็คสถานะที่ pgpool "คิด" ว่าเป็น

เหมือน Runbook 01 ข้อ 3 — ลายเซ็นคือ Status Name: down คู่กับ Backend Status Name: up ทั้ง 3 node 

for n in 0 1 2; do
  ssh ovh-pgpool1 "sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
    pcp_node_info -h localhost -p 9898 -U pgpool_admin -w -n $n -v"
done
ถ้า pcp_node_info ใช้ไม่ได้ (ไม่มี sudo / รหัส pcp หาย) มีทางสำรอง 2 ทาง

(1) อ่านไฟล์สถานะตรงๆ — cat /var/log/postgresql/pgpool_status คืนค่า 3 บรรทัด (node 0/1/2) · (2) นับ child process — pgrep -c pgpool อยู่ที่เพดาน num_init_children คาที่เดิม พร้อม ss -Htan | grep -c TIME-WAIT สูงผิดปกติ = fork storm กำลังเกิด · ข้อควรระวัง: ไฟล์ pgpool_status คือค่าที่เขียนลงดิสก์ ซึ่งอาจตามหลังค่าใน memory — ในเหตุการณ์จริงไฟล์ยังเป็น down/down/up ขณะที่ pgpool ปฏิเสธทุก connection ไปแล้ว (คือ down จริงทั้ง 3) อย่าใช้ไฟล์นี้ตัดสินว่า "ยังมี node เหลือ"

4 — สาเหตุ (Root Cause)

Health check แยกไม่ออกระหว่าง "node ตาย" กับ "ไม่มีสล็อตว่าง"

Health check ของ pgpool ตัดสินว่า node เป็นหรือตายด้วยการเปิด connection ใหม่ไปที่ backend — และมันเชื่อมต่อด้วย role ธรรมดาที่ไม่มีสิทธิ์แตะ superuser_reserved_connections ดังนั้นตอน max_connections เต็ม PostgreSQL จะตอบมันด้วย sorry, too many clients already ซึ่งจากมุมของ health check หน้าตาเหมือน node ตายเป๊ะ — retry ครบโควตาแล้วก็ degenerate

หัวใจของเคสนี้: มันเป็น positive feedback loop ไม่ใช่เหตุการณ์เดี่ยว

connection ล้น → degenerate node → เหลือ node น้อยลง → connection เดิมทั้งหมดอัดเข้า node ที่เหลือ → ล้นเร็วกว่าเดิม → degenerate ตัวถัดไป → … วนจนหมดทั้ง 3 · การ attach node กลับโดยไม่ปิดต้นทาง = ป้อน loop รอบใหม่ 

sequenceDiagram
    participant App as App (TypeORM pools)
    participant PP as Pgpool (health check)
    participant PG as PostgreSQL (จริง — ปกติตลอด)

    App->>PG: connection ทะลุ max_connections
    PG-->>App: FATAL: sorry, too many clients already
    PP->>PG: health check เปิด connection ใหม่
    PG-->>PP: FATAL: too many clients (ไม่มีสล็อต · ไม่ใช่ superuser)
    Note over PP: retry ครบโควตา → ตีความว่า node ตาย
    PP->>PP: starting degeneration → node = down
    PG-->>PP: 1 วินาทีถัดมา health check ผ่านแล้ว (ช้าไป)
    Note over PP: หา primary ใหม่ → เหลือแต่ standby
search_primary_node_timeout 300s หมด
→ set new primary node: -1
    App->>PP: write ทุกตัว
    PP-->>App: cannot execute UPDATE in a read-only transaction
    Note over App,PG: connection ทั้งหมดอัดเข้า node ที่เหลือ
→ ล้นเร็วกว่าเดิม → วนซ้ำข้อ 3
    Note over PP: node สุดท้ายตก → all backend nodes are down
→ ปฏิเสธทุก connection + fork storm

ทำไม auto_failback ไม่ช่วย — เหตุผลเดียวกับ Runbook 01

auto_failback ต้องอ่าน pg_stat_replication บน primary เพื่อยืนยันว่า standby streaming อยู่จริง — แต่พอ node 0 (primary ตัวจริง) ถูก degenerate เป็นตัวแรก pgpool ก็ไม่มี primary ให้อ่านตั้งแต่นาทีที่ 1 ขา DOWN → UP จึงตายสนิททั้งเหตุการณ์ รายละเอียดกลไกอยู่ใน Runbook 01 §4

ตัวเร่งที่มองข้ามง่าย — client_idle_limit ทำให้ connect rate สูงกว่าที่คิด

คลัสเตอร์นี้ตั้ง client_idle_limit = 60 — pgpool ตัด client ที่ idle เกิน 60 วินาทีทิ้ง (child connection forced to terminate due to client_idle_limit:60 is reached) แล้ว TypeORM ก็ต่อกลับมาใหม่ทันที ผลคือมีการเปิด connection ใหม่ตลอดเวลา แม้ traffic จริงจะนิ่ง — เห็นเป็น TIME-WAIT ค้างหลักพันบน pgpool node ยิ่งทำให้ช่วง spike ชนเพดานได้ง่าย

5 — การแก้ไข (Fix)

ปิดต้นทางก่อน แล้วค่อย attach — สลับลำดับแล้วตกซ้ำ

1

ลด connection ต้นทางก่อน (ถ้ายังล้นอยู่)

ถ้า §3 ข้อ 4 ชี้ว่ามี service restart loop หรือมี pool ที่เปิดไม่จำกัด ให้หยุด/จำกัดตัวนั้นก่อน — ถ้า attach ตอนที่ต้นทางยังล้น มันจะ degenerate ซ้ำภายในไม่กี่นาที · ถ้าตอนนี้ pgpool ปฏิเสธทุก connection อยู่แล้ว traffic จะไปไม่ถึง PG เลย ข้อนี้ข้ามได้ (แต่ยังต้องกลับมาปิดต้นทางใน §6 ไม่งั้นเกิดซ้ำวันหลัง) 

ssh app-server "pm2 stop <service-ที่-restart-loop>"
2

Re-attach ทั้ง 3 node — node 0 ก่อน ถ้ามันคือ primary จริง

ต่างจาก Runbook 01 ตรงนี้: ลำดับสำคัญ — pgpool จะรัน find_primary_node ทุกครั้งที่มี node กลับมา ถ้า attach standby ก่อน มันจะหา primary ไม่เจอแล้วเข้า search_primary_node_timeout (default 300 วินาที) รอเปล่าๆ · ยืนยันว่า node ไหนเป็น primary จริงจาก repmgr cluster show ใน §3 ข้อ 1 

# primary ก่อน (ในคลัสเตอร์นี้คือ node 0 = ppm) แล้วค่อย standby
for n in 0 1 2; do
  ssh ovh-pgpool1 "sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
    pcp_attach_node -h localhost -p 9898 -U pgpool_admin -w -n $n"
done

แต่ละคำสั่งควรตอบ pcp_attach_node -- Command Successful · ถ้าเจอ FATAL: authentication failed for user "pgpool_admin" แปลว่า .pcppass หาย/ผิด ดู §08 บั๊ก #13/#19 · จะเห็น failback done. reconnect host … ตามด้วย failover: set new primary node: 0 ใน journal

3

อย่า systemctl restart pgpool2 เป็นทางลัด

HINT ใน log บอกว่า "repair the backend nodes and restart pgpool" — ทำตามตรงๆ แล้วไม่หาย เพราะ pgpool อ่านสถานะ node กลับมาจากไฟล์ pgpool_status ตอนบูต ซึ่งยังเป็น down อยู่ → ตื่นมาก็ปฏิเสธ connection เหมือนเดิม แต่คราวนี้ตัด connection ที่ยังใช้งานได้ทิ้งไปด้วยฟรีๆ

ถ้าจำเป็นต้อง restart จริง (attach ไม่ได้เพราะรหัส pcp หาย)
# ต้องหยุดให้ครบทั้ง 3 node ก่อน ไม่งั้น watchdog เอาค่าเก่ามา sync กลับ
for h in ovh-pgpool1 ovh-pgpool2 ovh-pgpool3; do ssh $h "sudo systemctl stop pgpool2"; done

# ทางเลือก A: ล้างสถานะที่จำไว้ แล้วให้ pgpool ตรวจใหม่เอง (ปลอดภัยกว่า)
for h in ovh-pgpool1 ovh-pgpool2 ovh-pgpool3; do
  ssh $h "sudo mv /var/log/postgresql/pgpool_status /var/log/postgresql/pgpool_status.bak"
done

ป้องกัน #1 (สำคัญสุด) — ให้ health check ทนช่วง connection spike ได้

ต้นตอของ cascade คือ health check แยกไม่ออกระหว่าง "ตาย" กับ "ไม่มีสล็อต" · ขยายโควตา retry คือสิ่งที่ทำได้ทันทีและ reload ได้: ค่าที่เจอในคลัสเตอร์นี้คือ health_check_max_retries = 3 · health_check_retry_delay = 1 = ทนได้แค่ ~3 วินาที ขณะที่ node กลับมาเองหลัง degenerate เพียง 1 วินาที ทั้ง 3 ครั้ง → ตั้ง max_retries = 10 / retry_delay = 2 (ทนได้ ~20 วินาที)

กับดัก: "ให้ health check ใช้ reserved connection" อาจไม่ช่วยเลย — เช็คก่อนว่าใครเป็น superuser

คำแนะนำมาตรฐานคือให้ health_check_user ใช้สล็อตที่ superuser_reserved_connections กันไว้ — แต่ในคลัสเตอร์นี้ health check ก็เป็น postgres อยู่แล้ว และแอปก็ต่อเป็น postgres เหมือนกัน ทุกตัวเป็น superuser จึงกินสล็อตสำรองได้หมด = กลไกนี้ไม่ได้ป้องกันอะไรเลย · หลักฐานตรงเผง: ตัวเดียวที่ ไม่ใช่ superuser (exporter) เป็นตัวแรกที่ถูกปฏิเสธด้วย remaining connection slots are reserved for roles with the SUPERUSER attribute ขณะที่แอปยังต่อได้ต่ออีก 40 วินาที · reserved connection จะมีความหมายก็ต่อเมื่อแยก role ของแอปออกจาก superuser ก่อน ตรวจด้วย: grep health_check_user /etc/pgpool2/pgpool.conf เทียบกับ role ที่แอปใช้ใน PG log

ป้องกัน #2 — ตั้งงบ connection ให้ไม่ overcommit ตั้งแต่ต้น

เพดานที่ pgpool เปิดได้จริงคือ num_init_children × max_pool × จำนวน pgpool node ที่รับ traffic ต้อง ≤ max_connections − superuser_reserved_connections − (repmgr + exporter + งานคน) · เช็คค่าจริงของตัวเองก่อนคำนวณ: 

ssh ovh-pgpool1 "sudo grep -E '^(num_init_children|max_pool|client_idle_limit|health_check)' \
  /etc/pgpool2/pgpool.conf"
ssh ovh-ppm "curl -s localhost:9187/metrics | grep -E 'max_connections|superuser_reserved'"

# อ่าน pgpool.conf ไม่ได้ (0640 root:postgres)? exporter บอก num_init_children ตรง ๆ ไม่ต้อง sudo
ssh ovh-pgpool1 "curl -s localhost:9719/metrics | grep -E '^pgpool2_frontend_(total|used)'"
# frontend_total = num_init_children · frontend_used = client ที่ต่ออยู่จริงตอนนี้
# ใช้ได้เฉพาะตอน pgpool ยังรับ connection ได้ — ตอนล่ม pgpool2_up=0 จะไม่มี metric นี้

ในคลัสเตอร์นี้ max_connections = 400 · num_init_children = 300 · และ max_pool ไม่ได้ตั้งไว้ในไฟล์เลย จึงใช้ค่า default = 4 → เพดานจริง 300 × 4 = 1,200 ต่อ backend node = overcommit 3 เท่า (รวมทุก backend node ได้ 3,600 เทียบกับความจุคลัสเตอร์ 1,200)

ทำไมมันระเบิดหลังรันปกติมาหลายสัปดาห์ — child สะสมสล็อตไปเรื่อย ๆ

แต่ละ child เริ่มที่ 0 สล็อต แล้วสะสมทีละสล็อตตามคู่ (user, database) ที่มันเคยให้บริการ จนถึงเพดาน max_pool · ตอนตรวจใช้แค่ 1 ใน 12 สล็อต (pgpool2_backend_by_process_used เทียบกับ pgpool2_backend_by_process_total = 12) → ยิ่ง workload แตะ database มากขึ้น connection ยิ่งไต่ขึ้นเองแม้ traffic เท่าเดิม · ทางแก้ที่ปลอดภัยสุด: ตั้ง max_pool = 1 (เพดานเหลือ 300 ต่อ node) — ตัด overcommit ทิ้งโดยไม่ลดความจุ client เลย เพราะยังมี child ครบ 300 ตัว · max_pool ต้อง restart pgpool ไม่ใช่ reload (ต่างจาก health_check_* ที่ reload ได้) — และก่อน restart ต้องเช็คว่า pgpool_status เป็น up ทั้ง 3 บรรทัดก่อน ตามกับดักใน §5 ข้อ 3

อย่าแก้ด้วยการเพิ่ม max_connections — มันไม่ใช่ปัญหาขนาด

สัญชาตญาณแรกคือ "ก็เพิ่มเพดานสิ" แต่ตัวเลขบอกว่าผิดทาง: งานจริงพร้อมกัน peak 30 วัน = 9 connection (pg_stat_activity_count{state="active"}) ส่วน 385 ตัวที่ชนเพดาน คือ connection เปิดค้าง idle ที่พุ่งขึ้น +341 ใน 4 นาที จาก baseline 45–176 — นั่นคือ runaway ไม่ใช่ demand เพิ่มเพดานก็แค่ให้มันกินได้มากขึ้นก่อนชน

เพิ่มแล้วก็ไม่ได้ throughput เพิ่ม — connection ที่ล้นคือของที่เปิดค้าง idle ไม่ใช่งานที่รอทำ · และ pgpool มีไว้เพื่อจำกัด connection ที่ถึง PostgreSQL ถ้าเพดานของ pgpool สูงกว่า max_connections แล้วไปเพิ่มฝั่ง PostgreSQL ตาม คือไล่หางตัวเอง — ที่ถูกคือลดเพดานของ pgpool ลงมาให้อยู่ในงบ · OOM แย่กว่า connection refused: ตอนถูกปฏิเสธ ระบบใช้ไม่ได้แต่ PostgreSQL ยังยืนอยู่และข้อมูลปลอดภัย ถ้าชน RAM แทน OOM killer จะเก็บ postmaster แล้วต้อง crash recovery

อย่าประเมิน RAM ด้วย used ÷ จำนวน backend — มันสูงเกินจริง

ตัวเลขนั้นรวม fixed overhead (postmaster, shared memory, catalog cache) ที่ไม่โตตามจำนวน connection · วัดจริงหลายรอบได้ used ~740–800 MB ที่ 26–37 backend คือไม่เป็นเส้นตรง — ต้นทุนส่วนเพิ่มต่อ idle connection ต่ำกว่าที่คิดมาก (หลักฐานชี้ขาด: peak 373 backend เคยรันบนเครื่องเดียวกันโดยไม่ OOM) · ตัวที่กิน RAM จริงคือ work_mem ตอน query ทำงาน ไม่ใช่จำนวน connection ที่เปิดค้าง จึงต้องดู state="active" ไม่ใช่ยอดรวม · และถ้าเป็น VM ให้วัด RAM สดด้วย free -m ทุกครั้ง (free -g ปัดทิ้ง และ memory balloon เปลี่ยนขนาดได้โดยไม่ reboot)

ทำแทน: (1) superuser_reserved_connections 3 → ~10 — ต้นทุนเป็นศูนย์ เพราะกันสล็อตอยู่ใน 400 เดิม ไม่ได้เพิ่มเพดาน คู่กับ ป้องกัน #1 แล้ว health check + repmgr + exporter จะมีทางเข้าเสมอ · (2) แก้ leak ฝั่งแอปก่อน · (3) แล้วค่อยลด num_init_children/max_pool — ห้ามสลับ (2) กับ (3) เพราะ num_init_children คือจำนวน client ที่รับพร้อมกันได้ ไม่ใช่จำนวน query · วัดได้ว่า pgpool2_frontend_used เคย peak 300/300 เต็ม ถ้าลดก่อนแก้ leak client ตัวที่เกินจะค้างรอคิวจนแอป timeout = outage อีกแบบ
