01 — โมเดล 2 ชั้น

สองระบบที่ทำงานแยกกัน และไม่รู้จักกันโดยตรง

ความสับสนอันดับหนึ่งของคนที่เพิ่งเข้ามาดูแลระบบนี้คือคิดว่า pgpool เป็นคนสั่ง promote — ไม่ใช่ สองชั้นนี้แยกหน้าที่กันเด็ดขาด และคุยกันทางอ้อมเท่านั้น

ชั้นข้อมูล

repmgr — ตัดสินว่าใครเป็น primary

repmgrd รันอยู่บน ppm/ppr1/ppr2 คอยจับตาดู primary ถ้าติดต่อไม่ได้ครบตามเงื่อนไข จะเลือก standby ตัวหนึ่ง promote แล้วสั่งอีกตัว follow — pgpool ไม่มีส่วนในขั้นตอนนี้เลย

ชั้นทางเดิน

pgpool — ตัดสินว่าส่ง query ไปไหน

pgpool ถาม backend ทุกตัวด้วย pg_is_in_recovery() ทุก 5 วินาที (sr_check_period) แล้วค้นพบเองว่าใครเป็น primary — ไม่ได้อ่านจาก config และไม่ได้ถาม repmgr

ดี: pgpool ค้นพบ primary เองจากสภาพจริงของ backend เพราะฉะนั้นต่อให้ promote ด้วยมือ ด้วย repmgr หรือด้วยวิธีไหน pgpool ก็ตามทันเสมอ ไม่ต้องแก้ config · ระวัง: ขาลูกศรประที่ชี้กลับขึ้นไป (event hook) คือตัวที่คอยเคลียร์สถานะค้างของ pgpool หลัง promote ซึ่งตอนนี้พังอยู่ — ระบบยัง failover ได้ แต่ขาด safety net (§08)

สรุปเป็นประโยคเดียว

HA ระดับ VM สมบูรณ์แล้ว (2026-09-01) — กลไกทั้งสองชั้นทำงาน, safety net กลับมา, สเปก standby เท่า primary แล้ว และซ้อมผ่านครบ 3 ระดับ

แต่ HA ระดับเครื่องยังไม่มีเลย — VM ทั้งหมดอยู่บน hypervisor ตัวเดียว เพราะฉะนั้นระบบตอนนี้ "ล้มแล้วลุกได้" เฉพาะเมื่อสิ่งที่ล้มคือ VM ตัวใดตัวหนึ่ง ถ้าสิ่งที่ล้มคือตัว host เอง ยังไม่มีอะไรรองรับ (§08 ข้อ 0)

03 — เคส A

ppm (primary) ดับ — promote อัตโนมัติ ✅

คำตอบสั้น: ใช่ ระบบ promote เองอัตโนมัติ เคยทดสอบ kill จริงมาแล้ว ใช้เวลาจากตอน kill ถึง promote เสร็จ 29 วินาที คุณไม่ต้องทำอะไรเลยในนาทีแรก หน้าที่ของคุณคือเฝ้าดูว่ามันจบตามแผนไหม แล้วค่อยตามเก็บงานหลังบ้าน

ลำดับเหตุการณ์ที่ควรเห็น
เวลาใครทำเกิดอะไร
0 วิ—ppm ดับ · write ทั้งหมดเริ่ม error
~5–20 วิpgpoolhealth check ล้มครบ retry (period=5, max_retries=3) → degenerate node 0
~30 วิrepmgrdครบ reconnect_attempts=6 × interval=5 → ประกาศว่า primary ตาย เลือก standby แล้ว promote
~30–35 วิrepmgrdสั่ง standby อีกตัว follow primary ใหม่ · สร้าง replication slot ให้เอง (use_replication_slots=1)
~35–40 วิpgpoolsr_check รอบถัดไปเจอ primary ตัวใหม่ → เริ่ม route write ไปที่นั่น
~40 วิevent hookควรจะยิง pcp_attach_node เคลียร์สถานะค้าง — ตอนนี้ขั้นนี้ fail เงียบ

ช่วงที่ระบบเขียนไม่ได้จริงๆ ประมาณ 30–60 วินาที — แอปที่มี retry loop จะกลับมาเองโดยไม่ต้อง restart ส่วน transaction ที่ค้างอยู่ตอนนั้นจะ fail และต้องถูกส่งใหม่จากฝั่ง client

สิ่งที่คุณต้องทำ — ตามลำดับ
1

รอ 60 วินาทีก่อน อย่าเพิ่งแตะอะไร

นี่คือข้อที่สำคัญที่สุดและผิดกันบ่อยที่สุด — การเข้าไปแทรกระหว่างที่ repmgr กำลังทำงานทำให้เกิด split-brain ได้ ถ้าคุณ start ppm กลับขึ้นมาเองตอนที่ ppr1 เพิ่ง promote จะมี primary สองตัวพร้อมกันทันที

ห้ามทำเด็ดขาดในนาทีแรก

❌ systemctl start postgresql บน ppm · ❌ repmgr standby promote ด้วยมือ · ❌ restart pgpool · ❌ แก้ .env ให้ชี้ IP ใหม่ (VIP จัดการให้แล้ว)

2

เช็คว่า promote สำเร็จไหม

ssh ovh-ppr1 "sudo -u postgres repmgr cluster show --compact"
ผ่าน = มี primary หนึ่งตัว และ standby ที่เหลือ running ชี้ไปหามัน

ถ้าเห็น ? unreachable ที่ node เดิมคือปกติ (มันดับจริง) แต่ถ้าเห็น primary สองตัว ให้หยุดทุกอย่างแล้ว escalate ทันที — นั่นคือ split-brain

3

เช็คว่า pgpool ตามทันไหม — ขั้นที่คนลืมบ่อยที่สุด

repmgr สำเร็จไม่ได้แปลว่าแอปใช้งานได้ ต้องดูว่า pgpool มองเห็นภาพเดียวกันหรือเปล่า 

psql -h <vip> -p 5432 -U postgres -c "show pool_nodes;"
ต้องเห็นแปลว่า
มี role = primary หนึ่งแถวpgpool รู้แล้วว่าเขียนไปไหน
node ที่ดับ = status downถูกต้อง มันดับจริง
node ที่รอด = status upยังรับ read ได้
replication_state = streamingstandby ตามทัน primary ใหม่แล้ว
ถ้า node ที่ยังมีชีวิตอยู่ขึ้นเป็น down — นี่คือเคสที่ hook ควรแก้ให้ แต่มันพัง

สังเกตจาก status = down แต่ pg_status = up — แก้ตาม Runbook 01 คือ pcp_attach_node ให้ครบทั้ง 3 node ไม่ใช่แค่ตัวที่ผิด

แจ้งทีมว่ากำลังวิ่งบนเครื่องที่เล็กกว่าเดิม

primary ตัวใหม่มี RAM และ CPU ครึ่งเดียวของตัวเดิม (3.9 GB / 2 core เทียบกับ 6.9 GB / 4 core) — ให้เลี่ยงงานหนักทุกชนิด (report ใหญ่, bulk import, migration, re-index) จนกว่าจะกู้ ppm กลับมาและ switch กลับ รายละเอียดใน §08 ข้อ 2

04 — เคส B

pgpool1 (ตัวถือ VIP) ดับ — VIP ย้ายเอง ✅

คำตอบสั้น: ระบบทำงานต่อได้ ไม่ต้องแตะอะไร — watchdog เลือก leader ใหม่จาก wd_priority ที่ตั้งไว้ไม่ซ้ำกัน (pgpool1=3 > pgpool2=2 > pgpool3=1) แล้วยก VIP ขึ้นที่ node ใหม่ ฝั่งแอปไม่ต้องแก้อะไรเพราะยังต่อ IP เดิม

node ที่ดับเหลือกี่ตัวquorum (ต้องการ 2)VIP ไปอยู่ที่ระบบ
pgpool12✅ ครบpgpool2 (priority รองลงมา)ใช้งานได้ปกติ
pgpool2 หรือ pgpool32✅ ครบยังอยู่ที่ pgpool1ใช้งานได้ปกติ ไม่มีอะไรเปลี่ยน
สองตัวพร้อมกัน1❌ ไม่ครบไม่มี — VIP ตกแอปต่อ DB ไม่ได้ทั้งหมด
จุดสำคัญที่ต้องเข้าใจ: pgpool ที่เหลือ 1 ตัวจะไม่ยอมทำงาน

มันไม่ใช่บั๊ก แต่เป็นการป้องกัน split-brain โดยเจตนา — node เดียวไม่มีทางรู้ว่าตัวเอง "รอดอยู่คนเดียว" หรือ "โดนตัดขาดจากคนอื่นที่ยังทำงานกันอยู่" ถ้ามันยก VIP ขึ้นมาเองในกรณีหลัง จะมี VIP สองที่พร้อมกันบนเครือข่ายเดียว ซึ่งเลวร้ายกว่าการไม่มี VIP เลย

แปลว่า: PostgreSQL ทั้ง 3 ตัวสุขภาพดี 100% ก็ยังใช้งานไม่ได้ ถ้า pgpool เหลือตัวเดียว — อย่า reboot pgpool หลายตัวพร้อมกันเด็ดขาด ให้ทำทีละตัวและรอ join กลับครบก่อนเสมอ

วิธีเช็คว่า VIP ย้ายสำเร็จ
# 1) ใครถือ VIP อยู่ตอนนี้ — ต้องเจอที่ node เดียวเท่านั้น
for h in ovh-pgpool1 ovh-pgpool2 ovh-pgpool3; do
  echo -n "$h: "
  ssh $h "ip -4 -o addr show | grep -c '<vip>'"
done

# 2) watchdog เห็นภาพตรงกันไหม + quorum ยังอยู่ไหม
ssh ovh-pgpool2 "sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
  pcp_watchdog_info -h localhost -p 9898 -U pgpool_admin -w -v"
ผ่าน = เห็นแบบนี้

ข้อ 1 ต้องได้ 1 ที่ node เดียว และ 0 ที่เหลือ — ถ้าได้ 1 สองที่คือ VIP ซ้ำ ต้องแก้ทันที · ข้อ 2 ต้องเห็น Quorum state : QUORUM EXIST

→

เอา pgpool ที่ดับกลับเข้า cluster

แค่ start ขึ้นมา มันจะ join เองและรับสถานะจากเสียงข้างมาก — แต่ต้องเช็คสถานะ backend หลัง join เสมอ เพราะไฟล์ pgpool_status เก็บสถานะเก่าข้าม restart และเคยทำให้ backend ค้าง down มาแล้ว (บั๊ก #38) 

ssh ovh-pgpool1 "sudo systemctl start pgpool2"
# รอ ~15 วิ แล้วเช็คว่า 3 view ตรงกัน
psql -h <vip> -p 5432 -U postgres -c "show pool_nodes;"
05 — เคส C

standby ดับ — ระบบไม่สะดุด แต่มีเงื่อนเวลา ⚠️

write ไม่กระทบเลยเพราะ replication เป็น async ส่วน read จะกระจายไปที่ node ที่เหลือ พอ start กลับขึ้นมา auto_failback จะดึงกลับเข้า rotation เอง ภายใน ~10 วินาที (ตั้งแต่แก้บั๊ก #39 เมื่อ 2026-08-31)

แต่ห้ามปล่อยทิ้งไว้นาน — นี่คือกับดักที่จะทำให้ primary ล่มตามไปด้วย

ระบบตั้ง max_slot_wal_keep_size = -1 (ไม่จำกัด) แปลว่า replication slot ของ standby ที่ดับอยู่จะสั่งให้ primary เก็บ WAL ไว้ตลอดไป รอวันที่มันกลับมา — WAL จะกองสะสมใน pg_wal จนกิน disk ของ primary หมด แล้ว primary จะ PANIC และดับ ซึ่งเคยเกิดมาแล้วในเหตุการณ์ restore เมื่อ 2026-08-25

กฎ: ถ้า standby จะดับเกิน 1 วัน ต้องเฝ้าดู disk ของ primary ทุกวัน และถ้าจะเลิกใช้ node นั้นถาวร ต้องลบ replication slot ทิ้งด้วย ไม่ใช่แค่ปิดเครื่อง

คำสั่งเฝ้าระวังระหว่างที่ standby ดับ
# disk ของ primary เหลือเท่าไหร่ + pg_wal โตแค่ไหน
ssh ovh-ppm "df -h / | tail -1; sudo du -sh /var/lib/postgresql/18/main/pg_wal"

# slot ไหนไม่ active และค้าง WAL ไว้เท่าไหร่
ssh ovh-ppm "sudo -u postgres psql -tAc \
  \"select slot_name, active, \
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) as wal_held \
    from pg_replication_slots order by 3 desc;\""
ถ้าต้องเลิกใช้ standby ตัวนั้นถาวร
ssh ovh-ppm "sudo -u postgres psql -c \
  \"select pg_drop_replication_slot('<slot-name>');\""
ssh ovh-ppm "sudo -u postgres repmgr standby unregister --node-id=<id>"

standby ดับ 1 ตัว✅ ปกติstart กลับ · เฝ้า disk primary ถ้าดับนาน (§05)
standby ดับ 2 ตัว✅ write ปกติread ทั้งหมดกองที่ primary · ไม่มี standby ให้ promote แล้ว ถ้า primary ดับต่อคือดับยาว
primary + standby 1 ตัว⚠️ ขึ้นกับจังหวะrepmgr ต้องมี standby ที่มองเห็นกันเพื่อ promote — ถ้าเหลือตัวเดียวอาจไม่ promote เอง ต้อง promote ด้วยมือ (ดูล่าง)
ทั้ง 3 DB node❌ ดับสนิทกู้ตามลำดับ: primary ก่อน → standby ตาม → เช็ค pgpool ตามทีหลัง
promote ด้วยมือ — ใช้เมื่ออัตโนมัติไม่ทำงานเท่านั้น

ก่อนกดต้องมั่นใจว่า primary เดิมตายจริงและจะไม่ฟื้นขึ้นมาเอง — ถ้ามันกลับมาทีหลังโดยที่ยังคิดว่าตัวเองเป็น primary คือ split-brain และข้อมูลจะแตกเป็นสองสาย ทางที่ปลอดภัยคือปิดเครื่องเดิมให้แน่ใจก่อน แล้วค่อย promote

  echo -n "$h: "

07 — กู้ node กลับเข้า cluster

primary เก่ากลับมาแล้ว ทำยังไงต่อ

primary เก่ากลับเข้ามาเป็น primary เองไม่ได้ ต้องเข้ามาเป็น standby ของเจ้านายใหม่ก่อน ขั้นตอนนี้เรียก rejoin และใช้ pg_rewind ย้อน transaction ที่มันเขียนไว้แต่คนอื่นไม่มี — ระบบนี้พร้อมใช้ pg_rewind แล้ว เพราะ data_checksums = on (ตรวจแล้ว)

1

ห้าม start PostgreSQL บนเครื่องเก่าก่อน rejoin

ถ้ามัน start ขึ้นมาในฐานะ primary แม้แค่ไม่กี่วินาที ก็รับ write ได้แล้ว — ให้ปล่อยให้ service ดับไว้แล้วสั่ง rejoin ซึ่งจะ start ให้เองในโหมดที่ถูกต้อง

2

ลองแบบ dry-run ก่อนเสมอ

ssh ovh-ppm "sudo -u postgres repmgr node rejoin -f /etc/repmgr.conf \
  -d 'host=<new-primary> user=repmgr dbname=repmgr' --force-rewind --dry-run"

--dry-run บอกได้ว่าจะสำเร็จไหมโดยไม่แตะข้อมูลจริง ถ้าขึ้น error เรื่อง pg_rewind หา config ไม่เจอ ให้ดูบั๊ก #29/#30 ใน คู่มือฉบับเต็ม (Debian แยก config ออกจาก data directory ต้องมี symlink)

3

รันจริง แล้วยืนยันทั้งสองชั้น

# ตัดคำว่า --dry-run ออก
ssh ovh-ppm "sudo -u postgres repmgr node rejoin -f /etc/repmgr.conf \

# ชั้นข้อมูล: ต้องเห็น 3 node running

# ชั้นทางเดิน: ต้องเห็น up ครบ + replication_state = streaming

ถ้า rejoin ไม่สำเร็จ — ทางถอยที่ใช้ได้เสมอ

ลบ data directory ทิ้งแล้ว clone ใหม่จาก primary ปัจจุบันด้วย repmgr standby clone — ช้ากว่า (ต้องดึงข้อมูลทั้ง 20 GB ใหม่) แต่ได้ผลแน่นอนกว่า อย่าเสียเวลาไล่ pg_rewind เกิน 2 รอบ

4

สลับกลับให้ ppm เป็น primary เหมือนเดิม (ไม่รีบ)

เนื่องจาก ppm มีสเปกใหญ่กว่า (§08 ข้อ 2) ควรสลับกลับเมื่อสะดวก แต่ทำในช่วงที่ไม่มี traffic เพราะเป็นการ failover ตั้งใจอีกรอบ — connection จะหลุดอีกครั้ง

08 — ช่องโหว่ที่ต้องปิด

เรียงตามผลกระทบต่อ HA

ข้อ 0 — ใหญ่กว่าทุกข้อในหน้านี้รวมกัน: VM ทั้ง 7 ตัวอยู่บนเครื่องเดียว

ตรวจเมื่อ 2026-09-01: hypervisor ไม่ได้เป็น PVE cluster และมี node เดียว — pvecm status ตอบ corosync.conf does not exist - is this node part of a cluster? และ pvesh get /nodes คืนมา node เดียว บนนั้นรัน ppm + ppr1 + ppr2 + pgpool1/2/3 + เครื่องแอป ครบทั้งชุด

แปลว่ากลไกทุกอย่างในเอกสารนี้ — repmgr promote, watchdog VIP, quorum, auto_failback — ป้องกันได้เฉพาะกรณี VM ตัวใดตัวหนึ่งตาย ถ้า hypervisor ดับ PostgreSQL ตายพร้อมกันสามตัว pgpool ตายพร้อมกันสามตัว และแอปตายด้วย — ไม่มีอะไรเหลือให้ fail over ไปหา

และนี่ไม่ใช่ความเสี่ยงเชิงทฤษฎี — มี Runbook 03: Proxmox Host รีบูตเอง (CPU MCE) เขียนไว้แล้วจากเหตุการณ์จริงว่า "Hypervisor ดับเองไม่มี shutdown log · VM ตายพร้อมกันหมด"

พูดตรงๆ: โหมดความล้มเหลวที่เคยเกิดขึ้นจริง คือโหมดเดียวที่สถาปัตยกรรมนี้รับไม่ได้ ข้อ 1–6 ข้างล่างทั้งหมดคือการทำให้ HA ระดับ VM สมบูรณ์ ซึ่งคุ้มค่าและทำไปแล้วเป็นส่วนใหญ่ — แต่ไม่มีข้อไหนช่วยตอน host ดับ ทางแก้มีทางเดียวคือกระจาย VM ออกไปมากกว่าหนึ่ง hypervisor อย่างน้อยให้ standby หนึ่งตัวกับ pgpool หนึ่งตัวอยู่คนละเครื่องกับ primary

Event hook หลัง failover — แก้แล้ว 2026-09-01

/usr/local/bin/repmgr-pgpool-reattach.sh ยิง pcp_attach_node ไปที่ pgpool ทั้ง 3 ตัวหลัง promote/follow เพื่อเคลียร์สถานะค้าง — เคยพบว่า auth ไม่ผ่านทั้งสามปลายทาง (credential drift รอบที่สอง ต่อจากบั๊ก #32/#37) แก้โดย standardize รหัส PCP ใหม่ให้ตรงกันทั้ง 6 เครื่อง: pcp.conf บน pgpool ทั้ง 3 + .pcppass ของ postgres และ root บนทุกเครื่องที่ต้องเรียก pcp แล้ว reload ไล่จาก priority ต่ำสุดไปหา VIP leader เป็นตัวสุดท้าย

กันไม่ให้เกิดอีก 2 ทาง: (1) ใส่การทดสอบ 9 เส้นทางข้างบนเข้าไปใน checklist หลัง deploy ทุกครั้ง — มันเป็นคำสั่งอ่านอย่างเดียว รันได้ตลอดเวลา · (2) ตั้ง alert บน pgpool_watchdog_scrape_success == 0 ซึ่งใช้ credential เส้นทางเดียวกัน พอ PCP พังเมื่อไหร่ metric ตัวนี้จะเป็น 0 ทันที ทำให้ credential drift กลายเป็นสิ่งที่มองเห็นได้ แทนที่จะเงียบ

HA ที่แท้จริงแปลว่า "ล้มแล้วยังรับงานเท่าเดิมได้" — เดิม failover สำเร็จแต่กำลังหายครึ่งหนึ่งทันที บน DB 20 GB ที่พึ่ง OS page cache เป็นหลัก (shared_buffers ตั้งไว้แค่ 128 MB) RAM น้อยลงครึ่ง = cache hit ตกและ I/O พุ่ง พอดีกับตอนที่ระบบเครียดที่สุด

วิธีที่ใช้: ให้ทั้งสาม "แชร์" RAM ด้วย balloon แทนการจองตายตัว

host มี RAM ไม่พอให้ทั้งสามตัวจอง 7,168 ตายตัว (ดูข้อ 6) จึงตั้ง standby เป็น ceiling 7,168 / floor 4,096 — commitment ที่การันตีเท่าเดิมกับก่อนแก้ทุกประการ แต่เพดานสูงขึ้นเท่า primary แล้ว pvestatd เกลี่ยให้ตามที่ host ว่าง

จังหวะ failover คือตอนที่กลไกนี้ได้ผลที่สุด — primary ที่ตายคืน RAM 7 GB ให้ host พอดี ตัวที่ถูก promote จึงขยายขึ้นไปกินได้จริง ไม่ใช่แค่ตัวเลขบนกระดาษ · ส่วน ppm คง balloon: 0 ไว้ เพื่อไม่ให้ primary โดนบีบไม่ว่ากรณีใด

ข้อแลกเปลี่ยนที่ต้องรู้

balloon ทวง RAM คืนโดย "พอง" อยู่ในตัว guest ซึ่งไล่ page cache ทิ้ง — คือสิ่งที่ PostgreSQL พึ่งพาที่สุดในระบบนี้ ตั้ง floor ไว้ที่ 4,096 (= ค่าที่ใช้อยู่เดิม) จึงสำคัญ เพราะรับประกันว่า แย่ที่สุดก็ไม่แย่กว่าก่อนแก้ · และการพองขึ้นไม่ทันที pvestatd เกลี่ยทีละขั้น หลัง failover จะไต่ขึ้นในเวลาราวหนึ่งถึงสองนาที ไม่ใช่กระโดดทันที

3

ไม่มี WAL archive — มีแค่ replication ไม่มี PITR

archive_mode = off แปลว่ากู้ย้อนเวลาไม่ได้ replication ป้องกันเครื่องพัง แต่ไม่ป้องกัน DELETE ผิดตาราง — คำสั่งลบจะถูก replicate ไปทั้ง 3 node ภายในมิลลิวินาที ถ้าไม่มี backup แยกก็คือหายถาวร ต้องยืนยันว่ามี logical backup (pg_dump) นอกคลัสเตอร์ และเคยทดสอบ restore จริง ไม่งั้นถือว่าไม่มี backup

ทั้ง 3 node ตั้ง priority=100 ตอนนี้ยังไม่เป็นปัญหาเพราะ ppr1/ppr2 สเปกเท่ากัน แต่ทันทีที่แก้ข้อ 2 หรือเพิ่ม node ที่ตั้งใจให้เป็น reporting replica ควรตั้งให้ต่างกัน เพื่อคุมได้ว่าตัวไหนควรขึ้นเป็น primary (เลขสูงกว่าชนะ · ตั้ง 0 = ห้าม promote)
