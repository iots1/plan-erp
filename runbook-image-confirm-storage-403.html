Runbook · Application / Storage

อัปโหลดรูปสินค้าไม่สำเร็จ
เพราะ storage ตอบ 403 ให้ HeadObject

ไฟล์อัปขึ้น bucket เรียบร้อยแล้ว แต่ขั้น confirm บอกว่า "ยังไม่ได้อัปโหลด" — และการอัปใหม่ตามที่ข้อความบอกก็ไม่ช่วย เพราะปัญหาไม่ได้อยู่ที่ไฟล์เลย

Severity: High (ผู้ใช้เพิ่มรูปสินค้าไม่ได้) Est. fix time: 10–15 นาที (แก้ config + restart)
1 — อาการ (Symptom)

ข้อความที่เห็นจริง มี 2 แบบ ขึ้นกับว่าโค้ดเวอร์ชันไหน

ทั้งสองแบบคืออาการของสาเหตุเดียวกัน — ต่างกันแค่ว่าเวอร์ชันที่รันอยู่รายงานมันตรงหรือไม่ตรง ผู้ใช้ทำอะไร: เข้าแก้ไขสินค้าที่มีอยู่แล้ว แล้วเพิ่มรูปภายหลัง (Flow A · presigned upload)

แบบที่ 1 · ก่อนแก้ — ข้อความชี้ไปคนละทางกับสาเหตุ
// POST /products/:id/images  → 400
// (message จริงเป็นบรรทัดเดียว ตัดบรรทัดที่นี่เพื่อให้อ่านได้)
{
  "status": {
    "code": 400,
    "message": "No uploaded object found at '<object-key>'
       — upload the file to the presigned URL before confirming."
  },
  "errors": [ { "code": "BAD_REQUEST", "title": "Invalid Request" } ]
}
กับดักของข้อความนี้

มันบอกให้ไป "อัปโหลดไฟล์ก่อน" ซึ่งเป็นสิ่งที่ทำไปแล้ว และทำซ้ำอีกกี่ครั้งก็ไม่หาย — คนที่เจอครั้งแรกจะเสียเวลาไล่หาว่าทำไมไฟล์ "ไม่ขึ้น" ทั้งที่มันขึ้นไปนอนอยู่ใน bucket เรียบร้อยแล้ว

แบบที่ 2 · หลังแก้ — ข้อความตรงตามความจริงแล้ว (แต่ยังไม่หาย)
// POST /products/:id/images  → 503
{
  "status": {
    "code": 503,
    "message": "Failed to verify the uploaded object
       — the storage service is unavailable."
  },
  "errors": [ { "code": "SERVICE_UNAVAILABLE", "title": "Service Unavailable" } ]
}

เห็น 503 = ดี แปลว่าเวอร์ชันที่รันอยู่มี fix เรื่องการแยกประเภท error แล้ว และมันกำลังบอกความจริงว่า "ตรวจสอบไม่ได้" ไม่ใช่ "ไม่มีไฟล์" — เหลือแค่ไปแก้ที่ต้นเหตุตาม §5

อ่าน detail ของ 503 ให้ดี — มันมี 2 ที่มา

ข้อความข้างบน ("Failed to verify the uploaded object…") เป็นของ ผู้เรียก ไม่ใช่ของ storage-bc — StorageObjectService พูดประโยคนี้เมื่อ RPC ไม่ได้คำตอบที่ใช้ได้เลย ถ้า envelope ของ error เดินทางข้าม hop มาครบ คุณจะเห็นคำของ storage-bc เองแทน เช่น "Storage rejected the request to verify the file." (403) หรือ "An unexpected error occurred while trying to verify the file." · เห็นประโยคของผู้เรียกทั้งที่ storage-bc log 403 ไว้จริง = มีบั๊กชั้นที่ 4 ซ้อนอยู่ (ดู §4) — และเป็นเหตุผลที่เคสนี้ถูกวินิจฉัยผิดไปหนึ่งรอบว่า "RPC ไปไม่ถึง storage"

บรรทัด log ที่ชี้ขาด (storage-bc)
{"message":"Failed to verify file","context":{
  "key":"inventory/products/<id>/<name>.webp",
  "status":403,            // ← ไม่ใช่ 404
  "error_name":"Unknown"    // ← S3 parse error body ไม่ได้ = body ไม่ใช่ XML ของ S3
},"details":"UnknownError"}
สองค่านี้คือคำวินิจฉัยทั้งหมด

status + error_name ถูกเพิ่มเข้า log เพราะขาดตัวใดตัวหนึ่งก็แยกไม่ออก: 403 ที่ชื่อ SignatureDoesNotMatch (credential ผิดจริง) กับ 403 ที่ไม่มีชื่อ (มีอะไรขวางอยู่หน้า bucket) ต้องแก้คนละทางกันคนละเรื่อง · ถ้า log ของคุณยังไม่มี 2 field นี้ แปลว่ารันเวอร์ชันเก่ากว่า fix

2 — ผลกระทบ (Impact)

ผู้ใช้เพิ่มรูปไม่ได้ และ error โยนความผิดให้ผู้ใช้

ด้านผลกระทบ
ฟีเจอร์เพิ่ม/เปลี่ยนรูปสินค้าของสินค้าที่มีอยู่แล้ว (Flow A) ล้มเหลว — อัตราล้มเหลวไม่คงที่ วัดได้ตั้งแต่ ~1 ใน 6 จนถึงล้มทุกครั้ง
ข้อมูลไม่เสียหาย — ไฟล์อยู่ใน bucket ครบ เพียงไม่มีแถวใน product_images ชี้ถึง
ขยะที่ทิ้งไว้object ที่อัปแล้วแต่ confirm ไม่ผ่านจะค้างใน bucket โดยไม่มีใครอ้างถึง (orphan) — ไม่มีใครลบให้
Flow B (multipart create)ไม่กระทบ — ไม่ได้ใช้ HeadObject ยืนยัน จึงยังสร้างสินค้าพร้อมรูปได้ปกติ
ทรัพยากรอื่นกระทบทุก resource ที่สืบทอด BaseAttachmentService เท่ากันหมด — receipt / quotation / purchase-order attachments ไม่ใช่แค่รูปสินค้า
รีบแค่ไหน

ไม่ใช่ outage — ระบบอื่นทำงานปกติหมด แต่เป็นงานที่ผู้ใช้ทำไม่ได้และแก้เองไม่ได้ด้วย เพราะข้อความบอกให้ทำสิ่งที่ไม่ช่วย ควรแก้ภายในวันเดียวกัน · ถ้าต้องบรรเทาเฉพาะหน้าให้ผู้ใช้ใช้ Flow B (สร้างสินค้าพร้อมแนบรูปในคลิกเดียว) ไปก่อน

3 — วินิจฉัย (Diagnosis)

พิสูจน์ให้ได้ก่อนว่า "ไฟล์อยู่จริง แต่ storage ตอบ 403"

1

อ่าน log ของ storage-bc — ดู status กับ error_name

grep -o '{"message":"Failed to verify file".*}' /root/.pm2/logs/storage-error-*.log | tail -3

status: 403 → ใช่เคสนี้ ทำต่อข้อ 2 · status: 404 → ไม่ใช่เคสนี้ ไฟล์ไม่มีอยู่จริง ไปดูว่าขั้น PUT ของ client ล้มเหลวหรือไม่ · ไม่มี log เลย → RPC ไม่ถึง storage-bc ให้เช็ค consumer ของ erp_storage_queue ตาม RabbitMQ Reliability Guide

2

ยืนยันว่า object อยู่ใน bucket จริง

# ดูจากในคอนเทนเนอร์ของ object store ตรง ๆ — ไม่ผ่าน API ใด ๆ
docker exec <minio-container> ls -la '/data/<bucket>/inventory/products/<product-id>/<object-key>'

เห็นไฟล์ xl.meta = object มีจริง (MinIO เก็บไฟล์เล็กแบบ inline ไว้ใน metadata นี้ จึงไม่เห็นไฟล์ข้อมูลแยก — เป็นเรื่องปกติ ไม่ใช่ความผิดปกติ)

3

ยิง HeadObject ตรง ๆ เทียบ 2 endpoint

นี่คือขั้นที่ชี้ขาด — ยิงคำสั่งเดียวกัน key เดียวกัน credential เดียวกัน ต่างกันแค่ปลายทาง ให้ยิงหลายครั้ง เพราะอาการไม่คงที่ ยิงครั้งเดียวได้ 200 ไม่ได้แปลว่าไม่มีปัญหา 

# ผ่าน public domain (มี CDN/WAF/reverse proxy คั่น) — ยิง 6 ครั้ง
for i in $(seq 6); do aws s3api head-object \
  --endpoint-url https://files.example.com \
  --bucket <bucket> --key '<object-key>' >/dev/null 2>&1; echo $?; done

# ผ่าน endpoint ภายใน (ตรงถึง object store) — ยิง 6 ครั้ง
for i in $(seq 6); do aws s3api head-object \
  --endpoint-url http://<storage-host>:9000 \
  --bucket <bucket> --key '<object-key>' >/dev/null 2>&1; echo $?; done
ผลที่ยืนยันว่าเป็นเคสนี้

internal ผ่านทุกครั้ง · public มี 403 ปนมาเป็นบางครั้ง (ครั้งที่วัดจริง: internal 6/6 สำเร็จ · public สลับ 403/200 และช่วงที่หนักที่สุดคือ 403 ทุกครั้ง) — ถ้าทั้งสอง endpoint ให้ผลเหมือนกัน แปลว่าไม่ใช่เคสนี้

4

ดูว่า storage-bc ถูกตั้งให้ยิงไปทางไหน

grep -E '^STORAGE_S3_(PUBLIC_)?ENDPOINT=' <repo-dir>/.env

ถ้า STORAGE_S3_ENDPOINT เป็น public domain = ยืนยันสาเหตุตาม §4 · ถ้าเป็น endpoint ภายในอยู่แล้วแต่ยัง 403 ให้ดู error_name จากข้อ 1 อีกครั้ง — ถ้าเป็นชื่อ auth จริง (SignatureDoesNotMatch, InvalidAccessKeyId) แปลว่า credential ผิดจริง ไม่ใช่เคสนี้

⚠️ 4 ทางที่เคยเดินผิดในเคสนี้ — ข้ามไปได้เลย

ทั้งสี่ข้อดูน่าเชื่อมาก และแต่ละข้อกินเวลาไปหลายสิบนาที บันทึกไว้เพื่อให้คนถัดไปไม่ต้องเดินซ้ำ

เบาะแสที่ดูน่าเชื่อทำไมไม่ใช่
repro ด้วย cURL แล้วเห็นว่า ไม่มีเนื้อไฟล์ ใน multipart body DevTools Copy as cURL ไม่ copy เนื้อไฟล์ binary ของ FormData มาให้ — field ไฟล์จะว่างเสมอไม่ว่า browser จะส่งจริงหรือไม่ · อย่าใช้วิธีนี้ทดสอบ flow ที่มีไฟล์แนบ ให้ดู "Request payload size" สด ๆ ใน Network tab แทน
log ของ object store มี drive path full เป็นเหตุการณ์เก่า (คนละสัปดาห์) และ MinIO ใช้ logOnceIf จึง log ซ้ำแค่ครั้งเดียว ทำให้ดูเหมือนเพิ่งเกิด · เช็ค df -h กับ log ของวันนี้ก่อนเชื่อ
RabbitMQ มี 2 vhost ชื่อ queue ซ้ำกัน — ตัวหนึ่งไม่มี consumer เลย vhost ที่ไม่มี consumer เป็นของ local dev ของนักพัฒนา ไม่ใช่ที่ deploy ใช้ · ยืนยันด้วย RABBITMQ_VHOST ใน .env ของเครื่องนั้น ไม่ใช่ของ repo บนเครื่องตัวเอง
presigned URL มี x-amz-checksum-crc32=AAAAAA== (= checksum ของไฟล์ว่าง) AWS SDK รุ่นใหม่ใส่ checksum นี้ให้เองตอน presign (ตอนนั้นยังไม่มี body ให้คำนวณ) · ดูน่าสงสัยมากแต่ไม่ได้ทำให้ PUT ล้มเหลว — PUT ได้ 200 และไฟล์ลง bucket ครบ
บทเรียนของ §3

ทุกทางที่ผิดข้างบนถูกตัดออกได้ด้วยหลักฐานชิ้นเดียวกัน: ยิง HeadObject ตรง ๆ เทียบ 2 endpoint (ข้อ 3) ถ้าทำข้อนี้ก่อน จะประหยัดเวลาไปได้มาก — เพราะมันแยก "ของอยู่ไหม" ออกจาก "เส้นทางไปถึงของมีปัญหาไหม" ในคำสั่งเดียว

ชั้น 3 · ต้นเหตุ

endpoint เดียวถูกใช้ 2 หน้าที่

presigned URL ต้อง เป็น public domain (browser ต้องเข้าถึงได้) แต่ API call ของ service เอง ไม่ควร ออกไปทางนั้น — เอา WAF มาขวาง request ที่วิ่งอยู่ใน DC และ WAF มีสิทธิ์ตอบ 403 กับ request ที่เซ็นถูกต้องเมื่อไหร่ก็ได้

ชั้น 2 · ตัวบัง

เชื่อชื่อ error แทน status

HTTP HEAD ไม่มี response body ตามสเปก SDK จึงประกอบ error จาก status line ได้อย่างเดียว และใช้ชื่อ NotFound กับหลายสถานะ — 403 จึงกลายเป็น "ไม่มีไฟล์"

ชั้น 1 · ตัวบัง

null สองความหมาย

sendWithContext เป็น no-throw: คืน defaultValue เมื่อ RPC ล้มเหลว — แต่ถ้า defaultValue เป็น null และ callee ก็คืน null ได้เอง ผู้เรียกจะแยกไม่ออก

ชั้น 4 · ตัวบัง — พบเพิ่ม 2026-09-09

exception filter ของ microservice ไม่เคยถูกผูกเลย

app.connectMicroservice() เรียก registerListeners() + setIsInitialized(true) ทันทีก่อน return และนั่นคือขั้นที่ผูก handler เข้ากับ enhancer ที่มีอยู่ ณ วินาทีนั้น · อะไรที่ลงทะเบียนบน instance หลังจากนั้น จะถูกทิ้งเงียบ ๆ — Nest แค่ warn ตอน boot แล้วไปต่อ: 

[Nest] WARN [NestMicroservice] Cannot apply global exception filters:
       registration must occur before initialization.

ผลคือ exception ทุกตัวจาก @MessagePattern — รวมทั้ง NotFoundException ธรรมดา — ออกไปเป็น envelope default ของ Nest ({"status":"error","message":"Internal server error"}) ผู้เรียกอ่านไม่ออกจึงตกไปทาง defaultValue · ชั้นนี้ทำให้ชั้น 3 มองไม่เห็นทั้งหมด: storage-bc รายงาน 403 เป็น 503 พร้อมคำอธิบายที่ถูกต้อง แต่ผู้ใช้กลับได้ประโยคของผู้เรียกที่บอกว่า "ติดต่อ storage ไม่ได้" ทำให้ไล่ผิดทางไปหาเรื่อง RabbitMQ ทั้งที่ RPC เดินทางถึงและตอบกลับครบทุกครั้ง

เส้นแบ่งที่ต้องรักษาไว้

503 = ยังตอบไม่ได้ (retry ได้) · 400/404 = ตอบแล้วว่าไม่มี (retry ไปก็ได้คำตอบเดิม) — ถ้าสองอย่างนี้ยุบเป็นค่าเดียว ผู้เรียกจะเลือกทางผิดเสมอ และผู้ใช้จะได้คำแนะนำที่แก้ปัญหาไม่ได้ · กฎเต็มดูที่ Backend Convention §08

5 — การแก้ไข (Fix)

แก้ config ก่อน (ทำให้หายทันที) แล้วค่อยดูว่าโค้ดครบหรือยัง

1

แยก endpoint ออกเป็น 2 ตัวใน .env

# สิ่งที่ storage-bc เรียกเอง (HeadObject/PutObject/DeleteObject) — ต้องเป็น endpoint ภายใน
STORAGE_S3_ENDPOINT=http://<storage-host>:9000
# origin ที่ถูกเซ็นลงใน presigned URL ที่ส่งให้ browser — ต้องเป็น public domain
STORAGE_S3_PUBLIC_ENDPOINT=https://files.example.com
⚠️ .env บนเครื่องอาจไม่ใช่ของจริง

ถ้า deploy pipeline มี step ที่เขียน .env จาก secret (ในโปรเจกต์นี้คือ Sync .env from GitHub Environment secret ที่อ่านจาก ENV_FILE) การแก้มือบนเครื่องจะถูกทับทุก deploy — แก้ที่ secret ต้นทางด้วย ไม่งั้นอาการจะกลับมาเองแบบไม่มีใครเข้าใจว่าทำไม · วิธีจับ: ดู stat -c '%y' .env ถ้า mtime ตรงกับเวลา deploy พอดี = ถูกเขียนทับ

2

restart เฉพาะ storage-bc

pm2 restart storage --update-env

# ยืนยันว่า restart จริง (uptime ต้องรีเซ็ต, restarts ต้องเพิ่ม 1)
pm2 list | grep storage

ต้องมี --update-env — process ที่รันอยู่ไม่เคยอ่าน .env ซ้ำ การแก้ไฟล์เฉย ๆ ไม่มีผลจนกว่าจะ restart

3

4

(ทางเลือก) ให้ frontend retry ขั้น confirm

เพราะพิสูจน์แล้วว่าอาการหายเองเมื่อลองใหม่ การ retry ทำให้ผู้ใช้ไม่ต้องเจอ error เลยในเคส transient แต่ต้องแคบ — retry เฉพาะ 503:

statusretry?เพราะ
503✅ retryการันตีว่ายังไม่เขียน DB — HeadObject ถูกเช็คก่อน insert เสมอ
400❌ ไม่ retryเป็นคำตอบชี้ขาดว่าไม่มีไฟล์ retry ไปก็ได้คำตอบเดิม เสียเวลาเปล่า
500❌ ไม่ retryอาจ insert แถวสำเร็จไปแล้ว retry จะได้รูปซ้ำ 2 ใบ

และอย่า retry ตั้งแต่ขั้นขอ presigned URL — จะได้ object_key ใหม่ ทำให้ไฟล์ที่อัปไปแล้วกลายเป็นขยะค้าง bucket

6 — ยืนยัน + ป้องกัน (Verify / Prevent)

ยิงครบ flow หลายรอบ — รอบเดียวไม่พอ

อาการนี้ไม่คงที่ เคยวัดได้ตั้งแต่ล้ม 1 ใน 6 จนถึงล้มทุกครั้ง — ทดสอบรอบเดียวผ่านแล้วสรุปว่าหาย คือวิธีที่ทำให้เชื่อว่าหายทั้งที่ยังไม่หาย ให้ยิงอย่างน้อย 5 รอบติดกัน 

# ครบ flow: presigned-url → PUT → confirm · ต้องได้ 201 ทุกรอบ
for i in $(seq 5); do
  R=$(curl -s -X POST "$API/products/$PID/images/presigned-url" \
        -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
        --data-raw '{"original_name":"t.webp","mime_type":"image/webp"}')
  U=$(echo "$R" | jq -r .data.attributes.upload_url)
  K=$(echo "$R" | jq -r .data.attributes.object_key)
  curl -s -o /dev/null -X PUT "$U" -H 'Content-Type: image/webp' --data-binary @t.webp
  curl -s -o /dev/null -w "รอบ $i: %{http_code}\n" -X POST "$API/products/$PID/images" \
    -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    --data-raw "{\"bucket\":\"$BUCKET\",\"object_key\":\"$K\",\"original_name\":\"t.webp\",\"mime_type\":\"image/webp\"}"
done
✅ หายจริง
  • confirm ได้ 201 ครบ 5/5
  • upload_url ยังเป็น public domain (ไม่ใช่ IP ภายใน)
  • ไม่มีบรรทัด Failed to verify file ใหม่ใน log
❌ พลาดที่ตรวจง่าย ๆ
  • upload_url กลายเป็น IP ภายใน = ตั้ง PUBLIC_ENDPOINT ผิด/ขาด → browser จะ PUT ไม่ได้
  • ลืมลบรูปทดสอบที่ confirm สำเร็จออกจากสินค้าจริง
  • แก้ .env แต่ไม่ restart → ยังไม่มีผล
