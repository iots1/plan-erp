01 — Overview & Principles

ภาพรวม & หลักการ

เอกสารนี้สรุป convention กลางขององค์กร สำหรับทุกบริการ NestJS — ตั้งแต่การตั้งชื่อไฟล์/คลาส/ตาราง ไปจนถึงรูปแบบ Response, การ throw error และ Query Params เป้าหมายคือความ สม่ำเสมอ ทำให้ทั้ง codebase และ schema เข้าใจตรงกัน อ่านโค้ดแล้วรู้เจตนาทันที

NAMING

Singular Module · Plural Controller/Service · snake_case property/column · kebab-case ไฟล์/โฟลเดอร์

RESPONSE

JSON:API envelope: status · data|errors · meta · links — ห่ออัตโนมัติด้วย TransformInterceptor

ERRORS

Exception เฉพาะเจาะจงเสมอ · code 6 หลัก · controller ไม่ catch ปล่อยขึ้น global filter

CORE PRINCIPLE

โครงสร้าง envelope ชัดเจน · ส่ง อย่างใดอย่างหนึ่งระหว่าง data กับ errors ไม่ปนกัน · ใช้ exception ที่เจาะจงแทน Error ทั่วไป · ใส่ context เต็มใน exception · ไม่ leak ข้อมูล sensitive (password/token/internal) · log ทุกอย่างภายใน

02 — NestJS Naming Convention

การตั้งชื่อ (NestJS)

Module เป็น เอกพจน์ (แคปซูลเดียวของฟีเจอร์) ส่วน Controller/Service เป็น พหูพจน์ (จัดการหลาย endpoint/method) · Property ของ Entity/DTO เป็น snake_case เพื่อ map 1-to-1 กับคอลัมน์ PostgreSQL ลดการใช้ @Column({ name: '…' })

CategoryPatternExamples

ControllerPlural + ControllerGoodsReceiptsController, PatientsController
ServicePlural + ServiceGoodsReceiptsService, PatientsService
Entity / DTO (class)Singular · PascalCaseGoodsReceipt, CreateGoodsReceiptDTO
Propertysnake_caseimport_cost, lot_number, is_active
EnumSingular · PascalCaseGoodsReceiptStatus, QueueStatus
Folderkebab-casegoods-receipt, patient-change-request

ตัวอย่าง · Entity property = snake_case (1-to-1 กับคอลัมน์)
@Entity('goods_receipts')
export class GoodsReceipt {
  @PrimaryGeneratedColumn('uuid')  id: string;
  // snake_case → ไม่ต้องใส่ @Column({ name: '...' })
  @Column()  po_id: string;
  @Column()  supplier_id: string;
  @Column({ type: 'numeric' })  import_cost: number;
  @Column()  lot_number: string;
  @Column({ type: 'date', nullable: true })  expiry_date: Date;
  @Column({ default: false })  is_cancelled: boolean;
}
Class vs Property

คลาสเป็น PascalCase เอกพจน์ (มาตรฐาน OOP/NestJS) แต่ property เป็น snake_case (มาตรฐาน PostgreSQL) — สองระดับนี้ต่างกันโดยตั้งใจ

RULE · interface อยู่ไฟล์ของตัวเอง ห้ามอยู่ในไฟล์ที่มี class

ไฟล์ไหนประกาศ class (service, controller, guard, filter, interceptor, entity, DTO, module, abstract) ห้ามมี interface อยู่ในไฟล์เดียวกันเลย ไม่ว่าจะ export หรือไม่, เล็กหรือใหญ่, เป็น payload หรือแค่ shape ของ raw SQL row — ย้ายไป interfaces/<kebab-name>.interface.ts ใน module เดียวกัน ตั้งชื่อ I<PascalName> พร้อม doc comment บอกว่าทำไมถึงไม่ใช่ entity ตรง ๆ · shape ที่อธิบายข้อมูลของ BC อื่นไปอยู่ integrations/<other-bc>/interfaces/ แทน
ข้อยกเว้นเดียว — ไฟล์ที่ไม่มี class เลย: libs/contracts/src/*.contract.ts, *-message-patterns.ts และ *.util.ts ที่ interface นั้นคือ parameter/return type ของฟังก์ชันในไฟล์เอง (พอมีคนอื่น import shape ไปใช้โดยไม่ได้ import ฟังก์ชันด้วย = มันเลิกเป็น signature แล้ว ต้องย้ายออก)
ทุก interface ต้องมี prefix I ไม่ว่าจะอยู่ไฟล์ไหน · ไม่มี ESLint rule คุม (naming-convention ไม่ได้เปิดไว้) — ตัวบังคับคือ hook scripts/hooks/convention-guard.mjs กับรีวิว

RULE · ข้อความ Swagger อยู่ใน constants ไม่ inline ใน controller

@ApiOperation/@ApiParam/@ApiQuery ต้อง import ค่ามาจาก constants/<resource>.swagger.ts (ตัวแปร UPPER_SNAKE_CASE ตัวละหนึ่งข้อความ) · ข้อความที่ใช้ร่วมกันหลาย controller ใน BC เดียวกันไปอยู่ constants/swagger-common.ts

03 — Boolean & Status Prefixes

05 — API Response (JSON:API)

โครงสร้าง Response

ทุก Response ห่อด้วย envelope แบบ JSON:API: status · data หรือ errors (อย่างใดอย่างหนึ่ง) · meta · links — ทำงานอัตโนมัติผ่าน TransformInterceptor เมื่อ controller ประกาศ @ResourceType()

โครง envelope · Success
{
  "status": { "code": 200000, "message": "Request Succeeded" },
  "data": {
    "type": "goods-receipts",          // จาก @ResourceType('goods-receipts')
    "id": "uuid-grn",
    "attributes": {                    // snake_case + i18n nested object
      "status": "SUBMITTED",
      "po_id": "uuid-po", "import_cost": 98.5,
      "remark": { "th": "ของครบ", "en": null },
      "product": { "name": { "th": "ยาเซโกร", "en": "Zagro" } }
    }
  },
  "meta": { "timestamp": "2026-07-14T10:30:00.000Z" },
  "links": { "self": "/inventory/goods-receipts/uuid-grn" }
}
SINGLE

data: { type, id, attributes }

COLLECTION

data: [ { type, id, … } ]

PAGINATED

data: [ … ] + meta.pagination

@ResourceType จำเป็นบนทุก Controller
@Controller('goods-receipts')
@ResourceType('goods-receipts')   // ✅ กำหนด type ใน response · ถ้าไม่ใส่ = คืน raw ไม่ transform
export class GoodsReceiptsController {
  @Get()  findAll() { return this.service.findAll(); }
}
STATUS CODE · 6 หลัก

status.code เป็นเลข 6 หลัก = HTTP status × 1000 + serial ทุก response ทั้งสำเร็จและ error · serial 000 = รูปธรรมดาของสถานะนั้น (200000, 201000, 404000, 409000) · serial อื่นใช้เฉพาะเคสที่ต้องแยกให้ออก (400001 validation, 400002 invalid parameter) · ประกอบด้วย toEnvelopeStatusCode() อย่าเขียน HTTP status เปล่า ๆ · ฟิลด์ errors[].code เป็นคนละเรื่อง ไม่ขยาย — บอกว่าอะไรผิด: slug (NOT_FOUND, CONFLICT, VALIDATION_ERROR) หรือ SQLSTATE ของ Postgres บนเส้น executeDbOperation() (23505 ซ้ำ, 23503 FK) ซึ่งเป็นตัวที่ทำให้แยก "ซ้ำ" ออกจาก conflict อื่นที่ก็ตอบ 409000 เหมือนกันได้ · ต้องมี อย่างใดอย่างหนึ่งระหว่าง data กับ errors ไม่ส่งพร้อมกัน

i18n interplay

ภายใน attributes ฟิลด์ 2 ภาษาถูกยุบเป็น nested object { th, en } ด้วย LocalizationInterceptor เสมอ (แม้ค่าเป็น null) — ห้าม frontend ต่อ string key เอง · ขาเข้าก็รับ nested เป็น alias ได้แล้ว (LocalizedBodyPipe) แต่ DTO ยังประกาศ _th/_en เป็นสัญญาหลัก ดู i18n Guide §03.1

meta.pagination · ชื่อฟิลด์จริงที่ส่งออก

endpoint ที่คืน { data, pagination } จะถูกแปลงเป็น collection + meta.pagination ให้เอง · ฟิลด์ตาม PaginationDTO — มีทั้ง total และ total_records ซึ่งเป็นค่าเดียวกัน (ตัวหลังเก็บไว้เพื่อความเข้ากันได้ย้อนหลัง อย่าลบ)

ฟิลด์ความหมาย
pageหน้าปัจจุบัน (เริ่มที่ 1)
page_sizeจำนวนต่อหน้าที่ใช้จริง (หลังถูก cap ด้วย QUERY_MAX_LIMIT)
total · total_recordsจำนวนแถวทั้งหมดที่ match filter (ค่าเท่ากัน)
total_pagesจำนวนหน้าทั้งหมด
is_large_datasettrue เมื่อ limit ถูก clamp หรือ ignore_limit ถูกตัดทอน — ทำให้ status.code เป็น 200002 แทน 200000 (ยัง 200 อยู่ แต่เป็นสัญญาณว่าให้ไล่หน้าต่อ ไม่ใช่ผลลัพธ์ครบชุด)
links · นำทางหน้า สร้างจาก "path" ไม่ใช่ URL ที่ยิงมา

response ที่แบ่งหน้าได้ self · first · last · prev (เมื่อ page > 1) · next (เมื่อยังมีหน้าถัดไป) — ทุกตัวเป็น <path>?page=N&limit=M
เคยพังจริงและแก้แล้ว (2026-09-20 · ยืนยันบนเครื่องจริงหลังแก้ว่า next = /customers?page=2&limit=1 แล้ว): TransformInterceptor สร้าง baseUrl จาก request.url ซึ่งมี query string ติดมาด้วย แล้ว createPaginatedResponse ต่อ ?page=… เข้าไปอีก — GET /customers?limit=1 จึงได้ next = /customers?limit=1?page=2&limit=1 ซึ่งเครื่องหมาย ? ตัวที่สองทำให้ page กลายเป็นส่วนหนึ่งของค่า limit ลิงก์ทุกตัวใช้ไม่ได้ · ตอนนี้กิ่ง paginated สร้างลิงก์จาก path ล้วน ส่วน self ของ response ที่ไม่ได้แบ่งหน้ายังสะท้อน query เดิมตามเจตนา

คู่ i18n ที่ "ไม่ได้ถูก select" จะไม่ถูกส่งออก (แก้แล้ว 2026-09-20)

สัญญา "ส่ง { th, en } เสมอแม้ค่าเป็น null" ใช้กับคอลัมน์ที่ถูกขอมาเท่านั้น · null = โหลดมาแล้วและว่าง → ยุบเป็น { th: null, en: null } ตามเดิม · undefined ทั้งสองด้าน = ไม่ได้ถูก select → ไม่ส่งคีย์นั้นออกไปเลย
บั๊กเดิม: property ของคลาส entity ใน TypeScript เกิดเป็น own property ค่า undefined (target ES2023 → useDefineForClassFields) แถวที่ดึงด้วย ?fields=id,code จึงมีคีย์ name_th/name_en อยู่ interceptor เลยยุบให้เป็น name: { th: null, en: null } ทั้งที่ชื่อจริงไม่ได้เป็น null — client แยกไม่ออกระหว่าง "ไม่ได้ขอมา" กับ "null จริงใน DB" · เจอตอนยิง API จริง ไม่ใช่จากการอ่านโค้ด และตอนนั้นยังไม่มี spec คุม interceptor ตัวนี้เลยสักบรรทัด

meta.warnings · สำเร็จแต่มีเรื่องต้องบอก

envelope มี meta.warnings เป็น array ของ { code, detail } (รูปเดียวกับ errors เพื่อให้ client render ทางเดียวกันได้) — ไม่มีคีย์นี้เลยถ้าไม่มีอะไรเตือน response จึงเหมือนเดิมทุก byte สำหรับเคสปกติ
ฝั่ง service เรียก addRequestWarning({ code, detail }) จากที่ไหนก็ได้ในสายเรียก — ไม่ต้องมี @Req() ใน signature เพราะเก็บผ่าน AsyncLocalStorage ที่ requestWarningsMiddleware เปิดไว้ก่อน routing (ลงทะเบียนด้วย app.use() ไม่ใช่ guard/interceptor เพราะต้องครอบทั้งสาย async) · เรียกนอก request = no-op เงียบ ๆ ไม่ throw
ผู้ผลิตปัจจุบัน: PARTY_CURRENCY_MISMATCH (โหมด WARN), งบการเงินที่กำไรขั้นต้นคำนวณไม่ครบ และ LOCALIZED_INPUT_IGNORED (ส่ง i18n มาทั้งสองรูปแบบในฟิลด์เดียว) · หน้า admin ที่ต้องเห็น warning ต้องเรียก API ตรง ๆ ไม่ผ่าน client กลางที่แกะเอาแต่ data

ลำดับ interceptor ที่ประกอบ envelope

ClassSerializerInterceptor → LocalizationInterceptor → TransformInterceptor (ตามลำดับใน registerGlobalMiddleware()) · ยุบ _th/_en ให้เสร็จก่อนห่อ envelope เสมอ ไม่งั้น attributes จะหลุดเป็นคู่คอลัมน์แบน · ทั้งสามตัวสร้างด้วย new เอง ไม่ได้ผ่าน DI จึงเป็น Scope.REQUEST ไม่ได้ — นี่คือเหตุผลที่ warning ต้องเดินทางผ่าน AsyncLocalStorage

429 · errorResponseBuilder ต้องคืน Error ไม่ใช่ object

@fastify/rate-limit โยนสิ่งที่ errorResponseBuilder คืนออกมา (index.js:341 · default ของมันเองสร้าง Error พร้อม statusCode) — ก่อนหน้านี้เราคืน envelope เป็น object เปล่า ๆ มันจึงถูกโยนเข้า AllExceptionsFilter ในฐานะ exception ที่ไม่รู้จัก แล้วตกไปกิ่ง catch-all: ทุกคำขอที่โดน rate limit ตอบ 500 / 500000 ส่วน envelope 429 ที่อุตส่าห์ประกอบไว้ไปโผล่แค่ใน log ว่า Unhandled Exception: [object Object] · 429 จึงไม่เคยถึง client เลยสักครั้ง
เจอเพราะลดค่า RATE_LIMIT_MAX=5 บนเครื่อง dev จริงแล้วยิงทะลุดู ไม่ได้เจอจากการอ่านโค้ด — ก่อนหน้านั้นเอกสารก็เขียนว่าได้ 429 มาตลอด

08 — Microservice Calls (RMQ/TCP)

การเรียกข้าม BC · RMQ/TCP

MicroserviceClientService.sendWithContext() คือทางเดียวที่ถูกต้องในการเรียก BC อื่น — ไม่ throw เอง: คืน defaultValue/null เมื่อฝั่งรับไม่ตอบสนองจริง ๆ (connection/timeout) แต่ throw HttpException ที่ถูกต้อง เมื่อฝั่งรับตอบกลับมาเป็น business error (400/404/409 ฯลฯ) — ผู้เรียกตัดสินใจต่อจากตรงนั้น (เช่น if (!x) throw new NotFoundException(...) เฉพาะกรณี "หาไม่เจอจริง ๆ" ไม่ใช่กรณี "BC อื่นตอบ 404 มาแล้ว")

TRANSPORT · knob เดียวทั้งแพลตฟอร์ม

TRANSPORT ใน .env (rmq เป็นค่าเริ่มต้น · tcp เป็น fallback) ถูกอ่านทั้งฝั่ง client registration (CommonModule) และฝั่ง server listener (bootstrapApplication) จาก microservice-transport.util.ts ตัวเดียวกัน — เปลี่ยนที่เดียวพลิกทั้งระบบ ห้ามมี BC ไหนเลือกเองแยก

HANDLER · @UseInterceptors(RmqAckInterceptor) บังคับ

ทุก controller ที่มี @MessagePattern/@EventPattern ต้องมี RmqAckInterceptor — server รัน noAck: false + prefetchCount: 1 และ NestJS ไม่ ack ให้เองตอนสำเร็จ ถ้าลืม queue จะ head-of-line block ถาวร (อาการ: caller timeout 15s ทุกตัว โดยไม่มี error log ใด ๆ, restart service ก็ไม่ช่วย) ดู pattern ที่ SupplierEventsController/ProductEventsController · ตั้งแต่ 2026-09-05 ข้อความที่ nack เพราะไม่มี handler ตรงกันเลยไปนอนรอที่ dead-letter queue แทนที่จะหายถาวร — ดู RabbitMQ Reliability Guide

HANDLER · @UseFilters(RpcExceptionsFilter) บังคับ และต้องเป็น decorator ระดับคลาส

วางไว้เหนือ @UseInterceptors(RmqAckInterceptor) บนคลาสเดียวกัน — ตัวหนึ่งทำให้คิวเดินต่อ อีกตัวทำให้ error ยังมีความหมายเมื่อข้ามฝั่ง
ทำไมต้องเป็น class decorator ไม่ใช่ลงทะเบียน global: app.connectMicroservice() เรียก registerListeners() แบบ synchronous ก่อน return ซึ่งเป็นขั้นที่ผูก handler เข้ากับ enhancer ที่มีอยู่ ณ วินาทีนั้น — อะไรที่ลงทะเบียนบน instance ทีหลังจะถูกทิ้งเงียบ ๆ (Nest log แค่ Cannot apply global exception filters: registration must occur before initialization. แล้วไปต่อ) · setupMicroservice() จึงส่ง { deferInitialization: true } แล้วผูกเองด้วยมือ (ห้ามถอดออก) แต่ filter ระดับคลาสผูกจาก metadata ของคลาส ลำดับ lifecycle ทำอะไรมันไม่ได้เลย
ราคาที่จ่ายเมื่อลืม: exception ทุกตัวที่ออกจาก RPC handler — รวมถึง NotFoundException ธรรมดา — กลายเป็น { status: 'error', message: 'Internal server error' } ของ Nest ซึ่ง sendWithContext อ่านไม่ออก จึงตกไปที่ defaultValue แล้วผู้เรียกไปรายงานว่า "service ไม่พร้อมใช้งาน" ทั้งที่ปลายทางตอบชัดเจนแล้ว (เคสจริง: storage 403 กลายเป็น 503 ในเบราว์เซอร์อยู่สองวัน)
ห้ามใช้ try/catch ครอบตัว handler เพื่อเลี่ยงเรื่องนี้ — filter แปลง HttpException ที่โยนจากชั้นไหนก็ได้ใต้ handler ให้เป็น IRpcErrorPayload อยู่แล้ว · catch ที่คืน null แทนการ rethrow เปลี่ยน "ฉันล้มเหลว" ให้กลายเป็น "ไม่มีข้อมูล" ซึ่งผู้เรียกแยกไม่ออกจากผลลัพธ์ว่างจริง ๆ · การแปลง error ของ SDK ภายนอก (S3, HTTP client) เป็นคนละเรื่องและอยู่ที่ service ตรงขอบนั้น (translateS3Error) · catch ที่ยอมรับได้มีแบบเดียวคือใน @EventPattern ที่ไม่มีใครรอคำตอบ และต้อง log เสมอ

RETRY · ทั้ง sendWithContext และ emitWithContext retry ให้อัตโนมัติ — handler จึงต้องทนถูกเรียกซ้ำ

retry เฉพาะความล้มเหลวชั่วคราว: TimeoutError (ปลายทางไม่ตอบ) หรือ error ระดับ connection (ECONNREFUSED/ECONNRESET/EPIPE/ETIMEDOUT/socket hang up) — DEFAULT_RETRY_ATTEMPTS = 2 (ครั้งแรก + retry อีกหนึ่ง) backoff DEFAULT_RETRY_BACKOFF_MS คูณตามรอบ แล้วค่อยตกไปที่ defaultValue
business error ไม่ retry — อะไรที่ unwrap ออกมาเป็น IRpcErrorPayload/IRpcErrorResponse หรือ HttpException อยู่แล้ว (404, validation 400) คือคำตอบที่ตัดสินแล้ว ยิงซ้ำได้แค่ latency และเสี่ยงรัน handler ที่ไม่ idempotent สองรอบ
ผลที่ตามมาเป็นข้อผูกมัด: handler ฝั่งรับอาจถูกเรียกสองครั้งสำหรับสิ่งที่ผู้เรียกมองว่าเป็นครั้งเดียว (ที่หายไปอาจเป็นแค่ คำตอบ ไม่ใช่ งาน) — ทุก @MessagePattern/@EventPattern ต้อง idempotent เหมือนที่ event consumer ต้องเป็นอยู่แล้ว
DEFAULT_RETRY_ATTEMPTS × DEFAULT_RPC_TIMEOUT_MS (≈30 วิ) ตั้งไว้ต่ำกว่า read timeout 60 วิของ Kong โดยตั้งใจ — จะขยับต้องกลับไปคิดงบตรงนี้ใหม่ · ส่ง retryAttempts เป็นพารามิเตอร์ตัวท้ายเพื่อ override รายครั้ง (ใส่ 1 = ปิด retry สำหรับ handler ที่รันซ้ำไม่ได้)

พิสูจน์ว่าใช้ได้จริงต้องใช้ smoke — เทสต์แบบ static มองไม่เห็น

unit และ module-e2e mock transport ทั้งคู่ จึงไม่มีทางเห็น filter ที่ไม่ได้ผูก · ตัวล็อกคือ smoke ที่ยิง RPC จริงให้ล้มเหลวแบบไม่ใช่ 404 แล้ว assert ว่าข้อความของปลายทางรอดข้ามฝั่งมาถึง — ดูเคสที่สามใน apps/inventory-bc/test/smoke/product-images.smoke.mjs (confirm รูปด้วยชื่อ bucket ที่ผิดกฎ → 503 พร้อมข้อความจริงของ storage ไม่ใช่ sentinel ของผู้เรียก) · call ข้าม BC ใหม่ที่ taxonomy ของ error สำคัญ ให้ลอกรูปแบบนี้

⚠️ defaultValue ต้องเป็นค่าที่ callee คืนเองไม่ได้ — สำคัญเมื่อ null คือคำตอบที่ถูกต้อง

สัญญา "ไม่ throw เอง" ข้างบนหมายความว่า ความล้มเหลวของ transport ถูกแทนด้วย defaultValue — ดังนั้นถ้าส่ง null เป็น defaultValue ให้ handler ที่ คืน null เป็นคำตอบปกติได้อยู่แล้ว ผู้เรียกจะแยกไม่ออกระหว่าง "callee ตอบมาว่าไม่มี" กับ "ไม่เคยได้คำตอบเลย" เพราะทั้งสองกรณีมาถึงเป็น null เหมือนกันเป๊ะ

เจอจริง 2026-09-07 · Storage.cmd.HeadObject คืน null เมื่อ object ไม่มีอยู่จริง (เป็น outcome ปกติที่ผู้เรียกต้องตัดสินใจเอง) แต่ StorageObjectService.headObject() ก็ส่ง null เป็น defaultValue ด้วย → RMQ timeout หรือ storage ล่มชั่วคราวครั้งใด ก็ถูกรายงานเป็น 400 "ยังไม่ได้อัปโหลดไฟล์" ทั้งที่ไฟล์อยู่ใน bucket แล้วจริง ผู้ใช้จึงเห็นข้อความที่บอกให้อัปโหลดใหม่ ซึ่งเป็นสิ่งที่แก้ปัญหาไม่ได้เลย · กระทบทุก resource ที่สืบทอด BaseAttachmentService เท่ากันหมด (product images, receipt/quotation/purchase-order attachments) ไม่ใช่แค่ endpoint เดียว

วิธีที่ถูก — ส่ง sentinel ที่ callee ไม่มีทางคืนออกมาได้ แล้วแปลความที่ขอบ ก่อนส่งต่อให้ layer อื่น:

// null = "callee ตอบว่าไม่มี" เท่านั้น · sentinel = "ไม่ได้คำตอบ"
const RPC_FAILED = Object.freeze({ __rpcFailure: true }) as unknown as IStorageHeadObjectResult;

const result = await this.microserviceClient.sendWithContext<...>(
  logger, client, { cmd: AppMicroservice.Storage.cmd.HeadObject }, { bucket, key },
  RPC_FAILED,
);
if (result === RPC_FAILED) {
  throw new ServiceUnavailableException('...'); // 503 — ตอบไม่ได้ ลองใหม่ได้
}
return result; // null ที่เหลือ = ไม่มีจริง → ผู้เรียก map เป็น 400 ได้อย่างมั่นใจ

เส้นแบ่งที่ต้องรักษาไว้: 503 = ยังตอบไม่ได้ (retry ได้) · 400/404 = ตอบแล้วว่าไม่มี (retry ไปก็ได้คำตอบเดิม) — ถ้าสองอย่างนี้ยุบเป็นค่าเดียวกัน ผู้เรียกจะเลือกทางที่ผิดเสมอ และ error ที่ผู้ใช้เห็นจะชี้ไปคนละทางกับสาเหตุจริง

RULE · วัน/เวลาเป็น timestamptz เท่านั้น ห้าม date/time

แม้ค่าที่ "รู้สึกเหมือน" วันที่ล้วน (document_date, valid_until, effective_from, expiry_date) ก็เป็น timestamptz / Date | null — เพราะ date ทิ้ง offset ของ client ทำให้ backend ต้องเดาว่าหมายถึงโซนเวลาไหน · DTO ใช้ @IsISO8601() ของโปรเจกต์เอง (ไม่ใช่ @IsDateString() ซึ่งรับ YYYY-MM-DD เปล่า ๆ ผ่าน) · service แปลงด้วย parseInstant() · การอ่านเป็น "วันตามปฏิทิน" ต้องผ่าน toBusinessDate()/businessYearOf()/todayBusinessDate() ที่ปักหมุด Asia/Bangkok เสมอ — .toISOString()/getFullYear()/::date ดิบ ๆ ให้วันผิดทุกครั้งที่เหตุการณ์เกิดหลัง 17:00 น. ไทย

RULE · ไม่มีคอลัมน์ date/time เหลืออยู่แล้วทั้งระบบ (2026-08-28)

users.expired_at เป็นคอลัมน์ date ตัวสุดท้ายที่เหลือ ถูกแปลงเป็น timestamptz แล้ว (anchor แถวเดิมที่เที่ยงคืนกรุงเทพฯ ตามกฎ migration) · เป็นอาการเดียวกับ policies.valid_from/valid_until เป๊ะ: DTO ตรวจด้วย @IsISO8601() แบบเข้มซึ่งปฏิเสธ YYYY-MM-DD เปล่า ๆ แต่ฟอร์มแอดมินส่งค่าดิบจาก <input type="date"> — การตั้งวันหมดอายุบัญชีจากหน้าจอจึงล้มเหลวด้วย 400 มาตลอด จนกว่าฝั่ง client จะขยายเป็น instant เต็มด้วย fromDateInputValue()

12 — Params · Permissions · Body

RULE · path param ที่เป็น UUID ต้องผ่าน ParseUuidParamPipe

สายของ guard · ลำดับที่ลงทะเบียนใน CommonModule

ทั้งสี่ตัวเป็น APP_GUARD ใน CommonModule ซึ่งเป็น @Global() — ทุก BC ได้เหมือนกันหมดโดยไม่ต้องต่อสายเอง และทำงานตามลำดับนี้

Guardตรวจอะไรทางออก
AuthGuardverify JWT + เช็ค session ใน Redis · บล็อกทุก endpoint ด้วย 403 เมื่อ session มี must_change_password@Public() · @SkipPasswordChangeCheck()
AccessKeyGuardตรวจลายเซ็น HMAC ของ access key/secret key (system-to-system) แล้วเติม request.user ในรูปเดียวกับที่ AuthGuard ทำทำงานเมื่อ route ติด @UseAccessKey() (AuthGuard จะข้าม JWT ให้)
CsrfGuarddouble-submit: request ที่ไม่ใช่ GET/HEAD/OPTIONS และมีคุกกี้ csrf_token ต้องส่งค่าเดิมกลับมาใน header x-csrf-token@SkipCsrfCheck() (มีที่เดียวคือ POST /auth/login) · route ที่เป็น @UseAccessKey()
PermissionGuardเทียบ @RequirePermission() กับรายการ permission แบนใน JWT ก่อน · ถ้าเป็น permission ที่ติดธง conditional จะไปถาม iam-bc เพื่อประเมิน ABAC สด ๆ@SkipPermissionCheck()
CSRF ผูกกับ "มีคุกกี้ไหม" ไม่ใช่ "public ไหม"

ตัวตัดสินคือการมีอยู่ของคุกกี้ csrf_token ซึ่งแปลว่าเบราว์เซอร์นี้ถือ credential ที่ถูกส่งอัตโนมัติ — ไม่ได้ดูว่า endpoint เป็น @Public() หรือไม่ เพราะ POST /auth/refresh เป็น @Public() (ไม่ต้องมี JWT) แต่กลายเป็น cookie-ambient ทันทีที่ refresh_token เป็นคุกกี้ จึงยังต้องป้องกัน · client ที่ใช้ bearer อย่างเดียวไม่เคยได้รับคุกกี้นี้ จึงไม่ถูกบังคับโดยปริยาย

RULE · endpoint ที่ไม่ @Public() ต้องมี @RequirePermission พร้อมชื่อ { th, en }

@RequirePermission('resource:action', { th, en }) — ต้องส่งชื่อสองภาษาเสมอ ไม่ใช่แค่สตริง permission · AuthGuard + PermissionGuard ลงทะเบียนเป็น APP_GUARD ใน CommonModule ทุก BC — endpoint ที่ไม่ public และไม่มี @RequirePermission() จะถูก default-deny · แคตตาล็อก permissions ไม่ hand-maintain: รัน npm run permissions:sync หรือกดปุ่ม Sync Permissions ในหน้า admin (POST /permission-syncs) · sync แตะเฉพาะแคตตาล็อก ไม่ผูก permission เข้า policy ให้ — ต้องมี grant migration แยกอีกที

permissions:sync · สอง plane คนละแหล่งที่มา

plane api — สแกนจาก decorator @RequirePermission('resource:action', { th, en }) ใน apps/<service>/src/**/*.ts
plane ui (page:*, component:*) — สแกนจาก attribute data-permission="..." ใน views/** + public/** และจากไฟล์ประกาศ apps/<service>/ui-permissions.manifest.json ถ้ามี · manifest เป็นแหล่งที่ควรใช้ เพราะ attribute ใส่ชื่อ { th, en } ไม่ได้ (ได้ placeholder ที่ humanize เอา) และบอกไม่ได้ว่า component อยู่หน้าไหน · manifest ประกาศได้เฉพาะ ui plane — endpoint จริงยังต้องมี decorator ของตัวเอง · ชนกันเมื่อไร manifest ชนะ
resource เป็นค่าที่ derive มา ไม่ใช่แค่ข้างหน้า colon — derivePermissionParts() คือแหล่งความจริงเดียว: page:view_dashboard → resource page_dashboard (ตัด view_ ทิ้ง), component ที่อยู่ใต้ page ใน manifest สืบ resource ของ page นั้น, ส่วน api plane เก็บ prefix ไว้ (role:create → role) · seed migration ที่เขียนมือต้อง derive ให้ตรงกัน เพราะ sync ทั้งสองทาง UPDATE … SET resource = EXCLUDED.resource — derive ผิดจะทับแถวที่ seed ถูกไว้ทั้งหมดเงียบ ๆ
upsert ด้วยคู่ (service, permission) เพราะ resource:action เดียวกันมีความหมายต่างกันได้ในคนละ BC · ของที่หายไปจากทั้งสองแหล่งถูก soft-delete ไม่เคย hard-delete · ทุกรอบบันทึกเป็นแถวใน permission_sync_logs

⚠ กับดักลำดับ deploy · permission ใหม่กับ grant migration ขึ้นพร้อมกันไม่ได้

pipeline รัน migration:run ก่อน permissions:sync (ยืนยันจาก log ของ deploy จริง 2026-09-04) ซึ่งตรงข้ามกับสิ่งที่ grant migration ต้องการ — migration ที่ INSERT … JOIN permissions จะรันตอนที่ยังไม่มีแถวใน permissions เลย จึง grant ศูนย์ statement แต่บันทึกตัวเองว่า executed แล้ว — ไม่มี error ไม่มี log มีแต่ 403 Missing required permission ตอนยิงจริง
ลำดับที่ปลอดภัย: deploy @RequirePermission() ไปก่อนตัวเดียว ปล่อยให้ permissions:sync ของรอบนั้นสร้างแถวในแคตตาล็อก แล้วค่อย deploy grant migration ในคอมมิตถัดไป
ถ้าพลาดไปแล้ว: เขียน migration ตัวใหม่ที่ re-apply INSERT เดิม (มี NOT EXISTS กัน) — ห้ามแก้หรือรันตัวเดิมซ้ำ เพราะ migration ที่บันทึกไว้ในตาราง migrations แล้วจะไม่มีวันรันอีก (ดูรูปแบบที่ ReapplyVatReturnPermissionsToMockPolicies)

RULE · body ว่างของ action route ถือเป็น {} ไม่ใช่ 400

bootstrap.util.ts แทน content-type parser ของ application/json ด้วยตัวที่คืน {} เมื่อ body ยาว 0 ไบต์ (นอกนั้นส่งต่อ parser เดิมของ Fastify ทุกประการ รวมถึง JSON เสีย → 400 เหมือนเดิม) — action route อย่าง POST /{doc}/{id}/approve จึงเรียกได้โดยไม่ต้องส่ง {} มาเอง · ลำดับการติดตั้งสำคัญ: ต้องเรียก await app.init() ก่อน แล้วค่อย removeContentTypeParser + ลงทะเบียนตัวใหม่ — ติดตั้งก่อนหน้านั้นทุก BC จะ crash-loop ตอน boot ด้วย FastifyError: Content type parser 'application/json' already present

13 — Migrations & Seed

Migration ต้อง generate จาก entity · seed ต้องตามให้ทัน

migration อยู่ที่ libs/database/src/migrations/erp_<bc>/ และรันแยกต่อ BC (pnpm run migration:run:<bc>) — แต่ละ BC มีตาราง migrations ของตัวเอง ลำดับเวลาจึงต้องถูกต้องภายใน BC เดียวกันเท่านั้น

RULE · แก้ที่ entity ก่อน แล้ว generate — ห้ามเขียน SQL schema เอง

pnpm run migration:generate:<bc> --name=<Name> แล้วอ่าน SQL ที่ได้ก่อน commit (generator อาจ emit DROP/สร้างใหม่สำหรับการ rename และมันอ่าน state ของ DB ที่เครื่องคุณจริง ๆ) · migration:create (เขียนมือ) ใช้เฉพาะสิ่งที่ generator มองไม่เห็น: backfill, seed, จูน index/constraint, DML ที่ต้องเรียงลำดับ · synchronize ห้ามเป็น true ใน BC ที่มี migration แล้ว

RULE · timestamp ในชื่อไฟล์ต้องเป็น Date.now() จริง

ห้ามคิดเลขกลม ๆ ขึ้นเอง หรือก๊อปของไฟล์ข้างเคียงแล้วบวก 1 — ตัวเลขนี้คือลำดับการรันและเป็น key ในตาราง migrations · ไฟล์เขียนมือใช้ node -e "console.log(Date.now())" · ชื่อไฟล์ <epoch_ms>-<PascalCaseName>.ts คลาส <PascalCaseName><epoch_ms> และ property name ต้องตรงกับชื่อไฟล์เป๊ะ · down() ต้อง undo up() ได้จริง ถ้าทำไม่ได้ให้เขียนบอกไว้ใน docblock อย่าปล่อยเป็น no-op ที่ทำให้เข้าใจผิด · seed ที่ข้าม 2 BC = 2 migration แยกกัน ไฟล์ละฐานข้อมูล

RULE · migration ที่แปลง date → timestamptz ต้องปักที่เที่ยงคืนกรุงเทพฯ

USING (col::timestamp AT TIME ZONE 'Asia/Bangkok') — cast เปล่า ๆ จะเลื่อนวันตามปฏิทินของแถวเดิมทันทีถ้า session ไม่ได้ตั้ง timezone เป็น UTC+7 อยู่แล้ว

RULE · เปลี่ยน schema แล้วต้องไปแก้ seeder ด้วยเสมอ

seeder ใน libs/database/src/scripts/seed/ เป็น pg client เขียน SQL ดิบ ไม่ผ่าน entity/service/DTO จึงไม่มีอะไร type-check ให้ — มันพังตอน runtime บนเครื่องที่ติดตั้งใหม่ นานหลังจากคุณแก้ · ต้องตามแก้เมื่อ: เพิ่ม/เปลี่ยนชื่อคอลัมน์หรือทำให้ NOT NULL · เปลี่ยน natural key (seeder re-resolve reference จาก DB ด้วย natural key ไม่ได้ถือ id ไว้ในหน่วยความจำ) · เปลี่ยนชื่อ/ลบตาราง หรือมี entity ใหม่เข้ามาใน aggregate ที่ seed อยู่ (แก้ truncates + SEEDERS[] พร้อม depends_on) · BC ใหม่เริ่ม seed ได้ (เพิ่มใน ISeedDatabase + SEED_DATABASE_ENV) · tree entity มีแถวเพิ่ม (ต้อง rebuild lft/rgt) · seeder ต้อง idempotent + deterministic — สุ่มค่าจาก stable-index.util.ts (hash ของ SKU) ห้ามใช้ faker/Math.random · ตรวจด้วย npm run seed -- --dry-run และ --fresh --yes บน DB ทดสอบเมื่อเป็นการเปลี่ยนโครงสร้าง

✅ PRESIGNED — ค่าเริ่มต้น

"เพิ่มไฟล์ให้ resource ที่มีอยู่แล้ว" · GeneratePresignedUpload → client PUT ตรงไป MinIO → ยืนยันด้วย HeadObject

HeadObject คืน null = "ยังไม่เคยอัปโหลดจริง" ไม่ใช่ error

MULTIPART — เฉพาะ "สร้าง resource พร้อมไฟล์ในครั้งเดียว"

UploadWithMeta · bytes วิ่งผ่าน backend · ใช้เมื่อ route เดียวกันต้องรับ application/json ธรรมดาได้ด้วย
Fastify ไม่เติม request.body ให้ multipart — @Body() จึงใช้ไม่ได้ ต้องรับ @Req() แล้ว validate เองด้วย parseMultipartJsonBody/validateDto ซึ่งโยน ValidationException รูปเดียวกับ global pipe
ฟิลด์ที่ถือ JSON payload ชื่อ data ตามธรรมเนียม · @fastify/multipart ลงทะเบียนไว้ทั้งแพลตฟอร์ม (MULTIPART_MAX_FILE_SIZE_BYTES/MULTIPART_MAX_FILES · ค่าเริ่มต้น 5MB/5 ไฟล์) แต่ opt-in รายคำขอ

RULE · error ระหว่างวน multipart part = 400 เสมอ ไม่ใช่ 500

@fastify/multipart ไม่ได้โยน FST_* FastifyError ตามที่เอกสารบอกเสมอไป — เกินจำนวนไฟล์กลางสตรีมโผล่มาเป็น ERR_STREAM_PREMATURE_CLOSE ของ Node ธรรมดา (ยืนยันกับ instance จริงแล้ว) · parseMultipartJsonBody ครอบให้แล้ว — อย่าไปเขียนโค้ดอ่าน part เองที่อื่นโดยไม่มี catch-all แบบเดียวกัน

อย่าเพิ่มการถอดรหัสชื่อไฟล์กลับเข้ามาอีก

resource ที่ชื่อไฟล์เดินทางมาถึง backend ผ่าน @fastify/multipart เท่านั้น ไม่ต้อง decode ซ้ำ — มันเป็น UTF-8 ที่ถูกต้องอยู่แล้ว · storage.service.ts เคยตีความ originalname เป็น latin1→UTF-8 ทุกตัวโดยเดาว่าเจอบั๊ก mojibake ของ Busboy/Multer ซึ่งไม่จริงกับ transport ของแอปนี้ และมันทำให้ชื่อไฟล์ภาษาไทยที่ถูกอยู่แล้วเพี้ยน — ถอดออกไปแล้ว อย่าเอากลับมาโดยไม่มีผู้เรียกที่ต้องการจริง ๆ

15 — Scheduled Jobs

งานตามเวลา · *JobsController

งานตามเวลาอยู่ในคลาส <Resource>JobsController ที่ประกาศ @Controller() ไม่มี path — ที่ต้องเป็น controller เพราะ explorer ของ @nestjs/schedule สแกนทั้ง provider และ controller · controller เป็นแค่ตัวสั่งงาน: มันรู้ว่าเมื่อไรต้องรันและจะทำอย่างไรถ้าพัง ส่วนเนื้องานอยู่ใน service ที่ endpoint ปกติก็เรียกได้

RULE · dependency tree ของ host ต้อง static — ของที่เป็น Scope.REQUEST ต้อง resolve ผ่าน ModuleRef

@nestjs/schedule ลงทะเบียน @Cron ให้เฉพาะ host ที่ dependency tree เป็น static · service ที่พึ่ง MicroserviceClientService (ซึ่งเป็น Scope.REQUEST) ถ้า inject ตรง ๆ จะลาก controller ให้กลายเป็น request-scoped ตามไปด้วย แล้ว scheduler จะข้ามงานนั้นเงียบ ๆ เหลือแค่ warning ตอน boot — งานไม่เคยรันเลยโดยไม่มีใครรู้
ทางที่ถูก: moduleRef.resolve(Service, ContextIdFactory.create(), { strict: false }) ทุกรอบ tick (ไม่มี inbound request ให้สืบ context อยู่แล้ว ซึ่งถูกต้องสำหรับ cron) · ดู ExpiryAlertJobsController เทียบกับ OutboxJobsController ที่ inject ได้ตามปกติเพราะ OutboxService ใช้ ClientProxy ดิบ

RULE · ล็อกต่อ tick เมื่อ worker ทั้งสองตัวจะทำงานซ้ำกัน

ทุก BC ถูกสตาร์ทด้วย PM2 exec_mode: 'cluster' instances: 2 และ @nestjs/schedule ทำงานแยกต่อ process — ไม่มีล็อก = tick เดียวยิงสองครั้ง งานที่ emit event ก็ emit สองรอบ งานที่เขียนแถวก็เขียนซ้ำ (เพิ่ม instances ยิ่งแย่ขึ้นเงียบ ๆ)
ScheduledJobLockService.acquire(key, ttl) เป็น SET NX EX บน Redis — ใครจองได้ก่อนเป็นคนทำ อีกตัวข้าม · ตั้งใจไม่ปล่อยล็อกเมื่อทำงานเสร็จ: TTL คือสิ่งที่นิยามว่า "tick นี้จัดการแล้ว" worker ที่ตายกลางทางจึงส่งงานซ้ำให้เพื่อนไม่ได้ · key ต้องไม่ซ้ำทั้งต่อ job และต่อ tick (job:expiry-alert:2026-08-28) ไม่งั้นรอบแรกจะบล็อกทุกรอบถัดไป
ข้อยกเว้นที่ถูกต้อง: outbox relay ไม่มีล็อก เพราะ claimBatch() จองแถวด้วย FOR UPDATE SKIP LOCKED — worker สองตัวหยิบคนละ batch และทำงานที่มีประโยชน์ทั้งคู่ การเอาล็อกมาคั่นมีแต่ลด throughput ลงครึ่งหนึ่งโดยไม่ได้อะไร · ฐานข้อมูลแยกงานให้แล้ว

RULE · @Cron handler ต้องไม่ปล่อยให้ reject หลุดออกไป

rejection ของ @Cron คือ unhandled promise rejection ซึ่งภายใต้ --unhandled-rejections=throw (ค่าเริ่มต้นของ Node) จะลากทั้ง worker ลง — "สแกนของหมดอายุคืนนี้ล้มเหลว" กลายเป็น "inventory-bc รีสตาร์ตตอนตีหนึ่ง" · catch + log แล้วปล่อยให้ tick ถัดไปทำต่อ (สแกนที่ derive ทุกอย่างจากข้อมูลปัจจุบันรันซ้ำได้อยู่แล้ว) · ใช้ timeZone: BUSINESS_TIMEZONE กับทุก @Cron ที่ผูกกับเวลาทำการ

RULE · update() ที่ส่ง items มาใหม่คือการ SYNC ไม่ใช่ลบทิ้งแล้วใส่ใหม่

planDocumentLineSync() diff ของที่เก็บไว้กับที่ส่งมาด้วย product_id (เป็น key ที่ใช้ได้เพราะ assertNoDuplicateProductLines ปฏิเสธเอกสารที่มีสินค้าเดียวกันซ้ำ) — บรรทัดที่ match ถูก UPDATE อยู่กับที่ เก็บ id, created_at/created_by และทุกคอลัมน์ที่ client ไม่เคยส่งมาไว้ครบ — ที่สำคัญที่สุดคือ purchase_order_items.received_qty ซึ่งการ re-insert จะรีเซ็ตเป็นศูนย์ ลบประวัติของที่รับมาแล้วทิ้ง
อ่านแถวที่เก็บไว้ ภายใน transaction เดียวกัน ใต้ row lock ของ header และเขียนบรรทัดหลังผ่าน validation ครบแล้วเท่านั้น — request ที่ถูกปฏิเสธต้องไม่ทิ้งบรรทัดที่ sync ไปครึ่งทางไว้

RULE · DiscountMode สามแบบแยกขาดจากกัน ห้ามซ้อน

none ข้ามการคำนวณทั้งหมด · header ต้องมี discount_type/discount_value แล้วคิดกับ sub_total · per_item ใช้ส่วนลดของแต่ละบรรทัดแล้วรวมขึ้นมาเป็น total_discount ของ header
นอกโหมด per_item ส่วนลดรายบรรทัดที่ client ส่งมาถูกทิ้ง · นอกโหมด header discount_type/discount_value ถูกบังคับเป็น null
sub_total คือผลรวมก่อนหักส่วนลดเสมอ ดังนั้น total = sub_total − total_discount เป็นจริงทุกโหมด และทั้งสองค่าไม่เคยติดลบ

RULE · "ของชนิดไหน" เป็นของ inventory-bc · "อัตราเท่าไร" เป็นของ finance-bc

inventory-bc.tax_categories ตอบว่าสินค้านี้เป็นของประเภทไหน (VatTreatment = standard/zero_rated/exempt) — enum อยู่ใน @lib/common เพราะ finance-bc ต้อง snapshot ลงทุกบรรทัดใบกำกับ
finance-bc.tax_configs ตอบว่าอัตราเท่าไร และมีผลช่วงไหน — version ด้วย effective_from/effective_upto เพื่อให้การเปลี่ยนอัตราตามกฎหมายไม่ย้อนไปแก้เอกสารที่ออกไปแล้ว · สองแถวที่ code เดียวกันห้ามมีช่วงเวลาซ้อนกัน
ข้าม BC ผ่าน RPC เสมอ และห้ามให้ client เป็นคนบอก — ผู้เรียกที่ประกาศเองว่าบรรทัดนี้ exempt ได้ ก็ล้าง VAT ของการขายที่ต้องเสียภาษีได้ · สินค้าที่ไม่มี tax category ตกไปที่ STANDARD (เก็บเกินดีกว่าเก็บขาด)
zero_rated กับ exempt คำนวณได้ 0 เท่ากันแต่ต้องแยกกันจนถึง header (total_zero_vat_price เทียบ total_exempt_vat_price) — คนละช่องใน ภ.พ.30 และมีแต่ zero-rated ที่ยังเครดิตภาษีซื้อได้

RULE · ส่วนลด header ต้องปันลงบรรทัดก่อนคิด VAT · WHT ไม่เคยลด total

ยอดแยกตาม treatment เป็นตัวเลขระดับบรรทัด — ปล่อยส่วนลดไว้ที่ header จะทำให้ยอดเหล่านั้นสูงเกินจริงและ VAT ที่ต้องชำระผิดตาม · allocateProRata() โยนเศษจากการปัดให้ตัวที่น้ำหนักมากที่สุด ผลรวมจึงกลับมาเท่าเดิมพอดี
ภาษีหัก ณ ที่จ่ายไม่ลดยอดหนี้ มันลดเงินสดที่ได้รับ — เงินสดที่คาดว่าจะได้คือ total − total_wht ซึ่งคำนวณเอา ไม่เก็บเป็นคอลัมน์

RULE · เลขที่เอกสารตามกฎหมายต้องไม่มีช่อง (gapless)

Receipt ของ finance-bc (ใบเสร็จเงินสด / ใบกำกับภาษีเต็มรูป / อย่างย่อ แยกด้วย document_type) ไม่ใช่เอกสาร workflow จึงไม่มีชุดสถานะแบบ PO/Quotation — ReceiptStatus คือ DRAFT → ISSUED → VOID
เลขถูกดึงตอน issue() ไม่ใช่ตอน create — §86/4 บังคับว่าลำดับต้องไม่มีช่อง เลขจึงต้องไม่ถูกใช้ไปกับเอกสารที่ยังทิ้งได้ · ดึงอยู่ใน transaction เดียวกับที่พลิกสถานะ พังกลางคันจึงไม่เผาเลข · ปีมาจาก document_date ของเอกสารเอง ไม่ใช่วันนี้ เอกสารของเดือนธันวาคมจึงไม่ถูกออกเลขเข้าลำดับของปีหน้า
ISSUED แก้ไม่ได้ — update() รับเฉพาะ DRAFT การแก้ไขทำด้วยใบลด/ใบเพิ่มหนี้ที่อ้างถึงเอกสารเดิม ไม่ใช่การแก้ทับ · VOID เก็บทั้งแถวและเลขไว้ เลขที่ถูกใช้แล้วต้องมีที่อยู่เสมอ ไม่งั้นลำดับตรวจสอบไม่ได้ และไม่มีการนำกลับมาใช้ซ้ำ · DRAFT ไม่มีเลขและไม่มีตัวตนทางกฎหมาย จึงลบได้ ไม่ต้อง void

RULE · เอกสารธุรกรรมเป็น submittable · เหตุการณ์ออกหลัง commit

DRAFT → SUBMITTED → CANCELLED — สต็อก/บัญชีลงตอน submit และกลับรายการตอน cancel · domain event ออกหลัง commit ผ่าน outbox และ consumer ต้อง idempotent · available_qty มี CHECK (… >= 0) ที่ระดับฐานข้อมูล · อ้างข้าม BC ด้วย uuid เท่านั้น ไม่มี FK ข้ามฐานข้อมูล

17 — Admin UI (EJS)

หน้าแอดมินที่ render จากฝั่ง server

หน้าแอดมินเป็น EJS ที่ backend render เอง + vanilla JS ไม่มี framework — apps/iam/views คือ reference implementation และ skill init-view scaffold หน้าใหม่ที่ทำตามกติกาทั้งหมดนี้ให้แล้ว · กติกาฉบับเต็มอยู่ที่ .claude/rules/admin-ui-ejs.md — ข้างล่างคือข้อที่พลาดแล้วเจ็บที่สุด

ใช้ <dialog> แทนได้เฉพาะฟอร์มที่เล็กจนหน้าเต็มเป็นภาระเปล่า หรือสิ่งที่ไม่ใช่มุมมองของ resource เลย (เช่น dialog เผยความลับของ access key ครั้งเดียว)

แถวอยู่ใน <table class="p-table"><tbody> ใน .um-table-scroll-area เสมอ ห้ามทำเป็น grid ของ <article> เอง · ทุก list ที่ยิง endpoint แบบแบ่งหน้าจริงต้องมี pager.ejs พร้อม pageSizeId/pageSizeOptions

บัญชีหน้า/ขนาดหน้าไม่เขียนเองรายหน้า — ใช้ createPaginatedList({ fetchPage, infoId, prevId, nextId, defaultPageSize }) แล้ว resource จัดหาแค่ fetchPage

⚠ กับดัก · แก้ไฟล์ใน public/** แล้ว Nest ไม่ restart

nest start --watch รีโหลดเฉพาะการเปลี่ยนใน src/** — public/** เปลี่ยนแค่ bundle · ?v= ของทุก <script>/<link> มาจาก getAssetVersion() ที่อ่าน mtime ของ build-manifest.json ทุกครั้ง ห้าม memoize ไม่งั้น browser ได้ ?v= เดิมที่ cache ไว้แล้ว bundle ใหม่จึงไม่เคยถูกโหลด

CSS · theme.css ตัดสินธีม ไม่ใช่ไฟล์ component

อะไรที่ขึ้นกับธีมต้องประกาศเป็น token ในทั้งสามบล็อกของ theme.css (:root:not([data-theme="dark"]), @media (prefers-color-scheme: dark), :root[data-theme="dark"]) แล้ว component อ่าน token นั้นแบบไม่มีเงื่อนไข — admin-theme-tokens.spec.ts บังคับไว้ทั้งสองครึ่ง
ทำไมห้ามเขียน :root:not([data-theme="dark"]) ในไฟล์ component: มันอ่านเหมือน "เฉพาะธีมสว่าง" แต่ไม่ใช่ — มันแมตช์ทุกครั้งที่ attribute ไม่ใช่คำว่า dark เป๊ะ ๆ รวมถึงสถานะที่ผู้ใช้ทุกคนเริ่มต้น (ไม่มี attribute เลย + OS ตั้งเป็นมืด ซึ่ง media block เปลี่ยน palette เป็นมืดไปแล้ว) · เคยหลุดขึ้นเป็นแถวตารางสีขาวใต้ตัวอักษรของธีมมืด อ่านไม่ออก และหายเองทันทีที่กดสลับธีม (เพราะการกดเขียน attribute จริงลงไป) จึงเกิดซ้ำได้เฉพาะตอนโหลดครั้งแรก · :root กับ :not() นับเป็น class อย่างละตัว override แบบนี้จึงชนะ .foo:hover และฆ่า hover ของธีมเดียวเงียบ ๆ ด้วย — token ไม่มี specificity จึงทำแบบนั้นไม่ได้
กฎพื้นฐานของ Pico คือ td,th{background-color:var(--pico-background-color)} — ทุกเซลล์ทาพื้นทึบทับสิ่งที่ตั้งไว้บน <tr> จนมิด · กฎพื้นหลัง/hover ของแถวต้องเล็งที่ .p-table tbody td ไม่ใช่ tr
ปุ่มทำลายข้อมูลเรียก showConfirmDialog({ title, message, confirmText, danger }) เสมอ ห้ามใช้ window.confirm()
