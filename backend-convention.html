01 — Overview & Principles

ภาพรวม & หลักการ

เอกสารนี้สรุป convention กลางขององค์กร สำหรับทุกบริการ NestJS — ตั้งแต่การตั้งชื่อไฟล์/คลาส/ตาราง ไปจนถึงรูปแบบ Response, การ throw error และ Query Params เป้าหมายคือความ สม่ำเสมอ ทำให้ทั้ง codebase และ schema เข้าใจตรงกัน อ่านโค้ดแล้วรู้เจตนาทันที

NAMING

Singular Module · Plural Controller/Service · snake_case property/column · kebab-case ไฟล์/โฟลเดอร์

RESPONSE

JSON:API envelope: status · data|errors · meta · links — ห่ออัตโนมัติด้วย TransformInterceptor

ERRORS

Exception เฉพาะเจาะจงเสมอ · code 6 หลัก · controller ไม่ catch ปล่อยขึ้น global filter

CORE PRINCIPLE

โครงสร้าง envelope ชัดเจน · ส่ง อย่างใดอย่างหนึ่งระหว่าง data กับ errors ไม่ปนกัน · ใช้ exception ที่เจาะจงแทน Error ทั่วไป · ใส่ context เต็มใน exception · ไม่ leak ข้อมูล sensitive (password/token/internal) · log ทุกอย่างภายใน

02 — NestJS Naming Convention

การตั้งชื่อ (NestJS)

Module เป็น เอกพจน์ (แคปซูลเดียวของฟีเจอร์) ส่วน Controller/Service เป็น พหูพจน์ (จัดการหลาย endpoint/method) · Property ของ Entity/DTO เป็น snake_case เพื่อ map 1-to-1 กับคอลัมน์ PostgreSQL ลดการใช้ @Column({ name: '…' })

ตัวอย่าง · Entity property = snake_case (1-to-1 กับคอลัมน์)
@Entity('goods_receipts')
export class GoodsReceipt {
  @PrimaryGeneratedColumn('uuid')  id: string;
  // snake_case → ไม่ต้องใส่ @Column({ name: '...' })
  @Column()  po_id: string;
  @Column()  supplier_id: string;
  @Column({ type: 'numeric' })  import_cost: number;
  @Column()  lot_number: string;
  @Column({ type: 'date', nullable: true })  expiry_date: Date;
  @Column({ default: false })  is_cancelled: boolean;
}
Class vs Property

คลาสเป็น PascalCase เอกพจน์ (มาตรฐาน OOP/NestJS) แต่ property เป็น snake_case (มาตรฐาน PostgreSQL) — สองระดับนี้ต่างกันโดยตั้งใจ

03 — Boolean & Status Prefixes

Prefix ของ Boolean / Status

ฟิลด์ boolean/status ต้องมี prefix เสมอ เพื่อไม่ให้กำกวมระหว่าง “คำนาม / คำกริยา / สถานะ” — เช่น active อาจเป็นคำนามหรือคำสั่ง แต่ is_active ตอบชัดว่า “มันกำลัง active หรือไม่?”

05 — API Response (JSON:API)

โครงสร้าง Response

ทุก Response ห่อด้วย envelope แบบ JSON:API: status · data หรือ errors (อย่างใดอย่างหนึ่ง) · meta · links — ทำงานอัตโนมัติผ่าน TransformInterceptor เมื่อ controller ประกาศ @ResourceType()

โครง envelope · Success
{
  "status": { "code": 200000, "message": "Request Succeeded" },
  "data": {
    "type": "goods-receipts",          // จาก @ResourceType('goods-receipts')
    "id": "uuid-grn",
    "attributes": {                    // snake_case + i18n nested object
      "status": "SUBMITTED",
      "po_id": "uuid-po", "import_cost": 98.5,
      "remark": { "th": "ของครบ", "en": null },
      "product": { "name": { "th": "ยาเซโกร", "en": "Zagro" } }
    }
  },
  "meta": { "timestamp": "2026-07-14T10:30:00.000Z" },
  "links": { "self": "/inventory/goods-receipts/uuid-grn" }
}
SINGLE

data: { type, id, attributes }

COLLECTION

data: [ { type, id, … } ]

PAGINATED

data: [ … ] + meta.pagination

@ResourceType จำเป็นบนทุก Controller
@Controller('goods-receipts')
@ResourceType('goods-receipts')   // ✅ กำหนด type ใน response · ถ้าไม่ใส่ = คืน raw ไม่ transform
export class GoodsReceiptsController {
  @Get()  findAll() { return this.service.findAll(); }
}
STATUS CODE · 6 หลัก

status.code เป็นเลข 6 หลัก = HTTP status × 1000 + serial · success = 200000 · ต้องมี อย่างใดอย่างหนึ่งระหว่าง data กับ errors ไม่ส่งพร้อมกัน

i18n interplay

ภายใน attributes ฟิลด์ 2 ภาษาถูกยุบเป็น nested object { th, en } ด้วย LocalizationInterceptor เสมอ (แม้ค่าเป็น null) — ห้าม frontend ต่อ string key เอง ดู i18n Guide

CONTROLLER · ไม่ catch

07 — Query Parameters

Query Params

ใช้ @ValidatedQuery(QueryParamsDTO) แทน @Query() — ได้ทั้ง type-safe และ throw error code ถูกต้อง (400002) · ถ้าใช้ @Query() กับ DTO ที่มี type จะไปโดน Global ValidationPipe → ได้ 400001 ที่ผิด

❌ @Query()
@Get()
findAll(@Query() q: any) {
  // เสีย type safety
  return this.service.findAll(q);
}
✅ @ValidatedQuery
@Get()
findAll(@ValidatedQuery(QueryParamsDTO) q: QueryParamsDTO) {
  // type-safe + throw 400002
  return this.service.findAll(q);
}
Feature@Query()@Query() + type@ValidatedQuery(DTO)
Type Safety❌ (any)⚠️ (โดน Global Pipe)✅ Full
Error Code—400001 (ผิด)400002 (ถูก)
ValidationManualAuto (pipe ผิด)Auto (ถูก)
Recommended❌❌✅
FEATURES · @ValidatedQuery

แปลง type อัตโนมัติ ("123"→123, "true"→true) · strip property แปลกปลอม (whitelist) · รองรับ nested validation และ filter syntax filter=field||$eq||value (ส่งซ้ำได้หลายค่าเพื่อ AND — ไม่ใช่ filter[]=... ซึ่งจะโดนปฏิเสธด้วย 400002) · เงื่อนไข OR ใช้ or=field||$eq||value รูปแบบเดียวกัน

Manual throw · custom validation (query)
import { InvalidParameterException } from '@lib/common/utils/http-exception/invalid-parameter.exception';

@Get('search')
async search(@Query('keyword') keyword: string) {
  const allowed = ['lot_number', 'product_id'];
  const field = keyword?.split(':')[0];
  if (!allowed.includes(field)) {
    throw new InvalidParameterException([{
      field: 'keyword',
      message: `Invalid search field '${field}'. Allowed: ${allowed.join(', ')}`,
    }]);
  }
  return this.service.search(keyword);
}
08 — Microservice Calls (RMQ/TCP)

การเรียกข้าม BC · RMQ/TCP

MicroserviceClientService.sendWithContext() คือทางเดียวที่ถูกต้องในการเรียก BC อื่น — ไม่ throw เอง: คืน defaultValue/null เมื่อฝั่งรับไม่ตอบสนองจริง ๆ (connection/timeout) แต่ throw HttpException ที่ถูกต้อง เมื่อฝั่งรับตอบกลับมาเป็น business error (400/404/409 ฯลฯ) — ผู้เรียกตัดสินใจต่อจากตรงนั้น (เช่น if (!x) throw new NotFoundException(...) เฉพาะกรณี "หาไม่เจอจริง ๆ" ไม่ใช่กรณี "BC อื่นตอบ 404 มาแล้ว")

HANDLER · @UseInterceptors(RmqAckInterceptor) บังคับ

ทุก controller ที่มี @MessagePattern/@EventPattern ต้องมี RmqAckInterceptor — server รัน noAck: false + prefetchCount: 1 และ NestJS ไม่ ack ให้เองตอนสำเร็จ ถ้าลืม queue จะ head-of-line block ถาวร (อาการ: caller timeout 15s ทุกตัว โดยไม่มี error log ใด ๆ, restart service ก็ไม่ช่วย) ดู pattern ที่ SupplierEventsController/ProductEventsController

⚠️ Gotcha · Global filter/interceptor ไม่ไปถึง microservice instance

app.connectMicroservice() (ใน bootstrap.util.ts) เรียกแบบไม่ใส่ { inheritAppConfig: true } โดยตั้งใจ (ใส่แล้วจะลาก AuthGuard/ValidationPipe ของ HTTP มาด้วย แล้วเริ่ม reject internal service-to-service call ที่ไม่มี JWT แนบมา) ผลข้างเคียงที่ไม่มีใครตั้งใจ: app.useGlobalFilters(...) / app.useGlobalInterceptors(...) / APP_FILTER/APP_GUARD/APP_INTERCEPTOR — ที่ผูกกับ ApplicationConfig ของ HTTP app เท่านั้น — ไม่เคยถูกคัดลอกไปยัง microservice instance เลย ต้องผูกตรงเข้า microserviceInstance เองใน setupMicroservice() เสมอ

❌ Bug ที่เจอจริง (2026-08) — RpcExceptionsFilter ไม่เคยทำงาน
const microserviceInstance =
  app.connectMicroservice(options);
microserviceInstance.useGlobalInterceptors(
  new OtelRpcContextInterceptor(),
);
await app.startAllMicroservices();

// RpcExceptionsFilter ผูกไว้เฉพาะที่ app (HTTP)
// → ทุก exception ใน @MessagePattern
// → ตกไปที่ default ของ Nest:
// {"status":"error","message":
//   "Internal server error"}

// ธรรมดา ๆ ก็ตาม
✅ แก้แล้ว — ผูก filter ตรงเข้า microservice instance

  app.connectMicroservice(options);

// ฯลฯ ที่โยนใน @MessagePattern จะถูก
// format เป็น IRpcErrorPayload จริง
แหล่งอ้างอิง

ดู OtelRpcContextInterceptor's docblock (มีคำอธิบายกลไกนี้อยู่ก่อนแล้วสำหรับ interceptor) และ setupMicroservice() ใน libs/common/src/utils/bootstrap.util.ts — จุดเดียวที่ทุก BC ต้องแก้ถ้าจะเพิ่ม global filter/interceptor ใหม่สำหรับ RPC

⚠️ Gotcha ที่ 2 · error จาก RPC ถูกห่อไว้อีกชั้นบน wire

แม้ RpcExceptionsFilter จะ format IRpcErrorPayload ถูกต้องแล้ว (gotcha ด้านบน) — @nestjs/microservices client ฝั่งผู้เรียกจะ deserialize response ที่ error เป็น { message: 'Rpc Exception', error: <payload จริง> } เสมอ ไม่ใช่ payload เปล่า ๆ ที่ top level — ถ้า shape-check ไม่ unwrap ชั้นนี้ก่อน จะตกไปที่ fallback "service unavailable" เสมอ (คืน null) แม้ปลายทางจะตอบ 404/400 กลับมาถูกต้องแล้วก็ตาม — แยกไม่ออกระหว่าง "หาไม่เจอจริง" กับ "BC ปลายทางล่ม"

รูปแบบ (บน wire)ที่มาต้องเช็คก่อนไหม
{ status:{code,message}, errors:[...], meta:{...} }payload เปล่า (บาง path เก่า)ตรงอยู่แล้ว
{ message:'Rpc Exception', error:{status,errors,meta} }ค่าจริงจาก RMQ/TCP client เสมอต้อง unwrap .error ก่อน
{ status_code, message }legacy formatตรงอยู่แล้ว (คนละ helper)
MicroserviceClientService · unwrapRpcError()

sendWithContext's catch block เรียก unwrapRpcError(error) ก่อนเช็ค isRpcErrorPayload/isRpcErrorResponse เสมอ — unwrap เฉพาะ shape {error: X} ที่ X ตรงกับ payload จริงเท่านั้น (object อื่นที่บังเอิญมี key ชื่อ error เช่น driver error ดิบ จะไม่ถูก unwrap ผิด ๆ)

ทั้งสอง gotcha นี้กระทบทุก cross-BC lookup ในระบบเท่ากัน (ไม่ใช่แค่ endpoint ใดหนึ่ง) — ก่อนหน้านี้ assertValidSupplier/assertValidProductLine ทุกจุดจะรายงาน "service unavailable" แทน "not found" เสมอเมื่อ reference ไม่มีอยู่จริง หลังแก้ทั้งสองจุด (2026-08) พฤติกรรมถูกต้องทั่วทั้งแพลตฟอร์ม — ตรวจสอบด้วยการยิง RMQ ตรง ๆ ไปยัง handler ก่อน/หลังแก้ ดูตัวอย่างการ probe ใน commit message ของ M1 (Purchase Order)

10 — Entity & Column Rules

Entity · คอลัมน์ · คลาสฐานร่วม

RULE · comment ของคอลัมน์ต้องบอกชื่อตารางต้นทางเสมอ

FK ใน BC เดียวกัน: อ้างอิง <table>.id (ตารางเดียวกัน มี FK constraint) / References <table>.id · uuid ข้าม BC (ไม่มี FK จริง): อ้างอิง <table>.id ใน <bc> (คนละ database ไม่มี FK constraint จริง) · ค่าที่ copy/denormalize มา: คัดลอกจาก <table>.<column> ณ เวลา… — ชื่อ property ไม่ต้องมี _snapshot ต่อท้าย comment คือสิ่งที่บันทึกความหมายนี้

RULE · วัน/เวลาเป็น timestamptz เท่านั้น ห้าม date/time

แม้ค่าที่ "รู้สึกเหมือน" วันที่ล้วน (document_date, valid_until, effective_from, expiry_date) ก็เป็น timestamptz / Date | null — เพราะ date ทิ้ง offset ของ client ทำให้ backend ต้องเดาว่าหมายถึงโซนเวลาไหน · DTO ใช้ @IsISO8601() ของโปรเจกต์เอง (ไม่ใช่ @IsDateString() ซึ่งรับ YYYY-MM-DD เปล่า ๆ ผ่าน) · service แปลงด้วย parseInstant() · การอ่านเป็น "วันตามปฏิทิน" ต้องผ่าน toBusinessDate()/businessYearOf()/todayBusinessDate() ที่ปักหมุด Asia/Bangkok เสมอ — .toISOString()/getFullYear()/::date ดิบ ๆ ให้วันผิดทุกครั้งที่เหตุการณ์เกิดหลัง 17:00 น. ไทย

RULE · คอลัมน์เงินเป็น numeric(18,4) และปัดด้วย roundMoney() เท่านั้น

sub_total · total_discount · total · line_total · unit_cost/unit_price · discount_value — roundMoney() ใช้ทศนิยม 4 ตำแหน่งตรงกับ scale ของคอลัมน์ เปลี่ยนอย่างใดอย่างหนึ่งโดยไม่เปลี่ยนอีกอย่าง = ตัดเลขทิ้งเงียบ ๆ

RULE · CHECK constraint ต้องประกาศบน entity ด้วย @Check()

CHECK ที่เขียนไว้ใน migration อย่างเดียวจะถูก migration:generate รอบถัดไปสั่ง DROP ทิ้งเงียบ ๆ เพราะ TypeORM เทียบ constraint จาก metadata ของ entity เท่านั้น

คลาสฐานร่วมใน @lib/common/abstracts/ — เอกสารที่ submit ได้ทุกใบมีรูปทรงเดียวกัน (หัวเอกสาร + บรรทัด) ส่วนที่เหมือนกันแบบ byte-for-byte เท่านั้นที่ขึ้นไปอยู่บนคลาสฐาน:

คลาสให้อะไร
SubmittableDocumentEntityremark_th/en · sent_by/at · approved_by/at · cancelled_by/at · cancel_reason · is_vat_included
DocumentLineItemEntityproduct_id (ข้าม BC → inventory) · qty · line_total
DocumentNumberCounterEntityyear · last_number + สัญญาการ lock ด้วย SELECT … FOR UPDATE · subclass ใส่แค่ @Entity() + @Unique('uq_<table>_year', ['year']) ของตัวเอง — หนึ่งตารางต่อ BC เสมอ ห้ามมีตารางตัวนับกลาง

ตั้งใจไม่แชร์: status (แต่ละโดเมนมี enum ของตัวเอง) · เลขที่เอกสาร · reference ของคู่ค้า (supplier_id/customer_id) · ฟิลด์เงินเฉพาะโดเมน (unit_cost vs unit_price, received_qty)

RULE · interface ภายในต้องมีไฟล์ของตัวเอง

ห้ามประกาศ interface ไว้ในไฟล์เดียวกับ service/controller ที่ใช้ แม้จะใช้ที่เดียว — วางที่ <module>/interfaces/<kebab-name>.interface.ts และ export ชื่อขึ้นต้นด้วย I (IUserSession, IResponsePaginatedService) · ใช้กับทั้ง interface ที่ export ออกไปและที่ใช้ภายใน module เท่านั้น

11 — Module Boundaries

ขอบเขต Module · เข้าถึงข้อมูลข้าม module

RULE · inject service เจ้าของ ไม่ใช่ repository ของมัน

service ที่ต้องอ่าน/ตรวจ entity ของ module อื่น (เช่น ยืนยันว่า product_id ที่ client ส่งมามีจริง) ให้ inject *Service ของ module นั้น — ห้าม @InjectRepository(OtherEntity) · ใช้ findByIdOrNull() เมื่อต้องการเปลี่ยน "หาไม่เจอ" เป็น BadRequestException ของตัวเอง (findById() จะโยน 404 ทั่วไปของ module เจ้าของแทน) · ถ้าต้องการ query เฉพาะทาง ให้เพิ่ม method แคบ ๆ ที่ service เจ้าของ ไม่ใช่เปิด repository ออกมา

RULE · ห้าม module import กันไปกลับ (A ↔ B)

ทางออกเรียงตามลำดับที่ควรลองก่อน — 1) ย้ายที่อยู่ของ route: sub-route ของ resource แม่ประกาศไว้ใน module ลูกได้ (ReorderLevelsController · UomConversionFactorsController · ProductBarcodesController ต่างประกาศ @Controller('products') จาก module ของตัวเอง โดย ProductModule ไม่เคย import กลับ) — เคสส่วนใหญ่จบตรงนี้เพราะ dependency จริงเป็นทางเดียวอยู่แล้ว มีแต่ route ที่ดูเหมือนของอีกฝั่ง · 2) ถ้าต้องใช้ทั้งสองทางจริง ให้แยก facade service (<DomainPair>OperationsService) ที่ inject ทั้ง A และ B แล้วอยู่ใน module ที่ import ทั้งคู่ — เส้นใน dependency graph ยังเป็นทางเดียวหมด (Facade → A, Facade → B)

RULE · ข้าม BC = uuid เท่านั้น

database-per-context — ไม่มี FK ข้ามฐานข้อมูล และห้าม query ข้าม BC ตรง ๆ ทุกกรณี ต้องผ่าน RPC (§08)

12 — Params · Permissions · Body

Path param · สิทธิ์ · body ว่าง

RULE · path param ที่เป็น UUID ต้องผ่าน ParseUuidParamPipe

@Param('id', ParseUuidParamPipe) ทุกตัว (:id, :role_id, param ที่เป็น FK ทุกอัน) — ปฏิเสธ UUID ผิดรูปด้วย 400002 ก่อนถึง service/DB · @Param('id') เปล่า ๆ ถือว่าผิด convention

RULE · endpoint ที่ไม่ @Public() ต้องมี @RequirePermission พร้อมชื่อ { th, en }

@RequirePermission('resource:action', { th, en }) — ต้องส่งชื่อสองภาษาเสมอ ไม่ใช่แค่สตริง permission · AuthGuard + PermissionGuard ลงทะเบียนเป็น APP_GUARD ใน CommonModule ทุก BC — endpoint ที่ไม่ public และไม่มี @RequirePermission() จะถูก default-deny · แคตตาล็อก permissions ไม่ hand-maintain: รัน npm run permissions:sync หรือกดปุ่ม Sync Permissions ในหน้า admin (POST /permission-syncs) · sync แตะเฉพาะแคตตาล็อก ไม่ผูก permission เข้า policy ให้ — ต้องมี grant migration แยกอีกที

RULE · body ว่างของ action route ถือเป็น {} ไม่ใช่ 400

bootstrap.util.ts แทน content-type parser ของ application/json ด้วยตัวที่คืน {} เมื่อ body ยาว 0 ไบต์ (นอกนั้นส่งต่อ parser เดิมของ Fastify ทุกประการ รวมถึง JSON เสีย → 400 เหมือนเดิม) — action route อย่าง POST /{doc}/{id}/approve จึงเรียกได้โดยไม่ต้องส่ง {} มาเอง · ลำดับการติดตั้งสำคัญ: ต้องเรียก await app.init() ก่อน แล้วค่อย removeContentTypeParser + ลงทะเบียนตัวใหม่ — ติดตั้งก่อนหน้านั้นทุก BC จะ crash-loop ตอน boot ด้วย FastifyError: Content type parser 'application/json' already present

13 — Migrations & Seed

Migration ต้อง generate จาก entity · seed ต้องตามให้ทัน

migration อยู่ที่ libs/database/src/migrations/erp_<bc>/ และรันแยกต่อ BC (pnpm run migration:run:<bc>) — แต่ละ BC มีตาราง migrations ของตัวเอง ลำดับเวลาจึงต้องถูกต้องภายใน BC เดียวกันเท่านั้น

RULE · แก้ที่ entity ก่อน แล้ว generate — ห้ามเขียน SQL schema เอง

pnpm run migration:generate:<bc> --name=<Name> แล้วอ่าน SQL ที่ได้ก่อน commit (generator อาจ emit DROP/สร้างใหม่สำหรับการ rename และมันอ่าน state ของ DB ที่เครื่องคุณจริง ๆ) · migration:create (เขียนมือ) ใช้เฉพาะสิ่งที่ generator มองไม่เห็น: backfill, seed, จูน index/constraint, DML ที่ต้องเรียงลำดับ · synchronize ห้ามเป็น true ใน BC ที่มี migration แล้ว

RULE · timestamp ในชื่อไฟล์ต้องเป็น Date.now() จริง

ห้ามคิดเลขกลม ๆ ขึ้นเอง หรือก๊อปของไฟล์ข้างเคียงแล้วบวก 1 — ตัวเลขนี้คือลำดับการรันและเป็น key ในตาราง migrations · ไฟล์เขียนมือใช้ node -e "console.log(Date.now())" · ชื่อไฟล์ <epoch_ms>-<PascalCaseName>.ts คลาส <PascalCaseName><epoch_ms> และ property name ต้องตรงกับชื่อไฟล์เป๊ะ · down() ต้อง undo up() ได้จริง ถ้าทำไม่ได้ให้เขียนบอกไว้ใน docblock อย่าปล่อยเป็น no-op ที่ทำให้เข้าใจผิด · seed ที่ข้าม 2 BC = 2 migration แยกกัน ไฟล์ละฐานข้อมูล

RULE · migration ที่แปลง date → timestamptz ต้องปักที่เที่ยงคืนกรุงเทพฯ

USING (col::timestamp AT TIME ZONE 'Asia/Bangkok') — cast เปล่า ๆ จะเลื่อนวันตามปฏิทินของแถวเดิมทันทีถ้า session ไม่ได้ตั้ง timezone เป็น UTC+7 อยู่แล้ว

RULE · เปลี่ยน schema แล้วต้องไปแก้ seeder ด้วยเสมอ

seeder ใน libs/database/src/scripts/seed/ เป็น pg client เขียน SQL ดิบ ไม่ผ่าน entity/service/DTO จึงไม่มีอะไร type-check ให้ — มันพังตอน runtime บนเครื่องที่ติดตั้งใหม่ นานหลังจากคุณแก้ · ต้องตามแก้เมื่อ: เพิ่ม/เปลี่ยนชื่อคอลัมน์หรือทำให้ NOT NULL · เปลี่ยน natural key (seeder re-resolve reference จาก DB ด้วย natural key ไม่ได้ถือ id ไว้ในหน่วยความจำ) · เปลี่ยนชื่อ/ลบตาราง หรือมี entity ใหม่เข้ามาใน aggregate ที่ seed อยู่ (แก้ truncates + SEEDERS[] พร้อม depends_on) · BC ใหม่เริ่ม seed ได้ (เพิ่มใน ISeedDatabase + SEED_DATABASE_ENV) · tree entity มีแถวเพิ่ม (ต้อง rebuild lft/rgt) · seeder ต้อง idempotent + deterministic — สุ่มค่าจาก stable-index.util.ts (hash ของ SKU) ห้ามใช้ faker/Math.random · ตรวจด้วย npm run seed -- --dry-run และ --fresh --yes บน DB ทดสอบเมื่อเป็นการเปลี่ยนโครงสร้าง
