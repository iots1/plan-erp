Standby ค้าง down
หลัง apt Auto-Upgrade

show pool_nodes โชว์ standby เป็น status=down แต่ pg_status=up — ระบบยังใช้งานได้ ไม่มีใครแจ้ง และ auto_failback ก็ไม่ดึงกลับให้เอง ค้างอยู่แบบนั้นได้เป็นวัน

Severity: High (Silent — HA เหลือครึ่งเดียว) Est. fix time: 10–15 นาที
1 — อาการ (Symptom)

ไม่มี error ฝั่ง app — เห็นได้จาก pool_nodes เท่านั้น

เคสนี้ เงียบสนิท — ต่างจาก Runbook 01 (All Nodes Down) ที่ app ต่อ DB ไม่ได้ทั้งระบบ ที่นี่ app ยังทำงานปกติทุกอย่าง เพราะ pgpool ยังมี node เหลือให้ route จะเห็นก็ต่อเมื่อไปเปิด show pool_nodes ดูเองเท่านั้น 

psql -h 172.16.0.226 -p 5432 -U postgres -c "show pool_nodes;"

 node_id |   hostname   | port | status | pg_status |  role   | select_cnt | replication_state
---------+--------------+------+--------+-----------+---------+------------+-------------------
 0       | 172.16.0.221 | 5432 | up     | up        | primary | 170591     |
 1       | 172.16.0.222 | 5432 | down   | up        | standby | 0          |
 2       | 172.16.0.223 | 5432 | up     | up        | standby | 14794      |
ลายเซ็น 3 อย่างที่ต้องเห็นพร้อมกัน

(1) status = down แต่ pg_status = up — pgpool มาร์กว่าตาย แต่ health check ยังตอบ · (2) select_cnt = 0 บน node นั้น ขณะที่ node อื่นเดินหน้าเรื่อยๆ · (3) replication_state และ replication_sync_state ว่างเปล่าทุก standby (ไม่ใช่แค่ตัวที่ down) — ข้อ 3 นี่แหละคือเบาะแสว่าทำไม auto_failback ถึงไม่ทำงาน ดู §4

บน pgpool node ที่เป็น watchdog leader จะมี log ย้อนหลังตอนที่มันตัด node ออก: 

DETAIL:  postmaster on DB node 1 was shutdown by administrative command
LOG:  received degenerate backend request for node_id: 1 from pid [18836]
LOG:  starting degeneration. shutdown host 172.16.0.222(5432)
LOG:  failover done. shutdown host 172.16.0.222(5432)

คำว่า shutdown by administrative command สำคัญมาก — มันแปลว่า PostgreSQL ถูกสั่งปิดอย่างสุภาพ ไม่ใช่ crash ไม่ใช่ network หลุด ให้ไปตามหาว่า "ใครสั่ง" ต่อใน §3

2 — ผลกระทบ (Impact)

ไม่ล่ม แต่ HA หายไปครึ่งหนึ่ง — และไม่มีใครรู้

READ CAPACITY

Load balance เหลือ 2 จาก 3

read query ทั้งหมดถูกอัดลง primary + standby ที่เหลือตัวเดียว โหลดต่อโหนดเพิ่มขึ้น ~50% แบบเงียบๆ

FAILOVER RISK

เหลือ standby ให้ promote ตัวเดียว

ถ้า primary ตายตอนนี้ pgpool มีตัวเลือกเดียว — ถ้าตัวนั้นดันมีปัญหาด้วยคือ total outage เต็มรูปแบบ

DETECTION

อยู่ได้เป็นวันโดยไม่มีใครเห็น

ของจริงค้าง 2 วันเต็ม (29 → 31 ส.ค. 2026) เจอตอนเปิด pool_nodes ดูด้วยเรื่องอื่น ไม่ได้เจอจาก alert

ทำไมถึงไม่ escalate เป็น Critical

ข้อมูลไม่เสี่ยง — streaming replication ยังวิ่งปกติ (slot active, lag ต่ำกว่า 1ms) node ที่ down รับข้อมูลครบทุกไบต์ แค่ pgpool ไม่ยอม route traffic ไปหามันเท่านั้น พอ attach กลับก็ใช้งานได้ทันทีโดยไม่ต้อง re-clone

3 — วินิจฉัย (Diagnosis)

4 ขั้นตอน — อย่าข้ามขั้นที่ 4

ขั้นที่ 1–3 ยืนยันว่าเป็นเคสนี้และหาต้นเหตุที่ทำให้ node หลุด แต่ ขั้นที่ 4 คือขั้นที่คนมักข้าม — มันตอบคำถามว่า "ทำไม auto_failback ที่เปิดอยู่ถึงไม่ดึงกลับเอง" ถ้าไม่แก้ตรงนั้น attach กลับไปก็จะค้างซ้ำอีกในรอบหน้า

1

ยืนยันว่า PostgreSQL จริงยังปกติ (จะได้ไม่ไปแตะ replication)

ssh ovh-ppm "sudo -u postgres repmgr cluster show"
ssh ovh-ppm "sudo -u postgres psql -x -c \
  'select application_name, state, sync_state, write_lag from pg_stat_replication;'"
สิ่งที่ควรได้

repmgr โชว์ครบ 3 โหนด running · pg_stat_replication มี standby ครบทุกตัว state = streaming และ write_lag ระดับมิลลิวินาที — แปลว่า replication layer ไม่มีปัญหาเลย ปัญหาอยู่ที่ pgpool ล้วนๆ

2

หาว่า pgpool ตัด node ออกตอนไหน และเพราะอะไร

ใช้เวลาจากคอลัมน์ last_status_change ใน show pool_nodes เป็นจุดตั้งต้น แล้วไปขุด journal ของ pgpool leader รอบๆ เวลานั้น 

ssh ovh-pgpool1 "journalctl -u pgpool2 --since '2026-08-29 06:45' --until '2026-08-29 07:00' \
  --no-pager | grep -iE 'degenerate|shutdown|failover'"

หมายเหตุ: user ปกติอ่าน journal ได้โดยไม่ต้อง sudo ถ้าอยู่ในกลุ่ม adm — แต่ /etc/pgpool2/pgpool.conf ต้อง sudo เสมอ

3

ไปที่ DB node ตัวนั้น — ใครสั่งปิด PostgreSQL

กรอง postgres_exporter ออกก่อน ไม่งั้นมันจะท่วมจอ (ดู §6 — exporter บน replica พังอยู่) 

ssh ovh-ppr1 "journalctl --since '2026-08-29 06:48' --until '2026-08-29 06:56' --no-pager \
  | grep -viE 'postgres_exporter|sysstat'"

ssh ovh-ppr1 "grep -A6 '2026-08-29 06:51' /var/log/unattended-upgrades/unattended-upgrades.log"
ผู้ต้องสงสัยอันดับหนึ่ง

Starting apt-daily-upgrade.service ตามด้วย Stopping postgresql@18-main.service ภายในไม่กี่วินาที — ของจริงคือ libpam0g ถูกอัป แล้ว needrestart สั่งรีสตาร์ททุก service ที่ link libpam

4

ขั้นสำคัญที่สุด — เทียบ application_name สองฝั่ง

pgpool จับคู่ standby ใน pg_stat_replication ด้วยค่า backend_application_nameN ถ้าสองฝั่งนี้ไม่ตรงกัน auto_failback จะยืนยันไม่ได้ว่า node นั้น streaming อยู่ → ไม่ยิง attach ให้ 

# ฝั่ง pgpool คาดหวังชื่ออะไร
psql -h 172.16.0.226 -U postgres -tAc "show pool_status;" | grep backend_application

# ฝั่ง PostgreSQL ส่งชื่ออะไรมาจริง
ssh ovh-ppm "sudo -u postgres psql -tAc 'select application_name from pg_stat_replication;'"
Backendpgpool คาดหวังPostgreSQL ส่งมาจริงตรงกัน?
0 · 172.16.0.221node0ppm❌
1 · 172.16.0.222node1ppr1❌
2 · 172.16.0.223node2ppr2❌

ค่าฝั่ง PostgreSQL มาจาก application_name ใน primary_conninfo ซึ่ง repmgr เขียนให้เป็น node_name ของ repmgr เสมอ — ไม่ใช่ค่าที่ตั้งเองได้ตามใจ ดังนั้นให้แก้ฝั่ง pgpool ให้ตามมันดีกว่า (ดู §5)

4 — สาเหตุ (Root Cause)

ความผิดพลาด 3 ชั้นที่ต่อกันพอดี

แต่ละชั้นเดี่ยวๆ ไม่ร้ายแรง — ชั้นแรกเป็นพฤติกรรมที่ถูกต้องของ pgpool ด้วยซ้ำ แต่พอต่อกันครบสามชั้นจึงกลายเป็น "standby หายไปเงียบๆ เป็นวัน"

ชั้น 1

apt แตะ database เอง

apt-daily-upgrade.timer เปิดอยู่ทั้ง 6 เครื่อง รวม primary — และ needrestart ไม่มี override ให้ postgresql/pgpool เลย ของจริง primary ก็โดนรีสตาร์ทไปแล้ววันเดียวกัน

ชั้น 2

auto_failback เปิดแต่ใช้ไม่ได้

auto_failback = 1, interval = 10 ตั้งไว้ถูกทุกอย่าง แต่ชื่อไม่แมตช์ → เป็น config ที่ดู "เปิดอยู่" ในทุก dashboard แต่ไม่เคยทำงานสักครั้ง

ชั้น 3

monitoring ตาบอด

PCP password ถูก generate แยกต่อ node แต่ .pcppass ถูก copy ข้ามเครื่องมา → auth ไม่ผ่าน 2 ใน 3 node แถม log ถูก flood ทุก 15 วินาที

ต่างจาก Runbook 01 ยังไง

Runbook 01 บอกว่า "pgpool ไม่ re-attach ให้เองต้องใช้มือ" ซึ่งจริงในกรณี ทุก node down พร้อมกัน (ตอนนั้น pgpool ไม่เห็น primary เลย auto_failback ไม่มีทางทำงานได้อยู่แล้ว) — แต่ในเคส standby ตัวเดียวหลุด แบบนี้ auto_failback ควรจะฟื้นให้เองได้ การที่มันไม่ฟื้นคือบั๊ก config ไม่ใช่ข้อจำกัดของ pgpool

5 — การแก้ไข (Fix)

แก้ต้นเหตุก่อน แล้วค่อย attach — อย่าสลับลำดับ

ถ้ารีบ pcp_attach_node ก่อนโดยไม่แก้ §5.2 ระบบจะกลับมาปกติจริง แต่รอบหน้าที่มีการรีสตาร์ท PostgreSQL ก็จะค้าง down ซ้ำอีกเหมือนเดิม

1

ห้าม apt แตะ database — ทำครบทั้ง 6 เครื่อง

สร้าง snippet ให้ needrestart ข้าม service กลุ่ม DB ไฟล์ใน conf.d/ ถูก eval ต่อท้าย config หลัก และเรียงตามชื่อ — ขึ้นต้นด้วย 99- เพื่อให้ทับค่าอื่นได้แน่นอน 

# /etc/needrestart/conf.d/99-no-db-autorestart.conf
$nrconf{override_rc}->{qr(^postgresql)} = 0;
$nrconf{override_rc}->{qr(^pgpool)}     = 0;
$nrconf{override_rc}->{qr(^repmgr)}     = 0;
for h in ovh-ppm ovh-ppr1 ovh-ppr2 ovh-pgpool1 ovh-pgpool2 ovh-pgpool3; do
  scp 99-no-db-autorestart.conf $h:/tmp/
  ssh $h "sudo cp /tmp/99-no-db-autorestart.conf /etc/needrestart/conf.d/"
  ssh $h "sudo needrestart -v -b -r l 2>&1 | grep 'eval.*99-no-db'"
done
ต้องเห็นบรรทัดนี้ทุกเครื่อง = config ถูก parse จริง

[main] eval /etc/needrestart/conf.d/99-no-db-autorestart.conf
ถ้า syntax ผิด needrestart จะ die ทันที ซึ่งจะทำให้ apt ทั้งเครื่องพัง — ต้องเช็คทุกครั้ง

อย่าตกใจ ถ้า -r l ยังลิสต์ repmgrd.service อยู่ — โหมด list รายงานทุก service ที่ "ควร" รีสตาร์ท ส่วน override_rc มีผลตอนโหมด restart จริงเท่านั้น (ดู needrestart บรรทัด ~1092)

2

แก้ backend_application_name ให้ตรง repmgr — ทั้ง 3 pgpool node

ทำ backup ก่อนเสมอ แล้วแก้ทีละเครื่อง — config ต้องเหมือนกันทั้ง 3 ตัว ไม่งั้น watchdog จะมองเห็น cluster คนละแบบ 

for h in ovh-pgpool1 ovh-pgpool2 ovh-pgpool3; do
  ssh $h "sudo cp /etc/pgpool2/pgpool.conf /etc/pgpool2/pgpool.conf.bak-\$(date +%Y%m%d)"
  ssh $h "sudo sed -i \
    -e \"s/^backend_application_name0 = 'node0'/backend_application_name0 = 'ppm'/\"  \
    -e \"s/^backend_application_name1 = 'node1'/backend_application_name1 = 'ppr1'/\" \
    -e \"s/^backend_application_name2 = 'node2'/backend_application_name2 = 'ppr2'/\" \
    /etc/pgpool2/pgpool.conf"
  ssh $h "sudo systemctl reload pgpool2"
done

reload = SIGHUP ไม่ตัด connection ของ client — ยืนยันว่า pgpool รับค่าใหม่แล้วด้วย show pool_status ก่อนไปข้อ 3 ถ้า reload แล้วค่ายังเป็นของเก่า ให้ restart pgpool ทีละตัว โดยไล่จาก standby watchdog ก่อน แล้วค่อย leader เป็นตัวสุดท้าย

แก้มืออย่างเดียวไม่พอ — pgpool.conf ถูก generate ทับทุกครั้งที่รัน installer

install-pgpool.sh เขียน pgpool.conf ใหม่ทั้งไฟล์ เพราะฉะนั้นต้องส่ง flag ด้วยทุกครั้ง ไม่งั้น deploy รอบหน้าย้อนกลับเป็น node0/1/2 เงียบๆ: --backend-app-names=ppm,ppr1,ppr2 (เรียงตรงกับ --backends) — flag นี้เพิ่มเข้า script แล้ว 2026-09-01 ถ้าไม่ใส่จะ warn ดังๆ ถ้าใส่ไม่ครบจำนวนจะ die ทันที

3

ซ่อม PCP credential ถ้า auth ไม่ผ่าน

ต้องทำก่อนข้อ 4 ถ้าเครื่องที่จะรัน attach เป็นเครื่องที่ auth พัง — เช็คก่อนว่าเครื่องไหนใช้ได้: 

for h in ovh-pgpool1 ovh-pgpool2 ovh-pgpool3; do
  echo -n "$h: "
  ssh $h "cat /var/lib/node_exporter/textfile_collector/pgpool_watchdog.prom \
    | grep scrape_success"
done
# scrape_success 1 = PCP ใช้ได้ · 0 = auth พัง
แก้ทีละเครื่องไม่พอ — ต้องทำครบ 6 เครื่องพร้อมกัน

รหัส PCP ต้อง เหมือนกันทุก node เพราะ repmgr event hook เรียก pcp_attach_node ข้ามเครื่อง ไปหา pgpool ทุกตัว — ไม่ใช่แค่ -h localhost · สองไฟล์ที่ต้องตรงกัน: /etc/pgpool2/pcp.conf เก็บ username:md5(password) · .pcppass เก็บ host:port:username:password plaintext (0600)

host ต้องเป็น * ไม่ใช่ localhost — เขียนเป็น localhost จะใช้ได้แค่ในเครื่องตัวเอง แล้ว hook จะพังเงียบ (นี่คือสาเหตุที่บั๊กนี้กลับมาซ้ำ 3 รอบ) 

# 1) generate รหัสใหม่ 1 ค่า บนเครื่องเดียว แล้วสร้างไฟล์ทั้งสองจากมัน
ssh ovh-pgpool1 'umask 077
  PW=$(openssl rand -base64 32 | tr -dc "A-Za-z0-9" | cut -c1-28)
  printf "pgpool_admin:%s\n" "$(printf %s "$PW" | md5sum | cut -d" " -f1)" > /tmp/pcp.conf.new
  printf "*:9898:pgpool_admin:%s\n" "$PW" > /tmp/pcppass.new'

# 2) กระจายไป "ทั้ง 6 เครื่อง" — pgpool ได้ทั้งสองไฟล์ / DB node ได้แค่ .pcppass
#    pgpool ×3 :  pcp.conf (0644 root) + .pcppass ของ postgres และ root (0600)
#    ppm/ppr1/ppr2: .pcppass ของ postgres (0600) — hook รันเป็น postgres

# 3) reload ไล่จาก wd_priority ต่ำสุด → VIP leader เป็นตัวสุดท้าย
ssh ovh-pgpool3 "sudo systemctl reload pgpool2"
ssh ovh-pgpool2 "sudo systemctl reload pgpool2"
ssh ovh-pgpool1 "sudo systemctl reload pgpool2"   # ตัวถือ VIP
ยืนยันให้ครบ 9 เส้นทาง ไม่ใช่แค่ localhost — จุดที่การแก้รอบก่อนพลาด
for n in ovh-ppm ovh-ppr1 ovh-ppr2; do
  ssh $n 'for h in <pgpool1> <pgpool2> <pgpool3>; do
    sudo -u postgres env HOME=/var/lib/postgresql \
      pcp_node_info -h $h -p 9898 -U pgpool_admin -w -n 0 2>&1 | head -1
  done'
done
# ต้องได้ข้อมูล node ครบ 9 บรรทัด — ไม่มี FATAL แม้แต่บรรทัดเดียว

อย่าลืม merge entry ของ user อื่นที่มีอยู่เดิมใน pcp.conf ก่อนเขียนทับ · และแก้ที่ generator ด้วย — install-pgpool.sh เคยเขียน localhost: ตายตัว (แก้แล้ว 2026-09-01) และต้องส่ง --pcp-password ค่าเดียวกันให้ทุก node เสมอ ไม่ปล่อยให้ generate เอง

4

Attach node กลับ — ส่วนใหญ่ไม่ต้องทำเอง

ยืนยันจากของจริง 2026-08-31: พอ reload เสร็จ node กลับมาเอง ~8 วินาที

ทันทีที่ pgpool ตัวใดตัวหนึ่ง reload แล้วเห็นชื่อแมตช์ auto_failback จะยิง FAILBACK_REQUEST เองแล้ว watchdog กระจายให้ทั้ง cluster — ให้รอ 15 วินาทีแล้วเช็ค §6 ก่อนเสมอ ถ้ากลับมาเองแล้วก็ข้ามข้อนี้ไปได้เลย

รู้ไว้: failback มีผลกับ client ไม่ว่าจะมาจาก auto หรือสั่งเอง

failback event ทำให้ pgpool child process ทุกตัว restarting myself และ discarding existing connections — connection ที่ค้างอยู่จะถูกตัดทั้งหมด (~1–2 วินาที) query ที่กำลังวิ่งจะ error ส่วน connection pool ของ app จะ reconnect เอง แปลว่า §5.2 เองก็ทำให้เกิด connection reset ได้ทันที ไม่ใช่แค่ข้อนี้ — วางแผนจังหวะตั้งแต่ตอน reload เลย ไม่ใช่ค่อยมาคิดตอน attach 

# รันจาก pgpool node ที่ PCP auth ผ่าน (ดูข้อ 3)
# watchdog จะ propagate failback ให้ทั้ง cluster เอง
ssh ovh-pgpool2 "sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
  pcp_attach_node -h localhost -p 9898 -U pgpool_admin -w -n 1"

ควรได้ pcp_attach_node -- Command Successful — ถ้าเพิ่งผ่านเหตุการณ์ที่ primary ตาย มา ให้ attach ครบทั้ง -n 0 1 2 ตาม Runbook 01 แทน

คือคอลัมน์ replication_state ต้องขึ้นเป็น streaming แล้ว (จากเดิมที่ว่าง) — นั่นแปลว่า §5.2 ได้ผล และ auto_failback จะทำงานเองได้จริงในรอบหน้า ถ้า status เป็น up แต่ replication_state ยังว่าง แปลว่าแก้ยังไม่ครบ กลับไปดู §3 ข้อ 4

2

ทดสอบ auto_failback ว่าฟื้นเองได้จริง (ทำในเวลาว่าง)

เป็นการทดสอบเดียวที่พิสูจน์ว่า §5.2 ใช้ได้จริง — รีสตาร์ท PostgreSQL บน standby ตัวหนึ่งแล้วดูว่ามันกลับมาเองไหม ทำกับ standby เท่านั้น ห้ามทำกับ primary 

ssh ovh-ppr2 "sudo systemctl restart postgresql@18-main"
# เช็คได้เลยไม่ต้องรอนาน — ของจริงกลับมาเองใน ~2 วินาที
psql -h 172.16.0.226 -p 5432 -U postgres -c "show pool_nodes;"
ssh ovh-pgpool1 "journalctl -u pgpool2 --since '-2min' --no-pager | grep -i failback"
ผลซ้อมจริง 2026-09-01 — เร็วกว่าที่คาดมาก

15:25:49.524 degenerate node 2 → 15:25:51.446 received failback request → 15:25:51.489 failback done — รวม ~2 วินาที และคำสั่ง failback ยิงมาจาก health_check2 เอง ไม่ใช่จาก auto_failback_interval เพราะ health check เจอว่า node กลับมาแล้วก่อน interval จะครบด้วยซ้ำ ถ้าเกิน 30 วินาทีแล้วยังไม่กลับ = §5.2 ยังไม่ได้ผล ให้กลับไปดู §3 ข้อ 4

ป้องกันระยะยาว — 3 อย่างที่ควรทำต่อ

(1) Alert ที่ควรมีตั้งแต่แรก: ยิงเตือนเมื่อ status != pg_status บน node ใดนานเกิน 1 นาที — เคสนี้ค้าง 2 วันเพราะไม่มี alert ตัวนี้ · (2) pgpool_watchdog_scrape_success == 0 ต้องเป็น alert ด้วย ไม่งั้น monitoring พังแล้วก็ไม่มีใครรู้อีก (นี่คือ meta-bug ของเคสนี้) — metric ตัวนี้คุ้มเป็นพิเศษ เพราะใช้ credential เส้นทางเดียวกับ repmgr event hook พอ PCP drift เมื่อไหร่มันเป็น 0 ทันที เท่ากับ alert ตัวเดียวเฝ้าได้ทั้ง monitoring และ auto-reattach หลัง failover (scrape_success = 1 ครบ 3 node แล้วตั้งแต่ 2026-09-01 แต่ยังไม่มี alert) · (3) postgres_exporter บน replica ยังพังอยู่ — เวอร์ชัน 0.15.0 (ต.ค. 2023) เก่าเกินสำหรับ PostgreSQL 18 ขึ้น collector failed name=stat_bgwriter · column "checkpoints_timed" does not exist ทุก 15 วินาที เพราะ PG17+ ย้าย column ไป pg_stat_checkpointer แก้ด้วยการอัป exporter หรือปิด collector นั้นชั่วคราวด้วย --no-collector.stat_bgwriter
