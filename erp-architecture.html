01 — Executive Summary

บทสรุปผู้บริหาร

ระบบเดิมเป็น Legacy ERP System ที่รวมงาน คลังสินค้า (Stock), หน้าร้าน (Store/POS) และ บัญชี (Accounting) ไว้ในฐานข้อมูลก้อนเดียว (Monolith) ทำให้ขยายยาก แก้ไขเสี่ยง และไม่สามารถคำนวณต้นทุน–กำไรระดับ Lot ได้แม่นยำ

เป้าหมายคือการออกแบบใหม่เป็น Microservices แบบ DDD บน Monorepo (Nx + pnpm) โดยแต่ละ Bounded Context เป็นเจ้าของฐานข้อมูลของตนเอง ห้าม Join ข้ามฐานข้อมูล และอ้างอิงข้อมูลข้ามบริบทด้วย UUID เท่านั้น เพื่อให้แต่ละบริการ Deploy และ Scale ได้อิสระ

หัวใจของโครงการคือความถูกต้องของ การตัดสต็อกแบบ FIFO/FEFO, การจัดการ Lot & วันหมดอายุ และ การคำนวณ COGS และกำไร/ขาดทุนต่อ Lot ซึ่งอิงต้นทุนนำเข้าจริงของแต่ละล็อต ไม่ใช่ต้นทุนเฉลี่ย

Target Outcomes
  • →8 บริการอิสระ แยกฐานข้อมูลตามบริบทธุรกิจ
  • →ต้นทุนแม่นยำ ระดับ Lot ทุกธุรกรรม
  • →2 ภาษา (ไทย/อังกฤษ) ครบทั้ง UI, ข้อความระบบ และ Master Data
  • →Event-Driven ผ่าน RabbitMQ ลดการผูกกันระหว่างบริการ
  • →ไฟล์รวมศูนย์ บน MinIO พร้อม Presigned URL
02 — Architecture Blueprint

พิมพ์เขียวสถาปัตยกรรม

ทุกบริการเขียนด้วย NestJS 11 บน Fastify อยู่ในเวิร์กสเปซเดียวกัน (Nx) Frontend เป็น Next.js เรียกใช้ผ่าน Kong (API Gateway ระดับ infrastructure — ไม่ใช่ service ที่เขียนเอง) ทำหน้าที่ path-based routing เข้าแต่ละ BC ตาม prefix ของตัวเอง (`/auth/v1`, `/iam/v1`, ...) ผ่าน domain เดียว การสื่อสารระหว่างบริการแบ่งเป็น 2 รูปแบบชัดเจน: RabbitMQ สำหรับเหตุการณ์แบบ async (pub/sub) และ TCP สำหรับการร้องขอแบบ sync (request/response)

System Context Map · Database-per-Context & Supporting Infrastructure
Bounded Context BC · Critical (Lot/COGS) Supporting Infrastructure

ทุกกล่องในแผนภาพนี้มาจาก Docker Compose จริงใน infrastructure/ — stack infra-erp/ (Postgres · Redis · RabbitMQ · MinIO · Gotenberg) คือ dependency ที่ทุก BC ต้องพึ่งตอนรัน วาดเป็นแถบ "Supporting Infrastructure" แยกไว้ใต้ RabbitMQ โดยตั้งใจไม่วาดลูกศรเชื่อมจาก BC แต่ละตัว (เดิมทดลองวาดแล้วเส้นทับกันจนอ่านยาก) — ใครเรียกอะไรอธิบายเป็นข้อความแทน: Redis เก็บ session/CSRF token ที่ auth เขียนตอน login แต่ทุก BC อ่านผ่าน AuthGuard ที่มากับ libs/common ไม่ใช่แค่ auth เอง · Gotenberg เป็น headless Chromium ที่ report-bc เรียกแปลง EJS template เป็น PDF แล้วส่งต่อให้ storage-bc เก็บถาวรใน MinIO อีกที (ไม่ใช่ BC ใหม่ — เป็นแค่ renderer ไม่มีฐานข้อมูลของตัวเอง) · นอกจากนี้ยังมี stack observability/ แยกต่างหาก (Grafana Alloy · Tempo · Loki · Prometheus · Grafana) รับ trace/log จากทุก BC แต่ไม่ได้อยู่ใน request path ธุรกิจโดยตรง จึงไม่ได้วาดในแผนภาพนี้ — ดู infrastructure/README.md สำหรับรายละเอียด provisioning เต็ม

TCP — Synchronous

ใช้เมื่อผู้เรียก “ต้องรอคำตอบทันที” เช่น Gateway ถามสิทธิ์จาก iam, ตรวจ Availability จาก inventory-bc หรือขอ Presigned URL จาก storage-bc. ใช้ NestJS Microservice Transport แบบ TCP

RabbitMQ — Asynchronous

ใช้เผยแพร่ Domain Event แบบ fire-and-forget เช่น delivery.confirmed, stock.deducted, lot.created. ผู้สนใจ (เช่น finance-bc, report-bc) Subscribe เองโดยผู้ส่งไม่ต้องรับรู้ ทำให้ระบบ Decoupled

05 — Admin Console & Access Control

คอนโซลผู้ดูแลระบบ (IAM Admin Console) & กลไกควบคุมสิทธิ์

นอกจาก JSON:API ที่ทุก client (Next.js, mobile, service อื่น) เรียกใช้ iam-bc ยังเสิร์ฟ เว็บแอดมินแยกต่างหาก ด้วย NestJS-rendered EJS (ไม่มี framework ฝั่ง client) — เจาะจงสำหรับ Security Admin / Superadmin ใช้จัดการแกนความปลอดภัยของทั้งระบบ (ผู้ใช้ · บทบาท · policy · แคตตาล็อกสิทธิ์ · access key · session) โดยไม่ต้องพึ่ง frontend หลักเลย

หน้าจอทั้งหมดใน Admin Console

เสิร์ฟจาก apps/iam/views ที่ path /iam/v1/views/* — 1 หน้า = 1 route แยก (ไม่ใช่ SPA):

dashboardusers rolespolicies permissionspermission-sync-logs access-keyssessions audit-logsprint-templates document-typessystem-setting

SSR shell เปิดเผยได้ · ข้อมูลจริงยังถูกคุม

ทุก view controller เป็น @Public() — เสิร์ฟ HTML shell โดยไม่เช็ค session ฝั่ง server (route กันเข้าหน้าเป็นแค่ client-side JS ที่ redirect ออกถ้าไม่มี page:*) แต่ ทุก request ที่ดึง/แก้ข้อมูลจริง เป็นการเรียก JSON:API ปกติผ่าน httpOnly cookie จึงยังผ่าน Guard chain เต็มรูปแบบเสมอ (ดูขวา) — SSR shell เองไม่มีข้อมูลลับฝังอยู่เลย

Auth Middleware · Guard Chain (เรียงตามลำดับจริงที่รันทุก request)

ลำดับGuardทำอะไร
1AuthGuardข้ามถ้า @Public() · อ่าน token จาก Authorization: Bearer ก่อน แล้ว fallback ไปคุกกี้ access_token · verify JWT (ลายเซ็น+หมดอายุ) แล้วเช็ค Redis session ซ้ำ (session:<jti>) — revoke/logout มีผลทันทีแม้ JWT ยังไม่หมดอายุ
2AccessKeyGuardno-op ยกเว้น route ติด @UseAccessKey() — auth แบบ HMAC signature (X-Access-Key-Id/X-Timestamp/X-Signature) สำหรับเรียกแบบ system-to-system แทน JWT ตรวจสอบผ่าน iam-bc + ล็อก key ชั่วคราวถ้าผิดซ้ำเกิน 5 ครั้ง/นาที
3CsrfGuardข้าม GET/HEAD/OPTIONS และ route ที่ไม่มีคุกกี้ csrf_token — ถ้ามี ต้องมี header x-csrf-token ตรงกัน (double-submit) กันเว็บอื่นยิง request แทนผู้ใช้ที่ login ค้างไว้ผ่าน iam-view
4PermissionGuardต้องมี @RequirePermission('resource:action') เสมอ (default-deny) — เช็คจาก permission ที่ resolve ไว้ใน session ก่อน ถ้าเป็น conditional permission ถึงเรียก iam-bc ประเมิน ABAC condition แบบ live

ทั้ง 4 ตัวลงทะเบียนเป็น APP_GUARD ใน libs/common/src/common.module.ts ครอบทุก BC โดยอัตโนมัติ ไม่ต้องเปิดใช้ทีละบริการ

Permission Sync · แคตตาล็อกสิทธิ์ไม่ hand-maintain

npm run permissions:sync (หรือกดปุ่ม "Sync Permissions" ในหน้า Permissions ของ Admin Console) สแกนหาสิทธิ์จาก 3 แหล่งพร้อมกัน แล้ว diff/apply เข้าตาราง permissions — แถวที่หายไปจากโค้ดถูก soft-delete (ไม่ลบจริง), ทุกรอบบันทึกประวัติเป็น permission_sync_logs

api plane

สแกน @RequirePermission('resource:action', {th, en}) ทุกไฟล์ใน apps/<service>/src/**

ui plane · attribute scan

สแกนสตริง data-permission="page:*" / "component:*" ใน views/** + public/** — ไม่มีที่เก็บชื่อ th/en จึงได้แค่ placeholder

ui plane · manifest

อ่าน apps/<service>/ui-permissions.manifest.json ถ้ามี — ให้ชื่อ th/en มาตรง ๆ จึงชนะผลจาก attribute scan เสมอเมื่อ key ซ้ำกัน

UI Permissions Manifest · ทำไม frontend-web ต้องมี

apps/frontend-web/ui-permissions.manifest.json ในปัจจุบันเป็น โฟลเดอร์ placeholder มีแค่ไฟล์ manifest ไฟล์เดียว ไม่มีโค้ด NestJS จริง — ยืนแทนที่ frontend ในอนาคต (เช่น Next.js) ที่ JSX compile ทิ้ง literal string data-permission="..." ไปหมดหลัง build ทำให้สแกนแบบ regex หาไม่เจอ จึงต้องประกาศ page:* / component:* ล่วงหน้าเป็น JSON แทน 

{
  "pages": [
    {
      "permission": "page:view_dashboard",
      "name": { "th": "หน้าแดชบอร์ด", "en": "Dashboard page" },
      "components": [
        { "permission": "component:btn_fiter_date",
          "name": { "th": "ปุ่ม กรองวันที่", "en": "Filter date button" } }
      ]
    }
  ]
}

component ที่ซ้อนอยู่ใต้ page สืบทอด resource ของ page นั้น เสมอ (ไม่ใช่ resource ของตัวเอง) — เพื่อให้ dropdown "หน้าจอ / Component Group (UI)" ในหน้า Policy Generator รวมสิทธิ์ของหน้า + component ย่อยไว้กลุ่มเดียวกัน ต่างจาก apps/iam ที่มีทั้ง data-permission จริงใน EJS และ manifest ของตัวเอง — สแกนทั้งคู่ แต่ manifest ชนะเมื่อ key ชนกัน

RULE · SNAPSHOT ไม่ใช่ JOIN

ทุกครั้งที่เอกสารข้าม BC ข้อมูลที่ต้องพิมพ์บนเอกสาร จะถูก คัดลอกลงแถวนั้น ไม่ join ตอนพิมพ์ — ลูกค้าเปลี่ยนชื่อ หรือสินค้าถูกเปลี่ยนชื่อ/เปลี่ยนประเภทภาษีทีหลัง ต้องไม่ย้อนไปแก้เอกสารที่ออกไปแล้ว

RULE · อ้างข้าม BC ด้วย UUID เท่านั้น

ทุกลูกศรข้าม BC ในไดอะแกรมเป็น RPC หรือ event — ไม่มี FK ข้าม database และไม่มีการ query ตรงข้าม BC แม้แต่ครั้งเดียว

RULE · ราคาและภาษีเชื่อหลังบ้าน

client กำหนดราคาได้แต่ต้องอยู่ในกรอบ ±20% ของ item_prices · ส่วน ประเภทภาษี client กำหนดไม่ได้เลย ต้องมาจาก inventory-bc เท่านั้น

RULE · เอกสารภาษี immutable

ใบเสนอราคาแก้ได้ตอน DRAFT · ใบกำกับภาษีที่ ISSUED แล้วแก้ไม่ได้ เลขที่ถูกใช้แล้วห้ามนำกลับมาใช้ซ้ำ แก้ยอดต้องออกใบลด/เพิ่มหนี้

RULE · ฝั่งเจ้าหนี้ (AP) ครบเท่าฝั่งลูกหนี้ (AR) แล้ว — 2026-08-30

เดิมฝั่งซื้อมีแค่ PO → GRN แล้วข้ามไป PaymentEntry.type=PAY ตรงๆ โดยไม่มีเอกสารบอกว่าเป็นหนี้เท่าไหร่ · ตอนนี้มี ใบตั้งหนี้ผู้ขาย (AP Invoice) คั่นกลางแล้ว: PO → GRN → AP Invoice → Payment สมมาตรกับฝั่งขาย Quotation → SO → Delivery → Receipt → Billing Note → Payment · AP Clerk สร้างเองเมื่อใบแจ้งหนี้ของผู้ขายมาถึง (3-way match กับ PO+GRN) · payment_allocations ตัดได้ทั้ง receipt_id (AR) และ ap_invoice_id (AP) โดยมี CHECK บังคับให้มีทีละอัน — PAY จึงบอกได้แล้วว่าจ่ายไปตัดใบไหน และคำนวณยอดค้างจ่ายต่อผู้ขายได้จริง · รายละเอียดเต็ม: srs-p5.html "RULE · AP 3-WAY MATCH"

ชม. รวม BE+FE ต่อรายการ · #1–#6 (P0) คือ critical path ของ Stock — ต้องเสร็จก่อนจึงจะเดิน Phase 4 (Sales/PO) ได้ · งาน P2 ไม่กระทบ schema หลัก เพิ่มภายหลังได้โดยไม่ break ของเดิม

ปรับความแม่นยำจากการตรวจโครงสร้าง + source code จริง

รายละเอียดต่อไปนี้ถูก ยืนยัน/เพิ่มเข้า scope หลังตรวจ schema (736 ตาราง) และ controller logic ของระบบสต็อกเชิงอ้างอิง ทำให้ประมาณการงานสมจริงขึ้น (รวม ~+40–60 ชม. กระจายใน P0/P1):

  • 01Item Group + Warehouse เป็น tree (nested-set lft/rgt) ไม่ใช่ parent FK เฉย ๆ — ต้องเขียน logic rebuild lft/rgt ตอน insert/move (BE +16)
  • 02Ledger เก็บ running balance ต่อ movement + ตาราง cache balance ต่อ item×warehouse (แบบ Bin) เพื่อให้ Stock Balance เร็ว (BE +16)
  • 03Stock Entry เพิ่มเป็น 4 ประเภท (Receipt / Transfer / Issue / Repack) + รองรับ in-transit warehouse ตอนโอนข้ามสาขา (BE +8)
  • 04Stock Reconciliation ใช้จำนวน absolute (นับได้จริง) แล้วระบบคำนวณ delta เอง — เปลี่ยนจากกรอก qty_delta ตรง ๆ
  • 05Stock Settings เพิ่ม frozen period + over-receipt allowance · เตรียม seed หน่วยนับมาตรฐาน (UOM) ~200+ รายการเป็น master data ตั้งต้น (BE +8)
  • 06ทุกเอกสารธุรกรรมเป็น submittable (draft → submit → cancel) — ต้องมี state machine + logic โพสต์/ยกเลิก ledger ทุกใบ (GR, Delivery, Stock Entry, Reconciliation) ไม่ใช่ CRUD ธรรมดา
  • 07งานที่หนักสุดคือ valuation engine (FIFO/FEFO ต่อ warehouse×batch + recompute) — ในระบบอ้างอิงเป็นโค้ด ~2,600 บรรทัด · และ ฟอร์ม Item ใหญ่มาก (79 ฟิลด์ + 8 child tables: barcode, reorder, UOM conversion, variant, default, supplier ฯลฯ) → FE ต้องทำแบบ tabbed form
Phase 4 · Procurement & Sales — ที่พบจริง (+72 ชม.)
  • 01Pricing Rule engine — ราคาพิเศษ/ส่วนลดตามจำนวน·ช่วงวันที่·ลูกค้า เป็นเครื่องมือแยก ไม่ใช่ field ธรรมดา (BE +32)
  • 02Taxes & Charges แบบ per-line + item-wise tax detail ผูกทุกเอกสาร (Quotation/SO/PO) — ใช้ร่วมกับ P5 (BE +16)
  • 03Packed Item — bundle ถูก explode และเก็บ denormalized บนตัวเอกสาร SO/Delivery (BE +8)
  • 04เอกสารใหญ่มาก: SO 113 ฟิลด์ · PO 104 ฟิลด์ · Quotation 87 ฟิลด์ (submittable, 5–7 child tables) → FE tabbed form (FE +24)
Phase 5 · Finance — ที่พบจริง (+88 ชม.)
  • 01GL = double-entry ledger (debit=credit ต่อ account, immutable, post/cancel) — เป็น engine คู่ขนานกับ stock ledger, งานหลักของเฟส (BE +32)
  • 02Payment Entry + allocation — จ่าย/รับเงินแล้ว allocate ไปหลายใบกำกับ (AR/AP) พร้อม over/under-payment (BE +32)
  • 03Withholding Tax (หัก ณ ที่จ่าย) เพิ่มจาก VAT ปกติ — จำเป็นสำหรับภาษีไทย · + payment schedule (credit terms) (BE +16)
  • 04Sales Invoice = เอกสารใหญ่สุด 157 ฟิลด์ + 11 child tables (advances, timesheet, payment schedule, WHT) → FE +24

10 — Legacy Migration

การย้ายระบบเดิม

ใช้รูปแบบ Strangler Fig — รันระบบใหม่คู่ขนานกับระบบเดิม แล้วค่อย ๆ ย้ายทีละโมดูล ลดความเสี่ยงและไม่ต้องหยุดธุรกิจ

การย้ายข้อมูล (ETL)

  • 01สร้างตาราง legacy_id_map จับคู่ ID เดิม ↔ UUID ใหม่ ทุกบริการ
  • 02แปลง field เดิมเข้าสู่ schema ใหม่: ชื่อสินค้า → name.th, ประเภท → category, ราคาต้นทุน/ราคาขาย/ภาษี
  • 03ยอดคงเหลือปัจจุบัน (จำนวน) แปลงเป็น “Migration Lot” ตั้งต้น 1 ล็อต/สินค้า พร้อมต้นทุนล่าสุดและวันหมดอายุ
  • 04แยกข้อมูลลูกค้า/ผู้จัดซื้อไปยัง sales-bc / supplier-bc ตามบริบท

การย้ายไฟล์สู่ MinIO

  • 01Bulk copy โฟลเดอร์รูปสินค้า/เอกสารเดิมเข้าสู่ MinIO buckets ด้วย mc mirror หรือ SDK
  • 02ลงทะเบียน file_objects พร้อม context_ref = UUID ของสินค้า/เอกสารที่แมปไว้
  • 03ตรวจ Checksum และจำนวนไฟล์หลังย้าย ก่อนตัดการเข้าถึงพาธเดิม
  • 04Frontend เปลี่ยนมาเรียก Presigned URL จาก storage-bc แทน static path เดิม
