01 — ทำไมต้องมีคู่มือนี้

อาการที่ทำให้พบปัญหานี้

ระหว่างตรวจ P6 (CQRS Read Model, ยังไม่ได้ implement) พบว่า DOMAIN_EVENT_ROUTING route event หลายตัว (lot.created, stock.adjusted, item.updated ฯลฯ) ไปหา report-bc จริง แต่ report-bc/sales-bc/supplier-bc ไม่มี consumer เลยสักตัว — event เหล่านี้ถูก emit ไปแล้วในโปรดักชันตั้งแต่ก่อนหน้านี้ ทุกตัวถูกทิ้งอย่างเงียบๆ ที่คิวปลายทางทันทีที่ consumer เชื่อมต่อคิว

ทำไมไม่มี error log ให้เห็น

NestJS's ServerRMQ ไม่ throw หรือ log อะไรเลยตอน nack ข้อความที่ไม่มี handler ตรง — มันแค่ปิดจบเงียบๆ ตามสเปกของ RMQ transport เอง ผลคือทีมพัฒนาไม่มีทางรู้เลยว่ามีข้อมูลหายไป จนกว่าจะมีคนสังเกตว่า dashboard/รายงานที่ควรอ่านข้อมูลนี้ไม่อัปเดต ซึ่งอาจกินเวลาเป็นเดือน

02 — Transport & Ack Contract

พื้นฐานที่ทุกคนต้องรู้ก่อนแตะโค้ด RMQ

ค่าทำไมตั้งแบบนี้
TRANSPORT=rmqดีฟอลต์ทั้งแพลตฟอร์ม — อ่านจาก env เดียวกันทั้ง client registration (CommonModule) และ server listener (bootstrapApplication) เปลี่ยนค่าเดียวสลับทั้งระบบเป็น TCP ได้ถ้า broker ล่มยาว
noAck: falsemanual ack — server ไม่ ack เองตอนสำเร็จ ต้องมี RmqAckInterceptor ทำแทนทุก handler (ดู backend-convention.html)
prefetchCount: 11 consumer ถือได้ทีละ 1 ข้อความ — ทำให้ทั้งระบบไวต่อบั๊ก "ลืม ack" มากเป็นพิเศษ (ดู §03)
heartbeatIntervalInSeconds: 20ค่าดีฟอลต์ของ amqp-connection-manager (5s) จี๋เกินไปสำหรับ broker ที่อยู่ข้าม WAN — ปรับให้ทนแพ็กเก็ตหลุดเป็นช่วงสั้นๆ ได้
Retry ฝั่งผู้เรียก (sendWithContext/emitWithContext)

Timeout/connection error ได้ retry อัตโนมัติ (2 ครั้งรวมของเดิม) ก่อนตอบ defaultValue/null — error ทางธุรกิจจริง (404/400 ที่ unwrap ได้) ไม่ retry เพราะ retry คำตอบที่ตัดสินใจแล้วมีแต่เพิ่ม latency · ผลข้างเคียง: handler ปลายทางต้องทนถูกเรียกซ้ำได้ เพราะผู้เรียกอาจเห็นแค่ response หายไม่ใช่ว่างานไม่เกิด

03 — Head-of-Line Block

บั๊กคนละตัวกับเรื่องนี้ — แต่มาจากค่าตั้งค่าเดียวกัน

noAck:false + prefetchCount:1 เปิดช่องให้เกิดสองอาการที่หน้าตาคล้ายกันแต่ต้นเหตุตรงข้ามกัน — คู่มือนี้แยกไว้ให้ชัดเพื่อไม่ให้วินิจฉัยผิดตัว

อาการต้นเหตุสัญญาณที่ต่างกัน
Head-of-line block (§ตัวนี้)Handler มีอยู่จริง แต่ลืมใส่ @UseInterceptors(RmqAckInterceptor) — ไม่มีใคร ack ข้อความที่สำเร็จmessages_ready ค้างสูงขึ้นเรื่อยๆ พร้อม messages_unacknowledged ปักหมุดที่จำนวน consumer เป๊ะ — caller timeout 15s ทุกตัว restart service ก็ไม่ช่วย (consumer ใหม่หยิบข้อความค้างตัวเดิมทันที)
Silent message loss (§04 แก้แล้ว)Handler ไม่มีอยู่เลย — ServerRMQ nack(no-requeue) ทันทีที่ event name ไม่ matchไม่มี queue ไหนค้าง ไม่มี timeout ฝั่ง caller (เป็น event แบบ fire-and-forget) — สังเกตได้แค่ผลลัพธ์ปลายทางไม่เกิดขึ้น
วินิจฉัย head-of-line block

เช็ค RabbitMQ management: คิวที่สงสัยมี messages_ready ไต่ขึ้นเรื่อยๆ ขณะที่ messages_unacknowledged คงที่เท่ากับจำนวน consumer พอดี — แก้โดยเพิ่ม RmqAckInterceptor ให้ handler ที่ตกหล่น (ดู backend-convention.html) แล้ว restart service (ข้อความที่ค้างจะถูกส่งใหม่ให้ handler ที่แก้แล้ว)

04 — Dead-Letter Exchange

erp.dlx / erp.dlq — เพิ่ม 2026-09-05

ensureDeadLetterInfrastructure() (libs/common/src/utils/microservice-transport.util.ts) รันทุกครั้งที่ BC บูต (เฉพาะเมื่อ TRANSPORT=rmq) ประกาศ 3 อย่างแบบ idempotent — หลาย process แข่งกันประกาศพร้อมกันตอน deploy ปลอดภัย ไม่ error:

สิ่งที่ประกาศชนิดทำไม
erp.dlxExchange (fanout, durable)ปลายทางที่ข้อความ nack(no-requeue) ทุกคิวส่งมารวมกัน — ใช้ fanout เพราะข้อความเดิม publish ผ่าน default exchange (routing key = ชื่อคิว) ไม่มี exchange ของตัวเองให้ direct-route ตาม
erp.dlqQueue (durable)คิวเดียวรวมของทุก BC — ผูกกับ erp.dlx ด้วย binding key ว่าง (รับทุกอย่างจาก fanout)
Bindingerp.dlq ← erp.dlxให้ operator ตรวจสอบ/requeue ได้จากที่เดียว ไม่ต้องไล่ดูทีละ BC
ทำไมเป็น fanout เดียวรวม ไม่ใช่แยกต่อ BC

เป้าหมายรอบแรกคือหยุดข้อมูลหาย ไม่ใช่แยกวิเคราะห์ต้นทางอัตโนมัติ — ข้อความที่ dead-letter ยังพก x-death header ติดไปด้วย (RabbitMQ ใส่ให้เองเสมอ) ซึ่งบอกคิวต้นทาง/เหตุผล/เวลาไว้ครบอยู่แล้ว operator เปิดดู header นั้นเพื่อแยกต้นทางได้โดยไม่ต้องแยกคิวปลายทางล่วงหน้า

Best-effort โดยเจตนา — ไม่บล็อกการบูต

ถ้า broker ต่อไม่ได้ตอนเรียกฟังก์ชันนี้ (เช่น broker กำลัง restart พอดี) จะแค่ log error แล้วปล่อยให้ BC บูตต่อตามปกติ — ผลคือกลับไปเป็นพฤติกรรมเดิม (ข้อความ nack แล้วหายถาวร) ชั่วคราวเท่านั้น ไม่ใช่ทำให้ทั้ง BC บูตไม่ขึ้น เพราะ dead-letter infrastructure เป็น safety net ไม่ใช่ dependency ของ business logic

05 — Broker Policy

ทำไมแก้ที่ queue arguments ตรงๆ ไม่ได้

วิธีปกติที่จะให้คิวหนึ่ง dead-letter ไปที่ exchange คือประกาศคิวด้วย arguments: {'x-dead-letter-exchange': 'erp.dlx'} ตอน assertQueue — แต่คิวหลักของทั้ง 8 BC มีอยู่แล้วใน production ก่อน DLX จะถูกคิดขึ้น

RabbitMQ ปฏิเสธการ redeclare คิวเดิมด้วย arguments ต่างกัน

ทั้ง server (buildServerOptions) และทุก client ที่เรียกข้าม BC (ClientRMQ, ผ่าน buildClientProvider) ต่างก็ assertQueue() คิวเดียวกันเองตอน connect — ถ้าใส่ arguments ใหม่เข้าไปตรงๆ ใน queueOptions ของโค้ด จะได้ PRECONDITION_FAILED - inequivalent arg 'x-dead-letter-exchange' ทันทีที่ deploy — ทุก client ที่เคยเรียกข้าม BC ต่อไม่ติดเลย ไม่ใช่แค่ BC เจ้าของคิว

ทางที่ปลอดภัย — broker policy (ไม่ redeclare คิวเลย)

RabbitMQ policy ผูก behavior เข้ากับคิวที่มีอยู่แล้วได้โดยไม่ต้อง assert คิวใหม่ — ใช้จริงบน production (2026-09-05): 

# ผ่าน rabbitmqctl (บนเครื่อง broker) หรือ Management HTTP API ก็ได้ผลเหมือนกัน
rabbitmqctl set_policy dlx-erp '^erp_.*_queue$' \
  '{"dead-letter-exchange":"erp.dlx"}' --apply-to queues

ยืนยันแล้วว่าคิวเดิมทั้ง 8 ตัวขึ้น policy: "dlx-erp" โดย arguments ยังเป็น {} เหมือนเดิม — consumer/client ที่ต่ออยู่ไม่กระทบเลยแม้แต่วินาทีเดียว

06 — Monitor & กู้คืน

มีข้อความอยู่ใน erp.dlq แล้วทำอะไรต่อ

Monitoring — สัญญาณที่ควร alert

erp.dlq มี messages_ready > 0 ค้างนานกว่าสองสามนาที คือสัญญาณว่ามี event ถูกทิ้งจริง — ต่างจาก head-of-line block (§03) ตรงที่ ไม่มี caller คนไหน timeout ให้เห็น เพราะ event พวกนี้เป็น fire-and-forget การไม่ตั้ง alert ไว้เท่ากับกลับไปอยู่ในสถานะเดิมก่อนมี DLX (แค่ไม่ลบทิ้ง แต่ก็ไม่มีใครดู)

อ่าน x-death header เพื่อรู้ต้นทาง

ทุกข้อความใน erp.dlq พก header x-death (array) ที่ RabbitMQ ใส่ให้เองเสมอ — มี queue (คิวต้นทาง, บอก BC), reason (rejected สำหรับเคสนี้), time, count — เปิดดูได้จาก RabbitMQ Management UI (Queues → erp.dlq → Get messages)

Requeue กลับไปคิวต้นทาง — ไม่มีปุ่มอัตโนมัติ ต้องทำมือ

แพลตฟอร์มนี้ไม่มี consumer ที่ report-bc/sales-bc/supplier-bc เลย (§01) — requeue ข้อความกลับไปตอนนี้จะเจอ nack ซ้ำเหมือนเดิม ไม่มีประโยชน์จนกว่าจะมี consumer จริง (ดู §07 และ srs-p6.html) เมื่อถึงตอนนั้นค่อย publish ข้อความจาก erp.dlq กลับไปที่คิวต้นทาง (Management UI → Get messages → คัด payload → Publish message ใหม่ไปคิวเดิม) — เก็บ payload ไว้นอกระบบระหว่างรอ ไม่ลบทิ้งจาก UI โดยไม่ได้ backup ก่อน

07 — เพิ่ม Consumer ใหม่

Checklist ก่อน merge handler ใหม่

เมื่อ P6 (หรือฟีเจอร์ไหนก็ตาม) เริ่มเพิ่ม @EventPattern ให้ report-bc/sales-bc/supplier-bc จริง — เช็คทุกข้อนี้ก่อน merge:
