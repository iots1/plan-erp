ทุกเอกสารสร้างมาเป็น DRAFT ก่อนเสมอ และ แก้ไข/ลบได้เฉพาะตอนเป็น DRAFT เท่านั้น · พอกด submit/issue แล้ว เอกสารจะถูกล็อก เลขที่เอกสารถูกออก และสต็อก/บัญชีเคลื่อนทันที · การแก้ไขหลังจากนั้นทำได้ทางเดียวคือ ยกเลิกแล้วออกใหม่ หรือ ออกใบลด/เพิ่มหนี้ — ปุ่ม “แก้ไข” บนหน้าจอจึงต้องซ่อนเมื่อสถานะไม่ใช่ DRAFT

"ยกเลิก" = ระบบตีกลับให้อัตโนมัติเสมอ — FE ไม่ต้องไปทำ D2 (Stock Adjustment) เอง

ทุก cancel/void ที่เคยเคลื่อนสต็อกหรือบัญชีไปแล้ว ตีกลับให้เองในทรานแซกชันเดียวกับการยกเลิก ไม่มีจุดไหนในระบบที่ต้องให้ผู้ใช้ไปสร้างเอกสารแยกเพื่อดึงสต็อก/ยอดคืน — ถ้า FE เห็นสต็อก/ยอดไม่ตรงหลังยกเลิก ให้สงสัยว่าเรียก endpoint ผิด หรือแคช state ฝั่ง FE ค้าง ไม่ใช่ว่าต้องไปทำ D2/CN-DN เพิ่มเอง

wht_rate/total_wht เดิมเป็นคอลัมน์ที่เตรียมไว้แต่ไม่มีใครเซ็ต · ตอนนี้ระบบ resolve จาก tax_configs ตาม wht_config_code ที่ส่งมา (คิดจาก net_amount — หลังส่วนลด ก่อน VAT ฐานเดียวกับฝั่งขาย) · ไม่ลด total และไม่ลง GL ที่นี่ — การหักจริงเกิดตอนจ่ายเงินที่ C4 ซึ่งใช้ total_wht นี้เป็นเพดาน · ไม่ส่ง code = ไม่มีการหัก และใบจ่ายจะหักไม่ได้เลย
due_date คิดจาก document_date + suppliers.credit_terms ตอนสร้าง (ส่งมา override ได้) — เป็นตัวจัดกลุ่มในรายงานเจ้าหนี้ค้างชำระ (ดู C7) · ไม่ได้ตกลงเครดิตเทอมไว้ = null ไปอยู่คอลัมน์ no_due_date

ผู้ขายไม่ได้จด VAT = ไม่มีภาษีซื้อ (2026-08-31)

suppliers.is_vat_registered เขียน comment ไว้ตั้งแต่แรกว่า "ซื้อจากรายนี้แล้วขอเครดิตภาษีซื้อไม่ได้" แต่ไม่มีอะไรบังคับ · ตอนนี้ถ้าผู้ขายไม่ได้จด VAT ระบบบังคับ vat_rate = 0 ไม่ว่า tax_configs จะบอกอัตราเท่าไหร่ (ผู้ที่ไม่ได้จด VAT ออกใบกำกับภาษีตามกฎหมายไม่ได้ จึงไม่มีภาษีซื้อให้เครดิต — และการขอเครดิตภาษีซื้อจากผู้ขายที่ไม่ได้จดคือสิ่งที่สรรพากรไม่ยอมรับ)
ค่านี้ถูก snapshot ลงหัวเอกสาร (is_supplier_vat_registered) ไม่ใช่ถามใหม่ทุกครั้ง — เพื่อ (1) ตอบได้ว่าทำไมใบนี้ไม่มีภาษีซื้อ (2) แก้ DRAFT แล้วภาษีไม่เปลี่ยนไปตามสถานะผู้ขายที่ขยับหลังบันทึกบิล (3) แก้ DRAFT ได้แม้ supplier-bc ล่ม · ค่า default เป็น true จึงมีผลเฉพาะรายที่ตั้งใจบันทึกไว้ว่าไม่ได้จด และ supplier-bc รุ่นเก่าที่ไม่ส่งฟิลด์นี้มาถือว่า "จด" (ฟิลด์ที่หายไปต้องไม่ตัดภาษีซื้อทิ้งทุกใบ)

returned_qty แยกจาก delivered_qty ไม่หักกลบ

สถานะใบสั่งขายคิดจากยอดสุทธิ delivered_qty − returned_qty จึงพลิก CLOSED กลับเป็น PARTIAL ได้ เมื่อลูกค้าคืนของ — ถ้าไม่พลิก จะไม่มีใครถูกเตือนให้ส่งของแทน · ยอดใช้วงเงินเครดิต (ดู B2) ก็นับของที่คืนแล้วเป็น "ยังไม่ได้ส่ง" ด้วยเหตุผลเดียวกัน

เงินยังเป็นใบลดหนี้ — เอกสารนี้ไม่มียอดภาษี

ใบรับคืนไม่มี sub_total/VAT/ส่วนลด (เหมือน A4) — ผลทางการเงินของการรับคืนคือ ใบลดหนี้ §86/22 ที่ C2 ซึ่งมีอยู่แล้ว กระทบ VAT ตามอัตราของใบกำกับต้นทาง และเป็นเอกสารที่สรรพากรต้องการ · ทำยอดซ้ำที่นี่จะได้คำตอบที่สองว่า "ต้องคืนเงินลูกค้าเท่าไหร่" ซึ่งวันหนึ่งจะไม่ตรงกัน · unit_price บนบรรทัดเป็นแค่ snapshot ให้คนออกใบลดหนี้ใช้ ไม่มีผลต่อมูลค่าสต็อก
แต่ครึ่ง COGS ระบบทำให้อัตโนมัติ — submit ยิง event sales_return.received พร้อมต้นทุนรายล็อต แล้ว finance-bc กลับ COGS เฉพาะส่วนที่คืน (คนละ event กับ stock.deduction_reversed ที่ล้างทั้งการขาย ดู C7 ท้ายหัวข้อ E2)

customers.is_vat_registered เขียน comment ไว้ว่า "ออกใบกำกับภาษีให้รายนี้ไม่ได้" แต่ไม่มีอะไรบังคับ · ตอนนี้ FULL_TAX_INVOICE/INV_TAX_INVOICE ถูกปฏิเสธด้วย 400 ถ้าลูกค้าไม่ได้จด VAT
ยกเว้น 2 กลุ่มโดยเจตนา: ABB_TAX_INVOICE (§86/6) ยังออกได้ เพราะใบกำกับอย่างย่อมีไว้สำหรับหน้าร้านที่ผู้ซื้อมักเป็นผู้บริโภคนอกระบบ VAT — ถ้าบล็อกด้วยจะเหลือทางออกเป็น "ไม่มีเอกสารภาษีให้เลย" · และใบลดหนี้/เพิ่มหนี้ (§86/22) ยังออกได้ เพราะเป็นการปรับปรุงเอกสารที่ออกและตรวจไปแล้ว การห้ามแก้เพราะสถานะลูกค้าถูกปิดทีหลังจะทำให้ใบเดิมค้างโดยไม่มีทางปรับ
ค่า default เป็น true จึงมีผลเฉพาะรายที่ตั้งใจบันทึกไว้ว่าไม่ได้จด · ทางแก้ที่ error บอก: ออก ABB_TAX_INVOICE/RECEIPT แทน หรือแก้ข้อมูลลูกค้าก่อน

อ้างใบส่งของแล้วต้องอ้างให้จริง (2026-08-31)

เดิม delivery_note_id เป็น uuid ที่ไม่มีใครตรวจ — ออกใบกำกับสินค้าที่ไม่เคยส่ง หรือออกซ้ำใบส่งเดิมได้ (ตรงข้ามกับฝั่งซื้อที่ AP บังคับ grn_item_id มาตั้งแต่แรก)
กฎตอนนี้คือ "อ้างแล้วต้องอ้างให้จริง" ไม่ใช่ "ทุกใบต้องอ้าง" — ขายสด/ค่าบริการที่ไม่มีการส่งของ ไม่ต้องส่ง delivery_note_id (และห้ามมี dn_item_id ในบรรทัด) · แต่ถ้าหัวเอกสารอ้างใบส่งของ ทุกบรรทัดต้องระบุ dn_item_id แล้วระบบตรวจกับ sales-bc ว่า: บรรทัดนั้นอยู่ในใบส่งของที่อ้างจริง · ใบส่งของ SUBMITTED แล้ว (DRAFT = ของยังไม่ออก, CANCELLED = ของกลับเข้าสต็อกแล้ว) · เป็นของลูกค้ารายเดียวกัน · สินค้าตรงกัน (§86/4(5) — ใบกำกับต้องบรรยายของที่ส่งจริง) · และยอดที่ออกบิลรวมทุกใบไม่เกินที่ส่งจริง
400 = ผิดเงื่อนไขข้อใดข้อหนึ่ง · 409 = ออกบิลเกินที่ส่ง · ตรวจซ้ำอีกครั้งตอน issue() ใต้ row lock (นับเฉพาะใบที่ ISSUED แล้ว) — DRAFT สองใบจึงผ่านตอนสร้างได้ทั้งคู่ แต่ใบที่สอง issue ไม่ผ่าน · ใบลดหนี้/เพิ่มหนี้ (§86/22) ข้ามการตรวจนี้ทั้งหมด เพราะยึด reference_receipt_id ไม่ใช่การส่งของ

ภาษีหัก ณ ที่จ่าย ไม่ลดยอดหนี้

total_wht ไม่ถูกหักออกจาก total · ยอดที่ลูกค้าต้องจ่ายจริงคือ total − total_wht ซึ่ง FE คำนวณเองตอนแสดงผล · เพราะการถูกหักภาษีคือเงินสดที่ได้น้อยลง ไม่ใช่หนี้ที่น้อยลง — ตอนรับชำระจะเห็นชัดว่าปิดหนี้ได้เต็มจำนวน · และตั้งแต่ 2026-08-31 total_wht ยังเป็นเพดานที่ใบจ่ายเงินหักได้ (ดู C4) — wht_config_code จึงถูกเก็บไว้บนเอกสาร เพื่อให้แก้ DRAFT โดยไม่ต้องส่งรหัสซ้ำแล้วอัตราหายไปเป็น 0

จุดที่ FE พลาดได้ง่ายที่สุดของฟีเจอร์นี้ — allocated_amount คือ"ยอดหนี้บนใบกำกับที่ต้องการปิด" จึงเป็น THB ที่อัตราซึ่ง snapshot ไว้บนใบนั้น พูดง่ายๆ คือส่ง total ของใบนั้นมาตรงๆ ไม่ต้องแปลงอะไร ไม่ว่าเงินสดจะเข้ามาที่อัตราเท่าไร · ส่วน paid_amount/wht_amount เป็น THB ที่อัตราของใบจ่ายเอง (currency_rate ที่ส่งมา)
ดังนั้นสองยอดนี้จะไม่เท่ากันเป็นเรื่องปกติ — ใบ USD 100 บันทึกไว้อัตรา 35 (total = 3,500) ลูกค้าจ่ายครบตอนอัตรา 36 → ส่ง paid_amount: 3600 กับ allocated_amount: 3500 แล้วใบนั้นปิดครบพอดี · ผลต่าง 100 บาทไม่ใช่ยอดค้างและไม่ใช่เครดิตลูกค้า — ระบบโพสต์เป็นกำไรจากอัตราแลกเปลี่ยน (4300 / ขาดทุนที่ 5300) ให้ตอน submit เอง · อย่าพยายามให้ผู้ใช้ "ปรับยอดให้ตรง" เพราะจะกลายเป็นตัดหนี้ผิดจำนวนทันที
เพดานที่ FE ต้องคิด อยู่ฝั่งสกุลที่ทำรายการ — Σ (allocated_amount ÷ อัตราของใบนั้น) ≤ paid_amount ÷ currency_rate + wht_amount ÷ currency_rate · ถ้าคิดเพดานเป็น THB ตรงๆ จะขึ้น 400 ทั้งที่ผู้ใช้กรอกถูก · ตัดข้ามสกุลไม่ได้เลย (400) — ใบจ่ายสกุลหนึ่งตัดได้เฉพาะเอกสารสกุลเดียวกัน จึงควรกรองรายการใบที่ให้เลือกด้วย currency ตั้งแต่บน UI

สกุลเงินเอกสารต้องตรง billing_currency ของคู่ค้า — ตั้งค่าได้ (2026-09-02, warn → meta.warnings 2026-09-02)

เอกสารที่หันเข้าคู่ค้า (quotation, sales order, purchase order, receipt, AP invoice) เทียบ currency ของตัวเองกับ customers.billing_currency/suppliers.billing_currency ตามค่า party_currency_enforcement ที่ operator ตั้งไว้ (หน้า System Settings ของ iam) · off = ไม่ตรวจ (ค่าเริ่มต้น) · warn = สร้างได้ และข้อความเดียวกับที่ลง server log จะมากับ response ด้วย ที่ meta.warnings — array ของ object รูปร่างเดียวกับ errors ({ code, detail } — เทียบ code === 'PARTY_CURRENCY_MISMATCH' ได้โดยไม่ต้อง string-match detail, ไม่มี field นี้เลยถ้าไม่มีอะไรเตือน) — FE เช็ค response.meta.warnings แล้วเด้ง toast/banner ให้ผู้ใช้เห็นได้ทันทีโดยไม่ต้องไปเปิด server log · block = 422 ต้องแก้ billing_currency ที่บัตรคู่ค้าก่อน · FE ที่รองรับ mode block ควรเตือนผู้ใช้ตั้งแต่เลือกคู่ค้า/price list ว่าสกุลไม่ตรงกัน ก่อนกด save

เดิม PAY ต้องส่ง allocations: [] เพราะยังไม่มีตารางใบแจ้งหนี้ฝั่งซื้อ · ตอนนี้มี AP Invoice แล้ว (ดู A5) จึงตัดได้ — แต่ผูกข้ามฝั่งไม่ได้: RECEIVE ตัดได้เฉพาะ receipt_id · PAY ตัดได้เฉพาะ ap_invoice_id · แต่ละบรรทัดต้องมีอย่างใดอย่างหนึ่งเท่านั้น (บังคับด้วย CHECK constraint ที่ระดับ DB ไม่ใช่แค่โค้ด) · ส่งผิดฝั่งได้ 400

wht_amount มีเพดาน — ไม่ใช่ตัวเลขที่กรอกอะไรก็ได้ (2026-08-31)

เดิม wht_amount เป็นค่าที่ client ส่งมาแล้วเชื่อเลย · เพราะยอดที่ตัดหนี้ได้ = paid_amount + wht_amount จึงกรอก paid_amount: 1, wht_amount: 10699 ปิดหนี้ 10,700 ได้โดยเงินแทบไม่เข้า
ตอนนี้เพดานคือ total_wht ของเอกสารปลายทาง (ระบบ resolve จาก tax_configs ตอนออกเอกสาร ไม่ใช่ค่าที่ client บอก) หักที่ใบอื่นหักไปแล้ว — จึงหักซ้ำสองครั้งข้ามงวดไม่ได้ · เกินเพดานได้ 400 พร้อมบอกว่าเหลือให้หักเท่าไหร่
FE ไม่ต้องแตกยอดหักรายใบ — ไม่ส่ง wht_amount ในบรรทัด allocations ระบบเฉลี่ยให้ตามสัดส่วนยอดที่ตัดแต่ละใบ · ส่งเองได้เมื่อสองใบคนละอัตรา แต่ต้องส่งครบทุกบรรทัดและผลรวมเท่ากับหัวเอกสารพอดี · แต่ละบรรทัดหักได้ไม่เกินยอดที่ตัด (WHT เป็นส่วนหนึ่งของยอดที่ตัด ไม่ใช่บวกเพิ่ม)

ข้อจำกัดปัจจุบันที่ FE ต้องรู้
