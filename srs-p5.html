02

Core Use Cases & Data Entry · บันทึกข้อมูลยังไง

1

รับ event stock.deducted (allocations พร้อม unit_cost) → คำนวณ COGS ต่อ allocation = qty × lot.unit_cost → บันทึก cogs_entries ต่อล็อต

2

ดึงราคาขาย จาก sales-bc (TCP) → คำนวณ กำไรต่อล็อต = revenue − COGS → บันทึก profit_loss_records ต่อ allocation

3

ออกเอกสารการเงิน (Receipt) — เลือก document_type 1 ใน 8 แบบ (ดูตาราง ER ด้านล่าง) อ้างอิง delivery/SO → ระบบคำนวณ VAT (ภาษี 1/ภาษี 2) และตัดสิน เองว่าราคารวม VAT แล้วหรือยัง (is_vat_included) ตาม document_type — ไม่รับค่านี้จาก client เด็ดขาด · เลขที่เอกสารแบบต่อเนื่องแยกลำดับต่อ document_type → emit invoice.issued

4

ปรับปรุงยอด (Credit/Debit Note) — อ้าง reference_receipt_id ไปยังใบกำกับภาษีที่ ISSUED แล้ว (§86/22) → สืบทอด vat_rate/is_vat_included จากใบต้นทาง ไม่ใช้อัตราวันนี้ เพราะเป็นการปรับปรุงยอดของสิ่งที่เกิดขึ้นไปแล้ว

5

ใบวางบิล (Billing Note) รวมหลายใบกำกับเพื่อเรียกเก็บเงินรอบเดียว

Receipt ต้องอ่าน 2 แหล่งข้อมูล — คนละ BC

ขั้นตอน "คำนวณ VAT" ในข้อ 3 ต้องดึงข้อมูล 2 ที่: (1) tax_categories + products.tax_category_id (inventory-bc, มีโค้ดแล้ว — ดู P2) บอกว่าสินค้าแต่ละบรรทัด standard/zero_rated/exempt (2) TAX_CONFIGS (finance-bc, ตารางด้านล่าง) เก็บอัตราภาษีจริงที่ใช้คำนวณ (VAT7/WHT) — สองตารางนี้คนละหน้าที่กัน: inventory-bc บอก "สินค้านี้ประเภทไหน", finance-bc บอก "อัตราจริงเท่าไหร่และคำนวณยังไง" ต้องเรียกผ่าน TCP ข้าม BC เสมอ ไม่ query ตรง · ส่วน is_vat_included (ราคารวม VAT แล้วหรือยัง) ไม่ได้อ่านจากที่ไหนเลย — derive จาก document_type ของใบนี้เอง (ต่างจาก Quotation ที่ยัง snapshot มาจาก price_lists.is_vat_included)

Edge Cases · กรณีขอบเขต

แก้ใบกำกับที่ออกแล้ว

ใบกำกับที่ออกแล้ว ห้ามแก้ ต้องออก ใบลดหนี้/เพิ่มหนี้ (CREDIT_NOTE/DEBIT_NOTE) แทน — implement แล้ว: อ้าง reference_receipt_id, ต้องเป็นลูกค้าเดียวกับใบต้นทาง

เอกสารที่ไม่มี VAT

RECEIPT/INVOICE/PROFORMA_INVOICE บังคับ VAT เป็น 0 เสมอ แม้สินค้าจะจัดเป็น standard-rated ก็ตาม — ออกเอกสารแบบนี้คือการตัดสินใจไม่เก็บ VAT ของรายการนั้นเอง ไม่ใช่การคำนวณผิด

COGS event มาช้า

ถ้า allocation (stock.deducted) มาช้ากว่า invoice → คำนวณ COGS แบบ provisional แล้ว reconcile เมื่อ event มาถึง

สินค้าคืน (Return)

ต้อง กลับรายการ COGS และคืนสต็อกเข้าล็อตเดิม พร้อมออกใบลดหนี้

หลายอัตราภาษี

รองรับสินค้าที่ยกเว้นภาษี/หลายอัตราในใบเดียว คำนวณแยกบรรทัด

RULE · EXACT LOT COST

COGS = Σ(allocation.qty × allocation.unit_cost) ต้องใช้ unit_cost ที่มากับ event เท่านั้น ห้ามคำนวณเฉลี่ย และห้าม query ราคาปัจจุบันของสินค้า

RULE · PER-ALLOCATION P&L

คำนวณกำไรต่อ allocation แล้วค่อย aggregate — หนึ่ง delivery อาจกินหลายล็อตที่ต้นทุนต่างกัน

RULE · IMMUTABLE COGS

COGS เก็บเป็น snapshot immutable แก้ไขผ่าน adjusting entry เท่านั้น

RULE · DOCUMENT TYPE OWNS THE VAT DECISION

is_vat_included derive จาก document_type เท่านั้น — ไม่มีทางรับค่านี้จาก client ได้เลย (เหมือนกับ vat_rate/wht_rate ที่ server-resolve เสมอ) เพื่อกันไม่ให้ client ประกาศภาษีของตัวเอง — ดีไซน์นี้ (IVatDocumentHeader) ใช้ร่วมกับ Quotation/PO ใน P4 §07 ด้วย

RULE · GAPLESS NUMBERING — แยกต่อ document_type

เลขที่เอกสารต้อง gapless & transaction-safe (row lock ต่อปี) กันเลขซ้ำ/ข้าม — counter แยกต่างหากต่อ document_type เพราะเป็นเอกสารคนละใบตามกฎหมาย: ใบเสร็จเลข 1 กับใบกำกับภาษีเลข 1 ในปีเดียวกันไม่ใช่การชนกัน

RULE · DECIMAL & ROUNDING

ใช้ decimal(18,4) หรือ integer สตางค์ · ปัดเศษตามกฎภาษี · ห้าม float

RULE · IDEMPOTENT CONSUMER

consumer ของ stock.deducted ต้อง idempotent (processed_events) กันการสร้าง COGS ซ้ำ

RULE · INVOICE IMMUTABILITY

ใบกำกับที่ออกแล้ว immutable → แก้ไขด้วย credit/debit note pattern เท่านั้น — implement แล้ว: CREDIT_NOTE/DEBIT_NOTE อ้าง reference_receipt_id ไปยังใบต้นทางที่ต้อง ISSUED แล้ว, เคยมี VAT จริง, และเป็นลูกค้าเดียวกัน

RULE · GL DOUBLE-ENTRY BALANCED

ทุก financial transaction โพสต์ลง GL เป็นคู่ debit = credit เสมอ (ยอดรวมต้องเป็นศูนย์) · GL เป็น append-only + immutable เหมือน stock ledger · การ cancel เอกสารต้องโพสต์ entry กลับด้าน ไม่ลบของเดิม

RULE · PERIOD CLOSE

implement แล้ว (2026-08-30) — finance_settings.ledger_frozen_upto (singleton แถวเดียว มิเรอร์ inventory-bc.stock_settings.stock_frozen_upto) ล็อกงวดบัญชีอดีต · POST /finance-settings/close-period (permission period:close) เลื่อนงวดไปข้างหน้าเท่านั้น (one-way ratchet — ย้อนกลับไม่ได้ผ่าน endpoint นี้) · GeneralLedgerService.post()/reverse() ปฏิเสธทุกรายการที่ entry_date ≤ ledger_frozen_upto ด้วย 409 — บังคับใช้กฎ "a closed period must not move after the fact" ที่ comment ของ postVoid()/reverseCogs()/postCancel() พูดถึงไว้แต่เดิมไม่มีโค้ดบังคับจริง · แก้ยอดของเอกสารที่ตกในงวดที่ปิดแล้วต้องออกใบลด/เพิ่มหนี้ที่ document_date อยู่ในงวดปัจจุบันแทน

RULE · PAYMENT ALLOCATION

1 การชำระเงิน allocate ไปได้ หลายใบกำกับ · ผลรวม allocation ≤ paid_amount · ส่วนเกินเก็บเป็น unallocated_amount (เครดิตลูกค้า) · outstanding ของใบกำกับ = total − Σ allocation

ช่องโหว่ที่รู้ตัว · ฝั่งเจ้าหนี้ (AP) ยังไม่มีเอกสารให้ผูก

PaymentEntry รองรับ type=PAY (จ่ายผู้ขาย) และโพสต์ GL ได้ปกติ (Dr Accounts Payable / Cr เงินสด+ภาษีหัก ณ ที่จ่ายค้างนำส่ง) แต่ payment_allocations.receipt_id มี FK จริงชี้ไปที่ receipts เท่านั้น ซึ่งเป็นเอกสารฝั่งขาย (AR) ล้วน — ฝั่งซื้อไม่มี "ใบตั้งหนี้ผู้ขาย" (AP Invoice/Vendor Bill) ให้ผูกเลย ระบบจึงปฏิเสธการ allocate ทุกครั้งที่ type=PAY (PaymentEntriesService.assertAllocationsValid() throw 400 ตรงๆ) ผลคือบันทึกได้แค่ "จ่ายเงินออกไปเท่านี้" แต่บอกไม่ได้ว่าจ่ายไปตัดหนี้ก้อนไหน และไม่มีจุดไหนคำนวณยอดค้างจ่ายต่อผู้ขายให้เลย (ต่างจากฝั่ง AR ที่มี receipts เป็น GRN → PO ก็ยังไม่มีเอกสาร "ตั้งหนี้" เชื่อมต่อ (P4 §04 มีแค่ PO → GRN → ตัดยอด received_qty เข้าโกดัง ไม่มีขั้นตอนที่บอกว่าเป็นหนี้ที่ต้องจ่ายแล้ว) — ต้องออกแบบ "AP Invoice/Vendor Bill" (อ้าง GRN, มี outstanding, ผูก payment_allocations ได้) ก่อนฝั่ง AP จะสมบูรณ์เท่าฝั่ง AR ดูรายละเอียดเพิ่มที่ erp-architecture.html §04 "Flow ระบบเจ้าหนี้"

RULE · WITHHOLDING TAX

รองรับภาษี หัก ณ ที่จ่าย (WHT) แยกจาก VAT — ตอนรับ/จ่ายเงินคำนวณ WHT ตามอัตราของประเภทเงินได้ แล้วออกหนังสือรับรองหัก ณ ที่จ่าย · WHT ลดยอดเงินสดจริงแต่ไม่ลดยอดหนี้ · คำนวณเหมือนกันทุก document_type ไม่ขึ้นกับว่ามี VAT หรือไม่

RULE · §86/22 ADJUSTMENT INHERITS, NEVER RE-RESOLVES

CREDIT_NOTE/DEBIT_NOTE ต้องใช้ vat_rate และ is_vat_included ของใบที่อ้างอิง ไม่ใช่อัตราวันนี้ — ใบกำกับที่เก็บภาษีไว้ 7% ต้องถูกปรับปรุงด้วยอัตรา 7% เสมอ แม้กฎหมายจะเปลี่ยนอัตราไปแล้วก็ตาม
