Edge Cases · กรณีขอบเขต

Event มาไม่เรียงลำดับ

out-of-order → ใช้ version / event timestamp และ UPSERT idempotent เพื่อไม่ให้ข้อมูลเก่าทับข้อมูลใหม่

Event หาย / rebuild

Read model ต้อง สร้างใหม่ได้ (replay) จาก event store/outbox โดยไม่กระทบระบบหลัก

Eventual consistency

Dashboard อาจ lag ไม่กี่วินาที — ยอมรับได้สำหรับรายงาน แต่ต้องระบุเวลา last-updated

Event ซ้ำ

consumer ต้อง idempotent ผ่านตาราง processed_events (event_id unique)

05

Developer Implementation Guide · คำสั่งจาก SA

RULE · DENORMALIZE FOR READ

Read model ออกแบบเพื่อ อ่านเร็ว — ยอมให้ข้อมูลซ้ำ/denormalized เก็บชื่อสินค้า (JSONB) มาด้วย ไม่ต้อง join ข้ามบริการตอน query

RULE · IDEMPOTENT PROJECTION

ทุก consumer ต้อง idempotent ผ่านตาราง processed_events (event_id unique) กันการนับซ้ำ

RULE · HANDLE OUT-OF-ORDER

ใช้ version / updated_at + UPSERT เพื่อกัน event เก่าทับใหม่

RULE · NO SYNC CALL ON QUERY

ตอน query dashboard ห้ามเรียก transactional service — ต้อง pre-compute ล่วงหน้าเท่านั้น

RULE · SEPARATE READ DB

report-bc มีฐานข้อมูลของตัวเอง แยกจากบริการอื่น สามารถ rebuild ได้จาก replay

RULE · EVENT-DRIVEN REFRESH

อัปเดต summary ตาม event ที่เข้ามา ไม่ใช้ polling · ใช้ index ครบเพื่อให้ query < 200ms

RULE · SHOW FRESHNESS

แสดง last_updated บน dashboard เพื่อสื่อสาร eventual consistency ให้ผู้ใช้ทราบ

As-Built · สิ่งที่ report-bc เป็นอยู่จริงวันนี้ = บริการพิมพ์เอกสาร

หัวข้อ 01–05 ด้านบนคือแผนของเฟส 6 (CQRS Read Model) ซึ่งยังไม่ได้ implement เลยสักตาราง — ไม่มี sales_summary / profit_by_lot / low_stock / processed_events ในฐานข้อมูล erp_report และ report-bc ยังไม่ได้ subscribe event ใด ๆ — แก้ไข 2026-09-04: inventory-bc และ finance-bc มี outbox pattern จริงแล้ว (OutboxService.stage() ต่อ BC + relay ที่ drain outbox_events) ปัญหาที่เหลือคือฝั่ง consumer ไม่ใช่ producer: report-bc/sales-bc/supplier-bc ไม่มี @EventPattern เลยสักตัว ทั้งที่ routing table (DOMAIN_EVENT_ROUTING) ส่งอีเวนต์ไปหาแล้วจริง ๆ — เพราะ RMQ server ตั้ง noAck:false + prefetchCount:1 โดยไม่มี dead-letter exchange ข้อความที่ไม่มี handler จะโดน nack(msg,false,false) แล้วหายถาวรอย่างเงียบ ๆ ไม่ error ไม่ log (ดู backlog handoff เรื่อง report-bc consumers) · แก้ไข 2026-09-05: เพิ่ม dead-letter exchange erp.dlx/queue erp.dlq แล้ว (ทั้งประกาศในโค้ดที่ boot ทุก BC และผูก broker policy เข้ากับคิวเดิมทุกตัวบน production จริง) ข้อความที่ nack เพราะไม่มี handler จะไปนอนรอที่ erp.dlq แทนที่จะหายถาวร — แต่ยังไม่แก้ต้นเหตุ (report-bc/sales-bc/supplier-bc ยังไม่มี @EventPattern เลยสักตัว) รายละเอียดกลไก: RabbitMQ Reliability Guide · สิ่งที่ erp_report มีจริงตอนนี้คือ ระบบพิมพ์เอกสาร 4 ตาราง ซึ่งถูกสร้างขึ้นก่อนเพราะเอกสารฝั่งซื้อ/ขาย/การเงิน (P4–P5) ต้องพิมพ์ออกมาให้ลูกค้าได้ตั้งแต่วันแรก · หัวข้อนี้บันทึกของจริงไว้ให้ตรงกับโค้ด ไม่ได้ยกเลิกแผน CQRS ด้านบน

A1

ตัวเทมเพลตไม่ได้อยู่ใน Postgres — HTML/JS อยู่บน MinIO

ตัดสินใจ: แถวใน print_templates เก็บแค่ ที่อยู่ของไฟล์ — html_bucket/html_path/html_hash และ js_bucket/js_path/js_hash (JS เป็น optional) ตัวเนื้อ HTML ถูกอ่านจาก MinIO ตอน findById() เท่านั้น ไม่ติดไปกับ list/paginated response

ทำไม: เป็นรูปแบบเดียวกับ product_images และไฟล์แนบเอกสาร (srs-p2.html §05) — BC เก็บ bucket/object_key ไม่เก็บทั้ง blob และไม่เก็บ signed URL · ผลคือรายการเทมเพลตยังเบาแม้เทมเพลตจะยาวเป็นหมื่นบรรทัด และการย้อนเวอร์ชันคือการชี้ไปที่ object เดิม ไม่ต้องคัดลอกเนื้อไฟล์ซ้ำในฐานข้อมูล · *_hash มีไว้ให้รู้ได้ว่าไฟล์บน MinIO ตรงกับเวอร์ชันที่แถวนี้อ้างจริงหรือไม่

A2

สอง render engine ในตารางเดียว — simple กับ banded

template_engine = 'simple' (default)

HTML เป็นเอกสารแบน แทนที่ {{key}} ด้วยสตริงตรง ๆ ไม่มีการแบ่งหน้า — เหมาะกับเอกสารหน้าเดียวที่ความยาวคงที่

layout_config ไม่มีความหมายในโหมดนี้

template_engine = 'banded'

HTML ประกาศ <template data-band="..."> (page-header / detail-header / detail-row / filler-row / summary / page-footer) แล้ว paginator ในหน้าวัดความสูงจริงของแต่ละแถวแล้วแบ่งหน้าเอง — เหมาะกับเอกสารที่จำนวนบรรทัดไม่แน่นอน (ใบเสนอราคา/ใบกำกับที่มีหลายสิบรายการ)

layout_config (jsonb) คุมความสูง detail band, พื้นที่กันไว้ให้ summary และ margin

RULE · PDF ออกจาก Gotenberg ไม่ใช่ไลบรารีใน process

HTML ที่ render เสร็จถูกส่งไปแปลงเป็น PDF ที่ Gotenberg (ตั้งค่าด้วย env GOTENBERG_URL) · emulated_media_type ต่อเทมเพลต ส่งต่อเป็น emulatedMediaType ของ Gotenberg — ค่าปกติคือ 'print' ซึ่งจำเป็นถ้าต้องการให้ thead/tfoot ซ้ำทุกหน้า · mock_data ใช้เฉพาะ preview/Generate Test PDF ในหน้า admin เท่านั้น ผู้เรียกจริงส่ง params ของตัวเองเสมอ

A3

เลขรันของ document_types เป็นคนละกลไกกับเลขที่เอกสารของ PO/QT/Receipt

ต้องไม่สับสน: เลขที่ PO-{YYYY}-{00001} · QT-… · INV-… · ADJ-… ออกจากตัวนับใน BC ของเอกสารนั้นเอง (*_number_counters ที่ extend DocumentNumberCounterEntity) — ไม่ได้เรียกมาที่ report-bc · ตัวนับใน document_running_numbers เป็นบริการเลขรันแบบตั้งค่าได้จากหน้าจอ สำหรับประเภทเอกสารที่ admin ประกาศเอง ผ่าน POST /document-types/{id}/running-number/next

รูปแบบที่รองรับ: {YYYY} · {YY} · {MM} · {DD} · {SEQ:n} (บังคับมีพอดี 1 ตัว) เช่น INV-{YYYY}{MM}-{SEQ:5} · การออกเลขอยู่ใน transaction เดียวกับ SELECT … FOR UPDATE บนแถวตัวนับ (สร้างแถวด้วย INSERT … ON CONFLICT DO NOTHING ก่อน lock เพื่อไม่ให้ call แรกชนกันเอง)

RULE · เปลี่ยนงวด = รีเซ็ตเอง ไม่ต้องมีคอลัมน์ปี

token วันที่ถูกแทนเป็นค่าจริง ตอนสร้าง regex ไม่ใช่ \d{4} — พอขึ้นเดือน/ปีใหม่ last_value ของงวดก่อนจะ match ไม่ผ่านเอง แล้วลำดับเริ่มที่ 1 ใหม่ · กลไกเดียวกันนี้ครอบคลุมทั้ง "admin แก้ format" และ "ขึ้นงวดใหม่" จึงไม่ต้องมีคอลัมน์ year แยกแบบตัวนับของ PO/QT

RULE · เลขรันอ่านวันที่จาก BUSINESS_TIMEZONE ไม่ใช่นาฬิกาของ process (แก้แล้ว 2026-08-28)

running-number-format.util.ts เคยอ่านวัน/เดือน/ปีด้วย getFullYear()/getMonth()/getDate() จาก new Date() — ตอนนี้ผ่าน toBusinessDate() จาก @lib/common/utils/business-date.util.ts แล้ว · ข้อควรรู้ว่าทำไมของเดิมยังไม่เคยออกเลขผิดจริง: bootstrapApplication() ตั้ง process.env.TZ = PROJECT_TIMEZONE เป็นบรรทัดแรกสุด นาฬิกาของ process ในบริการที่รันอยู่จึงเป็น Asia/Bangkok อยู่แล้ว — บั๊กนี้จึงเป็นแบบซ่อนอยู่ (latent) ที่รอเงื่อนไขเดียวคือถูกเรียกจากที่ที่ไม่ผ่าน bootstrap (CLI script, migration, unit test) แล้วจะเงียบ ๆ ให้คำตอบของวันก่อนหน้า · การพึ่ง global side effect แบบนี้คือสิ่งที่กฎ business-date ของโปรเจกต์มีไว้เพื่อกำจัด
