Technical Implementation Guide

Observability: Distributed Tracing & HTTP Access Logging
(OpenTelemetry → Tempo · pino-http → Loki)

สรุปการทำงานของ pipeline สังเกตการณ์ระบบ (Observability) 2 เส้นทางที่ รูปแบบต่างกันโดยตั้งใจ — Trace เป็นแบบ push ตรงจากแอปไปหา Collector ผ่านเครือข่าย ส่วน HTTP Access Log เป็นแบบ pull คือเขียนลงไฟล์ แล้วให้ Alloy บน server อ่าน (tail) ไฟล์นั้นเองอีกที ทั้งสองแบบมีเหตุผลทางสถาปัตยกรรมของมันเอง และมีข้อจำกัดที่ต่างกัน

01 — ภาพรวม

ทำไม Trace ทำงานได้จาก localhost แต่ Log ไม่ได้

คำถามที่พบบ่อยที่สุดตอนทดสอบ local: รัน service บนเครื่องตัวเองแล้วเห็น trace ขึ้นใน Tempo ทันที แต่ไม่เห็น log ใน Loki เลย ทั้งที่ deploy โค้ดตัวเดียวกัน — สาเหตุคือทั้งสองระบบใช้ transport mechanism คนละแบบกันโดยสิ้นเชิง ไม่ใช่บั๊ก

PUSH

Trace (OpenTelemetry)

แอป export span ผ่าน OTLP gRPC ตรงไปที่ OTEL_EXPORTER_OTLP_ENDPOINT (server จริงที่ 172.16.0.220:4317) — เป็น network call ออกไปจากเครื่องไหนก็ได้ ไม่ว่าจะ localhost หรือ production ตราบใดที่ต่อ endpoint นั้นถึง ก็เห็น trace ใน Tempo ทันที ไม่ต้องรัน Alloy บนเครื่องตัวเอง

PULL

HTTP Access Log (pino-http)

แอปเขียน log เป็นไฟล์ JSON ที่ logs/<service>/http/http.log บนเครื่องที่รันแอปเองเท่านั้น Alloy บน server จะเห็นเฉพาะไฟล์ที่ mount เข้าไปจาก /root/erp-api/logs — โฟลเดอร์ logs/ บนเครื่อง local ของคุณ มองไม่เห็นจาก Alloy บน server เลย

RULE

ถ้าต้องการทดสอบ log pipeline แบบ end-to-end จาก local จริง ๆ ต้องรัน Alloy container บนเครื่องตัวเอง mount โฟลเดอร์ ./logs ของ repo เข้าไป แล้วชี้ output ไปที่ Loki บน server (ดู §02) — ไม่มีทางเลี่ยงด้วยการแก้โค้ดฝั่งแอป เพราะสถาปัตยกรรมปัจจุบันเลือกใช้ pull-based file tailing สำหรับ log โดยตั้งใจ (ไม่ใช่ push เหมือน trace)

Grafana Alloy · Tempo · Loki · Prometheus · Grafana

03 — Distributed Tracing → Tempo

OpenTelemetry NodeSDK

libs/common/src/tracing.ts เริ่ม OpenTelemetry SDK ก่อนโมดูลอื่นใดในแอป เพื่อให้ auto-instrumentation แพตช์ http/pg/ioredis/amqplib ได้ก่อนที่โค้ดจริงจะ require() พวกมัน

Import Order · apps/<bc>/src/main.ts → bootstrap.util.ts
// libs/common/src/utils/bootstrap.util.ts — บรรทัดแรกสุดของไฟล์
// MUST be first: starts the OpenTelemetry SDK before http/pg/nestjs are loaded
// so auto-instrumentation can patch them (see tracing.ts). Do not reorder.
import '../tracing';

import { timingSafeEqual } from 'crypto';
// ... imports อื่น ๆ ตามหลัง — ทุกตัวถูก instrument ทันเวลาแล้ว
ทำไมต้อง import ตรง path ไม่ผ่าน @lib/common barrel

ถ้า import ผ่าน barrel (@lib/common) จะทำให้ export อื่นทั้งหมด (decorators, DTOs, guards) ถูก evaluate ก่อน ซึ่งจะไป require() dependency ของมันเองล่วงหน้า — สายเกินไปสำหรับ instrumentation hook ที่ต้องติดตั้งก่อน module อื่นถูกโหลด

tracing.ts · การตั้งค่าหลัก
const endpoint =
  process.env.OTEL_EXPORTER_OTLP_ENDPOINT ?? 'http://127.0.0.1:4317';

otelSdk = new NodeSDK({
  traceExporter: new OTLPTraceExporter({ url: endpoint }),
  instrumentations: [getNodeAutoInstrumentations()],
});

otelSdk.start();
service.name resolution

1) OTEL_SERVICE_NAME ถ้าตั้งไว้ → 2) parse จาก entry path dist/apps/<name>/main.js อัตโนมัติ (ไม่ต้อง config ต่อแอป) → 3) fallback 'erp-service'

Fail-safe

ทั้งบล็อกครอบด้วย try/catch — tracing พังไม่มีทางทำให้ service ทั้งตัวพังตาม (console.warn แล้วปล่อยผ่าน)

RPC (TCP/RMQ) Span Propagation — OtelRpcContextInterceptor

Guard/Interceptor ระดับ APP_* ทำงานเฉพาะฝั่ง HTTP — app.connectMicroservice() ถูกสร้างด้วย ApplicationConfig ใหม่ที่ว่างเปล่า (ตั้งใจ ไม่ inherit guard เพื่อไม่ให้ inter-service call ที่ไม่มี JWT ถูก reject) จึงต้อง register interceptor นี้ตรงบน microservice instance เอง เพื่อเย็บ span tree ข้าม TCP/RMQ hop 

// libs/common/src/interceptors/otel-rpc-context.interceptor.ts
const carrier = this.extractCarrier(context); // W3C traceparent จาก _context.otel
const parentContext = carrier
  ? propagation.extract(ROOT_CONTEXT, carrier)
  : ROOT_CONTEXT;

const span = trace.getTracer('erp-rpc').startSpan(spanName, {}, parentContext);
return otelContext.with(trace.setSpan(parentContext, span), () => next.handle())
  .pipe(/* catchError → span.recordException + setStatus(ERROR) */
        /* finalize → span.end() */);

ฝั่งผู้เรียก: MicroserviceClientService.createCallContext() ฝัง active span ปัจจุบันลงใน _context.otel ก่อนยิง TCP/RMQ call — interceptor นี้ดึงกลับมาเปิด child span ต่อ หลังจากนั้น pg/ioredis auto-instrumentation ที่แพตช์ไว้ตั้งแต่ tracing.ts จะแนบทุก query เป็น child span ให้เองอัตโนมัติ ผ่าน AsyncLocalStorage โดยไม่ต้องเขียนโค้ดต่อ handler เลย

04 — HTTP Access Logging → Loki

pino-http · pino-roll · Multi-Target Transport

libs/common/src/utils/logger/pino-http.config.ts สร้าง connect-style middleware ที่ register ผ่าน app.use() ใน bootstrap.util.ts — แยกจาก Winston-based LogsService (business log) โดยสิ้นเชิง นี่คือ log เฉพาะ HTTP access เท่านั้น

buildPinoLogger() · pino.transport() แบบ multi-target
const transport = pino.transport({
  targets: [
    {
      target: 'pino-roll',      // เขียนไฟล์ + rotate รายวัน
      level: logLevel,
      options: {
        file: path.join(process.cwd(), logDir, 'http.log'),
        frequency: rotateFrequency,     // 'daily'
        dateFormat,                     // 'yyyy-MM-dd'
        mkdir: true,                     // สร้างโฟลเดอร์ให้เองถ้ายังไม่มี
        limit: { count: retentionDays }, // เก็บ 14 ไฟล์ล่าสุด
      },
    },
    {
      target: 'pino/file',       // เขียนออก stdout ด้วย (destination: 1)
      level: logLevel,
      options: { destination: 1 },
    },
  ],
});

logDir default มาจาก serviceSlug(moduleName) — แปลงชื่อ root module (IamModule, FinanceBcModule) เป็น kebab-case ให้ตรงกับชื่อโฟลเดอร์ apps/<slug> เป๊ะ (iam, finance-bc) → แต่ละ BC ได้ไฟล์ log แยกกันเป็น logs/<service>/http/http.log โดยไม่ชนกัน แม้ทุก BC จะรันจาก cwd เดียวกันบน server

05 — จุดที่ซับซ้อนที่สุด

ทำไม request body / authenticated user ต้องอยู่ใน res(), ไม่ใช่ req()

นี่คือจุดที่ non-obvious ที่สุดของทั้งไฟล์ และเป็นสาเหตุที่ log เคยว่างเปล่ามาตลอด (ดู §08) — pino ผูกค่า req เข้ากับ log line ผ่าน logger.child({ req }) ที่ทำงานตอน Fastify hook 'onRequest' ซึ่งเป็นจุดที่ เร็วที่สุด ใน request lifecycle — เร็วกว่าทั้ง body parsing (เกิดที่ preValidation) และ AuthGuard (ทำงานเป็นส่วนหนึ่งของ handler execution)

Pino Child Binding Gotcha

pino.child(bindings) serialize ค่า bindings ครั้งเดียวทันที ตอนเรียก ไม่ใช่ทุกครั้งที่ log บรรทัดใหม่ถูก emit — เขียนค่าใหม่ลง object เดิมหลังจากนั้น ไม่มีผลกับ log ที่ผูกไว้แล้ว เพราะ pino จับ snapshot ไปแล้ว

req() serializer

Frozen ที่ 'onRequest'

เก็บได้แค่สิ่งที่มีอยู่แล้วตอนนั้นจริง ๆ — method, url, headers เท่านั้น (body ยังไม่ parse, user ยังไม่ login-check)

res() serializer

รันสดที่ response-finish

pino-http เรียก res serializer ใน onResFinished (หลัง response จบแล้ว) — ถึงตอนนั้น body/user ถูก copy ไว้บน request.raw แล้ว และ Node ServerResponse.req ยังชี้กลับไปที่ IncomingMessage ตัวเดิมเสมอ จึงอ่านค่าสดได้จากตรงนี้

bootstrap.util.ts · registerHttpLogging() — สองฮุคที่แก้ปัญหานี้
// (1) copy request.body → request.raw.body หลัง parse เสร็จ
app.getHttpAdapter().getInstance()
  .addHook('preValidation', (request, _reply, done) => {
    if (request.body !== undefined) {
      request.raw.body = request.body;
    }
    done();
  });

// (2) copy request.user → request.raw.user หลัง AuthGuard ตั้งค่าแล้ว
// (guard ทำงานเป็นส่วนหนึ่งของ handler — 'onSend' คือจุดแรกที่ชัวร์ว่ารันหลัง guard เสมอ)
app.getHttpAdapter().getInstance()
  .addHook('onSend', (request, _reply, payload, done) => {
    const user = request.user;
    if (user !== undefined) {
      request.raw.user = user;
    }
    done(null, payload);
  });
pino-http.config.ts · res() serializer — จุดที่อ่านค่าจริง
res(res) {
  const raw = res.raw ?? res;                       // ServerResponse จริง
  const rawReq = raw.req;                          // ← ชี้กลับไป IncomingMessage เดิม

  if (includeReqBody && rawReq?.body !== undefined) {
    base.req_body = redactDeep(rawReq.body);        // ปลอดภัย: password ฯลฯ ถูก redact
  }

  const session = rawReq?.user?.user_session;
  if (session !== undefined) {
    base.user = { id: session.id, username: session.username, roles: session.roles };
  }

  // response body ก็ต้อง redact เช่นกัน — access_token/refresh_token/csrf_token
  return { ...base, body: redactDeep(raw.locals?.responseBody) };
}

ผลลัพธ์: log line หนึ่งบรรทัดมี req (headers, method, url — เบา ไม่มี PII) และ res ที่รวม req_body, user, body เข้าไปด้วย — โครงสร้างต่างจาก pino-http มาตรฐานเล็กน้อย แต่เป็นทางเดียวที่ข้อมูลจะไม่ถูก freeze เป็นค่าว่างตลอดไป

06 — เชื่อม Trace กับ Log เข้าด้วยกัน

trace_id ร่วมกันระหว่าง Tempo และ Loki

erp-api ไม่มี header x-trace-id แบบ hand-roll — เพราะมี OpenTelemetry span จริงวิ่งอยู่แล้ว (§03) จึงยืม trace ID จาก active span มาใช้เป็น reqId ของ pino-http โดยตรง แล้ว rename เป็น trace_id ที่ระดับบนสุดของ log line 

genReqId(req) {
  const traceId = trace.getActiveSpan()?.spanContext().traceId;
  if (traceId !== undefined) return traceId;      // ← ใช้ trace ID เดียวกับที่ Tempo เห็น
  return req.headers['x-trace-id'] ?? crypto.randomUUID(); // fallback ถ้า tracing ปิดอยู่
}

customAttributeKeys: { reqId: 'trace_id' }  // rename field ให้อ่านง่าย
ประโยชน์

ค้นด้วย trace_id เดียวกันใน Grafana จะเจอทั้ง span ใน Tempo และ log line ใน Loki ของ request เดียวกัน — เชื่อมสอง pipeline ที่ transport ต่างกันโดยสิ้นเชิงเข้าด้วยกันได้ที่ query time

07 — Metrics: Prometheus & Tempo Metrics-Generator

สอง "แหล่งที่มา" ของ metrics ที่ต้องไม่สับสนกัน

Metrics เป็น pipeline ที่สาม เพิ่มเข้ามาทีหลัง trace/log ทั้งสอง — ใช้ Prometheus เป็น storage แต่ metrics ที่อยู่ใน Prometheus มาจากสองทางที่ต่างกันโดยสิ้นเชิง ทั้งด้าน transport (pull vs push) และความหมาย (สุขภาพของ collector เอง vs ค่าที่แปลงมาจาก trace จริงของแอป)

PULL

otelcol_* — สุขภาพของ Alloy เอง

Prometheus scrape alloy:12345/metrics ทุก 15s (self-instrumentation ที่ Alloy เปิดให้เองอัตโนมัติ ไม่ต้อง config เพิ่ม) ได้ otelcol_receiver_accepted_spans_total, otelcol_exporter_sent_spans_total, process_cpu_seconds_total, process_resident_memory_bytes ฯลฯ — วัดตัว collector (รับ/ส่ง span สำเร็จกี่ตัว, ใช้ CPU/memory เท่าไหร่) ไม่เกี่ยวกับพฤติกรรมของแอปเลย

PUSH

traces_spanmetrics_* / traces_service_graph_*

08 — บั๊กที่เจอระหว่าง Implement และวิธีแก้

5 บั๊กเงียบ (Silent Failures) ที่ไม่มี error ให้เห็นเลย

ทั้งห้าข้อนี้มีจุดร่วมกันคือไม่มี exception หรือ error log ใด ๆ โผล่ขึ้นมาเลย — โค้ด/config "รันผ่าน" ปกติทุกอย่าง แต่ผลลัพธ์ผิด เป็นเหตุผลที่ควรบันทึกไว้ละเอียด กันคนถัดไปเจอปัญหาเดิม

1

Webpack bundle thread-stream ทั้งที่ nodeExternals ควร exclude

อาการ: MODULE_NOT_FOUND: dist/apps/iam/lib/worker.js ตอน boot — service ตายทันที ทั้ง dev และ prod

สาเหตุ: thread-stream เป็น transitive dependency ของ pino เท่านั้น ไม่มี top-level symlink ใน node_modules ภายใต้ pnpm — webpack-node-externals scan เจอแค่ dependency ตรงจึง bundle มันเข้าไปใน main.js โดยไม่ตั้งใจ เมื่อถูก bundle, webpack เขียนทับ __dirname เป็น path ของ bundle output — path ของ worker script ที่ thread-stream คำนวณเองจึงผิดไปเป็น dist/apps/<app>/lib/worker.js

แก้: เพิ่ม { 'thread-stream': 'commonjs thread-stream' } เข้า externals array ใน webpack.config.js ตรง ๆ

2

formatters.level เป็น string → pino.multistream ทิ้งทุกบรรทัด

อาการ: ไฟล์ log ถูกสร้างปกติ (mkdir:true ทำงาน) แต่มีขนาด 0 byte ตลอด — ไม่มี error ที่ไหนเลย แม้จะ attach transport.on('error', …) ก็ไม่เจอ

สาเหตุ: เดิม formatters.level: (label) => ({ level: label }) เปลี่ยนค่า level เป็น string ("info") แทนตัวเลข (30) — เมื่อ pino.transport() มีมากกว่า 1 target, pino worker (pino/lib/worker.js) จะ route แต่ละบรรทัดผ่าน pino.multistream ซึ่งเทียบ level >= dest.level — "info" >= 20 เป็น false เสมอ (string เทียบกับ number) ทุกบรรทัดจึงถูกทิ้งให้ทุก target อย่างเงียบ ๆ

แก้: คืนค่า level ให้เป็นตัวเลขเหมือนเดิม (level: (label, number) => ({ level: number, level_label: label })) — ใส่ label เป็น field แยกต่างหาก (level_label) ให้ Grafana/Loki อ่านง่ายแทน

3

req.body / req.user ไม่เคยปรากฏใน log แม้ includeReqBody: true

อาการ: log เขียนได้ปกติแล้ว (แก้บั๊ก #2 แล้ว) แต่ POST/PUT ไม่เคยมี field body เลย — ทั้งที่ code ดูเหมือนอ่านมันอยู่

สาเหตุ: อธิบายละเอียดใน §05 — root cause คือ pino child() bindings ถูก serialize ครั้งเดียวตอน 'onRequest' ซึ่งเร็วกว่าทั้ง body parsing และ AuthGuard

แก้: เพิ่ม preValidation/onSend hook คัดลอกค่าไปที่ request.raw แล้วย้ายจุดอ่านไปที่ res() serializer ซึ่งรันสดตอน response-finish (ดู §05 สำหรับโค้ดเต็ม) — พบบั๊ก response body ไม่ถูก redact ระหว่างตรวจสอบจุดนี้ด้วย (access_token/refresh_token/csrf_token หลุดเป็น plaintext) แก้พร้อมกันโดยเรียก redactDeep() กับ response body เช่นกัน

4

Alloy log-tailing glob ตกหล่น path segment ที่เพิ่มมาใหม่ → Loki ว่างเปล่าไม่มี error

อาการ: Alloy container รันปกติ ไม่มี error สักบรรทัดในล็อกของมัน แต่ query Loki ด้วย {job="erp-api-http"} ไม่เจอ log แม้แต่บรรทัดเดียว ทั้งที่ไฟล์ log บน disk มีข้อมูลปกติ

สาเหตุ: commit ที่เพิ่ม per-service log directory (logs/<service>/http/…) เปลี่ยนโครงสร้าง path ไปเพิ่มอีกหนึ่งชั้น แต่ config.alloy's local.file_match ยังตั้ง __path__ เป็น /var/log/erp-api/http/*.log (ไม่มีชั้น <service>) — glob ไม่ match ไฟล์ไหนเลยสักไฟล์ Alloy แค่ "หาไฟล์ไม่เจอ" ซึ่งไม่ใช่ error สำหรับมัน จึงเงียบสนิท

แก้: เพิ่ม * อีกชั้นให้ตรงกับ path จริง — /var/log/erp-api/*/http/*.log — กฎทั่วไป: glob path ต้องมี * ครบทุก path segment ที่ logger สร้างจริง ไม่งั้น Alloy จะไม่แจ้งอะไรเลยเมื่อ layout เปลี่ยนในอนาคต

5

Grafana provisioning ไม่ apply jsonData ใหม่ถ้าไม่ bump version

อาการ: แก้ grafana-datasources.yaml เพิ่ม serviceMap/tracesToMetrics ให้ Tempo datasource แล้ว restart container ปกติ แต่ GET /api/datasources/uid/tempo ยังคืน jsonData: {} เหมือนเดิมทุกประการ ไม่มี error ใน Grafana log เลย

สาเหตุ: Grafana's file-based datasource provisioning เทียบ version: field ในไฟล์ YAML กับ version ที่บันทึกไว้ในฐานข้อมูลภายในของมันเอง — apply เนื้อหาใหม่เฉพาะตอน version ในไฟล์มากกว่าค่าที่บันทึกไว้เท่านั้น แก้ jsonData โดยลืมขยับ version: 1 เดิม จึงถูกมองว่า "ไม่มีอะไรเปลี่ยน" แล้วข้ามไปเงียบๆ

แก้: bump version: ขึ้นทุกครั้งที่แก้ datasource ใดๆ ใน grafana-datasources.yaml ไม่ว่าจะเปลี่ยนอะไรก็ตาม — ไม่มี error ให้เตือน ถ้าลืม
