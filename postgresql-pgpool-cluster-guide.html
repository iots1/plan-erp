01 — ภาพรวม

Connection Pooling คืออะไร และทำไม ERP นี้ถึงต้องมี

แต่ละ Bounded Context (apps/*) เปิด connection ไปหา Postgres ของตัวเองผ่าน TypeORM connection pool อยู่แล้วในระดับแอป — แต่ปัญหาที่ pooling ระดับแอปคนเดียวแก้ไม่ได้คือ "เครื่อง Postgres ตัวเดียวคือ single point of failure" และ "read query ทั้งหมดยิงไปกองที่ primary ตัวเดียว ทั้งที่มี replica ว่างอยู่" — Pgpool-II คือ layer ที่แทรกอยู่ ระหว่าง แอปกับ Postgres cluster เพื่อแก้ปัญหาทั้งสองข้อนี้พร้อมกัน โดยแอปยังคงต่อผ่าน connection string เดียวเหมือนเดิมทุกประการ — เปลี่ยนแค่ DB_HOST ให้ชี้มาที่ Pgpool แทนที่จะชี้ ตรงไปที่ Postgres

CONNECTION POOLING

Pgpool-II เป็น Layer เดียวที่ทำทั้งสองอย่าง

  • Connection pooling จริง — เก็บ connection ไปยัง backend ไว้ใช้ซ้ำ ลดต้นทุนการเปิด/ปิด TCP + auth ต่อ request
  • Load balancing — กระจาย SELECT ไปทุก node ที่ healthy (primary + replica ทั้งหมด)
  • Query routing — รู้เองว่า node ไหนเป็น primary จริง (pg_is_in_recovery()) แล้วส่ง write ไปที่นั่นเสมอ ไม่ hardcode
HIGH AVAILABILITY

Watchdog + Virtual IP ทำให้ตัว Pgpool เองไม่เป็น SPOF

  • รัน Pgpool 3 ตัว พร้อมกัน เฝ้าดูกันเองผ่าน heartbeat
  • ทั้งสามตัวแชร์ Virtual IP เดียว — แอปต่อ IP เดียวตลอด ไม่ว่า node ไหนตายไปกี่ตัว (ไม่เกิน quorum)
  • node ตาย → node ที่เหลือ "เลือกตั้ง" leader ใหม่เองอัตโนมัติ ภายในไม่กี่วินาที
สิ่งที่ได้ vs สิ่งที่ไม่ได้ — อ่านให้ครบก่อนเริ่ม
✓ สิ่งที่ได้
  • ✓Read scaling + read HA — pgpool กระจาย SELECT ไปทุก backend ที่ผ่าน health check; node ที่ตายถูกถอดออกจาก rotation อัตโนมัติ (auto_failback=on คืนกลับเองเมื่อฟื้น)
  • ✓Write correctness — ตรวจ primary จริงตลอดเวลา (pg_is_in_recovery()) ไม่พึ่ง config แบบ hardcode
  • ✓Read-after-write ถูกต้องบน connection เดียวกัน — disable_load_balance_on_write='always' ปักหมุด connection ไปที่ primary ทั้ง session หลัง write ครั้งแรก
  • ✓Client-side HA — VIP ย้าย node เองผ่าน watchdog + gratuitous ARP โดยแอปไม่ต้องรู้เรื่อง
  • ✓PostgreSQL primary failover อัตโนมัติ — repmgr + repmgrd (§11) promote standby เองเมื่อ primary ตายจริง วัดเวลาได้จริง 29 วินาที จาก kill ถึง promote สำเร็จ โดยไม่มีคนแตะคำสั่ง (§11 Step 4) — ปิด gap เดียวที่เหลือจาก pgpool-only stack
✗ สิ่งที่ไม่ได้ (Known Gaps)
  • ✗ไม่ป้องกัน connection ใหม่คนละตัว อ่านทันทีหลังจาก connection อื่น write เสร็จ — ข้อจำกัดโดยธรรมชาติของ async streaming replication ไม่ใช่สิ่งที่ session-pinning ปิดได้
  • ✗2-node cluster ทนไม่ได้เลย (0 node loss) เว้นแต่เปิด half-votes ซึ่งแลกกับ split-brain risk — ดู §06
ทำไมไม่ใช้ PgBouncer แทน

PgBouncer ทำ connection pooling ได้ดีมาก แต่ ไม่มี concept ของ backend หลายตัว + watchdog HA ในตัวมันเอง — ต้องเอาไปต่อหลัง HAProxy/Consul/Patroni อีกชั้นเพื่อให้ได้ HA แบบเดียวกัน ในขณะที่ Pgpool-II ผูก connection pooling + load balancing + watchdog/VIP failover ไว้ใน process เดียว ลด moving part ที่ต้อง operate สำหรับ topology ขนาดนี้ (1 primary + 2 replica) — trade-off คือ Pgpool config ซับซ้อนกว่าและ debug ยากกว่าเมื่อมีปัญหา (ดู §08 บั๊กที่เจอ 40 ข้อ)

02 — สถาปัตยกรรม

ติดตั้ง PostgreSQL Primary

scp scripts/install-postgresql.sh pg-primary:/tmp/
ssh -t pg-primary "sudo /tmp/install-postgresql.sh --mode=primary \
  --allowed-cidrs=<subnet-cidr, e.g. 10.0.0.0/24> \
  --app-cidrs=<subnet-cidr> \
  --replication-slot=replica1_slot,replica2_slot"
  • --allowed-cidrs = ใครสตรีม replication ได้ (ครอบคลุม IP ของทุก replica — ใช้ whole-subnet CIDR ง่ายสุด)
  • --app-cidrs = ใคร query ปกติได้ (app server, pgpool node) — มักเป็น CIDR เดียวกัน
  • --replication-slot= — 1 slot ชื่อต่อ replica ที่วางแผนจะเพิ่ม คั่นด้วย comma สร้างไว้ล่วงหน้าทั้งหมด
ตัวเลขหน้า /24 ไม่มีผล — ไม่ต้องเสียเวลาไล่ IP ทีละตัว

PostgreSQL mask ทั้งสองฝั่งก่อนเทียบ ดังนั้น 172.16.0.221/24 กับ 172.16.0.0/24 มีความหมายเหมือนกันเป๊ะ — ครอบทั้งซับเน็ตทั้งคู่ จะเขียน IP ของเครื่องไหนก็ได้ตราบใดที่ prefix เป็น /24 (ใช้ /32 ถ้าต้องการเจาะจงทีละเครื่องจริง ๆ)

สร้าง replication password อัตโนมัติในการรันครั้งแรก บันทึกไว้ที่ /root/.pg_replication/replicator.password บน primary — ต้องใช้ในขั้นถัดไป

--priority

ตัวตัดสินตอน election — สูงกว่าชนะ ดังนั้น node 0 ในตัวอย่างคือตัวที่ "อยากให้" ถือ VIP เป็นค่าเริ่มต้น แต่มีผลเฉพาะตอน election — หลัง failover VIP จะยังค้างอยู่ที่ leader ใหม่แม้ node priority สูงกว่าจะกลับมาแล้ว (failback ไม่ preemptive)

--nodes ต้องตรงกันทุกตัวอักษร

พิมพ์ IP ผิดในนี้ ไม่ fail แบบชัดเจน — leader จะปฏิเสธ join request หน้าตาเหมือน auth ผิด (Add to watchdog cluster request is rejected by node) ทำให้หลงไปไล่ wd_authkey แทน ตรวจสอบหลังติดตั้ง: sudo grep -E '^hostname[0-9]' /etc/pgpool2/pgpool.conf ต้องพิมพ์ list เดียวกันทุก node

wd_authkey ต้องตรงกันทุก node

การรันครั้งแรกจะ generate wd_authkey (watchdog auth) และรหัส pcp admin เองอัตโนมัติ เก็บที่ /root/.pgpool/ บน node ที่รันก่อน — copy wd_authkey ไปยัง path เดียวกันบนทุก node ที่เหลือ ก่อน (หรือหลัง) รันที่นั่น 

scp pgpool0:/root/.pgpool/wd_authkey /tmp/wd_authkey
ssh pgpool1 'sudo mkdir -p /root/.pgpool'
scp /tmp/wd_authkey pgpool1:/tmp/
ssh pgpool1 'sudo mv /tmp/wd_authkey /root/.pgpool/wd_authkey && sudo chmod 600 /root/.pgpool/wd_authkey'

ข้ามขั้นตอนนี้ = แต่ละ node จะสร้าง key ของตัวเองแบบสุ่ม แล้ว watchdog handshake จะ fail แบบเงียบๆ (node จะไม่มีวันเห็นกันเป็นสมาชิก cluster เดียวกันเลย)

ยืนยันว่าตรงกันจริงโดยไม่ต้องเปิดดูค่า: sudo sha256sum /root/.pgpool/wd_authkey บนทุก node — hash ต้องเท่ากันหมด (ตัดประเด็น key ออกได้เวลา join ถูกปฏิเสธ)

เพิ่ม node เข้า cluster ที่รันอยู่แล้วภายหลัง — ลำดับสำคัญมาก

ต้อง re-run บน node เดิมทุกตัวด้วย --nodes list ใหม่ก่อน แล้วค่อยติดตั้ง node ใหม่ — เพราะ leader รับ join request เฉพาะจาก host ที่อยู่ใน hostnameN list ของตัวเองเท่านั้น ถ้าติดตั้ง node ใหม่ก่อนที่ leader จะรู้จักมัน จะโดนปฏิเสธด้วย error ที่หน้าตาเหมือน auth ผิด (บั๊ก #15) และ ไล่ node ที่ถือ VIP อยู่เป็นตัวสุดท้าย เพื่อให้ VIP ย้ายน้อยครั้งที่สุด
อย่าลืมว่าการเปลี่ยนจำนวน node จะเปลี่ยน enable_consensus_with_half_votes ไปด้วยอัตโนมัติ (คู่↔คี่) — ทดสอบ failover ซ้ำทุกครั้งหลังเพิ่ม/ลด node

ยืนยัน Pgpool — เช็ค 3 จุดที่บั๊กมักซ่อนอยู่

Backend detection (รันจาก host ไหนก็ได้ที่ต่อถึง pgpool node):

psql -h <pgpool0-ip> -p 5432 -U postgres -d postgres -c 'show pool_nodes;'

คาด backend ทุกตัว status=up, pg_status=up, แถวของ primary role=primary ที่เหลือ role=standby

Watchdog membership (ต้องมี node ขึ้นครบก่อนถึงจะ quorum):

ssh pgpool0
sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
  pcp_watchdog_info -h localhost -p 9898 -U pgpool_admin

install-pgpool.sh เขียน .pcppass ให้เองแล้วทุก node ถ้าเจอ authentication failed for user "pgpool_admin" บน install เก่า สาเหตุคือตำแหน่งไฟล์ ไม่ใช่รหัสผ่านผิด — pcp_* -w อ่าน ~/.pcppass โดย ~ คือ home ของ user ที่รันคำสั่งนั้น (postgres = /var/lib/postgresql) ไม่ใช่ /root

คาดเจอ 3 node เป็น MEMBER, 1 LEADER จากนั้นเช็คสามบรรทัดนี้เจาะจง — แต่ละบรรทัดตรงกับบั๊กจริงที่เงียบสนิท:

# 1. VIP ถูก config จริง (ว่าง = พิมพ์ 'delegate_ip' ตัวเล็กผิด
#    ต้องเช็คค่าที่ RUNNING จริง ไม่ใช่ไฟล์บนดิสก์ — key ที่ไม่รู้จักถูกเมิน)
psql -h <pgpool0-ip> -p 5432 -U postgres -d postgres -c 'show pool_status;' | grep -i delegate

# 2. quorum threshold ตรงกับจำนวน node (3 node -> 2; ถ้าติดที่ 2 node ต้องเป็น 1
#    ไม่งั้น failover ไม่มีวันเกิดขึ้นได้เลย)
sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
  pcp_watchdog_info -h localhost -p 9898 -U pgpool_admin -w -v | grep -i quorum

# 3. VIP ผูกอยู่บน leader จริง
ip -4 addr show | grep <virtual-ip>

ถ้า service ไม่ start เลย ขึ้น FATAL: has_setuid_bit: command '/sbin/sudo' not found คือ if_cmd_path/arping_path ชี้ผิด directory — ต้อง resolve sudo (/usr/bin) ไม่ใช่ path ของ ip/arping (script ปัจจุบันตั้งถูกต้องแล้ว)

6

ทดสอบ VIP Failover จริงก่อนเชื่อใจมัน

ทำขั้นนี้ก่อนเอาแอปจริงมาชี้ VIP:

# ยืนยัน VIP อยู่ที่ไหนตอนนี้
ssh pgpool0 "ip -4 addr show | grep <virtual-ip>"

# จาก host ที่สาม ยืนยันว่า VIP ตอบจริง
psql -h <virtual-ip> -p 5432 -U postgres -d postgres -c 'select 1;'

# ฆ่า node ที่ถือ VIP อยู่
ssh pgpool0 "sudo systemctl stop pgpool2"

# ภายในไม่กี่วินาที ยืนยันว่า VIP ย้ายไป node อื่นแล้ว
ssh pgpool1 "ip -4 addr show | grep <virtual-ip>"

# และยังตอบอยู่
psql -h <virtual-ip> -p 5432 -U postgres -d postgres -c 'select 1;'

# เอา node ที่หยุดไว้กลับมา
ssh pgpool0 "sudo systemctl start pgpool2"

# เช็ค backend อีกครั้งเสมอ — VIP test ผ่านไม่ได้แปลว่า backend กลับเข้า rotation แล้ว
psql -h <virtual-ip> -p 5432 -U postgres -d postgres -c 'show pool_nodes;'

ถ้า backend ไหนขึ้น status=down ทั้งที่ pg_status=up (และ pg_stat_replication ยัง streaming ปกติ) คือ stale sticky state ไม่ใช่ outage จริง — เคลียร์บน leader ปัจจุบัน: 

sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
  pcp_attach_node -h localhost -p 9898 -U pgpool_admin -w -n <node_id>
ห้ามข้ามขั้นตอนนี้

บั๊ก VIP ทุกข้อในตาราง §08 ดูเหมือนทำงานปกติดีทุกอย่างจนกว่าจะทำ kill-test จริง — quorum บอก OK, service เป็น active, escalation log SUCCESS ด้วยซ้ำ (ดู #16) แต่ VIP ไม่ขึ้นจริง มีทางเดียวที่จะรู้แน่ชัดคือฆ่า node จริงแล้วดู

ถ้า VIP ไม่ย้าย เช็คตามลำดับนี้:

  1. survivor บอกว่าไม่มี quorum ไหม? — journalctl -u pgpool2 บน node ที่รอด ขึ้น I am the cluster leader node but we do not have enough nodes in cluster = จำนวน node เป็นเลขคู่โดยไม่เปิด half-votes (สาเหตุที่พบบ่อยที่สุดบน 2-node cluster)
  2. VIP เคยถูก config จริงไหม? — show pool_status | grep -i delegate ว่างเปล่า = ไม่เคยถูกยกขึ้นมาเลย (ไม่มีอะไรให้ย้าย)
  3. ค่อยสงสัย anti-spoofing ที่ hypervisor/cloud layer บล็อก gratuitous ARP — ดู "VIP mechanics" ใน §06 (ยืนยันแล้วว่าไม่ใช่ปัญหาบน OVH vRack)

VIP จะไม่ย้ายกลับตอน node เดิมกลับมา — failback ไม่ preemptive โดยตั้งใจ ไม่ใช่ความผิดพลาด

7

ชี้แอปไปที่ Cluster

แก้ connection config ของแอป (เช่น .env ของ repo นี้ — AUTH_DB_HOST, IAM_DB_HOST ฯลฯ) ให้เป็น Virtual IP เท่านั้น ไม่ใช่ host ไหนใน layer ใดเลย:

AUTH_DB_HOST=<virtual-ip>
AUTH_DB_PORT=5432
ห้ามชี้แอปตรงไปที่ PostgreSQL host

การชี้ตรงข้าม load balancing และ failover ทั้งคู่ — ทำให้ทั้ง layer นี้ที่สร้างมาไม่มีความหมายอะไรเลย

1) เทียบ error กับตาราง §08 ก่อน — เคสส่วนใหญ่ที่ใครก็เจอกับ script คู่นี้มีบันทึกไว้แล้ว 2) systemctl status postgresql@18-main / systemctl status pgpool2 + journalctl -u <service> --no-pager | tail -50 ดู error จริง 3) สคริปต์ทั้งคู่ idempotent — รันซ้ำได้ปลอดภัยเสมอสำหรับ standalone/primary ของ PostgreSQL และ Pgpool ทั้งหมด; replica mode จะ wipe+clone ใหม่ (ปลอดภัย แค่ช้ากว่า)

มี NAT บน PVE map public IP พอร์ตหนึ่งเข้า VIP:5432 ให้ app ที่อยู่นอกวง (on-prem/บ้าน) ต่อเข้ามาได้ — พอรวมกับสามอย่างข้างล่างนี้เท่ากับ เปิดบัญชี superuser ของ production ให้ทั้งอินเทอร์เน็ตลองรหัสได้ไม่จำกัดจำนวนครั้ง

  • • pool_hba.conf บรรทัดสุดท้ายเป็น host all all 0.0.0.0/0 scram-sha-256 — รับทุก IP บนโลก
  • • ไม่มี firewall เลยบน pgpool node (ufw: inactive, iptables -P INPUT ACCEPT) — พอร์ต 9898 (PCP) และ 9000 (watchdog) ไม่ได้ถูก NAT ออกไป แต่เปิดโล่งต่อทั้ง LAN
  • • ทุก app ต่อด้วย role postgres ซึ่งเป็น superuser — บนคลัสเตอร์นี้มี login role แค่ 4 ตัว (postgres, repmgr = superuser ทั้งคู่, exporter_svc, replicator) ไม่มี role สำหรับ application เลย
  • • host all all 127.0.0.1/32 trust — ใครก็ตามที่มี shell บน pgpool node เป็น superuser ของทุก DB ได้ทันทีโดยไม่ต้องรู้รหัส (ทดสอบยืนยันแล้วจาก user ธรรมดา)

ทิศทางที่ตัดสินใจแล้ว — ยังไม่ implement (บันทึกไว้ 2026-08-31)

ย้าย client ที่อยู่นอกวงไปต่อผ่าน Tailscale แล้วปิด NAT ที่ชี้เข้า VIP ทิ้ง — พิจารณา Cloudflare Tunnel กับ static IP แล้วไม่เอา: PostgreSQL เป็น raw TCP ทำให้ Cloudflare ต้องใช้ cloudflared access tcp ซึ่งก็ต้องลง agent ฝั่ง client เหมือน Tailscale อยู่ดี (พอร์ต TCP สาธารณะตรงๆ ต้องใช้ Spectrum = Enterprise) ส่วน static IP ทาง ISP ไม่มีให้ และ IP ปัจจุบันเป็น dynamic residential ที่ whitelist แบบ /32 ไม่ได้จริง

เมื่อย้ายเสร็จ pool_hba.conf จะเหลือแค่นี้ ไม่ต้องมี 0.0.0.0/0 เลย (pgpool ปฏิเสธเองอยู่แล้วเมื่อไม่มี record ไหนแมตช์ — ไม่ต้องเขียน deny): 

local   all     all             trust
host    all     all             127.0.0.1/32     scram-sha-256   # เลิกใช้ trust
host    all     all             172.16.0.0/24    scram-sha-256

งานที่ต้องทำก่อนไม่ว่าจะเลือกทางไหน: สร้าง role สำหรับ application ที่ไม่ใช่ superuser แล้วเพิ่มเข้า pool_passwd ด้วย pg_enc ทั้ง 3 pgpool node (ถ้าลืมขั้นนี้จะเจอ username "x" or password does not exist in backend ทันที) — tunnel กันคนนอกได้ แต่ไม่ได้ลดความเสียหายถ้า credential หลุดจากในเครื่องเอง

06 — Watchdog Quorum & VIP Failover

จำนวน Node ตัดสินว่า Failover จะทำงานได้จริงหรือไม่

Pgpool จะไม่ยก VIP ขึ้นถ้าไม่มี quorum และ default ของ quorum คือเสียงข้างมากจริง (strict majority) — ทำให้ "จำนวน node" เป็นเรื่องความถูกต้อง (correctness) ไม่ใช่แค่เรื่อง capacity

Quorum Scenarios · เปรียบเทียบ 2-node vs 3-node หลังเสีย node
Nodesต้องการเพื่อ quorumทนได้enable_consensus_with_half_votes
2 (คู่)2 — ไปไม่ถึงหลังเสีย 10 (failover ไม่เกิดเลย)ต้อง on — แลกกับ split-brain
3 (คี่)21off — majority จริง ไม่มีข้อแลก
4 (คู่)31on เพื่อทน 2-loss ไม่งั้นไม่ดีกว่า 3
5 (คี่)32off

install-pgpool.sh คำนวณค่านี้ให้อัตโนมัติจากความยาวของ --nodes — คู่ = on พร้อม warning, คี่ = off cluster นี้รัน 3 node จึงเป็น off — majority จริง ไม่มีความเสี่ยง split-brain

โหมดล้มเหลวของ 2-node cluster เงียบสนิทจนกว่าจะ kill-test จริง

survivor ชนะ election กลายเป็น LEADER แล้วนิ่งอยู่ตรงนั้น log ว่า: 

I am the cluster leader node but we do not have enough nodes in cluster
DETAIL:  waiting for the quorum to start escalation process

— VIP ค้างdown ตลอดช่วง outage ซึ่งคือสถานการณ์ที่ VIP มีไว้แก้พอดี ตรวจ threshold ที่ใช้จริงหลังเปลี่ยนจำนวน node ทุกครั้ง: 

sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
  pcp_watchdog_info -h localhost -p 9898 -U pgpool_admin -w -v | grep -i quorum

คาด Nodes required for quorum: 2 และ Quorum state: QUORUM EXIST สำหรับ cluster 3-node นี้

เสีย 2 จาก 3 → VIP ลงถูกต้อง

verify แล้ว ไม่ใช่บั๊ก — survivor ตัวเดียวมี 1 จาก 3 เสียง ปฏิเสธ escalate เอง VIP ค้าง unbound จนกว่า node ที่สองจะกลับมา ต้องการทน 2-loss พร้อมกันต้องมี 5 node ไม่ใช่ 3

Failback ไม่ preemptive

node เดิมกลับมาจะ rejoin เป็น STANDBY เสมอ — VIP ค้างอยู่ที่ leader ปัจจุบัน wd_priority มีผลแค่ตอนตัดสิน election ไม่ได้ลาก leadership กลับ เป็นการตั้งใจ (กัน VIP กระพริบบน node ที่ไม่เสถียร) — ไม่ใช่บั๊กถ้า VIP ไม่กลับไป pgpool1 หลัง restart

VIP Mechanics — สำหรับใครไม่คุ้น watchdog+VIP

VIP ไม่ได้ผูกถาวรกับ pgpool host ตัวไหน — watchdog leader ผูกมันเข้ากับ NIC ตัวเอง (ip addr add) แล้วส่ง gratuitous ARP — แพ็กเก็ต ARP ที่ไม่มีใครขอ บอกทุกเครื่องในวง L2 ว่า "IP นี้อยู่ที่ MAC ของฉันแล้วนะ" ทุกเครื่องอัปเดต ARP table ทันที traffic ไป VIP จึงไหลไป leader ใหม่โดยฝั่ง client ไม่ต้อง reconfigure อะไรเลย ตอน failover leader ใหม่ทำ ip addr add + gratuitous ARP ซ้ำแบบเดียวกัน

  • pgpool node ทุกตัวต้องอยู่ L2 segment เดียวกับ VIP — จริงในกรณีนี้ (OVH vRack เป็น L2 network จริง)
  • process ต้องมีสิทธิ์ root รัน ip addr add/arping — จัดการผ่าน /etc/sudoers.d/pgpool-vip NOPASSWD grant เฉพาะสองคำสั่งนี้ ไม่ได้รัน pgpool เป็น root
  • บาง cloud/hypervisor layer มี anti-spoofing drop gratuitous ARP แบบเงียบๆ สำหรับ IP ที่ VM ไม่เคย "ประกาศ" ไว้ — ยืนยันแล้วว่าไม่ใช่ปัญหาบน OVH vRack นี้ (2026-08-09): VIP ย้ายระหว่าง pgpool node ได้จริงบน kill-test และตอบ query จาก client นอก subnet ตลอด
07 — ทดสอบ Step-by-Step

ทดสอบทีละขั้น — กำลังทำอะไร เพื่ออะไร และผลลัพธ์ที่ต้องเห็น

ลำดับนี้ออกแบบให้ ทดสอบจากชั้นล่างขึ้นบน — PostgreSQL ก่อน แล้วค่อย pgpool แล้วค่อย VIP — เพราะถ้าข้ามไปทดสอบชั้นบนทั้งที่ชั้นล่างยังไม่ดี จะได้อาการที่ตีความผิดทาง (เช่น pgpool บอก backend down ทั้งที่จริงๆ replica ยังไม่ streaming) แต่ละขั้นบอกว่ากำลังพิสูจน์อะไร และถ้าไม่ผ่านแปลว่าอะไร

T1

Replica กำลัง stream จาก primary จริงไหม

เพื่ออะไร: พิสูจน์ว่า layer 2 (PostgreSQL) ทำงานครบก่อนจะไปแตะ pgpool — ถ้าข้ามขั้นนี้ pgpool จะ mark node เป็น down แล้วเราจะ debug ผิดชั้น

# รันบน primary
psql -h localhost -U postgres -c \
  "SELECT application_name, client_addr, state, sync_state, replay_lag FROM pg_stat_replication;"
ผลที่ต้องเห็น

1 แถวต่อ 1 replica ทุกแถว state=streaming, sync_state=async · ไม่ครบ = ห้ามไปต่อ — ดู journalctl -u postgresql@18-main บน replica ตัวที่หาย

T2

Replication slot ถูกใช้งานอยู่จริง

เพื่ออะไร: slot คือสิ่งที่กัน primary ลบ WAL ทิ้งก่อน replica ตามทัน — active=f แปลว่า replica ตัวนั้นไม่ได้เกาะ slot อยู่ ถ้า replica ดับนานอาจตามไม่ทันแล้วต้อง re-clone

psql -h localhost -U postgres -c \
  "SELECT slot_name, active, restart_lsn FROM pg_replication_slots;"
ผลที่ต้องเห็น

ทุก slot active=t และ restart_lsn ขยับตามเวลา

T3

เครื่อง replica รู้ตัวว่าเป็น standby

เพื่ออะไร: ยืนยันจากฝั่ง replica เองว่าอยู่ในโหมด recovery — เป็นค่าเดียวกับที่ pgpool ใช้ตัดสินว่าใครคือ primary (sr_check)

# รันบนแต่ละ replica
sudo -u postgres psql -tAc 'SELECT pg_is_in_recovery();'
ผลที่ต้องเห็น

T4

Pgpool มองเห็น backend ครบและแยก primary/standby ถูก

เพื่ออะไร: พิสูจน์ว่า layer 1 ต่อ layer 2 ได้ (pg_hba + listen_addresses ถูก) และ sr_check ตรวจ role ได้จริง — ยังไม่เกี่ยวกับ VIP

# ยิงตรงที่ pgpool node ทีละตัว (ยังไม่ผ่าน VIP)
psql -h <pgpool-ip> -p 5432 -U postgres -d postgres -c 'show pool_nodes;'
ผลที่ต้องเห็น

ทุกแถว status=up + pg_status=up, primary 1 แถว role=primary ที่เหลือ standby, replication_delay=0
status=down แต่ pg_status=up = sticky state เก่า ไม่ใช่ปัญหาจริง → pcp_attach_node (บั๊ก #14/#20)

T5

VIP ถูก config จริง (ไม่ใช่แค่พิมพ์ไว้ในไฟล์)

เพื่ออะไร: ดักบั๊ก #16 โดยเฉพาะ — pgpool เมิน key ที่สะกดผิดแบบเงียบ ๆ ไฟล์บนดิสก์จึงเชื่อไม่ได้ ต้องถามค่าที่ daemon โหลดจริง

psql -h <pgpool-ip> -p 5432 -U postgres -d postgres -c 'show pool_status;' | grep -i delegate
ผลที่ต้องเห็น

delegate_IP | 172.16.0.226 | ... — ถ้าค่าว่าง แปลว่า VIP ไม่เคยถูกยกขึ้นเลย (สะกด delegate_ip ตัวเล็ก) ไม่ต้องไปหาสาเหตุที่ ARP/firewall

T6

เพื่ออะไร: ดักบั๊ก #18 — ตัวเลขนี้ตัดสินว่า failover จะเกิดขึ้นได้จริงหรือไม่ ถ้าผิดจะไม่มีอาการอะไรเลยจนกว่าจะมี node ตายจริง

sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
  pcp_watchdog_info -h localhost -p 9898 -U pgpool_admin -w -v
ผลที่ต้องเห็น (cluster 3 node)

Total Nodes: 3 · Nodes required for quorum: 2 · Quorum state: QUORUM EXIST · มี LEADER 1 ตัว ที่เหลือ STANDBY ทุกตัวเป็น MEMBER
required = 3 บน cluster 3 node แปลว่าตั้งค่าผิด (failover จะไม่ทำงาน) · auth failed = ปัญหา path ของ .pcppass ไม่ใช่รหัสผิด (บั๊ก #19)

T7

VIP ผูกอยู่บน NIC ของ leader จริง

เพื่ออะไร: ยืนยันว่า if_up_cmd ทำงานสำเร็จ (sudoers ถูก, if_cmd_path ถูก) — VIP ต้องอยู่บนเครื่องเดียวเท่านั้น

# รันบนทุก pgpool node — ต้องเจอที่เดียว
ip -4 addr show | grep 172.16.0.226
ผลที่ต้องเห็น

บน leader: inet 172.16.0.226/24 scope global secondary ens18:0 · node อื่นไม่มี · เจอมากกว่า 1 เครื่อง = split-brain (เกิดได้เฉพาะตอน half-votes เปิดบน cluster เลขคู่)

ยังไม่พอ — VIP ขึ้นได้จาก ip addr add อย่างเดียว แม้ arping จะ fail

ip addr add กับ arping เป็นคนละคำสั่งใน escalation chain — เช็คแยกด้วย sudo journalctl -u pgpool2 --no-pager | grep -E "if_up_cmd|if_down_cmd" ต้องเห็น 'if_up_cmd' returned with success ไม่ใช่ 'if_up_cmd' failed — ถ้า fail ทุกครั้งทั้งที่ T7 ผ่าน คือ package arping ผิดตัว (บั๊ก #21)

T8

VIP ตอบ query จากเครื่องภายนอกได้

เพื่ออะไร: พิสูจน์ว่า gratuitous ARP ไปถึงเครื่องอื่นจริง — ต้องยิงจากเครื่องที่สาม ไม่ใช่จาก pgpool node เอง (จากตัวเองจะผ่านเสมอแม้ ARP ถูกบล็อก)

# จากเครื่องอื่นที่อยู่ subnet เดียวกัน
psql -h 172.16.0.226 -p 5432 -U postgres -d postgres -c 'select 1;'
ผลที่ต้องเห็น

ได้ค่า 1 กลับมา · Network is unreachable = VIP ไม่ได้ผูกอยู่ที่ไหนเลย (กลับไป T5/T6) · timeout = ARP ถูกบล็อกที่ hypervisor

T9

Kill-test: ฆ่า leader แล้ว VIP ต้องย้าย

เพื่ออะไร: ขั้นที่สำคัญที่สุดและห้ามข้าม — บั๊ก #16/#17/#18/#21 ทั้งหมด "ดูปกติดี" ผ่าน T1–T8 ได้หมด แล้วมาโผล่ตรงนี้ที่เดียว (บั๊ก #21 โผล่แค่ใน journalctl เท่านั้น — VIP ยังย้ายและตอบได้ตามปกติ)

# 1) หยุด node ที่ถือ VIP อยู่
ssh <leader> "sudo systemctl stop pgpool2"

# 2) รอ ~25 วิ แล้วหาว่า VIP ไปโผล่ที่ไหน
ssh <node-อื่น> "ip -4 addr show | grep 172.16.0.226"

# 3) ยิงจากเครื่องที่สามซ้ำ — ต้องยังตอบอยู่
psql -h 172.16.0.226 -p 5432 -U postgres -d postgres -c 'select 1;'

# 4) เอา node กลับมา
ssh <leader-เดิม> "sudo systemctl start pgpool2"
ผลที่ต้องเห็น

VIP ย้ายไป node ที่ priority รองลงมาภายในไม่กี่วินาที และ query จากภายนอกยังตอบต่อเนื่อง · node เดิมกลับมาแล้ว VIP ไม่ย้ายกลับ — ถูกต้อง ไม่ใช่บั๊ก (failback ไม่ preemptive)
ไม่ย้าย? ดู journalctl -u pgpool2 บน node ที่รอด — ถ้าเจอ waiting for the quorum คือปัญหา quorum (กลับไป T6)

T10

เช็ค backend ซ้ำหลัง kill-test

เพื่ออะไร: VIP ผ่านไม่ได้แปลว่า backend กลับเข้า rotation แล้ว — บั๊ก #20 โผล่ตรงนี้ ถ้าไม่เช็คจะเสีย read scaling ไปเงียบ ๆ

psql -h 172.16.0.226 -p 5432 -U postgres -d postgres -c 'show pool_nodes;'

# ถ้าเจอ status=down แต่ pg_status=up — เคลียร์บน leader ปัจจุบัน
sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
  pcp_attach_node -h localhost -p 9898 -U pgpool_admin -w -n <node_id>
T11

Read-after-write ผ่าน connection เดียวกัน

เพื่ออะไร: พิสูจน์ว่า disable_load_balance_on_write='always' ทำงานจริง — insert แล้ว select กลับมาทันทีต้องไม่เจอ replication lag

# session เดียว ต่อผ่าน VIP — write แล้ว read ทันที
psql -h 172.16.0.226 -U postgres -d postgres <<'SQL'
CREATE TABLE IF NOT EXISTS raw_test(id serial primary key, note text);
INSERT INTO raw_test(note) VALUES ('read-after-write');
SELECT count(*) FROM raw_test WHERE note = 'read-after-write';
DROP TABLE raw_test;
SQL
ผลที่ต้องเห็น

count = 1 ทุกครั้ง ไม่มีวันเป็น 0 — เพราะ connection ถูกปักหมุดไป primary ตั้งแต่ INSERT แรก

T12

ข้อมูลไปถึง replica จริงทั้งสองตัว

เพื่ออะไร: ทดสอบ end-to-end ว่า write ที่ผ่าน pgpool ไปโผล่บนทุก backend — ยิงตรงที่แต่ละเครื่อง ไม่ผ่าน pgpool เพื่อไม่ให้ load balancer มาบังผลลัพธ์

# เขียนผ่าน VIP
psql -h 172.16.0.226 -U postgres -d postgres -c \
  "CREATE TABLE IF NOT EXISTS repl_test(id int); INSERT INTO repl_test VALUES (42);"

# อ่านตรงจากทั้ง 3 เครื่อง — ต้องเจอเหมือนกันหมด
for h in 172.16.0.221 172.16.0.222 172.16.0.223; do
  echo -n "$h: "
  psql -h "$h" -U postgres -d postgres -tAc 'SELECT count(*) FROM repl_test;'
done

# เก็บกวาด
psql -h 172.16.0.226 -U postgres -d postgres -c 'DROP TABLE repl_test;'
ผลที่ต้องเห็น

ทั้งสามเครื่องตอบ 1 เท่ากัน ภายในเวลาไม่ถึงวินาที

T13

Exporter ตอบ metric จริงทุกเครื่อง

เพื่ออะไร: node_exporter ขึ้นง่ายเสมอและมักบังปัญหาของ exporter ตัวจริง — ต้องเช็คแยกทีละตัว

curl -s http://<host>:9100/metrics | head -3

# PostgreSQL metrics (ppm/ppr1/ppr2)
curl -s http://<pg-host>:9187/metrics | grep -c '^pg_'

# Pgpool metrics (pgpool1/2/3) — ต้องได้มากกว่า 0
curl -s http://<pgpool-host>:9719/metrics | grep -c '^pgpool2_'
ผลที่ต้องเห็น

ทุก endpoint คืน metric · 9719 ได้ 0 บรรทัด = exporter_svc ยังไม่ได้ลงทะเบียนใน pool_passwd ของ node นั้น ตรวจด้วย journalctl -u pgpool2_exporter จะเจอ failed to authenticate with backend using SCRAM วน retry (ดู §12)

Test 2 — VIP Failover (2 รอบ: 2-node แล้วซ้ำที่ 3-node)
Round 1 · 2-node cluster (half-votes = on)
  1. Steady state: VIP อยู่บน pgpool1 (LEADER) — psql -h 172.16.0.226 จาก client นอก pgpool host ตอบทุก backend ปกติ

  4. Restart pgpool1: rejoin เป็น STANDBY, VIP ค้างที่ pgpool2 (failback ไม่ preemptive)

Round 2 · 3-node cluster (half-votes = off — majority จริง)
  1. Steady state: Nodes required for quorum: 2, QUORUM EXIST, ทั้ง 3 node MEMBER, VIP บน pgpool1 (priority 3)
  2. หยุด pgpool1 → VIP ย้ายไป pgpool2 (priority รองลงมา) ยังตอบ query จากภายนอกต่อ — failover ทำงานได้แม้ half-votes ปิด
  3. หยุด pgpool2 เพิ่มด้วย (เหลือ 1 จาก 3) → VIP ไปไหนไม่ได้เลย — pgpool3 log waiting for the quorum to start escalation process — ถูกต้อง ไม่ใช่ regression
  4. Restart pgpool1+pgpool2 → quorum กลับมา VIP ขึ้นที่ pgpool3 (leader ตลอด outage — non-preemptive)
  5. เจอจากการเช็คหลังทดสอบ: show pool_nodes โชว์ ppr1/ppr2 status=down ทั้งที่ pg_status=up — sticky state จาก outage (บั๊ก #20) เคลียร์ด้วย pcp_attach_node

Round 3 · หลังแก้บั๊ก #21 (arping ผิด package)

  2. รอบนี้ journalctl -u pgpool2 บน leader ใหม่ขึ้น 'if_up_cmd' returned with success / successfully acquired the delegate IP — ยืนยันคำสั่งจริงที่ pgpool รัน ไม่ใช่แค่ผลลัพธ์ปลายทาง

11 — Automatic Failover

ปิด Known Gap สุดท้าย: repmgr คุมชั้น PostgreSQL Replication โดยเฉพาะ

§10 พิสูจน์แล้วว่า Pgpool-II ยอมรับ primary ใหม่ได้เองทันทีที่มีใครสักคนหรือสักอย่าง promote ให้ (ไม่ต้องแก้ pgpool config เลยแม้แต่บรรทัดเดียว) — repmgr คือ tool ที่มา เป็น "ใครสักอย่าง" นั้นแทนคน: monitor primary ผ่าน repmgrd daemon บนทุก node, ตัดสินใจ + สั่ง pg_promote() เองเมื่อ primary หายจริง, สั่ง standby ที่เหลือ follow primary ใหม่อัตโนมัติ — แล้วรัน event hook ที่ปิดบั๊ก #24 ไปพร้อมกันในตัว (pcp_attach_node ทุก backend ทุก pgpool host อัตโนมัติ หลัง promote/follow) Script: scripts/install-repmgr.sh

ความแม่นยำการตัดสินใจ failover Witness-based health check — เร็ว ติดตั้งง่าย แต่เสี่ยง false-positive มากกว่าตอน network partition DCS consensus จริง (เหมือน raft) — กัน split-brain แน่นหนากว่า เป็นมาตรฐาน cloud-native

สรุป: topology ปัจจุบัน (native streaming replication + pgpool dynamic primary detection) เข้ากับ repmgr โดยตรง ไม่ต้อง rebuild อะไรที่มีอยู่แล้ว — ถ้าในอนาคตความเสี่ยง false-positive ของ witness-based failover กลายเป็น ปัญหาจริง (เช่น network partition บ่อยจน repmgr promote ผิดจังหวะ) ค่อยพิจารณาย้ายไป Patroni เป็น major re-architecture แยกต่างหาก

สิ่งที่ repmgr ไม่ได้ปิดให้ฟรีๆ: node เดิมต้อง rejoin ผ่าน repmgr เท่านั้น ห้าม auto-start เอง

รากปัญหาจริงของ §10 คือ ppm reboot เองแล้ว systemd สั่ง start PostgreSQL ให้ทันทีโดยไม่มีใครถามก่อนว่า "ตอนนี้ยังควรเป็น primary อยู่ไหม" — repmgrd ทำงานอยู่ไม่ได้แปลว่าปัญหานี้ หายไปเอง เพราะ systemd ไม่รอ repmgrd ตัดสินใจก่อน start install-repmgr.sh จึงปิด boot auto-start ของ postgresql@18-main ทุก node (systemctl disable) บังคับให้ node ที่ reboot กลับมาต้อง repmgr node rejoin ก่อนเสมอ ซึ่งเช็คกับ cluster ที่เหลือก่อนว่าใครเป็น primary จริงแล้ว rejoin เป็น standby ให้ถูกต้อง — ไม่ใช่ hard fencing (STONITH) แบบเต็มรูป แต่ปิดช่องโหว่หลักที่ เจอจริงได้

เจอจริงอีกเคส (2026-08-09): systemctl disable กันเฉพาะ auto-start ตอน reboot — ไม่ได้กันคนสั่ง systemctl start postgresql@18-main ตรงๆ ด้วยมือ ถ้ามีคนทำแบบนี้กับ node ที่เพิ่ง stop จาก primary ตัวเดิม (ไม่ผ่าน repmgr node rejoin) มันจะ start กลับมาเป็น primary อิสระทันที (pg_role=primary ใน show pool_nodes) แม้จะมี primary ตัวใหม่ที่ repmgr promote ไปแล้วอยู่ก่อน — split-brain window แบบเดียวกับ §10 เป๊ะ เกิดจากคน ไม่ใช่จาก reboot คราวนี้ กฎเหล็ก: ห้าม systemctl start postgresql บน node ที่เพิ่งตายหรือเพิ่ง stop โดยเด็ดขาด ใช้ repmgr node rejoin -d '...' --force-rewind เท่านั้นเสมอ (คำสั่งเต็มอยู่ใน warning ตอนติดตั้งข้างบน)
