ข้อมูลตั้งต้นที่ต้อง ตั้งค่าให้ครบก่อนเริ่มทำธุรกรรมสต็อก — เอกสารนี้ระบุว่าแต่ละ master ต้องกรอกฟิลด์ใดบ้าง (required) เพื่อ ส่งต่อให้ inventory (Phase 3) ทำงานได้

01

Business Overview & Roles · ใครตั้งค่าอะไร

MASTER DATA ADMIN
ผู้ดูแลข้อมูลหลัก

ตั้งค่า UOM, Item Group (โครงต้นไม้), Brand และ Warehouse — โครงสร้างพื้นฐานที่ทุกสินค้าอ้างถึง

PRODUCT OWNER
ผู้ดูแลสินค้า

สร้าง Item master (2 ภาษา), กำหนด stock UOM + conversion, สร้าง variant จาก attribute และตั้งจุดสั่งซื้อ

PURCHASING
ฝ่ายจัดซื้อ

ตั้งค่า Supplier (ใน supplier-bc) — inventory อ้างถึงด้วย supplier_id (UUID) ตอนรับสินค้า

วัตถุประสงค์ของเฟส: master data คือ รากฐาน — ต้องตั้งค่าให้เสร็จก่อนเปิดทำธุรกรรมใด ๆ (Goods Receipt / PO / SO) · ทุกฟิลด์ 2 ภาษาเก็บเป็น flat column name_th / name_en และทุกตารางสืบทอด BaseEntity (audit + soft-delete) ตาม Backend Conventions

supplier-bc เป็นเจ้าของ · inventory/finance อ้างด้วย supplier_id (UUID) เท่านั้น ไม่ join ข้าม DB

ตัดขอบเขตรอบนี้

Company Bank Account (รอ finance-bc) และ Withholding Tax (หัก ณ ที่จ่าย — แยกจาก VAT โดยสิ้นเชิง) ยังไม่ออกแบบในรอบนี้ — ดู TAX_CONFIGS ใน P5 · Finance ที่รองรับทั้ง VAT/WHT ไว้แล้วเป็นแผน (ยังไม่มีโค้ด) · VAT registration status (is_vat_registered) implement แล้วในรอบนี้

Fieldจำเป็นคำอธิบาย

Header/Line pattern (standard)

ตรงกับทุกระบบหลัก (ERPNext Price List, Odoo pricelist, Dynamics 365 BC Price List Header, NetSuite Price Level) — currency อยู่ที่ header เท่านั้น ไม่ปล่อยให้ line (item_prices) override ต่างสกุลเงินภายใน price list เดียวกัน ป้องกันการรวมยอด/เทียบราคาผิดพลาด

Validate ที่ service ไม่ใช่ DB

DB CHECK constraint (23514) ไม่ถูก map โดย PostgresErrorMapper (ตกไปเป็น 500) — ต้องเช็ค is_buying/is_selling ในชั้น DTO/service ก่อน insert เสมอ

Fieldจำเป็นคำอธิบาย

ทั้งคู่คำนวณเป็น 0.00 บาทในบรรทัดเหมือนกัน แต่ zero_rated ยังอยู่ในระบบ VAT — ภาษีซื้อของต้นทุนที่ใช้ผลิต/ขายสินค้านั้นยังขอเครดิตคืนได้ ส่วน exempt อยู่นอกระบบ VAT — ภาษีซื้อที่เกี่ยวข้องขอเครดิตคืนไม่ได้ ต้องแยก vat_treatment ให้ถูกตั้งแต่ระดับสินค้า ไม่ใช่แค่ "ไม่มี VAT" เฉย ๆ

ขอบเขต — คนละงานกับ TAX_CONFIGS ใน finance-bc

tax_categories ที่นี่คือ การจัดประเภทสินค้าทางภาษี (item-level) เท่านั้น — ตัวเลขจริงตอนออกใบกำกับภาษี (คำนวณ VAT ต่อบรรทัด, เลขที่ใบกำกับต่อเนื่อง, WHT) เป็นหน้าที่ TAX_CONFIGS + Tax Invoice ใน P5 · Finance ซึ่งยังไม่มีโค้ดเลย (ดู workflow เต็มด้านล่าง)

Unique scope + Overlap guard (บังคับจริงที่ ItemPricesService)

uq_item_prices_scope (product+price_list+uom+supplier+batch+valid_from) กันซ้ำค่าตรงเป๊ะที่ DB · ช่วงวันที่ทับซ้อนกัน (DB จับไม่ได้) เช็คที่ ItemPricesService.assertNoOverlap() ก่อน insert/update ทุกครั้ง → ทับซ้อน = 409 Conflict

ตั้งราคาได้เฉพาะสินค้าที่ "ซื้อขายตรงได้"

ItemPricesService.assertValidProduct() ปฏิเสธ product.has_variants=true (template) และ product.type='bundle' ทันที — ตั้งราคาได้เฉพาะ variant/สินค้าเดี่ยวที่ transact ได้จริงเท่านั้น (ดูตัวอย่างด้านล่าง)

ตัวอย่าง Data & Workflow · Business Rule ที่บังคับจริงในโค้ด

3 กฎด้านล่างเป็น validation ที่ implement จริงแล้วใน ItemPricesService/ItemSuppliersService (ไม่ใช่แค่แผนในเอกสาร) — แสดง request/response จริงเพื่อให้เห็นว่า data ไหลยังไง

RULE 1 ห้ามตั้งราคาช่วงวันที่ทับซ้อนกัน (409 Conflict) 
// แถวแรก — ตั้งราคาสินค้า A ช่วง 1-31 ม.ค.
POST /item-prices
{ "product_id": "prod-A", "price_list_id": "Standard-Selling", "uom_id": "uom-piece",
  "rate": 100, "valid_from": "2026-01-01", "valid_upto": "2026-01-31" }
// → 201 Created (id: ip-001)

// แถวสอง — ตั้งราคาสินค้า A ตัวเดียวกัน ช่วง 15-20 ม.ค. (ทับกับแถวแรก)
POST /item-prices
{ "product_id": "prod-A", "price_list_id": "Standard-Selling", "uom_id": "uom-piece",
  "rate": 120, "valid_from": "2026-01-15", "valid_upto": "2026-01-20" }
// → 409 Conflict
{ "message": "Item price overlaps existing row 'ip-001' for the same product/price list/uom/supplier/batch (valid 2026-01-01 to 2026-01-31)." }

ตั้ง valid_upto เป็นค่าว่าง (ไม่มีกำหนด) ก็ยังโดนตรวจ — ระบบตีความ null เป็น -∞/+∞ ตามด้าน เทียบ overlap ให้ถูกต้องเสมอ

RULE 2 ตั้งราคา/ผูกซัพพลายเออร์ให้ template หรือ bundle ไม่ได้ (400 Bad Request) 
// เสื้อยืด (template, has_variants=true) — ห้ามตั้งราคาตรง ต้องเลือก variant
POST /item-prices
{ "product_id": "TSHIRT", "price_list_id": "Standard-Selling", ... }
// → 400 Bad Request
{ "message": "Product 'TSHIRT' is a variant template (has_variants=true) and cannot be priced directly — price the generated variants instead." }

// ชุดของขวัญปีใหม่ A (bundle) — ห้ามผูกซัพพลายเออร์ตรง ไม่มี Lot ของตัวเอง
POST /item-suppliers
{ "product_id": "GIFTSET-A", "supplier_id": "sup-xyz" }
// → 400 Bad Request
{ "message": "Product 'GIFTSET-A' is a bundle (type=bundle) and is never purchased directly — assign suppliers to the component items instead." }
RULE 3 products.supplier_id (เดิม) sync ตาม item_suppliers.is_default อัตโนมัติ 
// 1) ผูกผู้จัดซื้อรายแรกเป็น default → products.supplier_id ถูกตั้งค่าตาม ในทรานแซกชันเดียวกัน
POST /item-suppliers
{ "product_id": "PARA-500", "supplier_id": "บ.เอบีซี", "is_default": true }
// → 201 Created · products.supplier_id (PARA-500) = "บ.เอบีซี" ทันที

// 2) เปลี่ยน default ไปอีกเจ้า → แถวเก่าถูก clear is_default + products.supplier_id ตามเจ้าใหม่
PUT /item-suppliers/{id-เมดิคอล}
{ "is_default": true }
// → 200 OK · แถว "บ.เอบีซี" is_default=false อัตโนมัติ · products.supplier_id = "บ.เมดิคอล"

// 3) ลบแถว default ทิ้ง → products.supplier_id กลับเป็น null (ไม่ค้างชี้ผู้จัดซื้อที่ไม่ผูกแล้ว)

// → 204 No Content · products.supplier_id (PARA-500) = null

06

Developer Implementation Guide · คำสั่งจาก SA

RULE · i18n FLAT COLUMNS

ฟิลด์ 2 ภาษาเก็บเป็น name_th / name_en (ไม่ใช้ JSONB) · Response ยุบเป็น name: { th, en } ผ่าน LocalizationInterceptor · input (DTO) เป็น flat keys

RULE · BASE ENTITY

ทุกตารางสืบทอด BaseEntity — ได้ id · created_at/by · updated_at/by · is_deleted · deleted_at/by/reason · การลบเป็น soft-delete เสมอ

RULE · NESTED-SET TREE

item_groups และ warehouses เป็น tree (lft/rgt) — rebuild ใน transaction ตอน insert/move · เฉพาะ leaf (is_group=false) ผูกสินค้า/เก็บสต็อกได้

RULE · STOCK UOM IMMUTABLE

stock_uom_id ห้ามแก้ทันทีที่มี stock movement แรก (DB trigger หรือ app guard) กัน available_qty ในอดีตตีความหน่วยผิด

RULE · TEMPLATE NOT TRANSACTABLE

สินค้า has_variants=true ต้องถูกปฏิเสธเมื่อใช้ใน GR/PO/SO ตรง — อนุญาตเฉพาะ variant ที่ generate จาก attribute

RULE · CONVERSION ROUND CHECK

ถ้า stock UOM is_whole_number=true ต้องตรวจว่า qty × conversion_factor เป็นจำนวนเต็ม มิฉะนั้น reject

RULE · UNIQUE KEYS

uq_products_sku · uq_suppliers_code — บังคับ unique ระดับ DB · UOM seed ~200+ รายการเป็น master ตั้งต้น

RULE · UUID CROSS-BC + EVENTS

supplier_id (supplier-bc) และ context_ref (storage-bc) อ้างด้วย UUID ห้าม FK ข้าม DB · การแก้ master ยิง item.updated ให้ report-bc/sales/supplier อัปเดต cache

RULE · SUPPLIER_ID VALIDATION (ไม่มี FK)

ก่อนบันทึก item_prices.supplier_id / item_suppliers.supplier_id ต้องเรียก supplier-bc ผ่าน sendWithContext (no-throw) เพื่อยืนยันว่ามีจริง — null กลับมา → throw BadRequestException เอง เพราะไม่มี FK ที่จะให้ Postgres จับ 23503 ให้

RULE · CHECK CONSTRAINT ไม่ auto-map

chk_price_lists_buying_or_selling (23514) ไม่อยู่ในรายการที่ PostgresErrorMapper แปลงให้อัตโนมัติ (มีแค่ 23505/23503/23502/22P02/22001) — ถ้าปล่อยให้ DB เป็นด่านเดียวจะได้ 500 แทนที่จะเป็น 400 ต้องตรวจ business rule นี้ที่ DTO/service ก่อน insert เสมอ

Glossary · อภิธานศัพท์เทคนิค ERP

ขยายความศัพท์ที่ใช้ในเอกสารนี้ เพื่อให้ทีมธุรกิจและทีมพัฒนาเข้าใจตรงกัน

สินค้า & หน่วยนับ

ศัพท์ความหมาย
Master Dataข้อมูลหลักที่ตั้งค่าครั้งเดียวแล้วอ้างอิงซ้ำ (สินค้า · คลัง · ผู้จัดซื้อ) — ต่างจาก transaction data ที่เกิดจากงานประจำวัน
SKUStock Keeping Unit — รหัสเฉพาะของสินค้าแต่ละรายการ (unique)
UOMUnit of Measure — หน่วยนับ (ชิ้น · กล่อง · กก. · ลิตร)
Stock UOMหน่วยหลักที่ใช้บันทึกสต็อกจริง — ล็อกไม่ให้แก้เมื่อมี movement แล้ว
Conversion Factorอัตราแปลงหน่วยทางเลือก ↔ stock UOM (เช่น 1 กล่อง = 12 ชิ้น)
Attributeคุณลักษณะสินค้า (สี · ขนาด) ใช้ประกอบเป็น variant
Variantสินค้าตัวเลือกที่ระบบ generate จากต้นแบบ × attribute (เช่น เสื้อ แดง-M)
Templateสินค้าต้นแบบ (has_variants=true) ใช้จัดกลุ่ม variant — ห้ามทำธุรกรรมตรง
Bundle / Kitสินค้าชุดที่ประกอบจากสินค้าย่อยหลายรายการ
BOMBill of Materials — สูตร/รายการส่วนประกอบของสินค้าชุด
Price Listรายการราคาแม่ (เช่น "ราคาซื้อมาตรฐาน"/"ราคาขายมาตรฐาน") กำหนดสกุลเงิน + ทิศทาง Buying/Selling
Item Priceแถวราคาจริงต่อสินค้า ต่อ price list ต่อหน่วยนับ — ระบุผู้จัดซื้อ/ล็อต/ช่วงวันที่มีผลได้
Item Supplierผู้จัดซื้อที่สามารถส่งมอบสินค้านี้ได้ (หลายรายต่อสินค้า) พร้อมรหัสสินค้าตามผู้จัดซื้อ

สต็อก & คลัง

ศัพท์ความหมาย
Lot / Batchล็อตสินค้า — กลุ่มที่รับเข้าคราวเดียวกัน มี ต้นทุนนำเข้า + วันหมดอายุ เฉพาะของตัวเอง
FIFOFirst In First Out — ตัดสต็อกล็อตที่เข้าก่อนออกก่อน
FEFOFirst Expired First Out — ตัดล็อตที่หมดอายุก่อนออกก่อน
Goods Receipt (GRN)ใบรับสินค้าเข้าคลัง → สร้าง Lot ใหม่
Warehouseคลัง/สถานที่เก็บสต็อก (เป็นโครงต้นไม้)
Nested-set (lft/rgt)เทคนิคเก็บโครงต้นไม้ใน DB ให้ query ทั้งกิ่ง (subtree) ได้เร็ว
Leaf / Node (group)Leaf = ปลายกิ่ง ผูกสินค้า/เก็บสต็อกได้ · Node/Group = โหนดจัดกลุ่ม ห้ามผูกข้อมูล
Reorder Levelจุดสั่งซื้อ — ต่ำกว่านี้ระบบแจ้งเตือนให้สั่งเพิ่ม
Safety Stockสต็อกกันขาด (buffer) เผื่อความไม่แน่นอนของ demand/lead time

สถาปัตยกรรม & ระบบ

ศัพท์ความหมาย
Bounded Context (BC)ขอบเขตบริบทของแต่ละ microservice ใน DDD — เป็นเจ้าของฐานข้อมูลตัวเอง
DDDDomain-Driven Design — ออกแบบระบบตามโดเมนธุรกิจ
UUIDรหัสเฉพาะสากล 128-bit ใช้อ้างอิงข้าม BC (แทน FK ข้ามฐานข้อมูล)
Denormalizeเก็บสำเนาข้อมูลซ้ำเพื่อความเร็ว (เช่น report-bc เก็บชื่อสินค้าไว้เอง)
Soft-deleteลบแบบไม่ลบจริง (ตั้ง is_deleted=true) เก็บประวัติไว้
Audit fieldscreated_by/at · updated_by/at — ใครสร้าง/แก้ เมื่อไหร่
Presigned URLURL ชั่วคราวมีลายเซ็น ให้ upload/download ไฟล์ตรงกับ MinIO โดยไม่ผ่าน backend
Seed dataข้อมูลตั้งต้นที่ import ล่วงหน้า (เช่น UOM มาตรฐาน ~200 รายการ)
i18nInternationalization — รองรับหลายภาษา (ไทย/อังกฤษ) ด้วยคอลัมน์ _th/_en
AP (Accounts Payable)เจ้าหนี้การค้า — ยอดที่ต้องจ่ายผู้จัดซื้อ (ใช้ต่อใน finance-bc)
