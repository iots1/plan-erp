02

Core Use Cases & Data Entry · บันทึกข้อมูลยังไง

กระบวนการขาย · Quotation → SO → Delivery

1

สร้างใบเสนอราคา (Quotation) — เลือกลูกค้า, สินค้า, unit price, discount, ภาษี, วันหมดอายุใบเสนอราคา (valid_until) → สถานะ DRAFT/SENT

2

ลูกค้าอนุมัติ → Quotation เปลี่ยนสถานะเป็น APPROVED

3

แปลงเป็น Sales Order (SO) — คัดลอกรายการ + ตรวจ availability จาก inventory ผ่าน TCP (sync) → สถานะ CONFIRMED (ยังไม่ตัดสต็อก)

4

ออกใบส่งของ (Delivery Note) → emit delivery.confirmed → inventory ตัดสต็อก FIFO/FEFO และส่ง allocations กลับมาเก็บใน delivery item

กระบวนการจัดซื้อ · Purchase Order

1

สร้าง PO — เลือก supplier, สินค้า (product_id ref inventory), จำนวน, ต้นทุนที่ตกลง, วันส่งมอบ → DRAFT

2

อนุมัติ & ส่ง → APPROVED → SENT (emit po.approved)

3

รับสินค้า (เชื่อม UC-3.1) → emit po.received → inventory สร้างล็อต → PO เป็น PARTIAL/RECEIVED

Edge Cases · กรณีขอบเขต

สต็อกไม่พอตอน SO

ตอน confirm SO ตรวจแล้วสต็อกไม่พอ → เตือน และตาม policy: อนุญาต backorder หรือ block. ไม่ตัดสต็อกจนกว่าจะออกใบส่งของ

Quotation หมดอายุ

หาก valid_until ผ่านไปแล้ว ห้ามแปลงเป็น SO ต้องต่ออายุหรือออกใบใหม่

ราคาพิเศษ

รองรับราคาพิเศษ 1/2/3 ตามช่วงวันที่ (เริ่ม–ถึง) — ระบบเลือกราคาที่มีผลอัตโนมัติ

รับของไม่ครบ PO

รับได้บางส่วน → PO สถานะ PARTIAL รอรับส่วนที่เหลือ ไม่ปิด PO อัตโนมัติ

ยกเลิก PO หลังรับของแล้ว

ยกเลิกได้จาก DRAFT/APPROVED/SENT/PARTIAL เท่านั้น และ บล็อกทันทีถ้ามีรายการใดถูกรับเข้าไปแล้ว (received_qty > 0) — PO ที่ถูกรับไปบางส่วนต้องปิดผ่านการคืนสินค้า (Purchase Return, inventory-bc) ไม่ใช่ยกเลิก PO ตรงๆ · RECEIVED ยกเลิกไม่ได้เลย (ไม่มีอะไรเหลือให้ยกเลิก)

Developer Implementation Guide · คำสั่งจาก SA

RULE · NO CROSS-DB QUERY

sales-bc / supplier-bc ห้าม query ตาราง products ของ inventory ตรง ๆ ให้เรียกผ่าน TCP หรือใช้ replicated read model

RULE · SYNC CHECK, ASYNC DEDUCT

ตรวจ availability ตอน confirm SO เป็น TCP sync แต่การตัดสต็อกจริงเป็น event async — ยอมรับ eventual consistency

RULE · IDEMPOTENT DELIVERY

การยิง delivery.confirmed ต้อง idempotent (มี delivery id) ป้องกันการตัดสต็อกซ้ำเมื่อ event ถูกส่งซ้ำ

RULE · DENORMALIZE SNAPSHOT

เก็บ ชื่อสินค้า + ราคา ณ เวลาออกเอกสาร ในตาราง item เพราะ master data อาจเปลี่ยนภายหลัง

RULE · STATE MACHINE

สถานะเอกสารเป็น state machine ชัดเจน (DRAFT→…→CLOSED) ห้าม skip state และตรวจ transition ที่ถูกต้อง

RULE · SAGA + COMPENSATION

ใช้ Saga สำหรับ SO→delivery→stock→invoice หากตัดสต็อกล้มเหลว ต้อง compensate (delivery กลับเป็น PENDING)

RULE · MONEY TYPE

จำนวนเงินใช้ decimal หรือ integer (สตางค์) ห้ามใช้ float

RULE · PRICING RULE ENGINE — implement แล้ว (M5)

ราคาพิเศษ/ส่วนลดเป็น engine แยก (pricing_rules, inventory-bc) ไม่ใช่ field คงที่ — match ตามเงื่อนไข (สินค้า/กลุ่ม/ยี่ห้อ/ลูกค้า/ช่วงวันที่/จำนวนขั้นต่ำ) แล้วเลือกกฎที่ priority สูงสุด · ราคาที่ได้ snapshot ลงเอกสาร (QuotationItem.unit_price) เหมือนราคาที่พิมพ์เอง — รายละเอียดที่ §08 D6

RULE · TAX PER LINE — implement แล้ว (M7)

คำนวณภาษี รายบรรทัด (per-line) ตามประเภทภาษีของสินค้าแต่ละตัว แล้วค่อย aggregate ขึ้นหัวเอกสาร — รองรับหลายอัตรา/ยกเว้นภาษีในใบเดียว · quotation_items เก็บ vat_treatment/vat_rate/vat_base/vat_amount ไว้ทุกบรรทัด (item-wise tax detail ตรวจสอบย้อนหลังได้) · ส่วนลดท้ายบิลต้องถูกปันส่วนลงบรรทัดก่อนคิด VAT เสมอ ไม่งั้นฐานภาษีแต่ละถังจะสูงเกินจริงทั้งใบ — ดู §08 D7

RULE · BUNDLE EXPLOSION — implement แล้ว (แต่ไม่ใช้ packed_items)

เมื่อขายสินค้า bundle ระบบ explode เป็นสินค้าย่อยเพื่อตัดสต็อกรายตัว — แต่ทำที่ inventory-bc ตอนรันไทม์ ไม่ได้ denormalize เป็น packed_items ลงเอกสารฝั่งขายอย่างที่บรรทัดนี้เคยระบุไว้เดิม: traceability ที่ต้องการมีอยู่แล้วครบใน stock_movements (ทุก movement ของสินค้าย่อยผูก source_doc_id เดียวกันคือบรรทัดใบส่งของ) การคัดลอก BOM ลงเอกสารอีกชุดจึงเป็นข้อมูลซ้ำที่ไม่มีใครรับประกันความตรงกันได้ — เหตุผลเต็มที่ srs-p3.html §08 D8

RULE · SUB_TOTAL คือยอดก่อนหักส่วนลดเสมอ

sub_total = ผลรวม qty × ราคาต่อหน่วย ก่อนหักอะไรทั้งสิ้น ทำให้ total = sub_total − total_discount เป็นจริงในทุกโหมด และทั้งสองค่าไม่มีทางติดลบ (ส่วนลดเกินยอด → 400 ไม่ใช่ปล่อยให้ติดลบ)

RULE · แก้ items คือ SYNC ไม่ใช่ลบทิ้งแล้วเขียนใหม่

จับคู่บรรทัดเก่า/ใหม่ด้วย product_id (ใช้เป็นคีย์ได้เพราะห้ามสินค้าซ้ำในใบเดียวอยู่แล้ว) — ส่ง [001,002,004] ทับของเดิม [001,002,003] จะลบแค่ 003 เพิ่มแค่ 004 ส่วน 001/002 แก้ที่แถวเดิม เก็บ id, created_at/created_by และที่สำคัญที่สุดคือ received_qty ไว้ — ถ้า re-insert ค่านั้นจะถูกรีเซ็ตเป็น 0 ลบประวัติของที่รับเข้าคลังมาแล้ว · อ่านแถวเดิมในทรานแซกชัน ใต้ row lock ของหัวเอกสาร และเขียนบรรทัดทั้งหมดหลัง validate ผ่านครบ เพื่อให้ request ที่ถูกปฏิเสธไม่ทิ้งบรรทัดค้างครึ่งๆ

RULE · ราคาต้องอยู่ในกรอบของราคาอ้างอิง

ตอน POST/PUT ระบบถาม inventory-bc ว่ามีราคาอ้างอิงใน item_prices สำหรับสินค้านั้นใน scope นี้ไหม (PO ดูตาม supplier_id, ใบเสนอราคาดูตาม price_list_id) — เบี่ยงเบนเกิน ±20% → 400 พร้อมบอกช่วงที่รับได้ · ไม่มีราคาอ้างอิงในระบบ → ผ่าน ไม่บล็อก เพราะ unit_cost/unit_price เป็นราคาที่ ต่อรองกันจริง ไม่ใช่ราคาตายตัวจากแคตตาล็อก · กันเคสพิมพ์ผิด/ทุจริต โดยไม่ขวางการต่อรองปกติ

RULE · ตัวเลขเงินเป็น numeric(18,4)

ทุกคอลัมน์เงิน (sub_total, total_discount, total, line_total, unit_cost/unit_price, discount_value/discount) ใช้ numeric(18,4) ตรงกับความละเอียดของ roundMoney() — แก้ฝั่งใดฝั่งหนึ่งโดยไม่แก้อีกฝั่ง = ตัดทศนิยมทิ้งเงียบๆ

Implementation Decision Record · บันทึกการตัดสินใจตอน implement

หัวข้อนี้บันทึก จุดที่โค้ดจริงตัดสินใจต่างจาก/ละเอียดกว่าที่ SRS ระบุไว้ ตอน implement Sales Order (M3 — แปลงจากใบเสนอราคา), Delivery Note (M4 — ตัดสต็อกจริง), Pricing Rule Engine (M5), และ Taxes & charges รายบรรทัด (M7) — เขียนไว้เพื่อให้คนที่อ่านสเปกแล้วไปเปิดโค้ดไม่ต้องเดาว่าทำไมไม่เหมือนกัน และเพื่อให้ decision เหล่านี้ถูก challenge ได้ในภายหลัง แต่ละข้อระบุ ทางเลือกที่ไม่ได้เลือก และ ต้นทุนของการเลือกผิด ไว้ด้วยเสมอ

D1

Quotation ↔ SalesOrder ไม่ import กันเป็นวง

ตัดสินใจ: quotations.sales_order_id เป็นคอลัมน์ uuid | null ธรรมดา ไม่ประกาศ @ManyToOne ในขณะที่ SalesOrder.quotation_id เป็น relation จริง (@ManyToOne(() => Quotation)) — และ QuotationsService เปิดเมธอดแคบสองตัวให้ SalesOrdersService เรียก คือ lockForSalesOrderConversion() กับ markConvertedToSalesOrder() แทนที่จะให้ SalesOrderModule reach เข้าไปหา repository ของ Quotation ตรงๆ

ทำไม: การแปลงเอกสารต้องเขียนทั้งสองฝั่งในทรานแซกชันเดียว (สร้าง SO + ปักคอลัมน์ sales_order_id บน Quotation) ซึ่งเป็นการพึ่งพากันแบบสองทิศทางโดยธรรมชาติของ business flow — แต่ backend-convention.html ห้าม ModuleA ↔ ModuleB import กันเพราะ Nest DI graph resolve วงจรแบบนี้ไม่ได้ ถ้า Quotation entity ประกาศ @ManyToOne(() => SalesOrder) กลับไปด้วย quotation.entity.ts จะต้อง import sales-order.entity.ts ย้อนกลับ ทำให้ QuotationModule ต้อง import SalesOrderModule ทันที เกิดวงจริง — การตัด relation ฝั่งเดียว (Quotation ไม่รู้จัก SalesOrder ในระดับ TypeORM) พร้อมเปิดเมธอดแคบแทนการเปิด repository เต็มรูป ทำให้ dependency คงทิศทางเดียว: SalesOrderModule → QuotationModule เท่านั้น

ทำไมไม่ใช้ facade service แทน

backend-convention.html เสนอ facade service เป็นทางออกที่สองเมื่อ "สองฝั่งต้องการข้อมูล/ตรรกะของกันและกันจริงๆ ทั้งคู่"

แต่ในเคสนี้ การพึ่งพาทางเดียวจริงๆ — SO ต้องอ่าน/ล็อก Quotation เพื่อสร้างตัวเอง แต่ Quotation ไม่เคยต้องรู้จักตรรกะของ SO เลย จึงเลือกทางแรก (nested route/narrow service methods) ซึ่ง ง่ายกว่าและตรงกับรูปแบบการพึ่งพาจริง ไม่ต้องเปิด module ที่สามโดยไม่จำเป็น

route อยู่ใต้ /quotations ไม่ใช่ /sales-orders

POST /quotations/{id}/convert-to-sales-order ประกาศใน QuotationConversionController ที่อยู่ใน sales-order module (mirror ReorderLevelsController's @Controller('products') sub-route)

ถ้า route นี้ประกาศใน QuotationsController แทน QuotationModule จะต้อง inject SalesOrdersService เพื่อสร้างแถว SO จริง — วงจรเดิมกลับมาอีกที่ระดับ module แม้ entity จะไม่มี relation ก็ตาม

D2

สต็อกไม่พอตอนยืนยัน SO — บล็อกทั้งใบ ไม่ backorder บางส่วน

ตัดสินใจ: ถ้าบรรทัดใดบรรทัดหนึ่งของใบเสนอราคามี available_qty น้อยกว่าที่ขอ assertAvailable() โยน 409 ConflictException ทั้งใบทันที — ไม่มีการยืนยันบางส่วนแล้วปล่อยส่วนที่เหลือเป็น backorder

ทางเลือกผลที่ตามมา
Backorder บางส่วน (ไม่ได้เลือก)ต้องมีฟิลด์ระดับบรรทัดบอกว่า "ยืนยันไปเท่าไหร่ ค้างเท่าไหร่" เพิ่มสถานะย่อยที่ SO ยังไม่มี (ไม่ใช่ PARTIALที่มีอยู่แล้ว ซึ่งหมายถึง "ส่งมอบบางส่วน" คนละความหมายกับ "ยืนยันบางส่วน") และต้องมี flow แจ้งเตือนเมื่อของกลับมามีพอ — เป็น feature ใหม่ทั้งชุดที่ SRS (srs-p4.html) เขียนไว้แค่ว่า "อนุญาต backorder หรือ block" โดยไม่ได้ฟันธง
บล็อกทั้งใบ (เลือก)เป็นค่า default ที่ conservative ที่สุดเมื่อไม่มี stock_settings-style toggle ให้เลือกพฤติกรรม (ยังไม่มีในเฟสนี้) — ตรงกับหลักที่ postIssue() ใช้อยู่แล้วสำหรับ allow_negative_stock คือ "ไม่พอ = ปฏิเสธทั้งก้อน ไม่มี partial write" การเปิด backorder ทีหลังทำได้โดยเพิ่ม toggle ใหม่ ไม่ต้องรื้อ guard นี้ทิ้ง
503 ≠ 409 — คนละความหมาย คนละ response

assertAvailable() แยกกรณี inventory-bc ไม่ตอบ (proxy คืน null → 503 ServiceUnavailableException) ออกจาก ตอบแล้วแต่สต็อกไม่พอ (409 ConflictException พร้อมรายการ product ที่ขาด) — การอ่าน null เป็น "ไม่มีของเลย" แล้วโยน 409 จะหลอกผู้ใช้ให้เข้าใจผิดว่าสต็อกหมดจริง ทั้งที่ระบบแค่คุยกับ inventory-bc ไม่ได้ชั่วคราว — รูปแบบเดียวกับที่ QuotationsService.create() แยก 400 (product ไม่มีจริง) ออกจาก 503 (inventory-bc ล่ม) อยู่แล้ว

D3

เช็คสต็อกตอนยืนยัน SO — รวมทุกคลัง ไม่ผูกกับคลังใดคลังหนึ่ง

ตัดสินใจ: StockResources.CheckAvailability (RPC ใหม่ที่ inventory-bc) คำนวณ SUM(lots.available_qty) ต่อ product_id ข้ามทุกคลังที่มีล็อตนั้น (ตัดล็อตที่หมดอายุแล้วออกก่อนรวม) — ไม่รับ warehouse_id เป็นพารามิเตอร์เลย

ทำไม: ตอนยืนยัน SO ระบบยังไม่รู้ว่าจะส่งมอบจากคลังไหน — การเลือกคลังที่จะตัดสต็อกจริงเป็นการตัดสินใจของ Delivery Note (เฟสถัดไป ยังไม่ implement) ไม่ใช่ของ SO การผูกเช็คสต็อกกับคลังใดคลังหนึ่งตั้งแต่ตอนนี้จะบล็อกออเดอร์ที่มีของพอในภาพรวมแต่กระจายอยู่คนละคลัง ทั้งที่ธุรกิจย้ายสต็อกข้ามคลัง (Stock Entry MATERIAL_TRANSFER) ได้อยู่แล้วก่อนวันส่งจริง

ผลที่ตามมาที่ Delivery Note (M4) ต้องรับมือ — และรับมือแล้ว

"SO ยืนยันได้" ไม่ได้แปลว่า คลังใดคลังหนึ่งมีของพอ — Delivery Note มี guard ของตัวเองตอนเลือกคลังจริง (เรียก postIssue() ที่มี all-or-nothing check อยู่แล้วในระดับล็อต) และรับมือกรณีที่ของกระจายหลายคลังจนต้องแบ่งส่งมอบเป็นหลายรอบได้แล้ว ซึ่งเป็นเหตุผลที่ SalesOrderStatus.PARTIAL มีอยู่แล้วในสถานะชุดนี้ตั้งแต่ต้น

D4

Delivery Note ตัดสต็อกจริง — ลำดับเรียก RPC สลับทางกับ Goods Receipt โดยตั้งใจ

ตัดสินใจ: DeliveryNotesService.submit() เรียก StockResources.ConfirmDelivery (RPC sync ไป inventory-bc) ก่อน เปิดทรานแซกชันของ sales-bc เอง — ตัดสต็อกสำเร็จที่ inventory-bc แล้วค่อยเขียน status=SUBMITTED/delivered_qty ในเครื่อง ตรงข้ามกับ GoodsReceiptsService.submit() ที่ commit ธุรกรรมของตัวเอง (สร้างล็อต) ก่อน แล้วค่อยเรียก applyGoodsReceipt ไปแจ้ง supplier-bc ทีหลัง

ทำไม: คำถามที่ต้องตอบก่อนเสมอคือ "เหตุการณ์ทางกายภาพ (ของจริงเคลื่อนย้าย) เกิดขึ้นฝั่งไหน" — สำหรับ GRN เหตุการณ์นั้นเกิดที่ inventory-bc เอง (สร้างล็อต) จึงเป็น ground truth ที่พร้อมอยู่แล้วในเครื่องตัวเอง commit ก่อนได้เลย ส่วนตัวเลข received_qty ที่ supplier-bc เป็นเพียงสำเนาสะท้อนกลับ (denormalized) แต่สำหรับ Delivery Note เหตุการณ์ทางกายภาพ (ตัดสต็อกออกจากคลัง) เกิดที่ อีกฝั่งหนึ่งของ BC boundary (inventory-bc) — sales-bc เองไม่มีอะไรที่เป็นความจริงทางกายภาพให้ commit ก่อนเลย ถ้า commit status=SUBMITTED ก่อนแล้วค่อยเรียกตัดสต็อกทีหลัง และการตัดสต็อกล้มเหลว (สต็อกหมดจากการแย่งกันของอีกใบส่งของที่ตัดไปพร้อมกัน) จะเกิดเอกสารที่อ้างว่าส่งของไปแล้วทั้งที่ของยังไม่ออกจากคลังจริง — เลวร้ายกว่าเคสของ GRN มาก

ไม่ต้องมี _synced_at หรือ endpoint ซ่อมแยก

GRN ต้องมี po_synced_at + POST .../sync-purchase-order เพราะฝั่งที่ commit ก่อน (inventory-bc) ไม่มีทางย้อน "ของที่รับเข้ามาแล้ว" ทิ้งได้ — ต้องมีกลไกซ่อมแยกให้ supplier-bc ตามทัน ส่วน Delivery Note ไม่ต้องมี เพราะ ConfirmDelivery/ReverseDelivery เป็น idempotent ต่อบรรทัดอยู่แล้ว (DeliveryIssue.source_doc_id UNIQUE) — ถ้า sales-bc commit ฝั่งตัวเองไม่สำเร็จหลัง inventory-bc ตัดสต็อกไปแล้ว แค่เรียก submit() ซ้ำก็คือการซ่อมในตัว (inventory-bc no-op แล้วปล่อยให้ sales-bc เขียนส่วนที่ค้างต่อ)

cancel() เรียก ReverseDelivery แบบไม่มีเงื่อนไขเสมอ

ไม่เช็คสถานะก่อนว่าจะเรียกหรือไม่ — เรียกทุกครั้งแม้ยังเป็น DRAFT (ไม่เคยตัดสต็อก) เพราะ reverseDelivery() เป็น no-op อยู่แล้วถ้าไม่พบ delivery_issues แถวนั้น การจะ "เช็คสถานะก่อนแล้วค่อยตัดสินใจเรียก" ต้องอ่านสถานะแบบ fresh+locked ซึ่งขัดกับกฎห้ามเปิดทรานแซกชันคาบเกี่ยว RPC — เลี่ยงทั้งปัญหาด้วยการเรียกเสมอแล้วให้ idempotency จัดการเอง

D5

Idempotency ledger ของ Delivery — ไม่มีตาราง allocations แยก

ตัดสินใจ: delivery_issues (ตารางใหม่ที่ inventory-bc) เก็บแค่ 1 แถวต่อ 1 บรรทัดใบส่งของ (คีย์ idempotency คือ source_doc_id UNIQUE) — ไม่มีตารางลูกเก็บว่าตัดจากล็อตไหนบ้าง ต่างจาก Stock Entry ที่มี StockEntryItemAllocation แยกต่างหากสำหรับ MATERIAL_ISSUE

ทำไม: ทุกครั้งที่ postIssue() ถูกเรียกจาก confirmDelivery() จะส่ง source_doc_type='DELIVERY'/source_doc_id เดียวกันติดไปกับทุก movement ที่มันเขียน — ข้อมูล "ตัดจากล็อตไหนเท่าไหร่" จึงมีอยู่แล้วครบใน stock_movements เอง reverseDelivery() แค่ query กลับด้วย source_doc_id เดียวกันก็ได้ชุดล็อต+จำนวนที่ต้องคืนแม่นยำเท่ากับมีตารางแยก — สร้างตารางที่สองจะเป็นการเก็บข้อมูลซ้ำที่ sync กันเองได้ (ถ้าวันหนึ่งไม่ตรงกันจะไม่รู้ว่าอันไหนถูก)

D6

Pricing Rule Engine — อยู่ที่ inventory-bc, unit_price เป็น optional ไม่ใช่บังคับใช้ระบบ

ตัดสินใจ: ตาราง pricing_rules อยู่ที่ inventory-bc ไม่ใช่ sales-bc แม้จะมีฟิลด์ customer_id (concept ฝั่งขาย) อยู่ในนั้น — และ unit_price บน CreateQuotationItemNestedDTO เปลี่ยนจาก required เป็น optional (ไม่ใช่ลบสิทธิ์กรอกเองแล้วบังคับให้ระบบคำนวณเสมอ): ไม่ระบุ = เรียก PricingRuleResources.ResolvePrice ให้เสนอราคาแทน · ระบุมา = ใช้ค่านั้นตรงๆ เหมือนเดิมทุกประการ

ทำไมอยู่ inventory-bc: การ match แบบ apply_on=ITEM_GROUP/BRAND ต้องไล่ nested-set (lft/rgt) ของ item_groups และเช็ค products.brand_id — ข้อมูล catalog ทั้งหมดนี้เป็นของ inventory-bc เอง ถ้าย้าย pricing_rules ไปไว้ sales-bc ทุกครั้งที่ resolve ราคาจะต้องยิง RPC ไปถามโครงสร้างสินค้าซ้ำอยู่ดี สู้เก็บกฎไว้ข้าง catalog แล้วให้ sales-bc ยิง RPC เดียวขอ "ราคาที่ควรใช้" ตรงๆ ดีกว่า — customer_id เป็นเพียง uuid ข้าม BC ธรรมดา (nullable, ไม่ validate ว่ามีจริง) เหมือนฟิลด์ cross-BC อื่นๆ ในระบบ

ทำไม optional ไม่ใช่บังคับ: การบังคับให้ระบบคำนวณราคาเสมอจะขัดกับหลักที่มีอยู่แล้วทั้งระบบว่า unit_price/unit_cost เป็น "ราคาที่ต่อรองกันจริง" (ดู §07 RULE · ราคาต้องอยู่ในกรอบของราคาอ้างอิง) — พนักงานขายยังต้องพิมพ์ราคาที่ต่อรองนอกระบบได้เสมอ engine นี้จึงเป็นแค่ ตัวช่วยเสนอราคาเริ่มต้น ไม่ใช่ผู้มีอำนาจตัดสินราคาเพียงผู้เดียว

กรอบ ±20% ใช้เฉพาะราคาที่ client พิมพ์เอง

เมื่อ unit_price มาจาก pricing rule engine (ไม่ว่าจะ match กฎจริงหรือ fallback เป็นราคาจาก item_prices) การตรวจ ±20% ใน §07 จะถูกข้าม — กรอบนี้มีไว้จับราคาที่คนพิมพ์ผิด/ทุจริต ไม่ใช่จับผลลัพธ์ของระบบตัวเอง กฎแบบ RATE ที่ตั้งใจให้ราคาต่างจากปกติมาก (เช่น ราคาพิเศษเทศกาล) จะต้องไม่ถูกปฏิเสธโดยกรอบที่ออกแบบมาเพื่อจับคนละปัญหา

D7

Taxes & charges รายบรรทัด — เปลี่ยนชื่อ total เดิมเป็น net_amount เพื่อให้ทั้งสายใช้คำเดียวกัน

ตัดสินใจ: คอลัมน์ total เดิมของ Quotation/SalesOrder (ที่หมายถึง "ยอดก่อนภาษี") เปลี่ยนชื่อเป็น net_amount และ total ตัวใหม่หมายถึง net_amount + vat_amount — ตรงกับความหมายบน Receipt ทุกตัวอักษร

ทำไมยอมเปลี่ยนชื่อคอลัมน์ที่มีอยู่แล้ว: ตัวเลขของใบเสนอราคาไหลต่อไปเป็นใบสั่งขาย แล้วไปจบที่ใบกำกับภาษี — ถ้ากลางทางคำว่า total เปลี่ยนความหมาย (ก่อนภาษีที่ Quotation/SO แต่รวมภาษีที่ Receipt) วันหนึ่งจะมีคนเขียน so.total → receipt.net_amount แล้วมันจะถูกต้องทางไวยากรณ์แต่ผิดทางความหมาย โดยไม่มี compiler ตัวไหนเตือน · ทางเลือกที่ไม่ได้เลือกคือเพิ่ม grand_total ไว้ข้างๆ ซึ่งเลี่ยง migration ได้จริง แต่แลกกับการฝังความกำกวมนั้นไว้ถาวร — ตอนนี้ยังไม่มีข้อมูลจริงในระบบ ต้นทุนการเปลี่ยนชื่อจึงต่ำที่สุดเท่าที่จะเป็นไปได้ (migration มี backfill net_amount = total ให้แถวเดิม เพราะค่าเดิมคือยอดก่อนภาษีพอดี)

ที่มาของภาษี 2 ฝั่ง ไม่รวมกัน: ประเภทภาษีของสินค้ามาจาก inventory-bc (tax_categories.vat_treatment, ติดมากับ RPC GetProductById ที่เรียกอยู่แล้ว ไม่ต้องยิงเพิ่ม) ส่วนอัตรามาจาก finance-bc (tax_configs ผ่าน RPC ใหม่ ResolveEffectiveRate) — ตาม srs-p5.html §2 ที่แยกสองคำถามนี้ออกจากกันโดยตั้งใจ: ถ้าอ่านอัตราจากแคตตาล็อกสินค้าจะข้ามอัตราที่ฝ่ายบัญชีเป็นเจ้าของและมีเวอร์ชันตามวันที่ ทั้งคู่ถูก snapshot ลงเอกสาร ไม่ join ตอนพิมพ์ การขึ้น VAT ตามกฎหมายจึงไม่ย้อนแก้ใบที่ส่งลูกค้าไปแล้ว

ส่วนลดท้ายบิลต้องปันลงบรรทัดก่อนคิด VAT

ถังภาษี 3 ถัง (standard/zero/exempt) เป็นตัวเลขรายบรรทัด — ถ้าปล่อยส่วนลดท้ายบิลไว้ที่หัวเอกสาร ทุกถังจะสูงเกินจริงเท่ากับส่วนลดทั้งก้อน และ VAT ที่คำนวณได้จะผิดตามไปด้วย · allocateProRata() ปันตามสัดส่วนยอดของแต่ละบรรทัด แล้วโยนเศษปัดให้บรรทัดที่ใหญ่ที่สุด เพื่อให้ Σ vat_base กลับมาเท่ากับ net_amount พอดีเสมอ ไม่เหลือเศษสตางค์ลอย

หา rate ไม่ได้ = 0% ไม่ใช่ error

ถ้า finance-bc ล่มหรือไม่มีอัตราครอบคลุมวันที่นั้น ระบบใช้ 0% แล้วออกใบเสนอราคาต่อ ไม่ปฏิเสธคำขอ — ใบเสนอราคาเป็นเพียงคำเสนอ ไม่ใช่เอกสารภาษี การบล็อกไม่ให้ขายเพราะ service อัตราภาษีสะดุดชั่วคราวจึงเสียมากกว่าได้ · และ 0% ก็เป็นคำตอบที่ถูกต้องอยู่แล้วสำหรับกิจการที่ไม่ได้จด VAT · อัตราที่ใช้ถูก snapshot ลงแถวเสมอ สิ่งที่เสนอลูกค้าไปจึงสร้างใหม่ได้ตรงเป๊ะเสมอ
