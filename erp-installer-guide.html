ERP Installer Guide · On-Premise ไม่ใช้ Docker

จาก git push
ถึงเครื่องลูกค้าในปุ่มเดียว

erp-installer รวม erp-api + erp-frontend เป็นไฟล์ release เดียว แล้วติดตั้ง / อัปเดต / ย้อนกลับบนเครื่องลูกค้า Windows · macOS · Ubuntu ด้วย PM2 + Caddy พร้อมหน้าควบคุม (ERP Console) สำหรับคนดูแลหน้างานที่ไม่ใช่ developer

macOS: ทดสอบจริงครบวงจร Release CI: build + publish อัตโนมัติ Windows / Ubuntu: ยังไม่ได้ทดสอบบนเครื่องจริง
อ่านย่อหน้านี้ก่อนถ้ามีเวลา 30 วินาที

เครื่องลูกค้าไม่รันจาก git repo — รันจากไฟล์ release (erp-<version>.tar.gz) ที่แตกไว้ใน <home>/releases/<version> · ทีม dev แค่ push main ของ erp-api / erp-frontend → CI ของ erp-installer build release ให้เอง · คนดูแลหน้างานกด Sync → ติดตั้ง ใน ERP Console — การติดตั้งรัน migration กับ DB ของลูกค้า และไม่ย้อน migration เมื่อ rollback

01 — หน้าที่

erp-installer มีหน้าที่อะไร

โจทย์คือติดตั้ง ERP บนเครื่องของลูกค้าเอง (ส่วนใหญ่ Windows) ใน local domain ของออฟฟิศ โดยไม่ใช้ Docker — ซึ่งต่างจาก Deployment Guide (Kong + Docker Compose บน server ของเรา) repo นี้จึงแยกออกมาเป็นของตัวเอง และไม่แก้โค้ดของ erp-api / erp-frontend

ทำไม่ทำ
build erp-api + erp-frontend จาก commit เป็นไฟล์ release เดียว พร้อม smoke testติดตั้ง Node / PostgreSQL / Redis / RabbitMQ / MinIO / Gotenberg — ลงเอง installer แค่ตรวจ
ติดตั้ง · อัปเกรด · ย้อนกลับ แบบ idempotent (รันซ้ำได้)ใช้ Docker / Kong / Cloudflare Tunnel
สร้าง DB ที่ยังไม่มี, รัน migration, sync สิทธิ์ย้อน migration (rollback สลับแค่โค้ด)
รันทุก process ด้วย PM2 และ HTTPS ด้วย Caddy (tls internal)ออก certificate สาธารณะ — ใช้ CA ภายในที่ทุกเครื่องในออฟฟิศต้องเชื่อ
หน้าควบคุม ERP Console (เว็บ + desktop app) สำหรับคนดูแลหน้างานแทนที่ CI / Deploy ของ erp-api / erp-frontend (ยังทำงานเหมือนเดิม)

03 — Workflow ภาพรวม

ทีม dev → GitHub → เครื่องลูกค้า

ทุกอย่างวิ่งผ่าน GitHub Release ของ repo erp-installer — เป็นจุดเดียวที่เครื่องลูกค้าดึงของไป ทีม dev ไม่ต้องเข้าเครื่องลูกค้า และคนหน้างานไม่ต้อง build อะไรเอง 

sequenceDiagram
  autonumber
  actor Dev as ทีม dev
  participant Src as erp-api / erp-frontend

  participant GH as GitHub Releases

  participant Con as ERP Console (เครื่องลูกค้า)

    Rel-->>Rel: ข้าม (~10 วินาที)
  else มีของใหม่
    Rel->>Rel: build-release (build · migration · smoke test ~5 นาที)
    Rel->>GH: publish erp-‹version›.tar.gz + .sha256 + VERSION.json
    Rel->>GH: ลบ release เก่า เหลือ 10 ตัว
  end
  Ops->>Con: กด Sync
  Con->>GH: อ่านรายการ release (UPDATE_GITHUB_TOKEN)
  Ops->>Con: กด ติดตั้ง

  Con->>Con: แตกไฟล์ → pnpm install --prod → migration → sync สิทธิ์ → สลับ current → restart → health check
ขั้นอัตโนมัติ?หมายเหตุ
push main → build releaseอัตโนมัติpush ติดกันหลายครั้ง = build เดียวหลังตัวที่กำลังรัน · push ทั้งสอง repo พร้อมกัน = build ครั้งเดียว
build จาก branch / tag อื่นกดเองGitHub → erp-installer → Actions → Release → Run workflow (เลือก ref ได้, build เสมอ)
ติดตั้งที่เครื่องลูกค้ากดเอง เสมอตั้งใจไม่ให้อัปเดตเอง — การติดตั้งรัน migration กับ DB จริงของลูกค้า ต้องมีคนเลือกเวลา
secret ที่ต้องตั้งครั้งเดียว (ชื่อเท่านั้น — ค่าอยู่ใน GitHub)

erp-installer: ERP_SOURCE_TOKEN — อ่าน erp-api + erp-frontend (Contents: read) · erp-api และ erp-frontend: ERP_INSTALLER_DISPATCH_TOKEN — เฉพาะ repo erp-installer (Contents: read & write) · เครื่องลูกค้า: UPDATE_GITHUB_TOKEN ใน config/erp.env — อ่าน release ของ erp-installer อย่างเดียว · Settings → Secrets and variables → Actions ของแต่ละ repo (org secret ใช้กับ private repo บน plan ปัจจุบันไม่ได้)

04 — ไฟล์ release

erp-<version>.tar.gz

ชื่อ = erp-<YYYY.MM.DD-HHMM>-<api sha>-<web sha> — วันเวลาไทยตอน build + commit ของ erp-api และ erp-frontend อ่านชื่อแล้วรู้ทันทีว่าโค้ดชุดไหน · ขนาดราว 15 MB เพราะไม่มี node_modules (เครื่องลูกค้าต้องต่ออินเทอร์เน็ตตอนติดตั้ง) · build บน OS ไหนก็ติดตั้งได้ทุก OS 

erp-<version>/
  VERSION.json   # version, built_at, node, commit ของทั้ง 3 repo, internal_api_port
  installer/     # bin/ lib/ templates/ docs/ + console-ui/dist — release ติดตั้งตัวเอง
  api/           # erp-api: dist/ (migration + data source compile แล้ว), permissions snapshot, lockfile
  web/           # erp-frontend: apps/web/.next, public, lockfile
ทำไมต้อง compile migration และ permission snapshot

release ไม่มี TypeScript source — migration / permissions:sync / seed ถูก compile ด้วย esbuild · permission scan ของ erp-api อ่าน apps/*/src/**/*.ts เป็นข้อความ ถ้าไม่มี source จะ scan ได้ 0 แล้ว soft-delete สิทธิ์ API ทั้งหมด → build-release สร้าง permissions.snapshot.ts และตรวจว่าผล scan เท่ากับ source ก่อนแพ็ก

build เองบนเครื่อง dev (เมื่อใช้ CI ไม่ได้)

# Node major เดียวกับเครื่องลูกค้า, git, pnpm (corepack enable) · commit งานก่อน — build จาก commit เท่านั้น
cd erp-installer && pnpm install
node scripts/build-release.mjs --api ../erp-api --web ../erp-frontend
# → release/erp-<version>.tar.gz + .sha256   (~5 นาที)
# ตัวเลือก: --api-ref / --web-ref (branch·tag·commit), --out DIR, --skip-smoke, --help

ขั้นตอนเดียวกันอยู่ในปุ่ม “วิธีสร้างไฟล์ .tar.gz” ในหน้า Release ของ ERP Console

05 — ติดตั้งครั้งแรก

ที่หน้างาน (ตัวอย่าง Windows)

1

ลงโปรแกรมพื้นฐานเอง

Node.js (major ตาม VERSION.json) · npm i -g pm2 · Caddy · PostgreSQL · Redis (Windows: Memurai) · RabbitMQ (บังคับ) · MinIO · Gotenberg (Windows: WSL2 หรือเครื่องอื่น) · ปิด Sleep · พอร์ต 80/443 ว่าง

2

ติดตั้ง แล้วกรอก config

tar -xzf erp-<version>.tar.gz
node erp-<version>\installer\bin\erp.mjs install --home C:\erp
# ครั้งแรกหยุดให้กรอก C:\erp\config\erp.env (ชื่อเว็บ, Caddy, token Sync) และ api.env (DB, Redis, RabbitMQ, MinIO)
C:\erp\erp.cmd install C:\erp\releases\<version>   # → "ERP <version> is running"
3

ปิดงานด้วยคำสั่งเดียว — PowerShell แบบ Administrator

C:\erp\erp.cmd finish     # --dry-run ดูก่อนได้ · รันซ้ำได้ ข้อที่ผ่านแล้วข้าม

ถามรหัสใหม่ของ superadmin ครั้งเดียว (migration ของ erp-api สร้างบัญชีนี้ด้วยรหัสที่อยู่ใน source) แล้วทำต่อเอง: ปิด login บัญชี mock staff · autostart ตอนบูต · firewall · ให้เครื่องนี้เชื่อ HTTPS + hosts · สร้างสคริปต์สำหรับเครื่อง client · erp status — จบด้วยตารางสรุป ✓ / ⚠ / ✗

4

เครื่อง client ทุกเครื่อง — ไฟล์เดียว

copy erp-client-setup.ps1 (จาก C:\erp\ หรือปุ่มดาวน์โหลดในการ์ด Web access ของ Console) → คลิกขวา Run with PowerShell — ติดตั้ง CA ของ Caddy เป็น Trusted Root, ใส่บรรทัด hosts ชี้ IP ของ server, แล้วทดสอบ HTTPS ให้เอง

ทำไมทุกเครื่องต้องเชื่อ CA

Caddy ออก certificate ให้ erp.internal จาก CA ภายในของเครื่อง server เอง (ไม่มี public CA ไหนออกให้ชื่อ .internal ได้) — เครื่องที่ยังไม่เชื่อ CA จะเห็นคำเตือน และ cookie ของ login (COOKIE_SECURE=true) ต้องใช้ HTTPS · CA นี้รับรองเว็บไหนก็ได้ ติดตั้งเฉพาะเครื่องที่ใช้ ERP

5

ตรวจรับใน ERP Console

ภาพรวม: ทุกการ์ดเขียว · Web access = เข้าเว็บได้ · Migration: ไม่มี “ยังไม่รัน” / “DB ใหม่กว่าโค้ด” · Release: Sync ต่อ GitHub ได้ · login จากเครื่อง client 1 เครื่อง — checklist เต็มอยู่ใน erp-installer/docs/windows.md

08 — ERP Console

หน้าควบคุมสำหรับคนดูแลหน้างาน

หน้าทำอะไรได้
ภาพรวมสถานะทุก service + DB / Redis / RabbitMQ / MinIO · โปรแกรมที่ต้องใช้ (node, pnpm, pm2, caddy) · Start / Stop / Restart · การ์ด Web access ทดสอบจากเบราว์เซอร์ที่เปิดอยู่ว่าขาดชื่อ / CA / พอร์ต + ปุ่มดาวน์โหลดสคริปต์ client
ตั้งค่าแก้ erp.env / api.env (ตรวจค่า, ซ่อน secret, backup อัตโนมัติ) แล้ว apply
ReleaseSync จาก GitHub · ติดตั้ง · อัปโหลดไฟล์เอง · ย้อนกลับ · คู่มือสร้าง .tar.gz
Migrationต่อ DB: ไฟล์ใน release เทียบตาราง migrations → รันแล้ว / ยังไม่รัน / DB ใหม่กว่าโค้ด · ปุ่มรัน migrate
งานlog สดของ install / update / rollback / migrate — ไม่หายแม้ console restart ระหว่างงาน

เปิดได้เฉพาะบนเครื่อง server โดยค่าเริ่มต้น (127.0.0.1:3399) · ดูได้ทุกคน แต่สั่งงานต้องปลดล็อกด้วย admin token (erp console-token) · เปิดจากเครื่องอื่นในออฟฟิศต้องตั้ง CONSOLE_PASSWORD

10 — กับดัก

ที่เจอมาแล้ว — อย่าเจอซ้ำ

อาการต้นเหตุ → ที่ทำไว้
คอลัมน์ / PK default หายจาก DBrelease เก่าชี้ DB ที่ใหม่กว่า + *_DB_SYNCHRONIZE=true → TypeORM synchronize ลบของใหม่ → installer บังคับ synchronize=false ทุกทาง · ก่อนชี้ไป DB ไหน ดูหน้า Migration ก่อน
Migration ขึ้น “DB ใหม่กว่าโค้ด”release ที่ติดตั้งเก่ากว่า DB → ติดตั้ง release ใหม่ ไม่ใช่กดรัน migrate
ทุก service crash-loopNODE_ENV=production — erp-api รับแค่ local|test|dev|staging|prod → installer ตั้ง prod ให้
login ตอบ 500TRANSPORT=tcp ใช้ไม่ได้ (RMQ interceptor) → RabbitMQ บังคับ, erp status ขึ้น ✗
