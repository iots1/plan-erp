erp-installer รวม erp-api + erp-frontend เป็นไฟล์ release เดียว แล้วติดตั้ง / อัปเดต / ย้อนกลับบนเครื่องลูกค้า Windows · macOS · Ubuntu ด้วย PM2 + Caddy พร้อมหน้าควบคุม (ERP Console) สำหรับคนดูแลหน้างานที่ไม่ใช่ developer · Redis / RabbitMQ / RustFS / Gotenberg ลงด้วยสคริปต์เดียวเป็น Docker stack

Windows 11: ติดตั้ง · migrate · อัปเดตจาก Console ผ่านบนเครื่องลูกค้าจริง macOS: ทดสอบจริงครบวงจร Release CI: build + publish อัตโนมัติ ยังไม่ทดสอบ: Ubuntu · Windows autostart ตอนบูต · สคริปต์ client
อ่านย่อหน้านี้ก่อนถ้ามีเวลา 30 วินาที

เครื่องลูกค้าไม่รันจาก git repo — รันจากไฟล์ release (erp-<version>.tar.gz) ที่แตกไว้ใน <home>/releases/<version> · ทีม dev แค่ push main ของ erp-api / erp-frontend → CI ของ erp-installer build release ให้เอง · คนดูแลหน้างานกด Sync → ติดตั้ง ใน ERP Console — การติดตั้งรัน migration กับ DB ของลูกค้า และไม่ย้อน migration เมื่อ rollback · บน Windows สั่ง erp จาก PowerShell เท่านั้น (ไม่ใช่ Git Bash — §10)

01 — หน้าที่

erp-installer มีหน้าที่อะไร

โจทย์คือติดตั้ง ERP บนเครื่องของลูกค้าเอง (ส่วนใหญ่ Windows) ใน local domain ของออฟฟิศ — ตัว ERP (8 BC + web + Caddy + console) รันด้วย PM2 ไม่ใช้ Docker ส่วน infra ที่ไม่มี build สำหรับ Windows ที่ดูแลง่าย (Redis, RabbitMQ, RustFS, Gotenberg) รันเป็น Docker compose stack ใน WSL2 ที่สคริปต์ลงให้ — ต่างจาก Deployment Guide (Kong + Docker Compose บน server ของเรา) repo นี้จึงแยกออกมาเป็นของตัวเอง และไม่แก้โค้ดของ erp-api / erp-frontend

ทำไม่ทำ
build erp-api + erp-frontend จาก commit เป็นไฟล์ release เดียว พร้อม smoke testติดตั้ง Node / PostgreSQL / Caddy — ลงเอง installer แค่ตรวจ (PM2 กดติดตั้งจาก Console ได้)
ลง Redis / RabbitMQ / RustFS (S3) / Gotenberg ด้วย install-infra.ps1 (Docker ใน WSL2) แล้วเขียนค่าเชื่อมต่อลง api.envรัน ERP เองใน Docker / Kong / Cloudflare Tunnel
ติดตั้ง · อัปเกรด · ย้อนกลับ แบบ idempotent (รันซ้ำได้) · ทีละคำสั่งต่อเครื่อง (ล็อก)อัปเดตเอง — ทุกการติดตั้งมีคนกด
สร้าง DB ที่ยังไม่มี, รัน migration, sync สิทธิ์ · ตรวจ DB ก่อน start ทุกครั้งย้อน migration (rollback สลับแค่โค้ด)
รันทุก process ด้วย PM2 และ HTTPS ด้วย Caddy (tls internal)ออก certificate สาธารณะ — ใช้ CA ภายในที่ทุกเครื่องในออฟฟิศต้องเชื่อ
ปิดสิทธิ์ไฟล์ของ install ให้เหลือเจ้าของเครื่อง (§11)เข้ารหัส secret ด้วย key บนดิสก์เดียวกัน (ไม่ช่วยจริง)
หน้าควบคุม ERP Console (เว็บ + desktop app) สำหรับคนดูแลหน้างานแทนที่ CI / Deploy ของ erp-api / erp-frontend (ยังทำงานเหมือนเดิม)

03 — Workflow ภาพรวม

ทีม dev → GitHub → เครื่องลูกค้า

ทุกอย่างวิ่งผ่าน GitHub Release ของ repo erp-installer — เป็นจุดเดียวที่เครื่องลูกค้าดึงของไป ทีม dev ไม่ต้องเข้าเครื่องลูกค้า และคนหน้างานไม่ต้อง build อะไรเอง

ติดตั้งที่เครื่องลูกค้ากดเอง เสมอตั้งใจไม่ให้อัปเดตเอง — การติดตั้งรัน migration กับ DB จริงของลูกค้า ต้องมีคนเลือกเวลา
secret ที่ต้องตั้งครั้งเดียว (ชื่อเท่านั้น — ค่าอยู่ใน GitHub)

04 — ไฟล์ release

erp-<version>.tar.gz

ชื่อ = erp-<YYYY.MM.DD-HHMM>-<api sha>-<web sha> — วันเวลาไทยตอน build + commit ของ erp-api และ erp-frontend อ่านชื่อแล้วรู้ทันทีว่าโค้ดชุดไหน · ขนาดราว 15 MB เพราะไม่มี node_modules (เครื่องลูกค้าต้องต่ออินเทอร์เน็ตตอนติดตั้ง) · build บน OS ไหนก็ติดตั้งได้ทุก OS 

erp-<version>/
  VERSION.json   # version, built_at, node, commit ของทั้ง 3 repo, internal_api_port
  installer/     # bin/ lib/ templates/ docs/ infra/ + console-ui/dist — release ติดตั้งตัวเอง
  api/           # erp-api: dist/ (migration + data source compile แล้ว), permissions snapshot, lockfile
  web/           # erp-frontend: apps/web/.next, public, lockfile
ทำไมต้อง compile migration และ permission snapshot

release ไม่มี TypeScript source — migration / permissions:sync / seed ถูก compile ด้วย esbuild · permission scan ของ erp-api อ่าน apps/*/src/**/*.ts เป็นข้อความ ถ้าไม่มี source จะ scan ได้ 0 แล้ว soft-delete สิทธิ์ API ทั้งหมด → build-release สร้าง permissions.snapshot.ts และตรวจว่าผล scan เท่ากับ source ก่อนแพ็ก

build เองบนเครื่อง dev (เมื่อใช้ CI ไม่ได้)

# Node major เดียวกับเครื่องลูกค้า, git, pnpm (corepack enable) · commit งานก่อน — build จาก commit เท่านั้น
cd erp-installer && pnpm install
node scripts/build-release.mjs --api ../erp-api --web ../erp-frontend
# → release/erp-<version>.tar.gz + .sha256   (~5 นาที)
# ตัวเลือก: --api-ref / --web-ref (branch·tag·commit), --out DIR, --skip-smoke, --help

ขั้นตอนเดียวกันอยู่ในปุ่ม “วิธีสร้างไฟล์ .tar.gz” ในหน้า Release ของ ERP Console

05 — ติดตั้งครั้งแรก

ที่หน้างาน (Windows — ลำดับที่ใช้จริง)

ทุกคำสั่งใช้ PowerShell แบบ Run as Administrator · ตัวอย่างใช้ C:\erp เป็น install home และ C:\Temp\erp-<version> เป็นที่แตก release · checklist เต็มอยู่ใน erp-installer/docs/windows.md

1

เตรียมเครื่อง + ลงโปรแกรมพื้นฐานเอง

Sleep = Never · ติดตั้ง Windows Update ให้จบ (“Update and restart” — ไม่งั้น WSL2 ขึ้นไม่ได้) · BIOS เปิด virtualization · Node.js (major ตาม VERSION.json, อยู่ใน PATH ของระบบ) · Caddy · PostgreSQL 18+ (จดพอร์ต / รหัส) · PM2 (npm i -g pm2 หรือปุ่มใน Console) · พอร์ต 80 / 443 ว่าง (IIS → net stop w3svc)

2

infra ด้วยสคริปต์เดียว

tar -xzf erp-<version>.tar.gz -C C:\Temp
$infra = 'C:\Temp\erp-<version>\installer\infra\windows\install-infra.ps1'
powershell -ExecutionPolicy Bypass -File $infra
# ยังไม่มี WSL → ลงให้แล้วจบที่ exit 3010 → รีสตาร์ท Windows → รันคำสั่งเดิมซ้ำ
# → Redis / RabbitMQ / RustFS / Gotenberg ขึ้น OK ครบ (ครั้งแรกโหลด image 5–10 นาที)

ทุก container ผูกพอร์ตที่ 127.0.0.1 เท่านั้น · รหัสสุ่มครั้งเดียวเก็บใน C:\erp-infra\secrets.env (อ่านได้เฉพาะ Administrators / SYSTEM) · scheduled task เปิด WSL ตอนบูต · รันซ้ำได้ ตัวที่ config ไม่เปลี่ยนไม่ถูก restart

3

ติดตั้ง ERP แล้วกรอก config

node C:\Temp\erp-<version>\installer\bin\erp.mjs install --home C:\erp   # รอบแรก: สร้าง C:\erp\config\ แล้วหยุด
powershell -ExecutionPolicy Bypass -File $infra -ErpHome C:\erp           # เขียนค่า Redis / RabbitMQ / S3 / Gotenberg ลง api.env + สร้าง bucket
node C:\Temp\erp-<version>\installer\bin\erp.mjs set-db-password --home C:\erp   # รหัส PostgreSQL ครั้งเดียว ลงทุก *_DB_PASSWORD (ไม่แสดงตัวอักษร)
# แก้มือ: erp.env → ERP_DOMAIN, ERP_API_DOMAIN, CADDY_BIN, UPDATE_GITHUB_TOKEN
#         api.env → *_DB_HOST / *_DB_PORT (ถ้าไม่ใช่ 5432), STORAGE_S3_PUBLIC_ENDPOINT=https://<ERP_DOMAIN>:9443
# ห้ามแก้: NODE_ENV (prod), SECRET_KEY, ACCESS_KEY_SECRET_ENCRYPTION_KEY, *_DB_SYNCHRONIZE
C:\erp\erp.cmd install C:\erp\releases\<version>   # รอบสอง → สร้าง DB + migration → "ERP <version> is running"

ใช้เวลาราว 5 นาที บน Windows (ดู §06) · อย่ากด Start ERP / สั่ง erp start ซ้อนระหว่างติดตั้ง — release ใหม่ล็อกให้ทีละคำสั่ง · start ครั้งแรกจะปิดสิทธิ์ไฟล์ทั้ง home (§11) ใช้เวลาเพิ่มอีกไม่กี่นาที ครั้งเดียว

4

ปิดงานด้วยคำสั่งเดียว — PowerShell แบบ Administrator

C:\erp\erp.cmd finish     # --dry-run ดูก่อนได้ · รันซ้ำได้ ข้อที่ผ่านแล้วข้าม · --ip <IP> · --no-hosts

ถามรหัสใหม่ของ superadmin ครั้งเดียว (migration ของ erp-api สร้างบัญชีนี้ด้วยรหัสที่อยู่ใน source) แล้วทำต่อเอง: ปิด login บัญชี mock staff · autostart ตอนบูต · firewall 80/443/9443 · ให้เครื่องนี้เชื่อ HTTPS + hosts · สร้างสคริปต์สำหรับเครื่อง client · erp status — จบด้วยตารางสรุป ✓ / ⚠ / ✗

5

เครื่อง client ทุกเครื่อง — ไฟล์เดียว

copy erp-client-setup.ps1 (จาก C:\erp\ หรือปุ่มดาวน์โหลดในการ์ด Web access ของ Console) → คลิกขวา Run with PowerShell — ติดตั้ง CA ของ Caddy เป็น Trusted Root, ใส่บรรทัด hosts ชี้ IP ของ server, แล้วทดสอบ HTTPS ให้เอง

ทำไมทุกเครื่องต้องเชื่อ CA

Caddy ออก certificate ให้ erp.internal จาก CA ภายในของเครื่อง server เอง (ไม่มี public CA ไหนออกให้ชื่อ .internal ได้) — เครื่องที่ยังไม่เชื่อ CA จะเห็นคำเตือน และ cookie ของ login (COOKIE_SECURE=true) ต้องใช้ HTTPS · CA นี้รับรองเว็บไหนก็ได้ — ติดตั้งเฉพาะเครื่องที่ใช้ ERP และถอนออกเมื่อเลิกใช้ / ย้ายเครื่อง server (§11)

6

ตรวจรับใน ERP Console

ภาพรวม: ทุกการ์ดเขียว (รวม security — ไม่มีบัญชีรหัส mock, ไฟล์ config / install home ไม่เปิดให้คนอื่น) · Web access = เข้าเว็บได้ · Migration: ไม่มี “ยังไม่รัน” / “DB ใหม่กว่าโค้ด” · Release: Sync ต่อ GitHub ได้ · login จากเครื่อง client 1 เครื่อง

ไม่ได้ช้าที่ดาวน์โหลด (pnpm store อยู่ไดรฟ์เดียวกัน → hard link) แต่สร้าง node_modules ใหม่ทั้งชุด ~106k ไฟล์ (api ~40k + web ~66k) ทุก release + Defender สแกนแบบ real-time · ERP ตัวเก่ารันต่อระหว่างติดตั้ง หยุดแค่ตอนสลับ / restart · ทางที่ยังไม่ได้ทำ: Defender exclusion ของ releases\, ใช้ node_modules ของ release ก่อนซ้ำเมื่อ lockfile เท่าเดิม

11 — ความปลอดภัย

บนเครื่องลูกค้า

ตรวจบนเครื่องลูกค้า Windows จริง (2026-11-22) แล้วแก้ใน erp-installer commit 1726cce — ใช้ได้กับ release ที่ build จาก installer commit นั้นขึ้นไปเท่านั้น (ดู VERSION.json → commit ของ installer) · release ที่ build อัตโนมัติก่อนหน้ายังไม่มี — ถ้ายังไม่มี push ใหม่ของ erp-api / erp-frontend ให้กด Actions → Release → Run workflow แล้ว Sync → ติดตั้ง · ติดตั้งครั้งแรกหลังจากนั้นช้ากว่าปกติหลายนาที (ปิดสิทธิ์ทุกไฟล์ใน releases\) และ PM2 รีสตาร์ทหนึ่งครั้ง · ภาพรวม: ERP ทุก process รันเป็น account เดียว (เจ้าของ install) ภายใต้ PM2 ดังนั้นไม่มีใครอื่นในเครื่องต้องอ่านหรือแก้ไฟล์ของ install

ความเสี่ยงที่ทำไว้
โฟลเดอร์ใต้ C:\ สืบสิทธิ์ Authenticated Users: Modify → user ไหนก็แก้ autostart.cmd / โค้ดใน releases\ ที่ task ตอนบูตรันด้วยสิทธิ์สูงสุดได้start / install ปิด inheritance ของทั้ง home — เหลือเจ้าของ + Administrators + SYSTEM (ครั้งแรกไล่ทุกไฟล์ ใช้หลายนาที) · macOS / Ubuntu: ตัดสิทธิ์เขียนของคนอื่น + โฟลเดอร์ส่วนตัว 0700 · erp status เตือน install home
caddy-data\…\root.key อ่านได้ทุก user — ใครได้ไปออก cert ปลอมของเว็บไหนก็ได้ให้ทุกเครื่องที่เชื่อ CA นี้อยู่ใต้ home ที่ล็อกแล้ว · เปิดอ่านได้เฉพาะ erp-local-ca.crt (cert สาธารณะ) · ย้าย / ทิ้งเครื่อง server → ถอน CA ออกจาก client
secret ใน config\*.env, backup, .env ของแต่ละ releaseเจ้าของเท่านั้น (Windows: icacls ด้วย SID, POSIX: 0600 / 0700) ทุกครั้งที่ start
PM2 เก็บ env ทั้งหมดของ shell คนสั่ง (token ส่วนตัว, PATH) ลง .pm2\dump.pm2 และส่งให้ทุก processคำสั่ง pm2 ได้ env แบบ allowlist (เฉพาะของ OS) · ครั้งแรกหลังอัปเดต pm2 kill หนึ่งครั้งเพื่อล้าง env เก่า (ERP หยุด ~30 วินาที)
Gotenberg รัน JavaScript ของ template — เดิม deny-list เทียบข้อความ URL จึงหลุดไป http://rustfs:9000, localhost, [::1]Gotenberg อยู่ docker network ของตัวเอง (มองไม่เห็น Redis / RabbitMQ / RustFS) + deny-list ใหม่ (ชื่อไม่มีจุด, IPv6, private range, .internal, file:) · ทดสอบแล้ว: ภายในทั้งหมด 403, เว็บภายนอกผ่าน · template ที่ใช้รูปจาก LAN ต้องฝังเป็น data URI
Redis แบบ native บน Windows ไม่มีรหัสถอดออกแล้ว — Redis เป็น container ที่มี requirepass เสมอ (รวม -Mode native)
หน้าเว็บภายนอกชี้ชื่อของตัวเองมาที่ 127.0.0.1 (DNS rebinding) แล้วอ่าน ConsoleConsole ที่ฟัง loopback ตอบเฉพาะ Host 127.0.0.1 / localhost / [::1]
ยังไม่ได้ทำ

สิทธิ์ต่ำสุดของบัญชี infra — erp-api ใช้ root key ของ RustFS, RabbitMQ user เป็น administrator, Postgres มักเป็น superuser (ต้องตกลงกับทีม erp-api ว่า migration / storage ต้องการสิทธิ์อะไร) · Console ผ่าน TLS เมื่อเปิดให้ LAN — ตอนนี้ CONSOLE_PASSWORD ส่งเป็น HTTP ธรรมดา
