Runbook · Database / Infra

Pgpool: All Backend
Nodes Down

ทุก BC (AUTH, IAM, SALES, …) ต่อ database ไม่ได้พร้อมกัน ขึ้น pgpool is not accepting any new connections — ทั้งที่ PostgreSQL/repmgr จริงยังทำงานปกติทุกโหนด

Severity: Critical (Total DB Outage) Est. fix time: 2–5 นาที
1 — อาการ (Symptom)

Log ที่จะเห็น

ทุก microservice ที่ TypeORM ต่อผ่าน pgpool VIP จะ retry connect วนไม่หยุด โดย error ซ้ำแบบนี้ในทุก BC พร้อมกัน (ไม่ใช่แค่ BC เดียว — ถ้าเจอแค่ BC เดียวไม่ใช่เคสนี้ ให้เช็ค credential/DB เฉพาะ BC นั้นแทน): 

[IAM] [Nest] ERROR [TypeOrmModule] Unable to connect to the database (erp_iam). Retrying (8)...
[IAM] error: pgpool is not accepting any new connections
[AUTH] error: pgpool is not accepting any new connections
[SALES] error: pgpool is not accepting any new connections

บน pgpool node เอง (journalctl -u pgpool2) จะเห็นบรรทัดนี้ซ้ำทุก ~15 วินาที: 

child pid xxxxx: FATAL:  pgpool is not accepting any new connections
child pid xxxxx: DETAIL:  all backend nodes are down, pgpool requires at least one valid node
child pid xxxxx: HINT:  repair the backend nodes and restart pgpool
2 — ผลกระทบ (Impact)

Total DB Outage — ทุก BC

SCOPE

ทุก BC ที่ผ่าน VIP นี้

auth, iam, inventory-bc, supplier-bc, sales-bc, finance-bc, report-bc — ทุก request ที่แตะ DB ล้มเหลว 100%

SEVERITY

Critical — escalate ทันที

ไม่ใช่ degrade แบบ node เดียวหาย — ระบบทั้งชุดหยุดทำงาน ไม่มี fallback

DATA SAFETY

ข้อมูลไม่เสี่ยง

นี่คือ pgpool routing layer ค้าง ไม่ใช่ PostgreSQL พัง/ข้อมูลหาย — แก้แล้วกลับมาใช้ได้ทันทีไม่ต้อง restore

3 — วินิจฉัย (Diagnosis)

ยืนยันว่าใช่เคสนี้ก่อนแก้

สิ่งสำคัญที่สุดของเคสนี้: PostgreSQL จริงมักจะปกติอยู่แล้ว — ปัญหาอยู่ที่ pgpool มองไม่เห็นมันเอง อย่าเพิ่งไป restart PostgreSQL/repmgr โดยไม่เช็คก่อน

1

เช็คว่า PostgreSQL/repmgr จริงยังปกติไหม

ssh เข้า primary (ovh-ppm) แล้วดู cluster ทั้งชุด

ssh ovh-ppm "sudo -u postgres repmgr cluster show"
ถ้าเจอแบบนี้ (ทุกโหนด running) = ยืนยันว่าใช่เคสนี้

ppr1 | standby | running · ppm | primary | * running · ppr2 | standby | running — PostgreSQL ปกติ ไม่ต้องแตะ repmgr เลย ข้ามไปข้อ 3

2

(ถ้าข้อ 1 ก็ผิดปกติด้วย) เช็ค TCP ไปยัง backend แต่ละตัวจาก pgpool node

แยกให้ออกว่าเป็น network/firewall หรือ PostgreSQL ตายจริง — ถ้า TCP ต่อไม่ได้เลยคือปัญหาคนละเรื่อง ไม่ใช่ runbook นี้

for ip in 172.16.0.221 172.16.0.222 172.16.0.223; do
  ssh ovh-pgpool1 "nc -zv -w3 $ip 5432"
done
3

เช็คสถานะ node ที่ pgpool "คิด" ว่าเป็น — เทียบกับ backend จริง

นี่คือคำสั่งที่ชี้ตัวปัญหาตรงๆ — psql ผ่าน pgpool port 5432 จะต่อไม่ติด (มันคือตัวปัญหาเอง) ให้ยิงผ่าน pcp_node_info แทน ทำครบทั้ง 3 node (-n 0, -n 1, -n 2) 

for n in 0 1 2; do
  ssh ovh-pgpool1 "sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
    pcp_node_info -h localhost -p 9898 -U pgpool_admin -w -n $n -v"
done
ลายเซ็นของเคสนี้: Status Name กับ Backend Status Name ไม่ตรงกัน

Status Name: down (pgpool คิดว่า node นี้ตาย — ค่านี้แหละที่บล็อก traffic) แต่ Backend Status Name: up (PostgreSQL จริงตอบสนองปกติ) — เห็นแบบนี้พร้อมกันทั้ง 3 node = ใช่เคสนี้แน่นอน ข้ามไปข้อ 5 (การแก้ไข) ได้เลย

4 — สาเหตุ (Root Cause)

Pgpool ไม่ re-attach node ที่เคย mark down เองอัตโนมัติ

Health check ของ pgpool ตรวจจับ UP → DOWN ได้เอง แต่ไม่ตรวจ DOWN → UP — เมื่อ node ใดถูก mark down ครั้งหนึ่ง (เช่นตอน failover, restart, หรือ watchdog เสีย quorum ชั่วคราว) มันจะค้างสถานะ down อยู่แบบนั้น แม้ PostgreSQL จริงจะกลับมาสมบูรณ์แล้วก็ตาม ต้องมีคนสั่ง pcp_attach_node ด้วยมือเท่านั้นถึงจะกลับมาใช้งานได้ 

sequenceDiagram
    participant Ev as เหตุการณ์ต้นทาง (failover / restart / watchdog quorum หลุด)
    participant PP as Pgpool
    participant PG as PostgreSQL (จริง)

    Ev->>PP: trigger degenerate/quarantine backend node
    PP->>PP: mark node เป็น Status = down
    Note over PG: PostgreSQL ฟื้นตัวเองปกติ (repmgr/manual)
    PG-->>PP: backend จริง = up
    Note over PP: Health check ตรวจ UP→DOWN เท่านั้น
ไม่ตรวจ DOWN→UP ให้เอง
    Note over PP: Status ค้างเป็น down ต่อไปเรื่อยๆ
= "all backend nodes are down"
    Note over Ev,PG: ต้อง pcp_attach_node ด้วยมือ
ถึงจะกลับมา route traffic ได้
ทำไมถึงมัก down พร้อมกันทั้ง 3 node ไม่ใช่แค่ node ที่มีปัญหาจริง

ช่วงที่ primary หาย/watchdog เสีย quorum pgpool อาจมองไม่เห็น "primary ตัวไหนเลยสักตัว" ชั่วขณะ (ไม่ใช่แค่โหนดที่ปัญหาต้นตอ) จึงมาร์ก down พร้อมกันได้ทั้ง 3 — เจอมาแล้วสองครั้ง (8/9 ตอน ppm ตายจริง และ 8/12 ตอน watchdog แย่ง quorum ระหว่าง pgpool restart วนหลายรอบ) ดูรายละเอียดเต็มที่ §10 Accident Playbook และ §08 Known Bugs (#24) ในคู่มือฉบับเต็ม

5 — การแก้ไข (Fix)

Re-attach ทั้ง 3 node — อย่าทำแค่ node เดียว

รันจาก pgpool node ตัวไหนก็ได้ที่ยัง ssh เข้าได้ (ไม่จำเป็นต้องเป็น watchdog leader) — ทำครบทั้ง 3 node เสมอ แม้จะสงสัยว่ามีแค่ node เดียวที่เพี้ยน เพราะเช็คแล้วบ่อยครั้งค้างพร้อมกันหมด (ดู §4) 

for n in 0 1 2; do
  ssh ovh-pgpool1 "sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
    pcp_attach_node -h localhost -p 9898 -U pgpool_admin -w -n $n"
done

แต่ละคำสั่งควรตอบ pcp_attach_node -- Command Successful — ถ้าเจอ FATAL: authentication failed แทน แปลว่า .pcppass หาย/ผิด ดูวิธีแก้ในคู่มือฉบับเต็ม §08 บั๊ก #13/#19

เช็คว่าหายจริง แล้วปิดสาเหตุ

1

  ssh ovh-pgpool1 "sudo -u postgres PGPOOLKEYFILE=/etc/pgpool2/.pgpoolkey \
    pcp_node_info -h localhost -p 9898 -U pgpool_admin -w -n $n -v"
done

ผลลัพธ์ที่ต้องได้

คืนแถวเดียว 1 — ถ้าได้แปลว่า routing กลับมาปกติแล้ว ไม่ต้อง restart pgpool หรือ service ฝั่ง Node.js เลย (มันมี retry loop รอต่ออยู่แล้วตาม TypeORM `retryAttempts`)

3

เช็ค log ฝั่ง pgpool ว่าไม่มี FATAL ใหม่เกิดซ้ำ

ssh ovh-pgpool1 "sudo journalctl -u pgpool2 --no-pager -n 30 | grep -iE 'fatal|not accepting'"
# ควรไม่มี output
ป้องกันระยะยาว — ยังไม่ได้ทำ ณ ตอนเขียน runbook นี้

Pgpool ไม่มี auto re-attach ในตัว (ต้องใช้ external script เฝ้า pcp_node_info แล้วยิง attach เอง หรือ cron ตรวจสอบ) — ทางที่ยั่งยืนกว่าคือ alert เร็วพอที่มนุษย์จะกดรันตาม runbook นี้ได้ทันที แนะนำเพิ่ม Grafana alert จาก metric ที่มีอยู่แล้วใน Pgpool-II Cluster Guide ให้ยิงแจ้งทันทีที่ node ใดมี Status Name != Backend Status Name นานเกิน 1 นาที แทนที่จะรอ user แจ้งว่า app ต่อ DB ไม่ได้เหมือนเคสนี้
