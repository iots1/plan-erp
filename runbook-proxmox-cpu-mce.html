Proxmox Host รีบูตเอง
CPU Machine Check Exception

เครื่อง hypervisor ดับเองโดยไม่มี shutdown log · VM ทุกตัวตายพร้อมกัน · ไม่มี kernel panic ให้ดู — และ Linux ไม่ได้บันทึกอะไรไว้เลย เพราะฮาร์ดแวร์รีเซ็ตเครื่องก่อนที่ kernel จะเขียน log ทัน

Severity: Critical (Host + ทุก VM ดับ) ไม่มี software fix — ต้องเปลี่ยนฮาร์ดแวร์ วินิจฉัยได้ใน ~10 นาที
1 — อาการ (Symptom)

เครื่องหายไปเฉยๆ แล้วกลับมาเอง

ลายเซ็นหลักคือ ไม่มีร่องรอยอะไรเลย — ไม่ใช่ OOM, ไม่ใช่ panic, ไม่ใช่ watchdog ที่พอจะเห็นใน log เครื่องแค่หยุดกลางประโยคแล้ว boot ใหม่ 

# last -x จะทำเครื่องหมาย "crash" ให้ boot ที่ไม่เคยบันทึก shutdown
reboot   system boot  6.x.x-x-pve    Sat Aug 29 19:49 - still running
reboot   system boot  6.x.x-x-pve    Sat Aug 29 19:24 - crash
reboot   system boot  6.x.x-x-pve    Sat Aug 29 19:12 - crash
reboot   system boot  6.x.x-x-pve    Sat Aug 29 16:31 - crash

journalctl -b -1 (log ของ boot ที่ตาย) จะจบกลางอากาศ — บรรทัดสุดท้ายเป็น log ธรรมดา ไม่มีคำว่า error/panic/shutdown อะไรเลย: 

Aug 29 19:22:03 pve pvedaemon[1760]: <user@pam> successful auth for user
Aug 29 19:22:05 pve pvedaemon[1759]: VM 100 qga command failed - got timeout
# ...จบแค่นี้ ไม่มีอะไรต่อ
อาการหลอกที่ทำให้ไล่ผิดทาง

ถ้าเข้า host ผ่าน Cloudflare Tunnel จะเจอ error สองแบบสลับกันแบบสุ่ม จนดูเหมือน tunnel เสียเอง — websocket: bad handshake (= เครื่องดับสนิท cloudflared ไม่ได้ลงทะเบียนกับ edge) สลับกับ Connection timed out during banner exchange (= เครื่องกำลัง boot, cloudflared ขึ้นแล้วแต่ sshd ยังไม่พร้อม) อย่าเสียเวลาแก้ tunnel config — ทั้งสองอย่างคืออาการของเครื่องที่กำลังวน crash-reboot อยู่

อาการหลอกอีกอย่าง: CI/CD job รายงานเป็น timeout

ถ้ามี GitHub Actions self-hosted runner อยู่บน VM ของ host นี้ job จะรายงานว่า The job has exceeded the maximum execution time — ซึ่งชวนให้ไปเพิ่ม timeout-minutes ในไฟล์ workflow แต่ job ไม่ได้ช้า เครื่องตายคาที่ runner จึงไม่เคยรายงานผลกลับ GitHub เลยตัดจบด้วย timeout เอง

2 — ผลกระทบ (Impact)

ทุก VM บน host ดับพร้อมกัน ไม่มีการเตือนล่วงหน้า

SCOPE

ทุก guest บนเครื่องนั้น

hypervisor ถูกรีเซ็ตระดับฮาร์ดแวร์ — VM/LXC ทุกตัวถูกตัดไฟพร้อมกันโดยไม่มี graceful shutdown

SEVERITY

Critical — และจะถี่ขึ้นเรื่อยๆ

เคสจริงที่เจอ: ห่างกัน 2 วัน → 2.6 ชม. → 22 นาที → 9 นาที ภายในวันเดียว ยิ่งปล่อยยิ่งแย่

DATA SAFETY

เสี่ยง — unclean shutdown ทุกครั้ง

DB ที่รันใน guest จะถูกตัดกลาง write ทุกรอบ ต้องพึ่ง WAL/journal recovery ล้วนๆ — ย้าย workload สำคัญออกก่อน

3 — วินิจฉัย (Diagnosis)

หาหลักฐานจากที่ที่ OS เข้าไม่ถึง

หัวใจของเคสนี้: อย่าเสียเวลาหาใน Linux log ของ boot ที่ตาย — มันไม่มีอะไรอยู่จริงๆ ต้องไปดู 2 แหล่งที่อยู่นอก OS แทน คือ BERT (firmware เขียนไว้ให้ kernel อ่านตอน boot ถัดไป) และ BMC/iDRAC System Event Log (ฮาร์ดแวร์บันทึกเอง ไม่พึ่ง OS)

1

ยืนยันก่อนว่าเป็น crash จริง ไม่ใช่ reboot ปกติ

ถ้าเห็นคำว่า crash = ไม่เคยมี clean shutdown record = ถูกตัดไฟหรือรีเซ็ตระดับฮาร์ดแวร์ 

last -x | head -12
journalctl --list-boots
2

อ่าน BERT — ขั้นตอนที่ให้คำตอบตรงที่สุด

ACPI BERT (Boot Error Record Table) คือกลไกที่ออกแบบมาสำหรับ error ที่ฆ่าเครื่องก่อน OS จะ log ทันพอดี — firmware เก็บ record ไว้ใน NVRAM แล้ว kernel อ่านออกมาให้ ตอน boot รอบถัดไป (ไม่ใช่ boot ที่ตาย) จึงต้องดูด้วย -b 0 ไม่ใช่ -b -1 

journalctl -b 0 -k | grep -A12 'BERT: Error records'
ลายเซ็นของเคสนี้
BERT: Error records from previous boot:
[Hardware Error]: event severity: fatal
[Hardware Error]:  Error 0, type: fatal
[Hardware Error]:   section_type: general processor error
[Hardware Error]:   processor_type: 0, IA32/X64
[Hardware Error]:   error_type: 0x08
[Hardware Error]:   micro-architectural error
[Hardware Error]:   processor_id: 0x0000000000000010
BERT: Total records found: 1
ฟิลด์ความหมาย
section_type: general processor errorความผิดพลาดอยู่ที่ CPU — ไม่ใช่ memory, ไม่ใช่ PCIe, ไม่ใช่ storage
error_type: 0x01cache error
error_type: 0x02TLB error
error_type: 0x04bus error
error_type: 0x08micro-architectural error — ตรรกะภายในตัว CPU เอง
processor_idAPIC ID ของ core ที่ error — ใช้แมปหา socket/core จริงในขั้นถัดไป
ข้อจำกัดที่ต้องรู้: BERT เก็บได้แค่ record เดียว

firmware เขียนทับทุกครั้งที่ crash — จะเห็นแค่ครั้งล่าสุดเสมอ ถ้าอยากได้ประวัติว่า core เดิมทุกครั้งไหม ต้อง archive ออกมาทุก boot (ดู §6)

3

แมป APIC ID → socket / core จริง

processor_id คือ APIC ID ซึ่งไม่ตรงกับเลข CPU ของ Linux เสมอไป — ต้องแมปจาก /proc/cpuinfo เอง (แทน 16 ด้วยค่าที่ได้จาก BERT) 

# APIC ID นี้ = cpu ไหน / socket ไหน / core ไหน
awk '/^processor/{p=$3} /^physical id/{s=$4} /^core id/{c=$4}
     /^apicid/{ if($3==16) printf "APIC %s -> cpu%s socket=%s core=%s\n", $3,p,s,c }' /proc/cpuinfo

# HT sibling ของ cpu นั้น (ต้องปิดคู่กันถ้าจะ offline)
cat /sys/devices/system/cpu/cpu16/topology/thread_siblings_list
ผลที่ได้จากเคสจริง

APIC 16 → cpu16 socket=0 core=8 · thread siblings = 16,48 — แปลว่า CPU ตัวที่ 1 (socket 0) core ที่ 8 คือตัวที่มีปัญหา

4

ยืนยันซ้ำจาก BMC/iDRAC System Event Log

SEL เป็นของฮาร์ดแวร์ ไม่พึ่ง OS — จึงบันทึกได้แม้เครื่องตายไปแล้ว (ติดตั้งก่อนถ้ายังไม่มี: apt install ipmitool) 

ipmitool sel elist | grep -iE 'Machine Chk|Additional Info'
ลายเซ็น: MSR Info Log ตามด้วย CPU Machine Chk ทุกครั้ง
4f | 08/29/2026 | 07:22:17 PM | Unknown MSR Info Log       | Asserted
53 | 08/29/2026 | 07:23:26 PM | Unknown Additional Info    | Asserted
54 | 08/29/2026 | 07:23:26 PM | Processor CPU Machine Chk  | Transition to Non-recoverable

เวลาใน SEL จะตรงกับวินาทีสุดท้ายของ journal — ใช้ยืนยันว่าเป็นเหตุการณ์เดียวกัน
Unknown MSR Info Log คือ record OEM ที่ ipmitool ถอดรหัสไม่ได้ ต้องดูใน iDRAC Lifecycle Log (web UI → Maintenance → Lifecycle Log) ถึงจะได้ข้อความภาษาคนพร้อมชื่อชิ้นส่วน

5

ตัดสาเหตุอื่นออกให้หมด ก่อนสรุปว่าเป็น CPU

ทั้ง 6 อย่างนี้ต้อง "สะอาด" ถึงจะสรุปได้ — ถ้ามีข้อไหนผิดปกติ แปลว่าเป็นคนละเคส 

# RAM — ECC error สะสมไหม (ต้องเป็น 0 ทั้งหมด)
for mc in /sys/devices/system/edac/mc/mc*; do
  echo "$(basename $mc): ce=$(cat $mc/ce_count) ue=$(cat $mc/ue_count)"
done
ras-mc-ctl --summary          # ต้องขึ้น "No Memory errors"

# OOM — ต้องได้ 0
journalctl -b -1 | grep -ci 'oom-killer\|out of memory'

# ความร้อน / ไฟ — ต้องอยู่ในเกณฑ์ปกติ
ipmitool sdr type Temperature
ipmitool sdr type 'Power Supply'

# ดิสก์ — ต้องไม่มี event และ SMART ต้องสะอาด
ipmitool sel elist | grep -icE 'drive|disk|storage|raid'
smartctl -a -d megaraid,0 /dev/sda | grep -E 'Reallocated|Media Error'

# kernel panic — pstore ต้องว่าง (ถ้ามี = คนละเคส ไปดู dump แทน)
ls /sys/fs/pstore/
ผลที่คาดหวังในเคสนี้ — สะอาดหมดทุกข้อ

EDAC ce=0 ue=0 · OOM = 0 · CPU ~55°C · PSU ปกติ · SMART Reallocated_Sector_Ct = 0 · pstore ว่าง — ทุกอย่างปกติแต่เครื่องยังดับ นั่นแหละคือลายเซ็นของ CPU MCE

4 — สาเหตุ (Root Cause)

CPU ส่ง CATERR แล้ว BMC รีเซ็ตเครื่องทันที — OS ไม่มีโอกาสเขียนอะไร

เมื่อ CPU เจอ uncorrectable machine check ในบริบทที่กู้ไม่ได้ มันจะ assert สัญญาณ CATERR (Catastrophic Error) ออกมาที่ระดับฮาร์ดแวร์ BMC เห็นสัญญาณนี้แล้วสั่งรีเซ็ตทั้งเครื่องทันที — เร็วกว่าที่ kernel จะเขียน panic log หรือ flush journal ลงดิสก์ได้ นี่คือเหตุผลที่ทุกอย่างฝั่ง Linux ดู "สะอาด" ผิดปกติ 

sequenceDiagram
    participant W as Workload (เช่น CI/CD job)
    participant C as CPU core ที่เสีย
    participant B as BMC / iDRAC
    participant K as Linux kernel
    participant F as UEFI firmware

    W->>C: รันงานที่ไปแตะ core นี้
    C->>C: uncorrectable machine check
(micro-architectural error)
    C->>B: assert CATERR
    Note over K: kernel ไม่ได้รับโอกาสทำอะไรเลย
ไม่มี panic, ไม่มี log, pstore ว่าง
    B->>B: บันทึกลง SEL (MSR Info Log + CPU Machine Chk)
    B->>F: สั่ง hard reset ทั้งเครื่อง
    F->>F: เก็บ error record ลง NVRAM (BERT)
    F->>K: boot ใหม่
    K->>K: อ่าน BERT ออกมา log ให้ตอน boot
= หลักฐานชิ้นเดียวที่ OS มองเห็น
ทำไมมันถึงเกิดๆ หายๆ ไม่ใช่ทุกครั้ง (probabilistic)

ในเคสจริงที่เก็บข้อมูลไว้: workload เดียวกันเป๊ะ (CPU peak 8–9%, load ~3, memory เท่ากัน) บางรอบเครื่องตาย บางรอบรอด — นับได้ ดับ 6 ครั้ง / รอด 7 ครั้ง ในวันเดียว นี่คือพฤติกรรมปกติของ CPU ที่กำลังเสื่อม: error เกิดเมื่อเงื่อนไขภายในบังเอิญมาบรรจบกัน จึงเป็นเรื่องความน่าจะเป็น อย่าใช้ "ลองรันแล้วไม่ดับ 1 ครั้ง" มาสรุปว่าแก้หายแล้ว ต้องทดสอบซ้ำหลายรอบ

โหลดไม่ใช่ตัวแปรเรื่องปริมาณ แต่เป็นเรื่อง "ไปแตะอะไร"

เครื่องในเคสจริงดับตอน CPU แค่ 4–7% กินไฟ 98W อุณหภูมิ 53°C — คือแทบ idle แต่ช่วง idle จริงๆ (ไม่มี job) กลับอยู่ได้ 20+ นาทีติดกัน ตัวแปรจึงไม่ใช่ความหนักของงาน แต่เป็นการที่ workload ไป schedule ลงบน core ที่เสียหรือเปล่า — ซึ่งเป็นเรื่องของ scheduler ล้วนๆ

5 — การแก้ไข (Fix)

ไม่มี software fix — มีแค่หยุดเลือด แล้วเปลี่ยนของ

ทำตามลำดับนี้ ข้อ 1 ก่อนเสมอ เพราะทุกนาทีที่ปล่อยไว้คือความเสี่ยงที่ DB ใน guest จะถูกตัดกลาง write อีกรอบ

1

หยุด workload ที่กระตุ้นให้เกิด

ถ้าระบุได้ว่างานประเภทไหนมักตามด้วย crash (เช่น CI/CD job) ปิดมันก่อนเป็นอันดับแรก 

# ตัวอย่าง: ปิด GitHub Actions runner ที่รันอยู่ใน guest
sudo systemctl stop 'actions.runner.*'
sudo systemctl disable 'actions.runner.*'
2

ย้าย workload สำคัญออกจากเครื่องนี้

migrate VM ไป node อื่นถ้ามี cluster — ถ้าไม่มี อย่างน้อยให้ backup แล้วเตรียม restore ที่อื่นไว้ อย่ารอให้ crash รอบหน้าทำ filesystem เสียหาย

3

(workaround ชั่วคราว) ปิด core ที่เสีย

ถ้าต้องใช้เครื่องต่อระหว่างรออะไหล่ ลอง offline core ที่ BERT ชี้ พร้อม HT sibling ของมัน — Linux จะไม่ schedule งานลงไปอีก (แทนเลข cpu ด้วยค่าที่ได้จาก §3 ข้อ 3) 

echo 0 | sudo tee /sys/devices/system/cpu/cpu16/online
echo 0 | sudo tee /sys/devices/system/cpu/cpu48/online
# ย้อนกลับ: echo 1 | sudo tee /sys/devices/system/cpu/cpuNN/online
ข้อควรระวัง 3 ข้อ

(ก) ไม่ persist ข้าม reboot — ต้องทำเป็น systemd unit ถ้าจะใช้จริง · (ข) BERT มี record เดียว crash ครั้งอื่นอาจเป็น core อื่นก็ได้ · (ค) เป็นแบบ probabilistic ต้องทดสอบซ้ำ 5–10 รอบ ถึงจะบอกได้ว่าช่วยจริง — นี่คือการซื้อเวลา ไม่ใช่การแก้

4

เก็บหลักฐานส่งเคลม

ipmitool sel elist > sel-full.txt        # ประวัติ MCE ทั้งหมด
ipmitool sel save sel-raw.bin            # ไฟล์ดิบสำหรับผู้ผลิต
journalctl -b 0 -k | grep -A12 'BERT' > bert.txt
journalctl --list-boots > boots.txt
dmidecode > dmidecode.txt

แจ้งผู้ให้บริการ/ผู้ผลิตด้วย service tag/serial + ข้อความว่า "CPU Machine Check Exception ทำให้เครื่องรีเซ็ตเอง N ครั้ง ความถี่เพิ่มขึ้น · BERT ระบุ fatal micro-architectural error ที่ APIC ID <x> (socket <s> core <c>) · RAM/ดิสก์/ความร้อน/ไฟ ปกติทั้งหมด"

6 — ยืนยัน + ป้องกัน (Verify / Prevent)

ทำให้ครั้งหน้าวินิจฉัยได้ใน 2 นาที ไม่ใช่ทั้งวัน

ปัญหาของ crash แบบนี้คือหลักฐานหายไปพร้อมเครื่อง — ติดตั้ง 4 อย่างนี้ไว้ล่วงหน้าบน ตัว host เอง ไม่ใช่ใน guest (guest เป็นเหยื่อ ไม่ใช่สาเหตุ — มันมองไม่เห็นอะไรเลย)

1

rasdaemon — จับ correctable error ก่อนจะกลายเป็น fatal

เก็บลง sqlite ข้ามการ reboot และ decode ให้ว่าเป็น CPU ตัวไหน/DIMM แท่งไหน — เป็นตัวเดียวที่อาจเตือนล่วงหน้าได้ 

apt-get install -y rasdaemon
systemctl enable --now rasdaemon
ras-mc-ctl --summary          # DB: /var/lib/rasdaemon/ras-mc_event.db
2

archive BERT ทุก boot — ก่อนถูกเขียนทับ

firmware เก็บ BERT ได้แค่ record ล่าสุด การ copy ออกมาทุก boot คือวิธีเดียวที่จะรู้ว่า "core เดิมทุกครั้ง" หรือ "กระจายหลาย core" — ซึ่งเปลี่ยนข้อสรุปว่าควรเปลี่ยน CPU ตัวไหน 

cat > /etc/systemd/system/bert-capture.service <<'UNIT'
[Unit]
Description=Archive the BERT record read at boot before the next crash overwrites it
After=multi-user.target
[Service]
Type=oneshot
ExecStart=/bin/sh -c 'journalctl -b 0 -k --no-pager \
  | grep -A12 "BERT: Error records" \
  > /var/log/crash-reports/bert-$(date +%%Y%%m%%d-%%H%%M%%S).txt 2>/dev/null; true'
[Install]
WantedBy=multi-user.target
UNIT

mkdir -p /var/log/crash-reports
systemctl daemon-reload && systemctl enable --now bert-capture
3

sampler ที่ fsync ทุกบรรทัด — ให้วินาทีสุดท้ายรอด

เครื่องตายแบบไม่มี shutdown = ทุกอย่างที่ค้างใน page cache หายหมด ต้อง sync ทุกบรรทัดถึงจะได้ข้อมูลวินาทีสุดท้ายจริงๆ ซึ่งเป็นตัวบอกว่าตอนตายเครื่องกำลังทำอะไรอยู่ 

#!/usr/bin/env bash
# /usr/local/bin/crash-watch.sh — เก็บทุก 1 วินาที
LOG=/var/log/crash-watch.log
while true; do
  load=$(cut -d' ' -f1-3 /proc/loadavg)
  mem=$(awk '/MemAvailable/{printf "%.1fG", $2/1048576}' /proc/meminfo)
  printf '%s load=%s memavail=%s\n' "$(date '+%F %T')" "$load" "$mem" >> "$LOG"
